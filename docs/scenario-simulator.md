# 시뮬레이터 시연 시나리오 (기본 시연)

**보드·VM·게이트웨이·관제는 실제로 돌리고, 차와 카메라만 화면 속 시뮬레이터로 둔 구성**을 데모의 기본으로 완성한다. 실차(RC카·ESP32·젯슨·카메라)는 준비되면 같은 자리에 꽂아 **추가로 보여 주는 확장 목표**다 (§7).
보여 주려는 것은 [RC카 시나리오](scenario-rc-car.md)와 같다. **주행 중인 VM 이 죽어도 차가 안전하게 계속 가거나 멈추고, 죽은 VM 은 자동으로 돌아온다.**

> 상태: 초안 (2026-10-22, S15P31E110-265). 에픽 S15P31E110-17, 이슈 -259 ~ -265, -267 ~ -272.
> 흐름·모드·장애 규칙은 [RC카 시나리오](scenario-rc-car.md) §3·§4 와 [MQTT 계약](contracts/mqtt-contract-v1.md) §5 를 그대로 따른다. 이 문서는 **무엇을 시뮬레이터로 두는지**와 시연 방법을 적는다.
> 2026-10-22 결정: 시뮬레이터 구성이 완성 기준이고, 실차는 추가 목표다 (실차는 제약이 많아 완성이 불확실).
> 2026-10-22 저녁: 웹 시안으로 트랙·화면·주행 규칙을 정했다 — 실제 서킷 트랙 2개, 1인칭 화면, F1 출발 신호, 가변 속도, 회피, 장애물 배치 검사 (§3·§4·§4-2·§7, 계약 v1.4).

## 1. 왜 시뮬레이터 구성이 기본인가

| 실차의 제약 | 내용 |
| --- | --- |
| 장비 도착 | 차체·모터 드라이버·D435f·젯슨 도착까지 일주일 이상 |
| 하드웨어 통합 | ESP32 펌웨어·배선·전원, 시리얼 프레임(-241), 엔코더·ToF·E-stop 을 모두 맞춰야 한다 |
| 인지 | 젯슨에서 D435f 로 차선·장애물을 실내 조명·트랙에서 안정적으로 찾아야 한다 |
| 주행 공간·안정성 | 트랙을 깔 공간, 주행이 흔들리면 핵심 장면(D3 인계·D4 복구)이 흐려진다 |

이 프로젝트가 보이려는 것(Xen 위 VM 격리, 장애 인계, 자동 복구, 재개)은 **보드와 VM 쪽**에 있다. RPi4 + Xen 보드와 VM 기동은 이미 확인됐다. 그래서 그 부분은 실제로 돌리고, 불확실한 차와 눈만 시뮬레이터로 두어 **확실히 끝나는 구성**을 먼저 완성한다.

원칙: **시뮬레이터 때문에 앱·게이트웨이·백엔드·화면 코드를 따로 만들지 않는다.** 실차가 준비되면 시뮬레이터 자리에 ESP32, 인지 대역 자리에 젯슨을 꽂기만 하면 실차 확장이 된다.

## 2. 구성

| | 기본 시연 (시뮬레이터) | 실차 확장 (추가 목표) |
| --- | --- | --- |
| 보드 | RPi4 + Xen | 같음 |
| VM | 자율·수동 Zephyr + 인터랙션 Debian | 같음 |
| dom0 | 브로커·게이트웨이·복구 서비스·표시 서비스 | 같음 |
| 차 | **시뮬레이터** (노트북, 이더넷 TCP 로 시리얼과 같은 프레임) | ESP32 + RC카 (USB 시리얼) |
| 인지 | **인지 대역** (노트북, 시뮬레이터 위치로 계산) | D435f + 젯슨 |
| 관객이 차를 보는 곳 | **시뮬레이터 화면** (§4) | 실제 차 + 같은 화면 |

```text
 ┌──────────────── RPi4 + Xen (실제) ────────────────┐            ┌────────── 노트북 ──────────┐
 │ 자율 VM ─┐                                         │            │                           │
 │ 수동 VM ─┴ drive.command ─▶ 게이트웨이 ── 프레임 ──┼── TCP ───▶ │ 시뮬레이터 (ESP32 + 차체)   │
 │                              ▲  │ vehicle.status   │ ◀─ 상태 ── │   │ 차 위치·트랙·장애물      │
 │ 인터랙션 VM                   │  ▼                  │            │   ▼                       │
 │                     Mosquitto ◀── perception.result ┼────────────┤ 인지 대역 (젯슨 자리)      │
 │                              │                     │            │   └ 합성 카메라 영상       │
 │ 백엔드 → 관리 콘솔·모니터 2대 (시뮬레이터 화면 포함)  │            └───────────────────────────┘
 └────────────────────────────────────────────────────┘
```

- 시뮬레이터는 **ESP32 자리**(게이트웨이 시리얼 뒤)에 들어간다 (-260). 게이트웨이는 시리얼 대신 TCP 로 같은 프레임(COBS + CRC, -241)을 보낸다 (-269). `vehicle.status` 는 실차와 똑같이 게이트웨이만 발행한다.
- 인지 대역은 **젯슨 자리**에 들어간다 (-268). 시뮬레이터가 알려 주는 차 위치·트랙·장애물로 `perception.result`(차선 오프셋·방향 오차·장애물 거리·정지 필요)를 계산해 15 Hz 로 낸다. 자율주행 앱이 낸 조향이 실제로 차를 트랙 위에 붙잡아 두는 **닫힌 고리**가 된다.

## 3. 시뮬레이터가 흉내 내는 것

| 실차 | 시뮬레이터 | 근거 |
| --- | --- | --- |
| ESP32 와치독 300 ms | 프레임 300 ms 끊기면 정지 + `flags.watchdog` | 계약 §5.5, -241 |
| 모터·조향 | 자전거 모델, 조향 속도 제한. **속도는 고정이 아니다**: 최고 = 예전 고정 속도(0.5 m/s)의 두 배 1.0 m/s, 가속은 빠를수록 덜 붙고(실제 환산 0→100 km/h 약 2.5초), 브레이크·놓았을 때 감속·후진이 따로 있다 | -47, -261 |
| 노면 | 연석까지 아스팔트, 그 밖은 잔디·흙(지나갈 수 있지만 최고 0.3 m/s), 그 밖은 벽(못 넘음) | -261 |
| ToF 장애물 | 차 앞 감지 거리 안에 장애물 → `flags.obstacle` + 전진 차단 | -47 |
| E-stop 버튼 | 관리 콘솔 [E-stop] (시뮬레이터 터미널 `e` 도 남김) | -47 |
| 엔코더 속도 | 모델 속도 그대로 | — |
| 트랙·위치 | **실차에 없는 값.** 시뮬레이터 전용 토픽 `xenova/v1/sim/pose`(20 Hz)·`sim/world`(retained). 트랙은 실제 서킷 2개 (§7 P4) | -261 |
| 출발 | F1 출발 신호 — 빨간 불 다섯 개가 1초마다 켜지고, 0.2~3초 뒤 모두 꺼지면 출발. 랩 시간·부정 출발 | -261 |
| D435f 영상 | 인지 대역이 시뮬레이터 장면을 그린 합성 MJPEG (`raw.mjpg` 자리) | -263, camera-stream-v1 |

## 4. 화면

```text
 모니터 1 (3분할)                                                  모니터 2 (상세)
┌──────────────────┬──────────────────┬──────────────────────┐   ┌──────────────────────────┐
│ 자율주행 VM       │ 수동주행 VM       │ 시뮬레이터            │   │ 모니터 1 의 칸 중 관리     │
│ 차 1인칭 화면     │ 차 1인칭 화면     │ 트랙·차·장애물 (탑뷰) │   │ 콘솔에서 고른 1개를 크게   │
│ 인식 박스·계획 경로│ 조작 키 ↑ ←      │ 출발 신호, 랩 시간    │──▶│ (보통은 시뮬레이터)        │
│ 184 km/h · 판단   │ 인계까지 82 ms   │ 인터랙션 알림 띠      │   │                          │
└──────────────────┴──────────────────┴──────────────────────┘   └──────────────────────────┘
```

| 화면 | 내용 | 실차 확장에서는 |
| --- | --- | --- |
| **시뮬레이터 화면** (-262) | 실제 서킷을 위에서 내려다본 그림(탑뷰): 아스팔트·연석·잔디·흙·벽·관중석·나무, 차(실제 크기)·장애물·계획 경로, 모드 색, 속도, 출발 신호·랩 시간, 3·2·1 카운트다운 | 실제 차를 직접 본다 |
| **1인칭 화면** (-262) | 자율·수동 칸 안에 차 앞 카메라 시점: 하늘·구름·먼 산, 사진 나무, 관중석, 출발 신호 다리, 장애물 인식 박스(종류·거리), 계획 경로 점, km/h. 수동 칸은 조작 키 | 젯슨 카메라 영상 |
| 모니터 1 (3분할) | 자율주행 · 수동주행 · **시뮬레이터** | 세 번째 칸은 **자동으로** 정해진다: 시뮬레이터 위치가 1초 안에 왔으면 시뮬레이터, 아니면 인터랙션 (2026-10-22 결정). 배치 조작이 필요 없다 |
| 모니터 2 (상세) | 관리 콘솔에서 고른 화면 1개 (자율주행 / 수동주행 / 시뮬레이터 / 인터랙션) | 시뮬레이터 대신 다른 화면 |
| 관리 콘솔 | VM 목록·장애 주입·재개 + **트랙 조작**: 장애물 놓기·옮기기·치우기, E-stop, 차 밀기 | 트랙 조작은 비활성 (장애물은 사람이 놓는다) |
| 카메라 | 합성 영상, 인터랙션 VM 화면·콘솔에서 | 젯슨 원본 영상 |

- 인터랙션 VM 은 그대로 돈다 (알림·재개 요청·카메라 AI). 모니터 1 칸에서 빠지는 대신 시뮬레이터 칸 아래 **알림 띠**에 그 VM 이 낸 알림을 보이고, 상세는 모니터 2 에서 고른다. 그 VM 이 죽으면 알림 띠가 "인터랙션 VM 응답 없음"으로 바뀌고 차는 계속 달린다 (D8 격리).
- 시뮬레이터 화면 데이터는 백엔드 중계로 받는다. 화면은 브로커에 직접 붙지 않는다 (MQTT 계약 D2 와 같은 원칙).
- **표시 단위**: 화면은 실제 서킷 단위로 보인다 — 한 바퀴 km, 속도 km/h, 거리·틈 m. 모의 값에 트랙의 `real_m` ÷ 중심선 길이(약 51)를 곱한다. 계약 값(m, m/s)은 그대로다. 같은 비율이라 차 폭이 약 10 m 로 보이는 점은 발표에서 "1/50 축소 트랙" 으로 설명한다.
- 보드(RPi4) 브라우저에서 1인칭 두 개 + 탑뷰를 함께 그리므로 화면은 그리기 빈도·품질을 낮출 수 있게 만든다. 실보드에서 프레임을 재고 정한다 (-262).

### 4-1. 정해진 코스가 아니라 자율주행이라는 증거

1. **아무 때나, 아무 곳에** 장애물을 놓는다 (콘·박스·타이어). 심사위원에게 위치를 고르게 한다.
2. 자율주행 칸이 **자기가 본 인지 값과 판단**을 실시간으로 보인다 (인식 박스·거리 → 감속 → 남는 틈으로 비켜 지나감, 차선 오프셋 → 조향, 계획 경로 점).
3. **차 밀기**: 콘솔에서 차를 옆으로 30 cm 옮기면 자율주행이 스스로 차선으로 돌아온다.
4. **못 지나가는 자리는 놓을 수 없다**: 콘솔이 "차가 지나갈 틈이 없어요" 를 띄우고 놓지 않는다. 놓을 수 있었던 자리는 실제로 지나간다 (§4-2).

### 4-2. 주행 규칙 (웹 시안으로 정함, 2026-10-22)

시안에서 맞춘 값이다. 시뮬레이터(-261)·자율주행 앱(-259)·화면(-262)이 같은 값을 쓴다.

| 항목 | 규칙 |
| --- | --- |
| 지나갈 수 있나 | 차 몸(0.42 × 0.20 m)과 장애물·벽 사이에 양옆 0.03 m 여유가 남으면 지나간다 → **틈 0.26 m 이상**. 탑뷰에 그린 크기와 판정 크기가 같다 |
| 회피 | 앞 4 m 안 장애물을 차 길이 안에 겹치는 것끼리 묶고, 묶음마다 어느 틈으로 갈지 모든 조합 중 차가 실제로 옮겨 갈 수 있는 것을 고른다 (엇갈린 장애물이면 미리 옮겨 두거나 한 줄로 지나감). 갈 조합이 없으면 정지 |
| 회피 조향 | 평소 0.8 m 앞, 회피 중 0.4 m 앞을 보는 pure pursuit (옆으로 옮겨 가는 거리가 절반) |
| 속도 (자율) | 직선 최고 1.0 m/s, 코너는 √(0.22 / 곡률) 을 넘지 않게 앞에서 미리 감속, 장애물 앞은 회피 속도 0.4 m/s 까지 미리 감속, 잔디·흙 0.3 m/s |
| 수동 | 전진 키를 꾹 누르면 최고 속도까지 서서히, 놓으면 천천히 감속, 아래 키 = 브레이크·후진. 조향은 빠를수록 덜 꺾인다 |
| 배치 검사 | 놓거나 옮길 때 ① 틈 0.26 m ② 자율주행을 미리 돌려 통과 ③ 달리는 차 바로 앞이면 지금 상태로도 통과 — 하나라도 안 되면 거부하고 이유를 띄운다 (계약 v1.4 MQTT-18) |
| 검증 (시안) | 장애물 7개 무작위 × 트랙 2개 × 12바퀴: 접촉·벽 접촉·정지 0. 경계 11가지: 허용 = 실제 통과, 거부 = 실제 못 지나감 |

## 5. 데모 순서

[RC카 시나리오](scenario-rc-car.md) §6 의 D1 ~ D8 을 그대로 따르고, 차 움직임은 시뮬레이터 화면에서 본다.

| # | 조작 | 시뮬레이터 화면에서 보이는 것 | 측정 |
| --- | --- | --- | --- |
| D1 | 세 VM 기동, 자율 출발 | 출발 신호 (빨간 불 다섯 개 → 모두 꺼지면 출발), 차가 트랙을 따라 돈다 (AUTO 색), 직선 가속·코너 감속 | 출발까지 시간, 랩 시간 |

| D8 | 인터랙션 VM 종료 | 알림 띠가 "응답 없음", 카메라만 멈추고 차는 계속 | 명령 주기 변화 없음 |
| D9 | 차 밀기 (콘솔) | 차가 옆으로 밀렸다가 스스로 차선으로 돌아옴 (§4-1) | 복귀 시간 |

핵심은 D3·D4. 시간이 부족하면 D1 → D1-1 → D3 → D4 → D5.

측정값 중 VM·게이트웨이 쪽(전환 시간, 재시작 시간, 명령 주기)은 **실보드 값**이다. 차 쪽(이동 거리, 와치독 정지)은 **모델 값**이라고 밝힌다.

**완성 기준**: 보드 + 노트북 구성에서 D1 ~ D9 를 리허설 2회 연속 성공 (-264).

## 6. 보여 줄 수 있는 것

| | 기본 시연 (시뮬레이터) | 실차 확장이 더하는 것 |
| --- | --- | --- |
| Xen 위 VM 격리 (D2·D8) | ✅ | — |
| VM 장애 → 인계 → 자동 복구 → 재개 | ✅ | 실제 차가 서고 다시 출발 |
| 실시간 OS(Zephyr) 주행 앱 | ✅ | — |
| 하드웨어 안전 (ESP32 와치독·E-stop) | 모델 | ✅ 실제 |
| 카메라 인지 (D435f + 젯슨) | 대역 | ✅ 실제 |

발표 멘트: **"차와 카메라는 시뮬레이터지만, 보드·VM·게이트웨이·관제는 실제로 돌고, 실차와 같은 코드다. 실차는 그 자리에 하드웨어를 꽂기만 하면 된다."** 실차 확장이 준비되면 그 장면을 덧붙인다.

### 7-1. 실차 확장 — 데모에 더하는 조건

실차는 기본 시연을 대신하지 않는다. 준비된 만큼 **기본 시연 뒤에 덧붙인다.**

| 단계 | 더하는 것 | 조건 |
| --- | --- | --- |
| E1 | 실제 ESP32·차체를 시뮬레이터 자리에 (인지는 대역 유지) | 게이트웨이 시리얼로 D1·D3 가 리허설에서 성공 |
| E2 | 젯슨·D435f 를 인지 대역 자리에 | E1 + 실제 트랙에서 차선 추종·장애물 정지 성공 |
| E3 | 실차로 D1 ~ D9 전체 | E2 + 리허설 2회 연속 성공 |

- 자율주행 앱은 다시 만들지 않는다 — 같은 코드에 설정값만 조정한다 ([자율주행 앱 README](../platform/apps/autonomous/README.md) "실차 전환 시 바꿀 것").
- 판단은 리허설마다 팀장이 하고 MM 에 공유한다. 조건이 안 되면 그 데모는 기본 시연만 한다 — 실패한 실차 장면을 무리하게 넣지 않는다.
- 데모 당일에도 기본 시연(보드 + 노트북)을 먼저 띄운다. 실차 확장은 그 뒤 별도 순서로 보여 준다.

## 9. 새 API (2026-10-22)

시뮬레이터 구성 때문에 생기는 메시지·API 다. 기준은 계약 문서이고 이 표는 요약이다.

| ID | 종류 | 경로·토픽 | 내용 | 구현 |
| --- | --- | --- | --- | --- |
| MQTT-15 | MQTT | `xenova/v1/sim/pose` | 시뮬레이터 차 위치·방향·속도 20 Hz | -261 (발행), -270·-268 (구독) |
| MQTT-16 | MQTT | `xenova/v1/sim/world` | 트랙(실제 서킷 중심선·구간별 벽)·트랙 목록·장애물(종류)·E-stop, retained, 바뀔 때 | -261, -270·-268 |
| MQTT-17 | MQTT | `xenova/v1/sim/command` | 장애물 놓기·옮기기·치우기, E-stop, 차 밀기, 트랙 바꾸기·다시 출발 (v1.4) | -271 (발행), -261 (적용) |
| MQTT-18 | MQTT | `xenova/v1/sim/result` | 명령 결과·배치 거부 사유 (v1.4) | -261 (발행), -270 (구독·WS 전달) |

| REST-33 | REST | `DELETE /api/v1/sim/obstacles/{obstacle_id}` | 장애물 치우기 | -271 |
| REST-34 | REST | `POST /api/v1/sim/estop` | E-stop 걸기·풀기 | -271 |
