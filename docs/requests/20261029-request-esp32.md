# ESP32·차량 피드백·적용 확인 구현 요청

대상: ESP32·차량 제어 담당자 / 박신영(Gateway). **신규 목표: 명시 feedback-3. 상태: Pi codec·원 clock/기한·encoder/STOP/HOLD 경로 구현, 고정 vector·Pi codec 교차 확인 / 실제 MCU·차량 미수락.**
이 저장소에서 ESP32 펌웨어 위치는 확인되지 않았다. 담당자가 실제 저장소·수신 dispatcher·명령 적용·센서 표본·watchdog과 후보/hash를 회신해야 한다.

## 현재 할 일과 읽는 순서

1. 신규 구현은 [feedback-3 계약](../contracts/gateway-feedback-3.md)에서 시작합니다. 정확 framing·기본9종 payload·capability·원4시각/INSTALL ACK·원 기한·STOP/HOLD·조향 품질과 optional ToF의 Pi 소비/MCU·실물 미수락을 구분합니다.
2. [고정 bytes](../contracts/vectors/gateway-feedback-3.json)와 [actual codec 교차시험](../../platform/services/gateway/tests/test_feedback3_vectors.py), 제품 `feedback3.py`·`feedback.py`·`scene_authority.py`·`odometry.py`를 대조합니다. vector의 UUID/hash/time/오차는 가상 codec 값이며 실물 설정이 아닙니다.
3. [Gateway 직접 구현·공동 연동](20261029-request-gateway.md)의 제출/적용/실제 정지 경계와 아래 조건을 공동 수락합니다. [주행 설계](../platform/drive-pipeline-architecture.md)는 시스템 배경이며 VM/AUTO·지도·회피/주차 알고리즘은 ESP32 구현 범위가 아닙니다.
4. 구형 장치를 명시 선택할 때만 [feedback-1/2 원본](../contracts/gateway-provider-v1.md#g3-명시-선택-serial-feedback-1)과 [기존1](../contracts/vectors/gateway-feedback-1.json)·[기존2](../contracts/vectors/gateway-feedback-2.json) vector를 사용합니다. 기존 bytes는 유지하며 새 profile을 묵시 전송·자동 승격·downgrade하지 않습니다.

## 제공물과 남은 결정

신규 MCU는 CLOCK_INSTALL의 원 clock/기한과 같은 설치 설정을 사용하고, DRIVE/HOLD apply 직전 `device_now+J_apply < device_cutoff`를 검사합니다. cutoff에서 안전 출력 진입을 시작해 J_cutoff 안에 완료해야 하며, 실제 차량 속도0·제동거리 확인은 별도입니다. Pi 지연/정지·USB 단절 때도 독립 timer가 원 cutoff를 지켜야 합니다. 같은 command key/bytes는 원 결과만 replay하고 재적용·기한 갱신은 하지 않습니다. 최근 결과8개+최고 sequence fence+별도 active STOP pin1개의 MCU 구현을 제공합니다.

조향은 measured/estimated/미지원과 **양의 오차**를 구분해야 합니다. 센서 없이 목표 PWM이나 추정값만 있는 하드웨어는 현재 AUTO HOLD_READY의 실측 조향 settle 조건을 충족하지 않습니다. estimated를 measured로 표시하지 않으며 별도 정책은 아직 수락되지 않았습니다.

`firmware_sha256`은 현재 Pi 등록값과 MCU 자기보고 digest의 일치 검사입니다. 실제 full binary/flash 검증으로 확정하지 않습니다. firmware/config의 정확 hash 대상·canonical domain·build manifest·NVS 저장/업데이트/boot 읽기 검증 절차와 같은 실측 clock/J_apply/J_cutoff 설정 주입 방식을 담당자가 제공해야 합니다. 실측 clock error/drift·servo settle/오차·encoder scale 상한·brake/정지거리 없이 가상 zeroJ/1mrad/반복문자 hash를 운영값으로 복사하지 않습니다.

ToF 없는 빈 source 목록은 유효합니다. 기존 ToF `0x0f16`/209B·전체 CRC393B의 **Pi payload decoder/assembler와 기존 J 전달은 선택 profile로 연결했습니다**. 새 소프트웨어 회귀의 동적 검증과 MCU producer·native 상태/reducer·보정·물리 수락은 별도입니다. 원 wire·source/generation/instance/capture와 실제 INSTALL ACK·TTL을 따르며 임의 packet을 추가하지 않습니다. ToF polling/reset/I2C 대기가 STOP/control/encoder를 막지 않아야 하고, ToF 포함460800/8N1 목표·실제 bridge/USB 지연을 계측합니다. ToF cap0x200은 실제 구현한 장착 source에만 광고하며 빈 목록의 clock/encoder/STOP 준비조건으로 요구하지 않습니다.

Gateway의 `--vehicle-limits` 설정은 [차량 한계 정의](../../platform/services/gateway/README.md#차량-한계와-출력-실패)를 따른다.
DEC-02 담당자는 실제 속도/조향 범위와 허용 제출 목표 변화율을 측정·확정해 제공한다.
코드/시험의 통제 수치를 차량 운용 기본값으로 사용하지 않는다. Gateway는 원 명령과
양자화 결과를 제한하지만 실제 가속도·조향각을 측정하지 않으며, STOP 제출 성공도 정지 ACK가 아니다.
ACK·로컬 피드백·명령 상실 정지·실제 제동의 생산/소비 연결은 DEC-13·ARCH-T22·38에서 계속 수락한다.

Gateway는 단일 serial owner에서 RX/TX·bounded parser·원 명령 대응·만료/재부팅을 처리한다.
실제 PTY/pyserial 시험은 Pi 제공자 경계이며 MCU·물리 정지 완료가 아니다. 센서 부재는 null로 남긴다.
장치 담당은 속도·조향·stationary의 실제 측정/추정/목표를 구분하고 측정 범위·표본 의미를 회신한다.
운영 ACK 기한·차량 한계/보정값은 장치·차량 측정 뒤 승인한다. PTY의 400ms fixture를 운영값으로 복사하지 않는다.
정상 handshake→DRIVE 접수/적용→STOP 적용·지원 센서 관측과, Pi timeout/FAULT의 철회/STOP·실제 watchdog/E-stop을 함께 수락한다.
회신에는 firmware 후보·toolchain·capability/vector·시험 명령/결과·물리 환경·미수행·승인값·배포 상태를 구분한다.

## 공동 수락 순서

- **Codec 묶음:** 고정 vector를 실제 Pi codec과 독립 MCU codec으로 교차하고 CRC/COBS/길이/partial·session/hash/cap/ABI·원 clock/expiry/STOP ref·quality/positive error·duplicate/replay를 유한 실행으로 확인합니다. 새 Pi codec 교차시험41개는 Nano에서 통과했으며, MCU codec과 실제 상태 전이·기한 수락은 별도입니다.
- **실제 보드 bench:** source commit/toolchain/artifact·hash manifest·설정·device boot session을 고정하고 원 wire transcript를 제출합니다. 실제 latch/encoder/조향, clock jitter, J_apply/J_cutoff, USB 단절·Pi 정지·MCU reset/만료에서 timer/FAULT·재무장 동작을 함께 계측합니다.
- **실제 차량:** 승인 저속·통제된 환경에서 양 wheel/yaw 정지창·측정 조향 settle·방향전환과 brake/정지거리를 수락합니다. output 제출·장치 APPLIED·실제 정지를 각각 표시하고 실패/미실행을 원 상태로 남깁니다.

기존 feedback3 PTY2개와 ControlFacts 실제 PTY3개는 pyserial 준비/승인 대기로 미실행입니다. 새 codec 시험이나 development-fd 성공을 이5개 또는 실제 MCU·차량 PASS로 바꾸지 않습니다.

## feedback-2 연결과 수락 — 구형 명시 호환

신규 encoder 작업의 실제 수정 위치는 MCU 담당자가 위의 수신 dispatcher·센서 수집 위치에
대응해 회신해야 합니다. ODOM_PROBE의 Pi session/device session·송신 시각을 그대로 echo하고
실제 원 표본의 장치 시각·증가 sequence·누적 좌우 encoder를 ODOM_REPORT로 생산합니다.
해당 probe를 받은 뒤 표본을 생성하거나 센서 누계를 래치하고 그 실제 시각을 넣어 주세요.
probe 이전 cache 표본에 새 송신 sequence만 붙이는 방식은 Pi 시계 구간의 전제를 충족하지
않습니다. 원 echo는 그대로 유지하며 장치가 Pi의 내부 제출 시각을 해석하거나 새 필드를
생산할 필요는 없습니다. 실제 dispatcher→센서 래치→회신 순서를 MCU 시험 근거로 회신해 주세요.
송신 횟수나 목표 속도 적분을 encoder 진행으로 보고하지 마세요. 측정/추정 steering과 오차,
encoder wrap/reset·장치 부팅 session 및 실제 센서 지원 capability를 함께 제공합니다.

Pi 제공자는 실제 serial 단일 owner에서 decode→시계 구간→연속성/기구학→odom epoch→
VehicleSample 발행을 처리합니다. Jetson 연결 없이 로컬 MANUAL 계산이 소비합니다.
정상 정지 보고를 확인하지 못한 AUTO→MANUAL 이동은 원 기한에서 차단합니다.
장치 담당 수락은 vector 교차와 정상 encoder 진행에 더해 partial/CRC·옛 session·표본 역전·
긴 단절·장치 reset 뒤 새 epoch·정상 회복을 포함합니다. 실제 watchdog/E-stop·제동·stationary
정의와 차량/시계/센서 오차의 실측 승인값은 별도 제공물이며 가상 장치로 완료 처리하지 않습니다.

## 진행 기록

- 2026-10-29: 현재 Pi codec과 미연결 장치 경계를 대조해 요청을 작성했습니다. 실제 장치 펌웨어·차량 검증은 수행하지 않았습니다.
- 2026-11-01: 세션/ACK가 없던 이전 Pi 상태는 write-only 이력이다. 명시 feedback-1의 Pi 구현과 PTY 계약 시험을 제공했다. 실제 firmware·차량 수락은 계속 미수행이다.
- 2026-11-02: 명시 feedback-2·고정 교차 vector·실제 누계 odom 소비 경로를 제공했다. MCU 생산과 실측 승인값은 담당자 수락으로 유지한다.
- 2026-11-09: 신규 연결 목표를 feedback-3로 맞추고 canonical 계약·독립 고정 vector·실제 codec 교차시험 코드를 추가했다. Nano Pi codec 교차시험41개는 통과했고 원 근거는 Jetson-drive-docs/making-reports의0065 보고서에 보존한다. MCU/실물 수락은 미실행이며 feedback-1/2 원문·vector는 명시 호환 자료로 보존했다.
