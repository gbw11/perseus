# RC카 시나리오

Xenova(RPi4 + Xen) 위의 VM 들이 RC카를 나눠 맡고, **주행 중인 VM 이 죽어도 차가 안전하게 계속 가거나 멈추며, 죽은 VM 은 자동으로 돌아오는 것**을 보여준다.
VM 역할, 정상 흐름, 장애·복구 흐름, 화면, 데모 순서와 측정 지표를 이 문서에 맞춘다.

> 상태: 초안 (2026-10-20, S15P31E110-45). 10/19 확정한 자율주행·수동주행·인터랙션 구성 기준(10/20 게스트·화면 반영)이며,
> 옛 기획(Alpine 주행 제어·Debian 안전 감시·Ubuntu 인포테인먼트)과 [아키텍처 설계서](architecture.md)의 핫 스탠바이 안(주행 VM 2대 + 콕핏)을 대체한다.
> 토픽·메시지 형식은 [MQTT 메시지 계약 v1](contracts/mqtt-contract-v1.md)이 기준이고, 이 문서는 그 위의 흐름을 설명한다.

## 1. 한눈에

```text
 D435f ─USB3─▶ Jetson Nano ──인지 결과 15 Hz──┐
              (vehicle/)                      ▼
 ┌─────────────────────────── RPi4 + Xen ───────────────────────────┐
 │ VM 자율주행  (Zephyr, autonomous)  ── drive.command 50 Hz ──┐       │
 │ VM 수동주행  (Zephyr, manual)      ── drive.command 50 Hz ──┤ 대기  │
 │ VM 인터랙션  (Debian, message-board) ◀── 모드·장애 알림       │ →인계 │
 │                                                            ▼       │
 │ dom0: Mosquitto │ 게이트웨이(제어권 판정) │ 복구 서비스 │ 표시(모니터 2대) │
 └──────────────────────────────┬─────────────────────────────────────┘
                             ▼ 활성 앱의 명령만 유효
                    ESP32 (모터·조향, 와치독 300 ms, E-stop)
```

| 누가 | 무엇을 | 무엇은 하지 않나 |
| --- | --- | --- |
| 젯슨 | 카메라로 차선·장애물을 인식해 `perception.result` 발행 | 주행 명령을 내지 않는다 |
| 자율주행 VM | 인지 결과로 판단·경로를 만들어 평소 주행 명령을 낸다 | — |
| 수동주행 VM | 대기하다가 자율주행에 문제가 생기면 **바로 이어받아** 콘솔 키 입력을 주행 명령으로 바꾼다 | 키 입력이 없으면 정지 명령(`v_mps = 0`)만 낸다 |
| 인터랙션 VM | 관제 메시지, 모드·장애 알림을 보여주고 자율주행 재개 요청을 보낸다. 젯슨 카메라 영상에서 AI 로 장애물을 찾아 감지 박스 영상을 낸다 (화면용, 주행 판단에는 안 씀) | 주행 명령을 내지 않는다 |
| dom0 게이트웨이 | 활성 앱 명령이 100 ms 끊기면 제어권을 바꾼다 | VM 을 재시작하지 않는다 |
| dom0 복구 서비스 | 죽은 VM 을 재시작한다 | 제어권을 바꾸지 않는다 |
| ESP32 | 활성 앱의 현재 세대 명령만 적용, 300 ms 끊기면 스스로 정지 | — |

## 2. VM 배치

| VM | app_id | 게스트 | 코어 | 비고 |
| --- | --- | --- | --- | --- |
| 자율주행 | `autonomous` | **Zephyr** | 전용 1 | 50 Hz 계산, 지연 민감. 실시간 OS 로 주기 보장 |
| 수동주행 | `manual` | **Zephyr** | 전용 1 | 대기 중에도 50 Hz 로 명령을 내서 즉시 인계할 수 있게 한다 |
| 인터랙션 | `message-board` | **Linux (Debian 13)** | dom0 와 공유 | 화면·알림·재개 요청·카메라 AI 감지, 지연 덜 민감 |
| dom0 | — | Yocto | 전용 1 + 공유 | 게이트웨이(코어 고정), Mosquitto, 복구 서비스, 표시 |

- 앱 코드는 `platform/apps/`, 젯슨 코드는 `vehicle/`, 게이트웨이는 `platform/services/` 아래에 둔다.
- 템플릿은 저장소의 기본 템플릿(`platform/guests/default-templates.lock.json`: Zephyr starter, Debian 13)을 쓴다. 코어·메모리 확정은 플랫폼 파트와 실보드 측정 후.
- 인터랙션 VM 의 토픽 id 는 MQTT 계약의 `message-board` 를 그대로 쓴다.
- **Zephyr 주행 VM 이라 생기는 일** (§8 결정 D3·D8, 화면은 §5):
  - VM 에이전트(Linux 전용 heartbeat)가 없다. 게이트웨이의 제어권 전환은 원래대로 `drive.command` 신선도로 본다. VM 생존(복구 서비스)과 `AUTO_READY` 는 **Xen 도메인 상태 + 앱 `app.heartbeat`** 로 판정한다 (D8).
  - Python MQTT 클라이언트(`xenova_mqtt`)를 못 쓴다. 같은 봉투 규칙의 C 라이브러리(`platform/apps/common/xenova-mqtt-c`)를 쓴다.
  - 네트워크: Zephyr 템플릿은 PV 네트워크를 지원하지 않으므로 **vchan + dom0 중계**로 MQTT 를 대신 주고받는다 (D3). 중계는 앱별 브로커 계정·ACL 을 대신 적용한다.

## 3. 정상 흐름 (AUTO)

1. 젯슨이 `xenova/v1/apps/perception/events` 에 `perception.result`(차선 오프셋·장애물·정지 필요)를 15 Hz 로 낸다.
2. 자율주행 VM 이 최신 인지 결과로 목표 속도·조향을 계산해 `drive.command` 를 50 Hz 로 낸다.
3. 수동주행 VM 도 대기 중에 `drive.command`(`v_mps = 0`)를 50 Hz 로 계속 낸다. 게이트웨이는 이것으로 수동 VM 이 바로 이어받을 수 있는지(신선도)를 본다.
4. 게이트웨이는 `vehicle/control`(retained)에 현재 모드 `AUTO`, 활성 앱 `autonomous`, 세대 `generation` 을 둔다.
5. ESP32 는 활성 앱 토픽의 현재 세대 명령만 적용하고, 20 Hz 로 `vehicle/status`(실제 속도·조향, E-stop·와치독·장애물 플래그, 배터리)를 낸다.
6. 자율주행 VM 이 장애물을 판단하면 `perception.event` 를 내고, 인터랙션 VM 이 알림으로 보여준다.
7. Linux VM(인터랙션)의 에이전트는 5초마다 heartbeat 를 내고, 백엔드가 VM 상태(ONLINE·STALE·OFFLINE)를 관리 콘솔에 보여준다. Zephyr 주행 VM 의 상태는 도메인 상태와 명령 신선도로 보여준다 (§8 D8).

## 4. 장애·복구 흐름

### 4.1 주행 모드

```text
            자율 명령 100 ms 끊김                       복구된 자율 VM 명령 3초 신선
   AUTO ──── + 수동 명령 신선 ────▶ MANUAL ──────────────────────────────────▶ AUTO_READY
    ▲                                 ▲                                              │
    │        활성 앱 끊김 + 넘길 앱 없음  │ 수동 명령이 다시 신선                          │ 인터랙션 VM 에서
    │              ▼                  │                                              │ 자율주행 재개 요청
    │          SAFE_STOP ─────────────┘                                              │
    └───────────────────────────────────────────────────────────────────────────────┘
```

| 모드 | 활성 앱 | 차 | 화면 표시 |
| --- | --- | --- | --- |
| `AUTO` | autonomous | 자율주행 | 자율주행 중 |
| `MANUAL` | manual | 운영자 키 입력대로 (입력 없으면 정지) | 수동주행 중 + 장애 알림 |
| `AUTO_READY` | manual | 계속 수동 | 자율주행 재개 가능 → [재개] 버튼 |
| `SAFE_STOP` | 없음 | 정지 | 안전 정지 |

모드나 활성 앱이 바뀔 때마다 세대(`generation`)가 1 오르고, ESP32 는 이전 세대 명령을 버린다.

### 4.2 장애별 흐름

| # | 장애 | 감지 | 차 | 복구 |
| --- | --- | --- | --- | --- |
| F1 | 자율주행 VM 죽음 | 게이트웨이: 자율 명령 100 ms 끊김 | **대기하던 수동주행 VM 으로 바로 인계** (`MANUAL`). 운영자가 키로 운전, 키 입력 전엔 정지 | 복구 서비스가 재시작 → 명령 3초 신선 → `AUTO_READY` → 인터랙션 VM 또는 관리 콘솔에서 재개 → 3·2·1 → `AUTO` |
| F2 | 자율주행 VM 이 느려짐 (CPU 과부하) | 같음 (명령 간격 100 ms 초과) | 같음 | 부하가 풀리고 3초 신선하면 `AUTO_READY` |
| F3 | 자율·수동 둘 다 없음 | 게이트웨이: 넘길 신선한 앱 없음 | `SAFE_STOP` 정지 | 수동 VM 명령이 신선해지면 `MANUAL` |
| F4 | 인터랙션 VM 죽음 | 에이전트 OFFLINE | 주행 영향 없음 (격리) | 복구 서비스가 재시작, 알림은 복구 뒤 다시 표시 |
| F5 | 게이트웨이·dom0 끊김 | ESP32: 명령 300 ms 끊김 | 와치독 정지 | 게이트웨이 재시작 뒤 사람이 확인하고 재개 (자동 출발 없음). ※ 지금 게이트웨이 구현은 시작 모드 기본값이 `AUTO` 라, 실차·데모에서는 `--start-mode SAFE_STOP` 으로 띄운다 |
| F6 | 젯슨 끊김 | 자율주행 VM: 인지 결과 끊김 | 자율주행 VM 이 정지 명령을 낸다 (§8 D5) | 인지가 돌아오면 재출발 |
| F7 | 하드웨어 E-stop | ESP32 | 모터 전원 차단 | 사람이 해제 |

원칙:
- **잘못 넘기는 것보다 멈추는 게 낫다.** 수동 VM 명령이 신선하지 않으면 넘기지 않고 `SAFE_STOP`.
- `MANUAL`(또는 `AUTO_READY`) 중 수동 명령이 끊기면 자율이 신선해도 `SAFE_STOP` 이다. `AUTO` 에는 시작과 재개로만 들어간다 (전환 표: [MQTT 계약](contracts/mqtt-contract-v1.md) §5.2).
- 게이트웨이는 제어권만, 복구 서비스는 재시작만, ESP32 는 최종 정지만 맡는다. 판정 주체가 겹치지 않는다.
- 자율주행 복귀는 자동이 아니라 **사람이 재개를 누른다** (`AUTO_READY` 에서만 받는다). 재개는 바로 바뀌지 않고 3초 카운트다운(`drive.resume.accepted`) 뒤 `AUTO` 가 되며, 그 사이 자율이 다시 끊기면 취소(`drive.resume.cancelled`)되고 `MANUAL` 로 돌아간다 ([MQTT 계약](contracts/mqtt-contract-v1.md) v1.2, Draft !118, 2026-10-21 결정).

### 4.3 '복구 중' 표시 기준

| 상태 | 시작 | 끝 | 화면 |
| --- | --- | --- | --- |
| 장애 | `drive.fault.detected` 수신 (게이트웨이) 또는 에이전트 `OFFLINE` | 도메인이 다시 실행 중 (Zephyr) / 에이전트 `ONLINE` (Linux) | 해당 VM 빨강, "○○ VM 장애" |
| 복구 중 | 복구 서비스가 재시작한 도메인이 실행 중 | 자율주행: `AUTO_READY` 진입 / 수동주행: 명령 신선 / 인터랙션: `ONLINE` 후 앱 이벤트 수신 | 노랑, "○○ VM 복구 중" + 경과 시간 |
| 복구 완료 | 위 '끝' 조건 | — | 초록. 자율주행은 [재개] 버튼 활성 |

사용자가 콘솔에서 일부러 끈 VM 은 장애가 아니라 '정지' 로 표시하고 재시작하지 않는다.

## 5. 화면

모니터 2대를 dom0 표시 서비스(화면 라우터, 박신영)가 HDMI 로 내보낸다.

```text
 모니터 1: 3분할 (전체 상황)                         모니터 2: 선택한 1개를 크게 (상세)
 ┌────────────┬────────────┬────────────┐        ┌──────────────────────────────────┐
 │  자율주행    │  수동주행    │  인터랙션    │        │  관리자가 고른 VM 의 상세 화면        │
 │  모드·인지   │  대기/인계   │  알림·재개   │  ───▶  │  (예: 자율주행 — 인지 결과, 경로,     │
 │  상태 배지   │  상태 배지   │  상태 배지   │  선택  │   명령 그래프, 전환 타임라인)         │
 └────────────┴────────────┴────────────┘        └──────────────────────────────────┘
```

| 화면 | 내용 |
| --- | --- |
| 모니터 1 (3분할) | VM 3개를 한 칸씩. 각 칸에 VM 이름, 상태 배지(정상·장애·복구 중, §4.3), 현재 모드(AUTO·MANUAL·AUTO_READY·SAFE_STOP)와 핵심 값 하나씩. 장애가 나면 해당 칸만 빨강으로 바뀌어 **격리**가 보인다 |
| 모니터 2 (상세) | 관리자가 3개 중 고른 1개를 크게. 자율주행: 인지 결과·목표 속도/조향·명령 주기, 수동주행: 키 입력·인계 상태, 인터랙션: 메시지 타임라인·[재개] 버튼. 차량 상태(속도·조향·배터리·장애물)는 공통 표시 |
| 관리 콘솔 (노트북 브라우저) | 모니터 2 에 띄울 VM 선택, VM 목록·메트릭·이벤트 로그, 장애 주입(강제 종료·부하) 버튼 |

- 모니터 배치는 관리 콘솔 → 화면 배치 API(REST-23·24, -129) → 백엔드 → `WS /ws/v1/display-service` → dom0 표시 서비스가 키오스크 주소를 바꾸고 `route.applied` 로 답한다 (화면 라우터 UI -130). 모니터 브라우저는 스스로 따라가지 않는다 (2026-10-21 결정, 화면 배치 계약 `display-route-v1` 작성 중).
- 데모 중 장애를 일으키는 조작은 관리 콘솔에서 하고, 결과는 두 모니터에서 보이게 한다.
- **화면은 각 VM 이 직접 낸다** (10/20 결정, 구 D9). 표시 서비스·화면 라우터는 VM 이 낸 화면을 모니터 칸에 배치만 하고, dom0 가 VM 대신 그리지 않는다. 장애 난 VM 칸이 실제로 멈추고 비는 것으로 **격리**가 보인다.
  - 메시지 보드(Debian): VM 안의 웹 화면 서버를 dom0 키오스크가 xenbr0 로 연다 (VM 앱 화면 -128). VM 이 죽으면 칸이 빈다.
  - 자율·수동주행(Zephyr): 그래픽이 없으므로 앱이 **자기 PV 콘솔에 텍스트 상태 화면**(모드·세대·목표 속도/조향·입력·heartbeat)을 주기적으로 그리고, 표시 서비스가 `xl console` → WebSocket → 웹 터미널로 칸에 띄운다 (웹 콘솔 프록시 -69 와 같은 경로, 읽기 전용 다중 구독).
  - 상태 배지(정상·장애·복구 중)는 표시 서비스가 칸 테두리에 덧붙인다 (§4.3, 근거는 백엔드 상태).
- **지금 구현 (2026-10-21):** 위 방식(VM 이 직접 낸 화면)은 아직 없다 — Zephyr PV 콘솔 상태 화면(-243)·웹 콘솔 프록시(-69)·표시 서비스(-129) 미구현. 대신 모니터 화면은 웹 앱 `frontend/apps/vm-screens`(3분할 `/split`, 상세 `/detail/{autonomous|manual|interaction}`)이고, 데이터는 백엔드 중계 WebSocket(`/ws/v1/drive/state`, `/ws/v1/events`)으로 받는다 ([화면 정의서](design/screen-spec.md) §5·Q5). 이 방식에서는 VM 이 죽어도 칸이 비지 않고 백엔드가 본 상태(명령 끊김·heartbeat)로 장애를 표시한다. 어느 쪽을 데모 기준으로 할지는 -128 에서 정한다.
- 재개 요청 경로는 둘이다: 메시지 보드 VM(MQTT-06)과 관리 콘솔 [자율주행 재개](`POST /api/v1/drive/resume` → MQTT-13 `xenova/v1/console/resume`). 콘솔과 모니터는 3·2·1 을 표시한다 (MQTT 계약 v1.2, Draft !118 — 백엔드·게이트웨이 구현 중).
- 카메라: 젯슨 원본 MJPEG → 인터랙션 VM 이 AI 감지 → 감지 박스 MJPEG → dom0 웹 프록시 `/camera/stream.mjpg`. 대시보드 세 번째 VM 카드, 모니터 3분할의 그 칸과 상세에 보인다. 감지 결과는 MQTT-14 `xenova/v1/apps/message-board/vision` (화면·기록용). 그 VM 이 죽으면 영상만 멈추고 주행은 그대로 (격리). 카메라 영상 계약 `camera-stream-v1` 작성 중.

## 6. 데모 순서

| # | 조작 | 보여주는 것 | 측정 |
| --- | --- | --- | --- |
| D1 | 시작: 세 VM 기동, 자율주행 출발 | 정상 흐름, 관리 콘솔에 VM 3대 ONLINE | 출발까지 시간 |
| D2 | 인터랙션 VM 에 CPU 부하 (`agent.command stress`) | 모니터 1 에서 인터랙션 칸만 부하, 주행은 영향 없음 (격리) | 자율 명령 주기 지터, 타 VM 메트릭 |
| D3 | **자율주행 VM 강제 종료** | 대기하던 수동주행 VM 이 100 ms 안에 바로 이어받고 운영자가 운전. 모니터 1 자율주행 칸 빨강, 인터랙션에 장애 알림 | 전환 시간, 전환 중 이동 거리 |
| D4 | 자동 복구 → 재개 | 복구 중 → `AUTO_READY` → [재개] → 자율주행 복귀 | VM 재시작 시간, 장애~재개 가능까지 시간 |
| D5 | 자율·수동 VM 둘 다 종료 | `SAFE_STOP` 으로 바로 정지 | 정지까지 시간·이동 거리 |
| D6 | 게이트웨이 강제 종료 | ESP32 와치독 300 ms 정지, 사람이 확인해야 재출발 | 정지까지 시간 |
| D7 | 하드웨어 E-stop | 모터 전원 차단 표시 | — |

핵심은 D3·D4 다. 시간이 부족하면 D1 → D3 → D4 → D5 순으로 줄인다.

### 측정 지표

| 지표 | 정의 | 목표 | 출처 |
| --- | --- | --- | --- |
| 제어권 전환 시간 | 자율 명령 마지막 수신 → ESP32 가 수동 세대 명령 적용 | ≤ 150 ms (판정 100 ms + 전달) | 게이트웨이 로그 + `vehicle.status.applied_generation` |
| 전환 중 이동 거리 | 같은 구간의 이동 거리 | ≤ 7.5 cm (0.5 m/s 상한) | 엔코더 |
| 와치독 정지 시간 | 마지막 명령 → 모터 정지 | ≤ 300 ms | ESP32 로그 |
| VM 재시작 시간 | 장애 감지 → 도메인 재실행 + 첫 명령 (Zephyr) / 에이전트 `ONLINE` (Linux) | 측정 후 확정 | 복구 서비스·게이트웨이 로그 |
| 재개 가능까지 시간 | 장애 감지 → `AUTO_READY` | Zephyr 재시작 + 3초 | 게이트웨이 이벤트 |
| VM 간 메시지 왕복 | MQTT-07/08 probe RTT | 측정 후 확정 | 지연 측정 (-131) |
| 명령 주기 | `drive.command` 수신 간격 p50·p99 | 20 ms ± | 게이트웨이 |

수치는 실보드 측정 전 제안값이다. 보드가 오기 전에는 시뮬레이터(-47)와 QEMU 로 흐름을 먼저 맞춘다.

## 7. 하드웨어 연결 (후보)

| 연결 | 후보 | 결정 |
| --- | --- | --- |
| 카메라 → 젯슨 | D435f USB3 | 확정 |
| 젯슨 → RPi4 | 이더넷, 인지 결과는 MQTT. 영상은 별도 스트림 (MQTT 부적합) | 영상 경로는 MQTT 계약 v1.1 |
| RPi4 → ESP32 | (A) ESP32 Wi-Fi 로 MQTT 직결 / (B) dom0 USB 시리얼 → 이후 CAN, 게이트웨이가 변환 | 제다빈·박신영과 결정 (§8 D1) |
| 모터·조향 | ESP32 소유 (MDD10A ×2, 조향 서보), 엔코더·E-stop·ToF(VL53L5CX) | 확정 |
| 화면 | dom0 듀얼 HDMI, 표시 서비스가 VM 화면 배치 | 박신영 |

모터·카메라는 어느 VM 도 직접 갖지 않는다. 카메라는 젯슨, 모터는 ESP32 가 소유하고 VM 은 메시지로만 다룬다. 그래야 VM 이 죽어도 하드웨어 상태가 꼬이지 않는다.
