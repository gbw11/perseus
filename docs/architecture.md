# 아키텍처 설계서

Raspberry Pi 4 + Xen 멀티 OS 플랫폼을 자율주행 RC카에 올린다. 세 보드가 자동차 ECU 역할을 나눠 맡고, 주행 컨트롤러는 RPi4의 VM 안에서 돈다.
**핵심 시연: 주행 중인 VM을 죽이면, 준비된 대기 VM이 있을 때는 멈추지 않고 이어받고, 없을 때는 안전하게 정지한다.** 죽은 VM은 자동으로 복구된다. 대기 VM이 준비되지 않았을 때 정지하는 것은 실패가 아니라 설계된 동작이다.

> 상태: 설계 초안. 구현 세부는 [차량 제어 상세 명세](design/vehicle-control-spec.md)에 있다.

## 1. 구성

```text
 D435f ─USB3─▶ Jetson Nano (ADAS ECU)  ─ Ethernet ─▶ RPi4 + Xen (중앙 컴퓨터)
                인지만. 주행 명령 없음                 ├─ VM-A Debian  주행 컨트롤러 활성
                                                       ├─ VM-B Ubuntu  주행 컨트롤러 대기 + 레코더
                                                       ├─ VM-C Alpine  콕핏(계기판·IVI·텔레매틱스)
                                                       └─ dom0  VM 매니저 │ 차량 게이트웨이 │ MQTT │ 표시
                                                                │ CAN (2단계) / USB 시리얼 (1단계)
                                                                ▼
                                                       ESP32 (섀시 ECU) ─▶ MDD10A 모터 ×2, UBEC 조향 서보
                                                       엔코더·E-stop·VL53L5CX·워치독
```

| 보드 | 역할 | 한 줄 |
| --- | --- | --- |
| Jetson Nano | ADAS ECU | 카메라로 장애물·차선·경로를 계산해 RPi4에 보낸다. 명령은 내지 않는다 |
| RPi4 + Xen | 중앙 컴퓨터 | VM이 명령을 계산하고, dom0 게이트웨이가 활성 VM의 명령만 차량에 전달한다 |
| ESP32 | 섀시 ECU | 모터·조향·엔코더. 명령이 끊기면 스스로 멈춘다 |

연결은 세 가지다. Jetson ↔ RPi4는 이더넷(영상·인지), dom0 ↔ ESP32는 1단계 USB 시리얼 → 2단계 CAN(명령·상태), 외부 ↔ RPi4는 내장 WiFi(콘솔·텔레매틱스)다.

## 2. 핵심 결정

| 결정 | 이유 |
| --- | --- |
| 주행 명령은 VM에서 낸다 | VM이 실제 제어를 맡아야 VM 장애 복구 시연이 의미를 가진다 |
| 대기 VM이 같은 입력으로 같은 계산을 한다 (핫 스탠바이) | 전환 순간 따라잡을 상태가 없다. 활성이 상태를 10 Hz로 복제해 준다 |
| 중재는 dom0 게이트웨이 한 곳만 한다 | VM이 스스로 "내가 활성"이라 하면 스플릿 브레인이 난다 |
| VM 재시작은 VM 매니저 복구 서비스 한 곳만 한다 | 게이트웨이는 승격·정지만. 판정 주체가 둘이면 경쟁 조건이 난다 |
| 최종 안전장치는 하이퍼바이저 밖(ESP32)에 둔다 | VM·dom0·네트워크가 다 죽어도 워치독 300 ms와 하드웨어 E-stop이 세운다 |
| 잘못된 승격보다 정지가 낫다 | 대기 VM이 신선하고 동기화됐고 출력이 비슷할 때만 넘긴다. 아니면 즉시 정지 |
| 게이트웨이는 매니저와 별도 프로세스다 | xl·콘솔 같은 느린 작업이 10 ms 주행 중재를 막으면 안 된다 |
| 중재자(게이트웨이)가 재시작하면 사람이 재무장한다 | 원인이 불확실한 복구 뒤에 차가 혼자 출발하면 안 된다 |
| VM 수준 미러링이 아니라 앱 수준 핫 스탠바이다 | Xen ARM은 라이브 마이그레이션·Remus를 지원하지 않는다 |

## 3. 핫 스탠바이 동작

1. Jetson이 인지 결과를 15 Hz로 보낸다. VM-A와 VM-B가 **둘 다** 받아 **둘 다** 50 Hz로 명령을 계산한다.
2. 게이트웨이는 활성 VM의 명령만 ESP32로 넘긴다. 대기 VM의 명령은 버리되 활성과의 차이를 기록한다.
3. 활성 명령이 100 ms 넘게 끊기면(10 ms 주기 검사라 감지까지 최대 약 110 ms), 대기 VM이 승격 조건을 만족할 때만 활성으로 바꾸고 바로 그 명령을 넘긴다. 조건이 안 되면 정지 프레임을 보낸다.
4. 복구 서비스가 죽은 VM을 재시작한다. 게이트웨이는 그 VM이 0.5초 동안 안정적으로 명령을 내고, 활성과의 상태 동기화·경로 일치·출력 편차 검사까지 통과해야 대기로 등록한다. 등록 조건은 승격 조건과 같다.

| 수치 | 값 | 상태 |
| --- | --- | --- |
| 전환 판정 | 100 ms 초과 감지(10 ms 주기 검사 포함 최대 약 110 ms, 스케줄링 지연 제외) | 가정 |
| 전환 목표 (ESP32가 새 명령 적용까지) | ≤ 150 ms | 목표 |
| ESP32 워치독 | 300 ms | 설계값 |
| 속도 상한 | 0.5 m/s, 전환 중 이동 ≤ 7.5 cm | 목표 |

## 4. 시연 시나리오

| # | 조작 | 보여주는 것 |
| --- | --- | --- |
| 1 | 대기 VM 정상 상태에서 활성 VM 강제 종료 | 최대 약 110 ms 안에 장애 감지, 대기 VM이 이어받아 차가 계속 달림. 대시보드에 전환 시간 |
| 2 | 대기 VM 정상 상태에서 활성 VM에 CPU 부하 | 명령 지연이 100 ms를 넘기면 최대 약 110 ms 안에 전환. 다른 VM은 영향 없음 (격리) |
| 3 | 컨트롤러 VM 둘 다 종료 | 최대 약 110 ms 안에 장애 감지 후 정지 프레임으로 정지. 이어서 dom0까지 끊으면 300 ms 워치독으로 정지 |
| 4 | 자동 재시작 | 복구 서비스가 VM을 올리고 대기로 복귀. 타임라인에 기록 |
| 5 | 하드웨어 E-stop | 모터 전원 차단, 계기판에 표시 |
| 6 | 콘솔에서 대기 VM 정지 | 사용자가 끈 VM은 재시작하지 않음 |
| 7 | 게이트웨이 프로세스 강제 종료 | 워치독 정지 → 새 세션 → 사람이 재무장해야 출발 |

## 5. RPi4 자원 배분

| 도메인 | OS | 역할 | 코어 | 메모리 |
| --- | --- | --- | --- | --- |
| dom0 | Yocto | 게이트웨이(cpu0 고정), 매니저, MQTT, 표시 | cpu0 전용 + cpu3 | 1.5 GB (제안) |
| VM-A | Debian | 주행 활성 | cpu1 전용 | 1 GB |
| VM-B | Ubuntu | 주행 대기 + 경량 레코더 | cpu2 전용 | 1 GB |
| VM-C | Alpine | 콕핏 | cpu3 (dom0와 공유) | 1 GB |

전제는 RPi4 8GB다. 현재 Yocto 설정은 dom0 1024M이라 문서와 다르다. 플랫폼 조가 값을 확정한다.

## 6. 저장소 위치

| 구성요소 | 위치 |
| --- | --- |
| VM 매니저, 복구 서비스 | `services/dom0-manager/` |
| 차량 게이트웨이 | `services/vehicle-gateway/` (신설 제안) |
| VM 에이전트 | `services/vm-agent/` |
| 주행 컨트롤러, 레코더, 콕핏 앱 | `apps/` |
| 표시 서비스 | `services/display/` |
| 관리 서버, 콘솔 | `backend/`, `frontend/` |
| 인지(Jetson), 섀시 펌웨어(ESP32) | 미정. `perception/`, `firmware/chassis-ecu/` 제안 |
| 메시지·CAN·시리얼 계약 | `contracts/` (3일차 확정 시 이동) |

## 7. 결정 필요

| 항목 | 선택지 |
| --- | --- |
| dom0 메모리 | Yocto 1024M / 제안 1.5 GB |
| VM → 게이트웨이 전송 | MQTT + ACL / UDP + vif 고정 IP |
| 대기 컨트롤러 위치 | VM-B Ubuntu(이종 이중화) / 4번째 Debian VM(코어 부족, 측정 전 보류) |
| 컨트롤러 알고리즘 | pure pursuit(무상태) / PI 포함(동기화 부담) |
| 새 폴더와 part 이름 | `vehicle-gateway`, `perception`, `firmware` 신설 여부 |
