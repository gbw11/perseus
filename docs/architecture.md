# 아키텍처 설계서

Raspberry Pi 4 + Xen 멀티 OS 플랫폼을 자율주행 RC카에 올린다. 세 보드가 자동차 ECU 역할을 나눠 맡고, 주행 컨트롤러는 RPi4의 VM 안에서 돈다.
**핵심 시연: Zephyr 자동주행 VM에 장애가 나면 안전하게 정지한 뒤 Linux 수동주행 VM으로 제어권을 넘긴다.** 자동주행 VM은 자동으로 복구하고, 준비 상태와 전환 조건을 확인한 뒤 자동주행으로 복귀한다. 유효한 수동 입력이 없으면 정지를 유지한다.


## 1. 구성

```text
 D435f ─USB3─▶ Jetson Nano B01 (ADAS ECU)  ─ Ethernet ─▶ RPi4 + Xen (중앙 컴퓨터)
                인지만. 주행 명령 없음                     ├─ VM-A Zephyr  자동주행
                                                           ├─ VM-B Linux   웹 키보드 수동주행
                                                           ├─ VM-C Linux   Interaction 앱 2개
                                                           └─ dom0  VM 매니저·전환 관리 │ 차량 게이트웨이 │ MQTT·표시
                                                                    │ CAN (2단계) / USB 시리얼 (1단계)
                                                                    ▼
                                                           ESP32 (섀시 ECU) ─▶ MDD10A 모터 ×2, UBEC 조향 서보
                                                           엔코더·E-stop·VL53L5CX·워치독
```

| 보드 | 역할 | 한 줄 |
| --- | --- | --- |
| Jetson Nano B01 | ADAS ECU | 카메라로 장애물·차선·위치를 추정해 RPi4에 보낸다. 주행 판단과 명령은 VM-A가 맡는다 |
| RPi4 + Xen | 중앙 컴퓨터 | VM이 명령을 계산하고, dom0 게이트웨이가 활성 VM의 명령만 차량에 전달한다 |
| ESP32 | 섀시 ECU | 모터·조향·엔코더. 명령이 끊기면 스스로 멈춘다 |

연결은 세 가지다. Jetson ↔ RPi4는 이더넷(영상·인지), dom0 ↔ ESP32는 1단계 USB 시리얼 → 2단계 CAN(명령·상태), 외부 ↔ RPi4는 내장 WiFi(원격 콘솔·수동주행·Interaction 화면)다.

dom0는 인지 정보를 VM-A에 중계한다. VM-A ↔ dom0는 Xen Event Channel + Grant Table 기반 통신을 검토하며, 실보드 부팅·양방향 메시징·전용 상태 보고를 검증해야 한다. Linux VM은 Xen 가상 네트워크를 사용한다.

## 2. 핵심 결정

| 결정 | 이유 |
| --- | --- |
| 주행 명령은 VM에서 낸다 | VM-A는 자동주행, VM-B는 수동주행을 맡고 실제 제어권은 하나만 갖는다 |
| 제어권은 dom0 전환 관리 모듈(Failover Manager) 한 곳에서 정한다 | 게이트웨이는 권한·세대 번호(epoch)·순서·유효기간을 확인해 현재 제어자의 명령만 전달한다 |
| VM 재시작은 VM 매니저 복구 서비스 한 곳만 한다 | 제어권 전환과 VM 복구의 책임을 나누고, 사용자가 끈 VM은 재시작하지 않는다 |
| 최종 안전장치는 하이퍼바이저 밖(ESP32)에 둔다 | 상위 시스템·통신 장애 시 워치독으로 정지하고, 하드웨어 E-stop으로 모터 전원을 차단한다 |
| 수동주행은 유효한 입력이 있을 때만 허용한다 | 준비되지 않은 VM이나 오래된 조작 값으로 움직이지 않는다. 속도·가속 명령도 제한한다 |
| 자동주행 복귀는 준비 상태와 전환 조건을 확인한 뒤 한다 | 복구만으로 제어권을 회수하지 않고, 수동 조작과 현재 차량 상태를 확인한다 |
| 게이트웨이·전환 관리는 느린 VM 관리 작업과 실행을 분리한다 | xl·콘솔·관리 API 지연이 주행 명령 전달과 장애 대응을 막으면 안 된다 |
| 전환 관리 모듈이나 게이트웨이가 재시작하면 사람이 재무장한다 | 원인이 불확실한 복구 뒤에 차가 혼자 출발하면 안 된다 |
| 수동제어·관리·Interaction·일반 메시징 경로를 분리한다 | VM-B는 독립된 수동주행 서비스를 제공하고, 관리 콘솔·VM-C·MQTT 장애가 주행 명령 전달을 막지 않게 한다 |

## 3. 장애 전환과 자동주행 복귀

1. Jetson이 인지 정보를 보내고 VM-A가 자동주행 명령을 계산한다. VM-B의 수동주행 서비스도 실행 상태를 유지하되 구동 권한은 갖지 않는다.
2. VM-A나 자동주행 앱의 장애가 감지되면 전환 관리 모듈이 기존 제어권을 회수하고, 게이트웨이를 통해 ESP32에 정지를 지시한다.
3. 안전 정지와 VM-B 준비 상태를 확인한 뒤 수동제어권을 부여한다. 웹 키보드 입력과 조작 활성화(Dead-man) 조건이 유효할 때만 움직인다.
4. 복구 서비스가 VM-A를 재시작한다. VM-A는 주행 기능·인지 정보·차량 상태를 확인하고 현재 위치에서 경로와 제어 상태를 초기화한다. 이 동안 VM-B의 제어권을 유지한다.
5. 수동 입력 중립, 차량 상태와 자동주행 명령의 연속성 등 복귀 조건을 만족하면 VM-A로 제어권을 자동 반환한다. 조건을 만족하지 못하면 수동주행을 유지한다.

수동 조작은 한 세션만 허용한다. 입력 만료, Dead-man 해제, 브라우저 포커스 상실, 연결 단절 시 수동 명령을 무효화하고 정지한다. VM-C의 두 앱은 차량 상태 조회·알림·기록을 맡으며 주행 명령은 내지 않는다.

| 항목 | 측정 기준 | 수용 기준 |
| --- | --- | --- |
| 장애 감지·안전 정지 | 장애 발생부터 감지·정지까지의 시간과 정지 거리 | 시험 후 확정 |
| 수동제어 준비 | 장애 감지부터 VM-B 제어권 부여까지. 사용자 입력 대기는 제외 | 시험 후 확정 |
| 수동제어 지연 | 키보드 입력부터 ESP32 구동 반영까지 | 시험 후 확정 |
| 자동주행 복구 | VM-A 재시작부터 주행 기능 준비 완료까지 | 시험 후 확정 |
| 자동주행 복귀 | 복귀 조건 충족부터 VM-A 명령 적용까지 | 시험 후 확정 |

## 4. 시연 시나리오

| # | 조작 | 보여주는 것 |
| --- | --- | --- |
| 1 | VM-A 강제 종료 또는 자동주행 앱 중단 | 안전 정지 → VM-B 수동제어 준비. 유효한 입력 전까지 정지 유지 |
| 2 | 수동주행 중 Dead-man 해제·포커스 상실·WiFi 단절 | 수동 명령 무효화와 안전 정지. 입력부터 구동까지 지연도 측정 |
| 3 | VM-A 자동 재시작 | 수동주행 유지 → 준비·복귀 조건 확인 → 자동주행 복귀. 타임라인에 기록 |
| 4 | VM-C 종료·CPU 부하 | 주행 기능의 독립성과 명령 지연·지터 검증 |
| 5 | 하드웨어 E-stop | 모터 전원 차단, 차량 상태 화면에 표시 |
| 6 | 콘솔에서 VM 정지 | 사용자가 끈 VM은 재시작하지 않음 |
| 7 | dom0 또는 게이트웨이 중단 | ESP32 워치독 정지. 게이트웨이 재시작 후 새 세션에서 사람이 재무장 |

## 5. RPi4 자원 배분

| 도메인 | OS | 역할 | 코어 | 메모리 |
| --- | --- | --- | --- | --- |
| dom0 | Yocto | 게이트웨이, 전환 관리, 매니저, MQTT, 표시 | I/O·제어 우선 배치 검토 | 측정 후 확정 |
| VM-A | Zephyr | 자동주행 | 분리 배치 검토 | 측정 후 확정 |
| VM-B | Linux | 웹 키보드 수동주행 | 분리 배치 검토 | 측정 후 확정 |
| VM-C | Linux | Interaction 앱 2개 | 주행 VM과 격리 검토 | 측정 후 확정 |

전제는 RPi4 8GB다. 코어 배치·메모리·우선순위는 dom0의 I/O 부하와 VM별 사용량·지터를 측정해 확정한다. 같은 보드의 VM 격리는 물리적 이중화를 대신하지 않는다.

| 안전·자원 기준 | 워치독·입력 타임아웃, 속도·가속 제한, 정지 방식, 코어·메모리 배분 |
