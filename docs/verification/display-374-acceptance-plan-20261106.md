# 374 — 정상 배포·두 표시 화면 연속 수신 수락 계획

기준 `origin/platform` ae6ac60. 373 MR !436의 코드가 병합돼 있다.
이 문서는 준비 기준이다. 실제 배포·실패한 연속 freshness 수락은
[시험 결과](display-374-acceptance-20261106.md)에 별도로 기록했다.

## 팀원이 보드를 사용 중일 때

- 로컬 소스 대조·설치 파일 묶음·원복 절차 준비는 병행 가능하다.
- 보드 조회도 CPU와 파일/소켓 자원을 사용한다. 팀원의 성능 측정과 겹치면 서로의 결과가 달라진다.
- 이미지/펌웨어 배포·VM 제어·주행 시험 또는 관리 API 의존 작업 중에는 적용하지 않는다.
- 관리 API가 잠시 끊겨도 되는 시험 시간을 확보한 뒤 진행한다. API restart는 관리 요청뿐 아니라
  API가 소유한 등록 통지 등 기존 동작에 영향이 있는지 먼저 확인한다.
- 팀원 작업이 무엇인지 모르면 보드에 접속하지 않고 준비까지만 한다.

## 적용 범위

| 파일 | 기존 정상 파일 SHA-256 |
|---|---|
| `/usr/lib/xenova/xenova_execution.py` | `2abe0fc5f7638cf652e6bd3afb1df56a2352809aeb53419193d88961931ccf04` |
| `/usr/lib/xenova/xenova_management.py` | `eaedf7c76ed276e5487b89dbd5b353baac7463c166915bc20ea890938de07762` |

이 해시는 직전 보드에서 확인한 기준일 뿐이다. 재배포 또는 팀원 변경으로 다르면 자동 적용하지 않는다.
후보 SHA-256과 Git commit은 준비 묶음 manifest에서 대조한다. 파일 두 개는 같은 소스 기준이다.
기존 native 신원 배치 도구와 Manager의 batch/read-fork 옵션·공유 관측 경로도 확인한다.
설치 경로가 다르면 실제 import 경로부터 확인하며 두 번째 설치 사본을 임의로 만들지 않는다.

VM·펌웨어·CPU 배치·Gateway/Recovery·MQTT 계정/ACL·Tailscale·토큰·Spring DB·화면 디자인은
변경하지 않는다. 관리 API만 재시작 대상으로 하며 다른 서비스 재시작이 필요해지면 범위를 다시 조율한다.
상태 유효기간은 3초, 앱 readiness의 기존 기한도 유지한다.

## 실행 순서

1. 사용 가능한 보드 시간 확인 후 현재 부팅 ID, 서비스 PID, 실제 import 경로/파일 해시,
   공유 관측 상태, CPU affinity, VM UUID/실행 식별자를 읽기 전용으로 기록한다.
   활성 API 관리 작업/팀원 배포가 있으면 중단한다. 비밀값은 기록하지 않는다.
2. 원본 파일과 소유권·권한·해시를 root 전용 백업 위치에 보존한다. 후보 해시·Python 문법을
   검사하고 기존 파일 해시가 그대로인지 교체 직전에 다시 확인한다.
3. Execution → Management 순서로 같은 디렉터리의 임시 파일을 rename해 교체한다.
   새 Execution은 기존 Management 호출 형식도 지원한다. 새 Management만 먼저 설치하지 않는다.
   두 파일 설치 후 관리 API만 재시작하고 실제 로드한 버전·준비 상태를 확인한다.
4. 인증된 정상 API에서 VM 목록과 기존 세 VM 상태를 확인한다. 실패 시 임시 원시 Xen 조회나
   오래된 관측으로 성공을 꾸미지 않는다. 화면 초기 수신이 안정되기 전 구간은 따로 기록한다.
5. 정상 표시 feed의 `/display/monitor-1`, `/display/monitor-2` 두 실제 브라우저를 열고
   이 브라우저가 이미 받는 presentation 응답만 PC에서 수동 계측 없이 수집한다.
   측정용 별도 API 소비자를 추가하지 않는다. 기존 프록시/SSH 권한과 인증 경계를 확인한다.
6. 초기 120초 구간에서 HTTP 오류, Xen source freshness·age, MQTT 연결·구독, VM/실행 식별,
   현재 앱 보고, Gateway 상태와 화면 결정을 기록한다. 정상 조건의 상태 만료가 남으면
   실패/미해결로 기록하고 253 전체 완료를 주장하지 않는다. API RTT는 영상 지연이 아니다.
7. 이전 단절·만료·재수신 증거와 현재 버전의 적용 범위를 대조한다. 새 장애 유도가 필요하면
   팀원의 작업과 분리한 시험 시간을 확보한다. 시험 때문에 제어 상태나 VM을 바꾸지 않는다.
8. API·feed 및 관련 서비스 상태, CPU/VM/통신 설정 보존을 재확인한다. 임시 뷰어·계측·SSH
   허용 항목을 본인이 추가했다면 복원한다. 결과/미검증 범위를 정리한다.

## 실패·원복

- 후보 적용 뒤 API 준비 실패·예상 밖 오류·심한 회귀가 나타나면 후보 유지와 임의 추가 수정을 멈춘다.
- 현재 두 파일 해시가 본인 후보와 일치하는지 확인한다. 다른 사람이 수정한 파일을 백업으로 덮지 않는다.
- 원복은 Management → Execution 순서로 원본·소유권·권한을 복원하고 관리 API를 재시작한다.
- 파일 복사만으로 실행 중 모듈이 복원됐다고 판단하지 않는다. 실제 프로세스와 정상 API를 확인한다.
- 원복 실패·보드 시간 종료·팀원 작업 재개 시 상태를 명시하고 무리하게 완료 처리하지 않는다.
