# 251번 PC→실보드 내부 API 연결 준비

**최신 상태: 사용자 승인 후 SSH 정책을 좁게 변경했고 PC→보드 8081 임시 터널 연결 검증을 완료했다.** 아래에는 최초 거절 기록과 승인 후 성공 결과를 함께 보존한다. API 인증·Spring 연결은 아직 미검증이다.

2026-10-23. 사용자가 외부 서버 연결을 나중으로 미루고 PC에서 먼저 진행하도록 요청했다. 보드 서비스 설치·VM 변경·재시작 없이 조회하고 PC loopback 임시 터널을 시험했다. [기계 판독 결과](display-251-local-preflight.json)를 따른다.

## 읽기 전용 관측

- `192.168.30.96`의 SSH 호스트 키는 앞서 확인한 값과 일치했다. 비밀번호는 대화형 입력으로 메모리에서만 사용했다.
- 보드 내부 `http://127.0.0.1:8081/openapi.json`은 200이며 제목은 Xenova dom0 manager API였다.
- `/healthz`, `/api/v1/vms`는 토큰 없는 요청에 401을 반환했다. 이는 서비스 도달/인증 요구의 증거이며 인증된 조회 성공은 아니다.
- Xen 조회의 실제 UUID: debian-dev `055226af-b876-4707-8b5d-99e7f33ad3d7`, zephyr-drive-a `64b1ab38-89cc-4454-8d94-b8201f4cdd33`, zephyr-drive-b `a77fa3fc-64e5-4d66-8225-2a49920bda2a`. 앱 ID/주·백업 역할·Spring DB 등록까지 확인한 것은 아니다.
- 보드 loopback TCP 8081은 연결 가능, 8082/1883은 연결 거부였다. 다른 포트의 서비스 존재 여부나 전체 수집 준비 상태를 단정하지 않는다.

## 터널 결과: 미완료

PC `127.0.0.1:18081`→SSH→보드 `127.0.0.1:8081` 전달을 시도했다. PC listener는 시작됐지만 SSH 채널이 `Administratively prohibited`로 거절돼 HTTP 응답을 받지 못했다. 따라서 터널 성공으로 기록하지 않는다. 임시 프로세스/listener는 종료했다.

포워딩 관련 항목만 필터링해 읽은 결과 `/etc/ssh/xenova-auth.conf`는 `AllowTcpForwarding local`, `GatewayPorts no`이며 PermitOpen은 `192.168.77.2:22`부터 `192.168.77.99:22`까지의 게스트 SSH 대상만 허용한다. dom0 API `127.0.0.1:8081`/`8082`는 없다. 다른 인증 정책이나 SSH 비밀 키는 수집하지 않았다.

## 최초 시도 후 적용 전 변경안

기존 PermitOpen 대상을 보존하고 `127.0.0.1:8081 127.0.0.1:8082`만 추가하는 안을 작업 폴더 `outputs/display-251/permitopen-api.patch`에 준비했다. 이 최초 조사 시점에는 미적용이었고 이후 사용자 승인·적용 결과는 아래에 구분한다. 8082는 후속 표시 수집기용 허용 대상이며 현재 서비스가 실행 중이라는 뜻이 아니다.

사용자가 허용하면 원본 정책을 보관하고, 실제 적용 전 현 설정이 조사 내용과 같은지 대조한다. SSH 설정 구문과 root 접속에 적용될 유효 정책을 검증한 뒤 기존 연결을 유지한 상태에서 설정 reload 및 새 접속/터널을 확인한다. 보드 서비스의 실제 제어 방식은 적용 전에 확인해야 하며, SSH 서비스 재시작이나 VM 재시작을 임의 수행하지 않는다. 파일이 이미지 기동 과정에서 생성되는 경우 지속성은 별도 확인한다.

자동 승인 검토는 초기 도구의 `/proc/*/environ`에서 서비스 토큰을 읽어 인증하려는 동작을 미승인 credential probing으로 거절했다. 해당 도구는 실행되지 않았고 그 동작을 제거했다. 이후 조회와 포워딩 시험에서는 환경변수·서비스 토큰을 읽지 않았다. 인증된 API 검증은 담당자의 정식 토큰 제공 경로가 준비된 뒤 별도 진행한다. SSH 비밀번호와 API 서비스 토큰은 서로 대체할 수 없다.

보드 설정·서비스·VM·펌웨어·DB는 변경하지 않았다. 커밋·푸시·Jira 변경도 하지 않았다. PC→보드 터널이 성공한 뒤 PC Spring 연결, 프론트 로컬 연동·단절 시험을 진행하고 외부 서버 연결은 마지막으로 미루는 순서다.

## 사용자 승인 후 적용·재검증: PC 터널 연결 성공

사용자가 “두 API 포트만 터널 허용”을 승인한 뒤 `/etc/ssh/xenova-auth.conf`의 기존 PermitOpen 목록을 그대로 보존하고 `127.0.0.1:8081`·`127.0.0.1:8082`만 추가했다. 다른 SSH 정책은 변경하지 않았다. 최초 실패 [JSON](display-251-local-preflight.json)은 당시 결과로 보존하며 성공으로 덮어쓰지 않는다.

- [정책 적용 결과](display-251-ssh-policy-change.json): 원본 백업 `/etc/ssh/xenova-auth.conf.display251-20261023T010315650715Z.bak`, 변경 전후 SHA256 기록.
- 변경 전후 `sshd -t` 통과. 실제 접속의 root/클라이언트 주소 문맥을 지정한 `sshd -T -C`로 유효 PermitOpen에 두 대상만 추가됐고 `AllowTcpForwarding local`·`GatewayPorts no`가 유지됨을 확인했다.
- `systemctl reload sshd.service` 후 서비스 active 확인. 기존 연결에서 명령이 완료됐고 새 SSH 연결도 성공했다. SSH 서비스·VM·API 서비스 재시작은 하지 않았다.
- 새 연결의 PC loopback `127.0.0.1:18081`→SSH→보드 `127.0.0.1:8081`에서 공개 OpenAPI 200, health/VM API 401 확인. [실제 터널 결과](display-251-local-tunnel-evidence.json). 401은 토큰 없는 요청의 인증 요구이며 인증된 API 조회 성공으로 표시하지 않는다.
- VM 세 대의 UUID·domid가 최초 관측과 같았다. 8082·1883 서비스는 여전히 미기동 관측이며 신규 실행/설치하지 않았다. 콘솔 점유나 게스트 명령 입력도 하지 않았다.

이 결과로 현재 요청한 **PC→보드 내부 API 터널 준비**를 완료했다. PC Spring 접속·서비스 토큰 인증·Spring DB 등록·웹 콘솔 및 표시 수집기 실행은 다음 단계다. 정식 API 서비스 토큰을 준비해야 하며 프로세스 환경변수에서 추출하지 않는다. 외부 서버→보드 연결 성공을 뜻하지 않는다.

터널은 이번 작업의 PC 임시 프로세스로 유지하며 현재 Windows 호스트의 `127.0.0.1:18081`에서만 접근한다. WSL·Docker의 `127.0.0.1`에서 같은 경로가 접근 가능한지는 별도 확인해야 한다. 실행 프로세스를 종료하거나 SSH가 끊기면 터널도 종료된다. 동일한 일반 SSH 포워딩 명령은 아래와 같으며, 실제 이번 실행은 작업 폴더의 Paramiko 도구를 사용했다.

```sh
ssh -N -L 127.0.0.1:18081:127.0.0.1:8081 root@192.168.30.96
```

중지할 때는 해당 터널 프로세스에 Ctrl+C를 보낸다. 현재 PC 포트가 이미 사용 중이면 같은 명령을 중복 실행하지 않는다. 보드 재부팅 후 정책 파일의 유지/재생성 여부와 8082 서비스 경로는 미검증이다. 이번 단계에서 비밀번호·서비스 토큰은 파일/Git에 저장하지 않았다. 정책 변경은 보드에만 적용했으며 저장소의 플랫폼 제품 코드·브랜치는 변경하지 않았다.
