# 374 — 신원 관측의 지연 실패 기록 순서 보완

2026-11-07. 직전 [실보드 재시험](display-374-board-retest-20261107.md)에서 남은 오류와 만료를
조사했다. 이번 수정으로 확인한 경합 하나를 보완했지만 **374의 연속 freshness 수락은 여전히 미완료**다.

## 발견과 로컬 재현

운영 모듈을 바꾸지 않은 별도 조회 프로세스에서 기존 비교·반환 동작을 유지하고 오류 발생
위치만 기록했다. 13번째 조회가 재확인을 거쳐 성공했으며 내부 사건은 publish_observation의
ReadChanged였다. 저장된 더 최신 오류는 DEADLINE_EXCEEDED, 저장 오류 시각과 이번 관측
sampled 시각의 차이는 204ms였다. 이것만으로 그 운영 오류를 쓴 프로세스까지 단정하지 않는다.

소스상 일반 Manager 조회는 ReadContext.started_ms를 오류 sink에 전달한다. 반면
신원 전용 observe(identity_only=True)는 문맥이 없다는 이유로 시작 시각 없이 오류를 기록했다.
이 신원 경로는 xenova_drive_binding에서 사용하며 Worker의 재바인딩·텔레메트리 관측에서도 호출한다.
따라서 먼저 시작한 느린 신원 조회가 나중에 실패하면, 그 사이 완료된 더 최신 검증 성공을
실패로 덮을 수 있었다. 실제 파일·잠금·스레드와 기존 Xen 대역으로 이 순서를 재현했다.
수정 전 새 테스트는 2 failed / 2 passed였다.

## 변경 범위와 유지한 검증

xenova_execution.Execution.observe에서 신원 전용 조회에도 진입 시각을 전달한다.
기존 probe_error의 host/시간 순서 검사를 재사용하며 실패를 성공으로 변환하지 않는다.
실패한 호출자는 원 오류를 그대로 받는다. 일반 제어 관측(identity_only=False, 문맥 없음)은
기존의 시각 미지정 의미를 유지한다.

두 Xen 목록·두 incarnation 검사, VM별 최종 메타데이터 검사, deadline·실행 교체·설정/의도·
barrier 보호를 생략하지 않는다. TTL은 3초 그대로이며 원 관측 시각을 새 시각으로 갱신하지 않는다.
더 최신인 성공/실패가 저장돼 있을 때 오래된 실패가 이를 덮지 않게 하는 수정이다.
기존 밀리초 시각의 엄격한 순서 비교를 유지한다. 같은 tick의 순서까지 새로 추정하는 변경은 아니다.

회귀 141 passed, 24 subtests passed, 기존 helper 종료 100ms 타이밍 문제 1개 제외.
신원 바인딩·동시 조회·실행·설정 변경 및 경로 검사 테스트가 포함된다. 추가한 최신 실패 보존
사례까지 전용 테스트 5개가 통과했다(그중 4개는 위 회귀와 중복). 최신 실패 테스트는 두 사건을
명시적으로 10ms 분리해 실제로 더 최신인 기록의 보존을 확인한다. product deadline은 바꾸지 않았다.
