# 373 — 공유 VM 상태 만료의 재조회 경합 개선

기준 `origin/platform` 18904f8, 브랜치
`feat/platform/S15P31E110-373-observation-freshness`. 이전 신원 배치 MR !435가 병합된 뒤의 후속이다.

## 확인한 원인

실제 보드의 읽기 요청에서 `publish_observation`의 더 최신인 관측과 비교하는 분기가
`ReadChanged`를 발생시켰다. 값 전체나 자격증명을 출력하지 않고 차이가 난 키 이름만
기록했다. 확인된 세 사례는 `xen_state_flags`만 다르거나 `xen_state`와
`xen_state_flags`만 달랐고, 더 최신인 관측의 오류는 없었다.

실행 식별자는 그대로여도 정상 VM은 실행·I/O 대기·미스케줄 사이를 이동한다.
동시에 들어온 다른 읽기가 더 최신인 이 스케줄링 상태를 게시하면, 기존 구현은
이미 전후 신원을 검증한 요청까지 전체 Xen 조회를 다시 했다. 공유 관측 만료를 만드는
대기 비용의 한 원인이다. 모든 지연 원인을 이것으로 확정하지 않는다.

추가 API 조회 없이 기존 공유 파일만 60초 관측한 구간에서는 236개 표본 모두 status=ok,
3초 이상 표본 0개, 최대 age 2500ms였다. 이는 두 화면 브라우저 수락 시험이 아니다.
실보드 dom0 부하도 높았으므로 모든 환경의 연속 freshness를 보장하지 않는다.

## 변경과 유지하는 경계

1. 한 조회 회차의 시작 입력에서 호스트 공통 admission·shutdown 정보를 한 번만 읽는다.
   VM별 실행·의도·부팅 허가는 각각 읽으며, 게시 직전에는 호스트 정보도 VM마다 다시 검사한다.
   VM 3대 정상 회차에서 호스트 barrier 읽기는 6회에서 4회로 줄어든다.
2. 읽기 전용 요청에서 더 최신인 성공 관측과 차이가 **정상 스케줄링 상태뿐**이면
   전체 재조회를 피한다. 허용 flags는 `------`, `r-----`, `-b----`, `rb----`이며
   상태 문자열도 기존 `xen_state(flags)` 결과와 일치해야 한다.

더 최신인 값을 가져와 반환하지 않는다. 요청 자신이 검증한 과거의 상태와 원래 관측 시각을
반환하며 더 최신인 디스크 관측을 덮어쓰지 않는다. 게시하지 않은 새 revision도 만들지 않는다.
중간 pause·shutdown·crash·dying·잘못된
flags, 실행 신원·domid·presence·lifecycle·구성·의도·admission 변화, 더 최신인 관측 오류는
기존처럼 재확인/실패 처리한다. 실제 제어 경로는 이 읽기 예외를 사용하지 않는다.

전후 Xen 전체 목록·VM 신원 검사는 그대로다. 3초 유효기간·readiness 기한·CPU 배치·VM·펌웨어·
통신 자격증명을 바꾸지 않는다. 요청 간 결과 캐시나 새 수집 파이프라인도 추가하지 않는다.

## 검증

### Linux 회귀

새 공통 입력 시험 5개, 스케줄링 비교·실제 동시 게시 시험 35개를 추가했다.
실제 동시 조회 시험은 정상 실행/대기 차이에 한 회차로 응답하면서 원래 시각과 더 최신인
파일 바이트를 보존하는지 확인한다. pause로 바뀐 대조 사례에서는 두 번째 전체 회차가
실행되고 과거의 정상 상태가 반환되지 않는다.

최종 선택 회귀: **181 passed, 28 subtests passed, 1 deselected**, 약 24.68초.
신원 배치/단건 ABI·조회 일관성·읽기 진행/동시성·실행 경계·관리 예산·관리 경계를 포함한다.
기준선에서도 실패한 100ms 자식 PID 파일 타이밍 시험
`test_S4_T08_owned_helper_timeout_after_pipe_eof_reaps_child`는 명시적으로 제외했다.
그 시험의 한도나 기대값을 바꾸지 않았으며 전체 저장소 시험 통과라는 의미가 아니다.

### 실보드 별도 프로세스 비교

후보 함수는 별도 Python 시험 프로세스의 메모리에만 넣었다. 정상 서비스의 코드 파일·unit·
프로세스·SSH 설정을 바꾸거나 재시작하지 않았다. 실제 Manager/registry/Xen 읽기를 사용한다.
기존/후보 모두 같은 trace 계측을 사용했고, 두 읽기를 동시에 실행하는 네 묶음을 교차 비교했다.

| 구성 | 요청 수·성공 | 평균 | 최대 | 전체 재조회 요청 |
|---|---|---:|---:|---:|
| 기존 | 4/4 | 1.8374초 | 2.6695초 | 1 |
| 후보 | 4/4 | 1.4446초 | 1.5354초 | 0 |

짧은 비교의 평균은 약 21% 감소했다. 적은 표본·변동 부하이며 단일 원인의 속도 향상을
보장하는 통계가 아니다. 앞선 단일 요청 교차 시험에서도 모두 성공했지만 후보 쪽에
재조회가 남은 사례가 있었고, 그 뒤 스케줄링 경합 구분을 추가했다. 작은 공통 입력 최적화만으로
문제가 해결됐다고 주장하지 않는다.

이 동시 읽기 부하 자체도 진단용 추가 소비자다. 실제 두 브라우저를 띄운 공유 producer 수락이나
영상 지연 시험으로 확대하지 않는다. 증거는 [정리 JSON](display-373-freshness-20261106.json)을 따른다.
실보드 비교 뒤, 지연된 읽기가 게시하지 않은 새 revision을 반환하지 않도록 추가 보완했다.
이 revision 보완은 최종 Linux 동시성/회귀 시험으로 검증하며 최종 파일 전체의 실제 배포 수락은
374번에서 수행한다.

## 종료 상태와 374번으로 남기는 항목

정상 서비스 7개는 active이고 Manager 1537·표시 feed 598 및 기존 Gateway/Recovery/MQTT/
로그/Tailscale PID가 유지됐다. 정상 코드 두 파일은 시험 전 해시와 같았다.
최종 공유 상태는 ok·age 965ms, 기존 세 VM은 running이었다.
CPU affinity는 dom0·Debian=0,3, VM1=1, VM2=2를 유지했다. 시험 SSH 프로세스는 종료 코드 0으로 끝났다.

보완 코드는 아직 정상 서비스에 배포하지 않았다. **374번에서** 대상 커밋/해시·팀원 변경을
확인한 배포, 실제 두 브라우저만 사용하는 연속 수신, 만료/복귀와 이전 실행 데이터 혼입 방지,
운영 설정 보존을 수락해야 한다. 373의 코드·격리 비교 결과로 253 전체나 374를 완료하지 않는다.
373의 코드·검증 결과는 platform 대상 MR에서 리뷰한다. 정상 배포·두 화면 연속 수락은
374에서 추적하며, 이 결과만으로 253 전체를 완료하지 않는다. Jira 상태는 별도로 관리한다.
