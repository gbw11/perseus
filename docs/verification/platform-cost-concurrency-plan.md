# 5.5번 계획: 소유 플랫폼의 비용·대기 경합 점검

## 1. 출발점과 마감 범위

2026-10-31, `feat/platform/recovery-scenario-closure`의
`9b69cdf1df65408403e148868d19ab51cdaa9179`를 계획의 출발점으로 한다.
1번은 **기능별 기준선·비용·소유권 대응 정리 완료**로 마감했다.
이번 문서는 5.5번의 실행 기준이다. 최초 초안 이후 사용자가 제공한 실행 상세안을
아래 8~9절에 반영했다. 실제 계측·구현 결과는 [검증 보고](recovery-scenario-closure-20261030.md#stage55)에 구분한다.
착수 때 실제 HEAD/diff와 제품·시험·recipe를 다시 대조하고 후속 변경을 보존한다.

> 반복 처리하지 않고, 관계없는 작업이 기다리는 원인을 확인한다.

읽는 순서는 [개념 문서](../platform/conceptual-architecture.md) →

줄이며, 정상 진행과 오류 보호를 함께 비용 회귀로 남기는 것**이다.
각 점검은 `확인된 결함 / 비용 의심 / 필요한 재검증 / 로컬 증거 부족 / 담당자 인계`로
판정한다. 모든 검사를 없애거나 모든 경로를 병렬화하는 것을 완료 조건으로 삼지 않는다.

## 2. 조사 범위와 수정 권한

**비용과 대기의 원인 추적은 실제 호출·의존 경계를 따라간다. 직접 수정은 승인된
소유 코드에 한정하고, 공유·타 담당자 영역의 원인은 기존 담당 요청으로 인계한다.**
예를 들어 DHCP/helper·상위 선행 조회·직렬화에서 기다린다면 그 구간의 호출자/실행자와
대기 원인을 조사한다. 소유 경계 밖이라는 이유로 원인 추적까지 중단하지 않는다.

| 범위 | 5.5번에서 확인할 것 | 수정·인계 경계 |
|---|---|---|
| 하위 Manager/Platform/Execution, creation/preparation/recovery/CPU/resources, 공통 Linux 준비·seed | 관리 기능 전체, 원장·예약·현재 실행 guard, 파일/자식/저장·잠금 | 소유 하위 코드와 관련 시험·정식 계약·부분 패키징. 변경 필요가 입증된 파일만 수정 |
| Zephyr runtime·Store/netfront·공통 앱/MQTT·Diagnostics/Telemetry | 초기화/종료·대기·수집·발행·복사·메모리/stack·자원 반환, 관리/주행과의 간섭 | 기존 소유 공통 구현 범위. planner·새 기능 건강 정책·장치 기능을 대신 구현하지 않음 |
| Bootstrap/receipt/binding, Gateway, 콘솔 원자료/trace | 재관측·Store 호출, actor/시리얼·권위 저장, 로그 보존/회전·공간과 비차단 | 신영 소유·승인 경계의 국소 수정. 신원·출력 권한/재무장·원 실패 의미는 보존 |
| 부팅·종료·네트워크·broker·Yocto recipe/wrapper/unit·이미지 조립 | 실제 의존 호출·프로세스 귀속·공유 자원·패키지 포함, 독립 CLI/legacy 우회 | 공유 소유와 수정 권한을 먼저 확인. 미배정은 미배정으로 남기고 운영 정책/실제 설치 변경은 별도 |
| FastAPI/dom0-manager·Worker·Linux Agent·Spring·프론트·장치 | 상위 mutex/pre-call get/재시도/timeout·후속 이행이 하위 대기에 미치는 영향 | 제품 대리 수정 금지. [HTTP](../requests/20261029-request-http-spring-ui.md), [Worker](../requests/20261029-request-recovery-worker.md), [Linux·Agent](../requests/20261029-request-linux-agent.md) 등 기존 요청에 위치·계수·최소 변경·인수 조건 누적 |

전체 영역을 같은 깊이로 한꺼번에 재감사하지 않는다. 기준선 7장의 **모든 행**에
실제 진입점·공유 자원·기존 근거·소유자·점검 결과 또는 남은 근거를 연결한 뒤,
관측된 비용/대기·사용 빈도·영향 범위에 따라 상세 점검 순서를 정한다.
관리 Python과 차량/Zephyr 중 어느 한쪽의 통과로 전체 범위를 닫지 않는다.

최초 요청은 계획 작성까지였고, 후속 지시로 A~E의 로컬 점검·국소 수정·검증을 승인받았다.
실행은 로컬 소유 fixture를 기본으로 하며
보드/EC2·운영 `/srv`/`/run`·실제 VM/서비스·broker/네트워크/CPU 정책·실데이터를
변경하지 않는다. 정규 설치·실측·HTTP/화면·장치는 7번 수락에 남긴다.
운영 생성 정책 공급/소비 연결은 6번이며 시험값을 운영 기본값으로 정하지 않는다.

## 3. 먼저 확인할 세 가지

아래는 현재 소스/기준선에서 확인한 **비용의 위치**다. 불필요한 중복이나 결함이라는
판정은 아직 하지 않았다. 소스 경로는 기준선의 [기호 표](platform-management-baseline.md#sources)를 따른다.

| 우선 대상·현재 근거 | 실제로 물을 질문 | 첫 계측·반례와 보존할 경계 |
|---|---|---|
| 남은 공통 실행 잠금: `Manager._dispatch_locked/_transition/_purge`, restore의 `e2fsck -fn`, 물리 제어·사용 열람·필수 저장 | 어떤 긴 외부 효과가 어느 잠금을 보유하며 무관한 요청까지 기다리게 하는가? 동일 VM/공유 자산의 필요한 배타성은 무엇인가? | 외부 단계만 barrier로 막고 다른 VM 조회·원 조회·stop 수락/실제 종료를 각각 관측. 같은 VM 충돌·동시 writer·quiesce·중단 보호도 짝지음. 모든 조합의 완료를 현재 지원한다고 가정하지 않음 |
| `xenova_creation.holds/released(durable=True)`와 그 소비자 | 한 요청/원장당 read·parse·file/parent fsync가 몇 회인가? 반복 사이 원장/자산·소유·내구 근거가 바뀔 수 있는가? | 미수습/수습 complete/SUCCEEDED를 분리해 생성·주소·stop·복구·자원·CPU·Zephyr 소비자별 계수. complete JSON 가시성만으로 예약을 반환하지 않는 S5-T15/16 유지 |
| registry/tombstone·원 key 검색·수습 inventory의 규모 증가 | 단건 get의 전체 검증, 유일성 확인용 원장 검색, proc/FD·항목별 사용 검사가 VM/보관/이력/FD 수에 어떻게 증가하는가? | 한 축씩 늘려 read/parse/bytes/helper/fsync·잠금 비용 측정. 늦은 중복 key·열람 실패·다른 inode/열린 FD를 검출하는 완전 검색/현재 사용 확인은 유지 |

`holds`가 공통 함수라는 사실만으로 중복 비용이 해결됐다고 보지 않는다.
반대로 동일 함수를 두 번 호출했다는 사실만으로 두 번째 검사를 지우지 않는다.
**검사 대상·목적·유효 문맥·변경 가능 구간·재사용 종료 조건**을 호출별로 적은 뒤 판단한다.

## 4. 실행 순서와 작업 단위

| 단계 | 수행할 일 | 산출물·그 단계의 종료 조건 |
|---|---|---|
| 5.5-A 기준 후보·계측 복원 | HEAD+diff/새 파일/recipe를 봉인. 전체 범위 색인에 진입점·소유자·의존을 대응. 현재 후보의 동일 fixture 기준 계수와 lock wait/hold를 수집 | 후보 manifest, 영역별 점검표, 재실행 가능한 baseline 명령/입력/원 facts. 과거 P4 수치를 현재 baseline으로 대신하지 않음 |
| 5.5-B 관리 비용·규모 점검 | 위 세 우선 대상과 templates/probe/recovery-operation·자원/firmware/CPU·boot/autostart/legacy의 반복/대기를 추적 | 기능별 비용/잠금 표, 의심별 재현·필요 재검증/중복 판정. 생성·조회뿐 아니라 자산 수명과 원 결과·수습까지 포함 |
| 5.5-C 나머지 소유 플랫폼 점검 | runtime/Store·통신·앱·Telemetry·Bootstrap/binding·Gateway·콘솔·recipe/공유 기반을 기존 도구·시험으로 선별 확인 | 각 영역의 비용 발생/증가 조건·공유 대기·수명 보호·실계측 또는 증거 부족. 관리 경로에서 도달하는 타 담당자 원인도 인계 |
| 5.5-D 확인된 원인의 국소 수정 | 한 원인씩 반례→최소 수정→같은 조건 재계측. 요청 내 근거 재사용을 우선 검토하고 필요한 효과 직전 guard를 유지 | 변경 전후 같은 계수/정상 결과·오류 주입·진행성. 수정이 불필요하면 이유와 정상 상한을 남김. 잠금 분리는 관련 writer/소유/게시/종료까지 닫을 수 있을 때만 수행 |
| 5.5-E 비용 회귀·포장·인계 | 변경한 영역의 비용 assertion과 2~5번 관련 보호 회귀. 패키지 소유 파일/모드/import 대조, 소비자 요청과 기준선 근거 갱신 | 단일 최종 후보와 시험/원 facts/부분 묶음 대응. 전체 범위 점검표에 빈 행이 없고 남은 항목은 근거·영향·책임·다음 수락이 명시됨 |

새 daemon/자동 실행기·범용 영구 큐·DB·TTL cache부터 만들지 않는다.
새 구조가 필요하다는 결론이면 현재 국소 변경으로 해결되지 않는 반례와 영향을 별도로
제시하고 그 결정을 먼저 확정한다. timeout 상향·오류 숨김·lock/원장 삭제·자동 force로
진행성을 만들지 않는다. 작업 단위는 원인과 회귀가 함께 검토 가능한 크기로 유지한다.

## 5. 같은 조건의 비용 비교

계측은 기존 [trace](../../platform/yocto/meta-xenova/recipes-core/xenova-platform/files/xenova_trace.py),
[조회 시험](../../platform/tests/test_xenova_read_progress.py),
[생성 수습 시험](../../platform/tests/test_xenova_creation_reconcile.py)의 fixture/barrier를 먼저 재사용한다.
[기존 benchmark](../../platform/tests/benchmark_management_boundaries.py)는 **CPU-on Zephyr reboot와
가상 command/fsync 지연 모델**이다. 이를 전체 관리·실제 SD benchmark라고 부르지 않는다.
부족한 계수는 소유 로컬 시험에만 좁게 추가하고 제품의 영구 계측 서비스를 만들지 않는다.

각 요청에서 다음을 구분해 남긴다.

- 진입/수락/대기/실행/필수 결과 저장/반환, 잠금별 wait·hold·획득 순서, 슬롯·원 실행 소유 수명.
- 원장/registry/manifest/lease별 열람·JSON parse·논리 바이트와 같은 원장 재방문 횟수,
  file/parent fsync·replace·snapshot 저장 횟수, 외부 명령·Xen/identity/Store 호출 횟수.
- payload hash/검증 복사 횟수·논리 처리 바이트·할당 블록·부분 write, guest/mount/loop와
  수습 proc/FD/항목 수, queue/drop/잘림·메모리/스레드 비용 중 해당 영역이 실제 제공하는 값.
- 정상 성공/거절/수락 후 pending/효과 미확정·원 결과 회수, 성공한 조회 수와 물리 효과 횟수.

같은 source profile·OS/template 선택·정책 fixture·VM/이력/FD 수·poller 수·지연 주입·도구에서
변경 전후를 짝지어 비교한다. 순서/파일시스템 cache 영향을 기록하고 각 원 표본을 보존한다.
실제 wall time과 주입 지연/가상 시계, 논리 read bytes와 물리 I/O를 분리한다.
실행 환경·반복 수·분포/최대 관측치를 적고 로컬 최대를 보드 지연 보장값으로 쓰지 않는다.

규모 시험은 등록 VM 수, 보관 자산 수, 자산/control 원장 수를 한 축씩
**1/10/100의 제한된 로컬 입력**으로 늘리는 것을 출발점으로 제안한다.
수습 원 작업 수와 관측 대상 FD 수는 별도 축으로 두고, 원 작업당 파일 수는 현재
지원되는 고정 topology 안에서 변화시킨다. 항목 수를 늘리려고 허용되지 않는 파일을 추가하지 않는다.
0건 부재/빈 목록과 성공/미수습/수습 complete 이력의 혼합도 포함한다.
이 수는 운영 한도가 아니다. fixture의 실제 topology/계약 상한을 지키며 실행 전
시간·파일/프로세스 상한을 정하고, 유효하지 않은 fixture로 비용 결과를 만들지 않는다.

비용 회귀 assertion은 먼저 현재 호출 수·성장 원인을 확인한 후 고정한다.
전체 실행시간만 낮추거나 필요한 관측을 생략해 목표를 맞추지 않는다.
어느 호출/스캔/저장이 줄었는지와, 어느 변경 경계의 검사가 남았는지 함께 입증한다.

## 6. 중심 수락과 보호 회귀

아래는 **후속 실행의 수락 계획**이며 이번에 새 통과한 시험 목록이 아니다.
제품 Manager/원장/파일/잠금을 실제 실행하고 Xen·guest·Store 등 대체 경계를 명시한다.
barrier는 특정 긴 단계만 멈추며 검증 대상 호출이나 잠금 자체를 대역으로 우회하지 않는다.

| 묶음 | 반드시 확인할 결과 |
|---|---|
| 남은 긴 효과와 B의 진행 | A의 fsck/사용 열람/정리·저장 등 조사 대상 단계가 미해제인 동안 B list/get·원 조회·stop 수락과 실제 종료를 각각 확인. 현재 필요한 배타성으로 막히면 이유/범위를 재현하고 국소 수정의 전후를 비교. 같은 자산의 상충 효과 0 |
| 양 Linux 긴 생성+polling | Debian·Ubuntu 각각 A 검증 복사 barrier를 유지하고 1/2/4 폴러의 정상 조회가 성공하는 동안 B의 실제 stop·원 결과 확정 완료. A는 해제 후 같은 원 작업으로 성공 |
| 느린 조회·응답 역전 | 느린 Xen/identity 관측 해제 전 다른 VM 제어·원 조회가 진행. 정상 조회 성공과 요청 내 호출 계수를 함께 확인. 현재 실행/수명이 바뀌면 제한 재관측/기존 오류, 옛 관측으로 최신 상태 덮기 0 |
| 이력 증가와 완전성 | 단건/전체 조회·key replay/부재·생성/제어/수습을 규모별 실행. 이력 끝의 중복/손상·읽기 실패/예산 소진을 정상 부재/유일성으로 반환 0. 성공한 원 결과를 현재 관측 실패로 뒤집기 0 |
| 예약 내구 확인 | 같은 원장의 소비 횟수 전후 비교와 함께 완료 저장/fsync EIO·ENOSPC/응답 유실·다른 writer 교차를 확인. 조기 예약 반환 0, 저장 회복 뒤 같은 수습 종결·예약 반환과 별도 신규 생성 성공 |
| 수습의 비용·사용 보호 | A private 정리 미해제 중 B 조회·실제 stop 완료. inode 교체·열린/삭제된 FD·mount/loop 미확정·부모 종료/상속 FD·gate 경합에서는 오삭제/재사용/unmount 0. 종료·수습 후 정상 재사용도 확인 |
| 전체 소유 공통 경로 | 점검/변경한 Store·runtime·Telemetry·Gateway·콘솔의 지연/포화·부분 실패를 실제 소유 시험으로 확인. 계산/출력 보호·원 자원 종료가 부가 진단/전달/저장 대기를 잘못 기다리지 않음 |

2번의 Debian·Ubuntu **prehash 0·검증 root 복사 1**, manifest/사용 바이트·source guard·sparse·독립 사본,
3번의 단일 Linux 슬롯·정확한 원 실행 소유·private/게시·요청별 출력,
4번의 유한/일관된 관측·슬롯·polling 진행성,
5번의 원 host/기한·정상 실패 종료·원 오류/부분 자산·명시 수습/내구 예약 반환을 보존한다.
화면용 관측을 실제 제어 제출 직전 guard로 재사용하지 않는다.
원 key/spec·UUID/MAC/IP·의도/실행 신원·기한과 CPU/네트워크 정책을 최적화 때문에 재발급하지 않는다.
Zephyr bundle·seed·독립 CLI의 별도 계약도 회귀로 유지한다.

게스트 코드를 바꿨다면 해당 정규 빌드/소유 시험을 선택하고, 바꾸지 않은 게스트의 ARM
빌드를 형식적으로 덧붙이지 않는다. 부분 설치 대조는 BitBake/RPM·전체 이미지·설치본 수락과 구분한다.
모든 요청 거절, polling 종료 뒤 성공, sleep/timeout 증가만으로 중심 수락을 통과시키지 않는다.

## 7. 완료 산출물과 다음 단계

최종 보고에는 다음 다섯 가지를 남긴다.

1. 전체 범위 색인별 조사 결과·소유/의존 경계·남은 근거. 미조사 행을 숨기지 않는다.
2. 원인별 수정 전 반례/호출 계수·필요한 보호·최소 변경 또는 무변경 이유.
3. 같은 조건의 전후 원 facts·규모 증가·barrier 순서·정상 성공/오류 보호 비용 회귀.
4. 후보 HEAD+diff/파일 manifest·실행 명령/결과·관련 부분 패키지/설치 import 대응.
5. 기존 담당 요청 ID에 연결한 영향·담당·인수 조건과 운영/설치/보드 미수행 범위.

확인된 불필요한 비용·대기를 수정하고 정상 기능과 보호를 함께 재현한 범위를 마감한다.
새 권한·정책·공개 의미가 필요하거나 소유가 불명확해 수정하지 못한 항목은
근거·제품 영향·현재 다음 행동과 책임을 적고 그 항목을 완료로 표시하지 않는다.
실측이 필요한 비용은 7번의 구체 측정 질문으로 남긴다.

그 뒤 **6번은 원 key/기한/상태/권한·수습/운영 정책 공급의 실제 소비자 정합화**,
**7번은 같은 후보 설치와 실제 Xen/SD·mount/loop·OS·HTTP/화면/장치의 종단 수락**이다.
API cgroup/backend 귀속, Linux 기능 건강·Worker 정책·주행/장치의 기존 미완료는
원 담당 요청을 유지한다. 5.5번 점검이나 계획 작성으로 대신 완료하지 않는다.
commit/push·운영 적용과 6·7번 실행은 별도 지시에 따른다.

## 8. 실행 상세안: 유효 구간과 변경 채택

보존 대상은 검사 함수의 현재 개수/배치가 아니라 **계약의 불변 조건**이다.
같은 요청이라도 잠금 해제·원장 쓰기·외부 효과·callback·실행/의도 변경 뒤에는 같은
근거라고 단정하지 않는다. 대상/목적·writer·현재성·내구 조건·무효화 사건이 같은 좁은
구간에서는 이미 검증한 파싱 결과나 순수 판정을 전달한다. 효과 제출 직전의 현재 guard는
화면 관측이나 이전 호출의 RAM 값으로 대체하지 않는다.

원인별 기록은 다음 순서를 따른다. 별도 운영 원장이나 범용 검증 토큰은 만들지 않는다.

| 기록 | 확인할 내용 |
|---|---|
| 보호·대상 | 실제 불변 조건·계약/시험과 원 작업/VM/실행/자산/정책 중 근거의 소속 |
| writer·유효 구간 | 다른 요청/프로세스·외부 효과·callback과 잠금/phase/신원/내구의 변경 가능 경계 |
| 비용·사전 목표 | 최초 설치/부팅/요청/주기/실패별 primitive 횟수·bytes·잠금/큐·잔존. 줄일 처리와 유지할 검사를 수정 전에 명시 |
| 판정·조치 | 기존 다섯 분류와 유지/재사용/순수 계산 분리/범위 축소/소유권 보존 분리 중 선택 |
| 수락·잔여 | 같은 결과/성공률의 전후 계수·지연·CPU/메모리·실패 수습 비용, 무효화/오류/회복 시험과 미검증 환경 |

A로 전체 경계/비교 조건을 고정한 뒤 B/C에서 좁혀진 원인은 D로 바로 연결한다.
C 전체를 마칠 때까지 첫 수정을 보류하지 않고, 첫 관리 개선을 이유로 C를 생략하지 않는다.
모든 반영 변경을 합친 단일 후보에서 E를 수행한다.

전후 fixture는 동등한 초기 상태로 각각 만든다. 앞 실행의 완료/수습을 뒤 실행이
재사용해 싸게 보이는 오염을 피한다. 계수 hook의 교란은 양쪽에 동일하게 두고,
시간/메모리 결과는 계측 유무와 함께 표시한다. inclusive helper 시간이나 병행 단계
시간을 중복 합산하지 않는다. 다른 실행자에게 미룬 비용은 실제 종료까지 비교한다.
주기/품질·성공률을 낮춰 얻은 개선은 채택하지 않는다. 공개 의미/schema/운영 정책·
새 writer 프로토콜이 필요한 항목은 국소 최적화로 위장하지 않고 그 항목의 결정을 분리한다.
