# 251 외부 웹 콘솔 최종 연동 확인 — 2026-10-29

상태: **진행 중**. 외부 서버의 팀원 배포 완료를 기다리는 중이며, 실제 게스트 콘솔 출력·재연결을 아직 통과로 기록하지 않는다.

## 확인한 경로

- 외부 웹: `https://k15e110.p.ssafy.io/console`. 사용자가 직접 로그인했다.
- 외부 서버 Tailscale: `100.80.180.63`.
- 보드 Tailscale API: `http://100.108.226.65:8081`.
- 외부 Spring 컨테이너에서 보드의 실제 서비스 토큰을 사용한 `/healthz`와 `/api/v1/vms` 호출이 각각 HTTP 200으로 성공했다. 이후 목록 호출에는 timeout, `OPERATION_IN_PROGRESS`, `OBSERVATION_UNAVAILABLE`도 관측됐다. 성공 한 건을 안정적 연동 성공으로 확대하지 않는다.
- 외부 TLS WebSocket upgrade 성공. 잘못된 사용자 JWT를 첫 인증 프레임으로 보냈을 때 4401로 종료됐다. 게스트 터미널 입력은 0바이트다.

## 적용한 설정과 보존 범위

외부 서버에서 확인한 실제 `/opt/xenova/.env`와 기존 컨테이너에는 이전 API 주소와 빈 서비스 토큰이 남아 있었다. 원본을 서버 내 권한 0600 백업으로 보관하고 `DOM0_MANAGER_BASE_URL`, `DOM0_MANAGER_SERVICE_TOKEN` 두 항목만 적용했다. 토큰을 Git·PC 파일·검증 출력에 저장하지 않았다. 같은 이미지 `xenova-backend:10`으로 backend 서비스만 재생성했다. 두 항목 외 환경파일 값이 보존됐음을 비교했다.

이후 사용자가 팀원이 새 컨테이너를 준비 중이라고 알려와 외부 서버·DB의 추가 변경을 보류했다. 마지막 읽기 확인에서 이미지 `xenova-backend:10`, 시작 시각 `2026-10-29T00:40:24.371521305Z`, VM 명세 테이블 0건이었다. 이것은 마지막 관측이며 이후 배포 결과를 대신하지 않는다.

보드는 재부팅 후 `XENOVA_CONSOLE_ENABLED`가 미설정이었다. 기존에 허용된 임시 시험 범위로 `/run/systemd/system/xenova-dom0-manager.service.d/251-console-verification.conf`에 활성화 설정을 추가하고 API 서비스만 재시작했다. 영구 설정은 변경하지 않았고, 이 설정은 보드 재부팅 시 사라진다. 운영 활성화 여부는 별도로 확정해야 한다.

VM·펌웨어·MQTT·Tailscale·CPU 정책은 이번 검증에서 변경하지 않았다. 등록된 시험 VM 7개도 사용자 요청대로 유지했다.

## 배포 후 남은 종료 조건

1. 새 컨테이너 버전·실제 API 설정을 읽고, 현재 사용자 세션에서 VM 3대의 기존 UUID와 상태가 표시되는지 확인한다.

3. Debian은 연결 시 프론트가 Enter를 자동 전송할 수 있으므로, 먼저 현재 hvc0가 로그인 대기임을 확인한다. 로그인·명령은 입력하지 않는다.
4. 정상 연결 해제 후 수동 재연결, 이전 PTY/점유 해제, 중복 연결 오류 표시를 확인한다. 중복 소켓 때문에 정상 소켓이 종료되지 않는지도 확인한다.
5. 실패·시한 초과 안내를 확인하고 최종 설정·시험 조건·남은 성능 제한을 기록한다. 위 항목 통과 전 251 전체 완료로 표시하지 않는다.
