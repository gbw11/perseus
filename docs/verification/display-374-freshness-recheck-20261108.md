## 관측 방법

보드 SSH 정책에 loopback 8082가 허용돼 있지 않아 허용 목록을 수정하지 않았다. 기존 SSH exec 채널에 임시 Python stdio HTTP 중계 프로세스 1개를 두고, PC loopback의 HTTP 서버에서 제품 페이지 요청만 전달했다. 토큰은 보드 중계 프로세스 안에서 읽어 인증 헤더로만 사용했고 브라우저나 결과 파일에는 제공하지 않았다. 새 수신 포트·MQTT 소비자·상태 진단 폴러는 보드에 추가하지 않았다.

`/display/monitor-1`, `/display/monitor-2`로 연 두 브라우저는 현재 제품 동작에 따라 `/display/combined`로 이동했다. 따라서 실제 소비자는 두 개지만 서로 다른 물리 HDMI 화면의 검증으로 해석하지 않는다. 계측은 브라우저가 요청한 presentation 응답만 기록했다. 화면 자체의 기존 렌더 ACK 요청은 전달했다.

초기 도구 헤더 처리 오류로 502가 발생했으나 로컬 중계 도구를 고친 뒤 화면 로딩을 확인하고 관측했다. 첫 저장은 약 80.734초로 너무 일러 정해진 120초 수락에 사용하지 않았다. 그 원시 기록과 결과도 보존했다: 115/115 HTTP 200, fresh 112, stale 3. 다음 구간은 중간에 저장하거나 실패 응답을 잘라내지 않고 약 132초 전체를 보존했다. 통과할 때까지 반복 측정한 결과가 아니다.

## 후속 원인 분리 — 배포 메타데이터와 관측 간격

최신 `origin/platform`은 후속 조회 시에도 `d54f1ed7`이었다. 보드 파일 내용은 반출하지 않고 SHA256·LF 정규화 SHA256·크기·권한·수정 시각과 허용된 이미지/패키지 메타데이터만 조회했다.

- 불일치 세 모듈은 CRLF를 LF로 정규화해도 같은 보드 해시였다. 따라서 이번 불일치는 단순 줄바꿈 차이로 설명되지 않는다.
- 조회한 이미지 메타데이터에는 BUILD_ID/소스 커밋이 없었고, 정해진 opkg/dpkg 메타데이터 경로에서도 대상 패키지 버전을 얻지 못했다. 설치 소스의 정확한 기준 커밋은 여전히 미확정이다. 패키지 메타데이터 미발견을 패키지 미설치로 해석하지 않는다.
- 보드 시각 00:43~00:47의 API/feed journal을 최대 500행으로 제한해 483행을 분류했다. `shared VM query unavailable`, `shared VM publication unavailable`, `Shared VM display observation unavailable`, `DEADLINE_EXCEEDED`, `PlatformUnavailable` 패턴은 관측되지 않았다. 원문 로그는 반출하지 않았다. 이 결과는 다른 오류의 부재나 해당 모듈 정상성을 증명하지 않는다.

## 브랜치 재대조 정정 — vm-stress-integration / vehicle

사용자가 지정한 두 원격 브랜치를 fetch하고 기존 보드 해시와 대조했다. 이번 브랜치 검토에서는 보드에 다시 접속하지 않았고, 새 소스 반출이나 배포도 하지 않았다.

- `origin/platform`: `d54f1ed7`
- `origin/feat/platform/vm-stress-integration`: `8d37fab5`
- `origin/vehicle`: `c1045fc3`

**앞서 미확정이었던 세 모듈의 출처가 확인됐다.** 보드의 Execution, Management, drive binding 세 파일은 vm-stress-integration HEAD의 Git blob과 바이트 SHA256이 모두 일치한다. telemetry_support도 이 브랜치와 일치한다. 따라서 위의 'Git 이력에서 식별하지 못함', '기준 커밋 또는 별도 수정 여부부터 확인 필요'는 두 브랜치를 가져오기 전의 한계다. 이 세 파일에 대해서는 더 이상 출처 불명으로 취급하지 않는다. 전체 이미지·Gateway·Worker 설치 조합 및 프로세스 로드 바이트까지 확인한 것은 아니다.

이 브랜치의 `1ab5ee7f`에는 A/B binding 관측을 한 회차로 묶어 Xen 목록·native incarnation 조회를 재사용하는 최적화가 있다. 기존 native helper를 재사용하며 별도 runtime 의존성을 추가하지 않는다고 배포 문서에 명시돼 있다. `1da02fe3`/`73e7f859`는 부하 장애를 해당 기능 범위로 제한하고 기능 전환·복구 종결을 맞추는 변경이다. 이 변경은 화면 계층이 제어 권한을 새로 판단해도 된다는 뜻이 아니다.

중요한 차이도 남아 있다. stress HEAD에는 platform의 `f1013ad3`(늦게 끝난 identity-only 실패가 나중의 정상 관측을 덮지 않도록 관측 시작 시각으로 순서를 보존하는 374 수정)이 포함되지 않는다. 실제 diff에서 identity_only 시작 시각 전달이 없는 구형 경로를 확인했다. 이는 의도적 삭제라고 단정하지 않고 브랜치 분기 차이로 기록한다. 지금 보드 Execution 해시는 stress와 일치하므로 **platform의 해당 수정까지 포함된 설치 조합으로 374를 시험한 것이 아니다.** 다만 이 누락이 이번 stale 1건의 직접 원인이라는 증거는 아직 없다.

vehicle 최신 변경은 Jetson의 인지·국소 지도, 상주 계산과 제어 응답 분리, 지도 체크포인트·주차 후보 저장, 광선 배치 처리 최적화 등을 포함한다. Jetson README는 Pi 시각/odom/차량 보정/지도 provenance 준비 전 metric_ready와 world_valid를 false로 유지하고 로컬 준비를 주행 허가로 간주하지 않는다고 명시한다. 주차 선택·경로 계획·추종·모드 권한은 RPi 책임이다. 따라서 vehicle의 인지·지도 준비와 374의 공유 VM 관측 freshness는 구분한다. vehicle의 세 플랫폼 모듈은 현재 보드 해시와 일치하지 않았고, 이 브랜치 전체를 보드 배포 기준으로 바꾸지 않는다.
