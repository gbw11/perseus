## trace 라벨 해석 정정

`xenova_execution.py`의 `@traced('execution.publish_observation')`는 실제 `observation_inputs` 함수에 붙어 있다. `publish_observation` 자체에는 별도 trace decorator가 없다. 앞선 문서의 두 함수가 같은 라벨을 쓴다는 설명을 이 분석에서 정정했다. 관측값은 변경하지 않았다.

기존 Linux 모의 VM fixture에서 두 조회를 실행해 확인했다. VM은 2대이고 Xen은 모의 처리이며, 보드 시간 측정이나 실제 제어가 아니다.

| --- | ---: |
| 입력 읽기 / 해당 trace 라벨 | 4 / 4 |
| 실제 `publish_observation` 호출 | 2 |
| 게시 직전 `validate_one` | 2 |

따라서 라벨이 많다는 이유로 실제 게시를 중복 제거하면 안 된다. 초기·최종 입력은 시간상 다른 검증이다. 경로 확인 34회도 모두 중복이라는 뜻은 아니며, 파일별/검증 경계별 필요성을 따져야 한다.

### 네 코드에서 진행할 수 있는 다음 단계

`SerializedManager.call`의 read-fork 분기에는 요청 전용 `forked` 객체가 있다. `call_with_budget(forked, ...)`가 끝난 직후 `forked.last_trace`를 읽으면 그 회차의 결과를 얻는다. 기존 소스의 Manager는 요청별 trace를 만들고 fork 간 가변 예산/trace를 공유하지 않는다. 로컬 fixture에서도 요청별 trace 존재와 action=list를 확인했다.

다음 구현은 다음 조건을 지켜야 한다.

- 관측 진단이 명시적으로 활성화된 list 조회 범위에서만 수집한다. 기본 경로의 조회 횟수·응답·예산을 유지한다.
- 공유 inner의 나중 `last_trace`를 읽지 않는다. 다른 요청의 trace가 섞일 수 있다.
- 호출별 격리된 수집 범위를 쓰고, 알려진 숫자 집계만 고정 크기로 보관한다. 인자·경로·payload·토큰·불필요한 식별자는 제외한다.
- 실패·trace 부재·예외에도 원래 조회 결과를 바꾸지 않는다. 재조회해서 trace를 만들지 않는다.
- 일반 조회의 trace를 느린 회차에 대신 붙이지 않는다. 같은 호출 경계에서 연결됐음을 검증해야 한다.
- 이 추적 연결 자체를 속도 개선이라고 표현하지 않는다. 장시간 회차의 분해 결과를 보고 최적화 후보를 선택한다.

팀원 Manager/Execution의 동작을 고치지 않고 시작할 수 있다. 구체적 최적화가 팀원 모듈에 걸리면 함수·검증 경계·측정 기대치를 정리한 뒤 담당 범위를 확인해야 한다. 아직 이 다음 단계를 구현하지 않았다.
