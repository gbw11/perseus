  다른 팀원 변경을 백업으로 덮거나 이미지 전체를 교체하지 않았다.
- 관리 API만 재시작했다. PID 1537 → 139068, active/running과 인증된 `/healthz` HTTP 200을 확인했다.

## 조건 변화와 보존 범위

시작 전부터 Recovery Worker는 inactive/PID 0이었고, 팀원의 추가 시험 VM
`parallel-budget-b-20261106`(domid 16)이 공유 코어 0·3에서 실행 중이었다.
이를 중지·삭제·재시작하지 않았다. API 조회 진단에는 등록 view 5개가 반환됐다.
기존 VM1·VM2·Debian 세 대만 있는 앞선 373 시험과 같은 부하 조건이 아니다.

초기 공유 파일도 status=ok지만 age 4206ms로 3초 기한을 넘었다. 배포 후 한 번의 별도
직접 읽기 진단은 2.386초에 성공했고 Python 예외는 확인되지 않았다. 이후 이 진단 소비자는
종료했다. 이 사례만으로 모든 공유 producer 지연의 원인이나 회귀 여부를 확정하지 않는다.

CPU는 dom0·Debian=0,3, VM1=1, VM2=2를 유지했고 추가 시험 VM도 초기 affinity를 유지했다.
Gateway·MQTT·로그·Tailscale 및 표시 feed의 상태/PID와 Recovery inactive 상태가 전후 동일했다.
VM·펌웨어·주행 명령·MQTT 계정/ACL·기존 자격증명·Spring DB를 변경하지 않았다.

## 실제 두 브라우저의 수신

정상 보드 feed의 기존 `/display/monitor-1`과 `/display/monitor-2` 제품 자산을
PC loopback 프록시로 열었다. 서비스 토큰은 PC 중계기 메모리에만 두고 브라우저에 넘기지 않았다.
실제 물리 HDMI 출력/영상 지연 시험이 아니다. 두 화면이 이미 요청하는 presentation 응답만
기록했으며 다음 표의 측정 중 추가 보드 API 소비자·진단 조회는 0개였다.

| 조건 | 구간 | 응답 | fresh | stale | HTTP/중계 오류 |
|---|---:|---:|---:|---:|---:|
| 팀원 동시 사용 | 136.141초 | 167 | 104 | 63 | 0 |
| 새 명령·배포·부하 시험 중단 확인 후 | 136.813초 | 169 | 92 | 77 | 0 |

두 구간 모두 모든 응답은 HTTP 200이었고 MQTT 연결·구독과 Gateway fresh 수신이 유지됐다.
Gateway 모드는 SAFE_STOP, 현재 구동 VM은 미확인이었으며 실제 주행 성공으로 해석하지 않는다.
VM 관측이 만료됐는데 앱 lifecycle `current`가 남은 표본은 두 구간 모두 0개였다.
새 관측 수신 후 정상 표시로 돌아오는 전환도 기록했다.

브라우저에서 드라이버 계기판과 인포테인먼트 화면의 연결·값 대기·VM 실행 미확인·지연 알림을
확인했다. 미수신 속도·배터리·미디어/경로를 정상 수치로 꾸미지 않았다.

두 번째 구간도 실행 중인 서비스/VM은 유지한 채 새 명령을 멈춘 조건이다. 완전히 유휴한 보드나
동일 부하의 A/B 비교가 아니다. 새 명령 중단만으로 지연이 해소되지 않았으며,
팀원 작업 탓으로만 단정하거나 373 수정의 역효과로 확정할 수 없다.

## 종료·정리

시험 중에만 SSH `PermitOpen`에 `127.0.0.1:8082`를 추가했고 기존 허용 목록은 보존했다.
종료 후 원래 해시로 복원하고 `sshd -t`와 임시 항목 제거를 확인했다.
PC 프록시와 SSH helper는 종료 코드 0으로 끝났다. 토큰·비밀번호·cookie는 증거에 저장하지 않았다.

최종 공유 파일은 status=ok·age 3506ms로 여전히 만료 상태였다. 관리 API는 active였으며
배포한 후보 코드와 원본 백업은 보드에 유지했다. 기준선도 이미 만료가 있었고 후보 예외/새로운
기능 오류를 확인하지 않았으므로 임의로 원복하지 않았다. 원복 시에는 현재 후보 해시를 대조하고
Management → Execution 복원 및 API 재시작 절차를 따른다.
