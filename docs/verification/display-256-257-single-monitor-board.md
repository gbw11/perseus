# 단일 HDMI 실보드 표시·전송 시험

## 범위

- 보드: 기존 SSH 호스트 키를 고정한 Raspberry Pi dom0.
- 모니터 한 대에서 기존 `/display/monitor-1`, `/display/monitor-2`를 순서대로 표시한다.
- VM1 주 구동, VM2 백업, VM3 Debian의 Xen 상태를 조회한다. 이 시험의 표시 수집기는 MQTT를 연결하지 않으므로 앱 상태·OS 근거·주행 모드 확인으로 해석하지 않는다.
- VM·펌웨어·부팅 이미지·기존 Manager 서비스·자동 시작 설정은 변경하지 않는다.
- 새 계기판·인포테인먼트 디자인, HDMI 두 대 동시 출력, 외부 Spring 서버 경유는 범위 밖이다.

## HDMI 표시 결과 (2026-10-27)

1. 실제 활성 framebuffer `/dev/fb1`에서 RGB 막대와 흰 테두리를 표시했다. 사용자가 실제 모니터에서 보였다고 확인했다. 해당 시험의 픽셀 복원 해시는 일치했다.
2. `/dev/fb0`, `/dev/fb1`은 동일한 물리 메모리를 가리킨다. 두 HDMI 출력의 증거가 아니다. 화면은 1824×984, 32bpp이다.
3. 별도 디렉터리에 ARM64 Xorg·Chromium·FFmpeg 실행 묶음을 추출하고, private mount/PID namespace 안에서만 실행했다. 시스템 패키지 설치나 유지관리 스크립트 실행은 하지 않았다. Chromium은 kiosk 사용자로 실행했고 `--no-sandbox`를 사용하지 않았다.
4. 기존 전체 화면과 VM 상세 화면을 각각 30초 표시했다. 사용자가 두 화면 모두 정상 크기로 보인다고 확인했다. X11에서 새로 캡처한 JPEG도 각각 확보했다.
5. 해당 화면 시험 종료 후 그래픽 프로세스와 임시 마운트는 정리됐지만, framebuffer 전체 바이트 비교는 불일치했다. 원인은 확정하지 않았다. 2026-10-28 재조회에서는 그래픽 프로세스·임시 마운트가 없고 활성 VT가 1임을 확인했다. 픽셀 단위 원상복구가 증명됐다고 보고하지 않는다.

## 출력 식별의 제한

현재 fbdev Xorg는 `default` 커넥터만 보고하고 DRM 커넥터·EDID를 노출하지 않는다. 운영 `x11` 설정의 EDID 검증을 통과한 상태가 아니다.

연속 전송 시험에서는 `virtual_x11`을 명시적으로 허용한 **진단용 상태 어댑터**로 현재 표시 중인 논리 화면 하나만 활성화한다. 실제 픽셀은 물리 framebuffer를 사용하는 Xorg에서 캡처하지만, 전송 메타데이터의 `physical_verified`는 `false`이다. 나머지 논리 출력은 `unavailable`이다. 운영 Kiosk의 화면 배치·렌더 ACK 검증을 대체하지 않는다.

## 전송 시험 방법 (2026-10-28)

- 현재 작업 브랜치의 `stream.py`를 메모리에서 로드해 실제 `Capture`, `JpegParser`, 인증 및 MJPEG 응답을 사용한다.
- FFmpeg만 기존 private mount namespace에 진입시킨다. 스트림 서버는 loopback에서만 수신한다.
- 최초 임의 포트는 기존 SSH `PermitOpen` 정책에 의해 거부됐다. 정책을 넓히지 않고 기존 허용 포트 `127.0.0.1:8082`가 비어 있음을 확인한 후 사용한다.
- PC는 호스트 키를 고정한 SSH `direct-tcpip` 채널로 실제 HTTP MJPEG를 연속 수신한다. 파일 복사를 연속 영상 수신으로 간주하지 않는다.
- 무인증·오인증 거부, 세션 쿠키 인증, 연결 해제 후 새 연결, 소스 제거 후 이전 프레임 차단을 확인한다.
- 토큰은 난수로 생성해 SSH 연결의 메모리 안에서만 교환하며 문서·증빙에 저장하지 않는다.
- 수신 FPS와 JPEG 데이터량은 이번 진단의 관측값이다. 1280×720·5 FPS, p95 500ms, 합계 8Mbps, CPU 1코어 목표에 대한 정식 성능 판정은 별도다.

PC에서 받은 두 JPEG를 직접 열어 전체 화면과 상세 화면임을 확인했다. 테스트는 실제 X11 캡처 → 기존 MJPEG 인증 서버 → 암호화 SSH → PC HTTP 수신으로 수행했다. 수신 시험은 총 80프레임이며 고유 프레임 변화도 확인했다. 체크 요약은 10/10 통과했다. 5 FPS 성능 목표 충족이나 원격 브라우저 운영 배포 완료를 뜻하지 않는다.

## 남은 검증

- EDID/DRM 식별이 가능한 런타임에서 모니터 두 대의 출력·재연결·화면 배치 검증.
- 기존 단일 framebuffer의 종료 시 픽셀 비교 불일치 원인 확인.
- 새 HDMI 계기판·인포테인먼트 화면 및 확정된 실제 앱 보고 연결.
- 외부 서버를 통한 화면 수신과 정식 인증·배포 설정.
- 목표 해상도에서 지연·CPU·대역폭 측정.
