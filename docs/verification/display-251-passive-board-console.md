# 251: 실보드 웹 콘솔 무입력 연결·해제·재연결 검증

2026-10-27 17:07~17:11 KST. 실제 Raspberry Pi dom0 `192.168.30.96`, 실제 세 게스트를 대상으로 시험했다. 게스트에 Enter·로그인 정보·명령 등 텍스트/바이너리 터미널 입력을 보내지 않았다. 터미널 출력 내용과 인증정보는 보관하지 않고 프레임·바이트 수만 기록했다.

## 범위

현재 실행 중인 Manager PID는 1088이며 콘솔 활성화 환경변수가 설정되지 않았다. 기본 비활성 상태를 바꾸거나 Manager를 재시작하지 않았다. 대신 현재 작업 트리의 콘솔 PTY 모듈과 WebSocket router를 단기 프로세스 메모리에 로드하고, 보드 loopback 임시 포트에 콘솔 전용 FastAPI를 띄웠다. 모듈별 SHA256은 증거에 기록했다.

UUID·이름을 실제 Xen과 대조하고 읽기 전용 Xen 조회로 현재 domid를 얻었다. 콘솔 API는 이 세 UUID만 허용하는 조회 어댑터를 사용했다. 실제 `xl console -t pv <domid>`와 PTY, 공통 VM별 flock 경로를 사용했다. 임시 API 토큰은 메모리에서 생성하고 출력/저장하지 않았다.

이 결과는 현재 코드의 실제 게스트 콘솔 연결 기능 검증이다. 기존 8081 API 활성화·Spring·Nginx·프론트 터미널 화면을 연결한 검증이나 영구 배포 완료를 의미하지 않는다. 프론트의 자동 Enter 기능도 사용하지 않았다.

세 VM 모두 인증된 WebSocket Upgrade 101, 동시 두 번째 접속 4409 종료, 정상 해제 1000, 재연결 101, 재해제 1000을 확인했다. 동시 접속 중 콘솔 프로세스는 하나였고, 각 해제 뒤 프로세스 종료와 flock 재획득 가능 여부를 확인했다. 토큰 없음/잘못된 토큰은 각각 HTTP 403으로 Upgrade가 거부됐다.

초기 시험의 프로세스 탐지기가 `xl`만 인식해 프로세스 확인 항목은 false였다. 실제로 `xl`이 `xenconsole`로 전환하는 실행을 놓친 시험 도구 문제였고, 초기 수신/해제 자료는 그대로 보존했다. 탐지기를 수정해 재시험한 연결·프로세스·잠금 조건은 모두 통과했다. 이 수정은 로컬 시험 도구에만 적용했다.

재시험 및 최초 재연결의 짧은 수신 대기 동안 새 바이트는 0이었다. 수동 입력으로 새 출력을 유발하지 않았으며, 이전 부팅 로그가 자동 재전송된다고 가정하지 않는다. 새 출력이 없는 상태의 연결 성공과 출력 내용의 의미 검증은 구분한다.

WebSocket 종료 제어 프레임만 클라이언트에서 보냈다. 서버의 기존 PTY 종료 구현은 `xl console`이 소비하는 escape 바이트와 필요 시 프로세스 신호로 연결을 정리한다. 이 종료 동작을 게스트 셸 입력이나 명령 전송으로 사용하지 않았다.

## 종료 후 재조회

임시 API 스레드·리스너 종료, xl/xenconsole 잔여 프로세스 없음. 기존 Manager PID 1088과 세 VM domid 1/2/3 유지. TCP 리스너는 기존 22·loopback 8081만 남았다. VM·펌웨어·서비스 환경설정 변경이나 시스템 서비스 재시작은 없었다. 공통 잠금 파일은 설계상 삭제하지 않고 잠금만 해제한다.
