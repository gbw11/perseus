# 표시 파이프라인 실보드 수락 시험

이 문서는 실행 절차다. 작성만으로 실보드·HDMI 시험이 통과한 것은 아니다.
현재 가상 검증 결과는 [5단계 기록](display-step5.md)에 구분한다.

2026-10-28 새 차량 화면의 단일 모니터 표시·PC 수신은 [실보드 기록](display-vehicle-board-20261028.md)을 따른다. 아래 두 출력·장시간·장애 주입·성능 항목은 그 시험으로 완료 처리하지 않는다.

## 사전 준비

Raspberry Pi의 실제 dom0 이미지, HDMI 모니터 두 대, 별도 시연 PC와 네트워크가 필요하다.
VM1·VM2는 같은 Zephyr의 주 구동/백업 역할, VM3는 Debian으로 UUID 매핑을 확인한다.
실제 차량 모터 동작 없이 표시를 시험할 수 있는 환경에서 수행한다.

1. dom0의 Xorg 세션/창 관리자, GPU 드라이버, Chromium, XRandR, FFmpeg x11grab/MJPEG, 한글 글꼴과 Python 의존성을 확인한다. Wayland 세션이면 현재 X11 실행기를 지원한다고 처리하지 않는다.
2. 실제 그래픽 사용자로 `python -m xenova_display.outputs --display :0`을 실행해 connector·EDID·지원 모드를 증거로 저장한다.
3. [설정 예제](../../platform/services/display/router/examples/x11-runtime.json)의 placeholder EDID를 실제 값으로 교체한다. 논리 monitor-1/2와 각 물리 모니터를 라벨로 대응시킨다.
4. [실행 안내](../../platform/services/display/router/README.md)에 따라 로컬 feed·키오스크·송신기를 각각 실행한다. feed 키와 원격 시연 키를 구분하며 URL에 넣지 않는다. systemd를 사용하면 실제 Python/Chromium 경로를 적용한다.
5. 시연 PC는 SSH 포워딩 등 준비된 연결로 `/demo`에 접속하고 두 영상을 받는다. 로컬 표시가 외부 Spring 서버 없이도 동작하는지 확인한다.

## 수락 항목

| 시험 | 기대 결과 | 남길 증거 |
| --- | --- | --- |
| 초기 두 출력 | 모니터 1에 차량 계기판, 모니터 2에 인포테인먼트·게스트 콘텐츠. 뒤바뀌거나 겹치지 않음 | 두 실제 모니터 영상, connector/EDID, runtime JSON |
| OS·역할 | VM1/2 동일 Zephyr·서로 다른 역할, VM3 Debian. 기대/관측 OS 구분 | 화면과 실제 inventory |
| 앱 미준비·오류 | Xen running과 앱 오류를 구분, 미수신을 정상으로 만들지 않음 | 실제 발행 로그와 화면 |
| 자동→수동 | 확인된 mode만 변경되며 활성 VM을 임의 변경하지 않음 | 제어 발행자 상태와 화면 |
| 주→백업 | 제어 담당의 active_vm_id 확인 후 배지 갱신. pinned 유지, follow_active에서만 상세 전환 | 제어/복구 담당이 제공한 실제 전환 기록 |
| 화면 소스 일치 | 두 로컬 화면의 각기 다른 움직이는 표식/타임코드가 대응하는 원격 화면에 도착 | 로컬·원격 동시 촬영, 출력별 프레임 기록 |
| HDMI 한쪽 분리/재연결 | 해당 출력만 unavailable. 다른 출력 유지. 원래 EDID 복귀 시 원래 화면 재적용 | 두 모니터 영상, runtime 상태, journal |
| 다른 모니터 연결 | 저장된 EDID 불일치는 임의 매핑하지 않음 | EDID 비교와 상태 |
| 한쪽 Chromium 종료 | 해당 창만 복구. 다른 창과 송신기 유지 | PID·창·출력별 상태 기록 |
| 송신기 중단/재시작 | 로컬 두 화면 유지. 원격 마지막 프레임 안내. 재시작 후 다시 연결 | 로컬·원격 영상과 프로세스 기록 |
| feed 재시작 | 로컬 창 유지, 이전 값 안내 후 인증/연결 회복. 이전 ACK를 새 실행의 증거로 쓰지 않음 | epoch·ACK·화면 기록 |
| 원격망 단절/복구 | 로컬 두 화면 유지. 원격 중단 안내 후 재연결 | 시연 PC의 연결 조작과 동시 로컬 촬영 |
| 10분 이상 연속 실행 | 두 로컬 화면 유지, 두 원격 디코드 관측. 실패/중단 횟수도 기록 | 타임스탬프별 상태·측정 원본 |

표시 서비스는 VM·모터·실제 승계 명령을 실행하지 않는다. VM 장애/재시작과 실제 주행 승계 시험은 해당 제어 담당이 준비한 절차로 발생시킨 뒤 표시 결과를 대조한다. 현재 AI 상태·그래픽 앱 소스 어댑터가 미연결이므로 `unknown`·미연결 안내가 정상적인 현재 결과이며 해당 기능 완료로 처리하지 않는다.

## 성능 기록

2026-10-22 사용자가 1차 목표를 출력별 1280×720·5 FPS로 확정했다. 지연 p95 ≤500ms, JPEG payload 합계 ≤8Mbps, 송신기+인코더 평균 CPU ≤1코어를 목표로 측정한다. 실제 달성 여부는 미검증이며 10 FPS는 후속 개선이다. [결정 기록](../contracts/display-250-decisions.md)을 따른다.
해상도·FPS·JPEG 품질·커널/이미지·CPU governor·온도·네트워크 종류·시연 PC 정보를 함께 저장한다.

- 실제 Pi 송신기와 두 FFmpeg의 CPU·RSS를 별도로 측정한다. 가능하면 로컬 Chromium/수집기·시스템 전체 값도 분리한다. 100%는 CPU 1코어에 해당하는 기준으로 환산한다.
- 각 출력의 프레임 번호 차이/시간으로 FPS, JPEG 바이트와 실제 인터페이스 전송량으로 payload/네트워크 대역폭을 나눠 기록한다.
- 같은 실제 화면에 움직이는 타임코드를 표시하고 로컬·원격 동시 촬영으로 지연 분포를 구한다. 두 장비 시계를 쓰면 동기화 오차를 기록한다. 샘플 수·p50/p95/max·프레임 누락·정지 구간을 함께 보고한다.
- 사용자 확정 목표와 실제 달성 여부를 나눠 보고한다. 미달이면 FPS/해상도/코덱 변경을 협의해 재측정하고 기존 측정도 보존한다. 미달한 결과를 목표 변경만으로 통과 처리하지 않는다.

가상 시험의 전체 프로세스 RSS/CPU에는 Xvfb·수신 Chromium도 포함된다. 그 값을 Pi 송신기 예산이나 실제 HDMI 성능으로 대입하지 않는다.
