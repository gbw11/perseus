# 253 — 공유 VM 조회 비용 개선 및 두 표시 화면 재검증

## 판정

일반 조회의 프로세스 실행 비용은 줄었지만, 공유 VM 관측의 간헐적 만료는 남아 있다.
따라서 이번 결과만으로 253 전체를 완료 처리하지 않는다. CPU 배치·VM·펌웨어·MQTT 권한은
변경하지 않았다. 실제 주행 READY·자동/수동 전환이나 물리 HDMI 출력 시험 결과도 아니다.

## 변경

`XENOVA_IDENTITY_BATCH_READS=1`을 Manager의 다중 VM 읽기 경로에만 선택 적용한다.
VM 3대 정상 조회의 외부 실행은 8회에서 4회로 줄어든다. 전후 Xen 목록 2회와
VM별 전후 실행 신원 검증은 유지한다. 새 도구는 한 프로세스·한 handle로 신원을 읽으며,
일부 실패·잘못된 응답·기한 초과 시 전체 조회를 실패 처리한다.

관측 시각은 최종 배치 **시작 전**으로 기록한다. 3초 상태 유효기간을 늘리거나,
오래된 결과에 새 시각을 붙이거나, 별도의 원시 Xen 조회로 우회하지 않는다.
기본 설정은 비활성화이며 단건 조회·변경 명령 경로는 기존 도구를 사용한다.
배포 및 원복 조건은 [선택형 신원 배치](../platform/read-identity-batch.md)를 따른다.

## 실보드 비교 — 2026-11-05

같은 프로세스에서 비활성/활성을 교차 비교했다. 각 4회, 총 8회 모두 VM 3대 조회에 성공했다.
소수 표본이며 한 회에는 기존 재확인 절차가 실행됐다. 장시간 성능 보장으로 해석하지 않는다.

| 설정 | 조회 시간(초) | 평균 |
|---|---|---|
| 기존 단건 도구 | 2.4673, 1.7983, 1.6779, 1.6711 | 1.9037초 |
| 신원 배치 | 1.8929, 1.1789, 1.3503, 0.8371 | 1.3148초 |

평균 약 31% 감소했다. 별도 호출 추적에서도 `xl.list` 2회·배치 2회를 확인했다.
다만 어제 부하 시험은 실제 브라우저 2개와 진단 요청 소비자 2개가 함께 연결된 결과다.
그 시험의 78개 응답 중 fresh 58·stale 12·disconnected 8을 순수한 두 화면 결과로 사용하지 않는다.

## 실보드 재확인 — 2026-11-06

보드 재부팅 후 Manager와 표시 서비스가 같은 공유 관측 파일을 사용하고,
선택형 배치 도구가 Manager에서만 활성화된 것을 확인했다.
이번에는 실제 계기판·인포테인먼트 브라우저가 이미 요청하는 응답만 PC에서 기록했다.
측정 때문에 추가하는 보드 API 요청은 없다. 임시 PC 프록시의 응답 시간은 SSH 전달을 포함하며,
HDMI 원격 영상의 종단 지연이나 257번 영상 성능 수치가 아니다.

56.766초 동안 응답 70개가 모두 HTTP 200이었고 프록시 오류는 없었다.
공유 Xen 상태는 fresh 66개·stale 4개였다. 네 만료 구간 모두 후속 응답에서 fresh로 복귀했다.
만료된 VM의 앱 `current`가 남은 응답은 0개였다. MQTT와 Gateway 상태 수신은 70개 모두
연결/fresh였으며, 표시 서비스 epoch도 하나로 유지됐다.
PC 프록시 왕복은 중앙값 594ms·p95 890ms·최대 1015ms였다. 이는 영상 지연 수락값이 아니다.
측정 수치·만료 시 표시 판정·최종 정리 결과는 [동명 JSON](display-253-query-latency-20261106.json)을 참조한다.
브라우저에서 두 화면과 VM 3대, 앱 보고를 확인했다. 미수신 속도·배터리·음악·경로는 대기로
표시한다. Gateway는 SAFE_STOP·출력 미허가였으며, 앱 보고는 WAITING/NOT_READY였다.
이를 실제 구동 준비 완료로 표시하지 않는다. Zephyr 실제 OS 보고는 미수신이고,
Debian OS 근거는 수신 이력이 있으나 현재 freshness와 분리한다.

## 검증 범위와 남은 조건

- 새 ABI/응답 검증·부분 실패·차단된 자식 종료·신원 변경 거부·시각 보존·기존 경로 유지 시험 33개 통과.
- 11월 6일 새 시험과 기존 단건 ABI·조회 일관성·실행 경계 회귀: 81개 및 subtest 14개 통과.
- 더 넓은 11월 5일 실행은 111개 및 subtest 24개 통과, 기존 100ms 자식 종료 시험 1개 실패.
  `test_S4_T08_owned_helper_timeout_after_pipe_eof_reaps_child`는 자식 PID 파일 생성 전에
  전체 기한이 끝나는 환경 의존 실패이며, 변경 전 platform에서도 동일하게 재현됐다.
  이 시험의 기한·기대값은 바꾸지 않았고 전체 시험 통과라고 주장하지 않는다.
- CPU 배치는 dom0 및 Debian 공유 코어 0·3, VM1 전용 1, VM2 전용 2를 유지한다.
  사용자 결정에 따라 CPU 수·pinning 비교는 수행하지 않는다.
- 간헐적 공유 관측 만료의 추가 원인 분리와 정상 부하에서의 연속 신선도 수락이 남는다.
  유효기간을 늘려 현상을 숨기는 방법은 사용하지 않는다.

보드에는 검증 후보 코드와 Manager 전용 활성 설정이 남는다. 이전 코드와 새 후보 해시는
root 전용 백업 manifest로 보호한다. 임시 표시 접속을 위해 추가한 SSH 허용 항목은
시험 후 원래 설정으로 복원하고 PC 프록시·SSH 연결을 종료한다.
검증 결과는 platform 대상 MR에서 검토하며, 이 결과만으로 이슈를 완료하거나 자동 머지하지 않는다.

최종 점검에서 원본 SSH 해시 복원과 `sshd -t` 통과, 임시 포트 제거를 확인했다.
PC 프록시와 SSH helper는 종료 코드 0으로 종료했다. 정상 서비스 7개는 active였고 Manager와
표시 서비스 PID는 오늘 초기 조회와 같았다. API 목록은 503 두 번 후 200으로 복귀했고
VM 3대는 모두 running이었다. 이 최종 조회 역시 간헐적 지연이 해결되지 않았다는 근거다.
CPU affinity는 초기 값과 동일하며 기존 단건 도구 두 파일의 해시도 유지됐다.
