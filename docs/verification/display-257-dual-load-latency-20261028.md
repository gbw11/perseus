# 257 실보드 2인코더 동시 부하·전달 지연 시험 (2026-10-28)

**결과: 이번 시험 경로에서는 평균 CPU 1코어와 전달 지연 p95 500ms 목표를 충족하지 못했다.** 한 대만 연결됐으므로 실제 HDMI 두 출력 동시 수락은 여전히 미검증이다. 앞선 [단일 출력 순차 재시험](display-257-idle-encoding-retest-20261028.md)의 통과 범위를 확장해서 해석하면 안 된다.

## 실행 범위

사용자가 HDMI 모니터 한 대 연결을 확인했다. 실제 dom0의 전용 fbdev X11 세션에 인포테인먼트 화면을 띄우고, 같은 1824×984 원본을 독립 FFmpeg 두 개가 각각 1280×720·5 FPS 설정으로 캡처·인코딩했다. 실제 제품 Capture, 상태 검증, 인증된 MJPEG HTTP 경로를 사용했고 PC가 두 HTTP 스트림을 동시에 받아 JPEG를 디코딩했다. 접속은 고정 SSH 호스트 키를 검사한 LAN SSH direct-tcpip이다. 외부 Spring·Tailscale·원격 브라우저의 경로를 시험한 것은 아니다.

시험용 capture factory는 각 인코더의 활성 원본 영역을 (0,0,1824,984)로 명시한다. 두 상태 metadata 모두 실제 원본 좌표를 보고한다. virtual_x11 진단 모드이며 physical_verified=false다. 생산용 EDID 매핑을 우회해 성공으로 기록한 것이 아니다. 서로 다른 화면 두 개의 렌더링 부하, 실제 두 케이블·EDID·출력 장치의 동시 동작은 포함하지 않는다.

전용 세션의 screen saver·DPMS 방지는 이전에 보완한 제품 IdleGuard를 사용했다. VM 입력, VM·펌웨어 변경, 상시 서비스 설정 변경은 하지 않았다. 시험용 색상 사각형은 `LATENCY TEST`라고 명시했고 차량 데이터나 제어 명령으로 취급하지 않는다.

CPU 100%=1코어이고 시간 가중 평균이다. Python에는 수집기·송신기와 진단 sampler가 함께 포함된다. 추가 시험에는 시계 보정 HTTP 요청과 색상 표식 변경 작업도 있으므로 순수 인코딩 비용만 분리한 수치가 아니다. 브라우저·Xorg CPU는 위 합계에서 제외하며 원본 summary에서 별도로 확인할 수 있다. RSS 합은 공유 페이지를 중복 계산하므로 실사용 물리 메모리로 해석하지 않는다. 추가 시험의 최소 MemAvailable은 136,876,032바이트(약 130.5MiB), 최고 온도는 40.894°C였다.

수신 간격이 1초 미만이어도 최신 화면이라는 뜻은 아니다. 프레임 번호 건너뜀은 관측됐으며 인코더 종료나 HTTP 오류로 단정하지 않는다. 원인 위치를 이 자료만으로 확정할 수 없다.

## 실제 픽셀로 측정한 전달 지연

첫 시험은 PC 단조 시계로 표식 변경 요청 시작부터 JPEG 디코딩·색상 인식까지를 측정했다. 이 값에는 PC→보드 제어 요청 시간이 포함된다. 지연이 길게 나와 두 번째 시험에서 보드 시계 기준 시작점을 추가했다.

두 번째 시험은 다음과 같다.

1. 두 인코더가 실행 중인 상태에서 실제 화면 위 색상 표식을 고유한 RGB 30개로 차례로 바꾼다.
2. 보드가 CDP 화면 변경 요청을 시작한 시각을 기록한다. PC는 실제 전송 JPEG 전체를 Pillow로 디코딩하고, 축소된 표식 내부 픽셀을 읽어 해당 색상이 처음 도착한 시각을 기록한다. 프레임 간격을 지연으로 대체하지 않는다.
3. 보드·PC perf_counter 시계 차이는 시험 전후 각 12회의 인증된 HTTP 왕복으로 추정한다. 각 구간 최소 RTT 표본을 사용한 시계차 범위의 합집합을 오차 범위로 삼는다. 시험 도중 시계차가 이 범위 내에 유지된다는 가정이 있으며, NTP 동기화를 전제하지 않는다. 최소 RTT는 전 128.16ms / 후 84.44ms, 최종 시계 추정 오차 반폭은 약 75.56ms다.
4. 3초 내 확인되지 않은 표식도 최종 수신 프레임에서 다시 찾는다. 늦게 도착한 표식을 버려 지연 분포를 좋게 만들지 않는다. 두 스트림 모두 최종적으로 30개 전부 인식했다.

| 보드 표식 변경 요청 → PC JPEG 디코딩·인식 | 스트림 1 | 스트림 2 |
| --- | --- | --- |
| 최종 측정 표식 수 | 30 / 30 | 30 / 30 |
| 3초 관찰 창을 넘긴 표식 | 12 | 10 |
| 평균 추정 지연 | 2717.74ms | 2156.45ms |
| p95 추정 지연 | **7699.45ms** | **6329.71ms** |
| 시계 오차를 반영한 p95 구간 | 7623.89~7775.01ms | 6254.15~6405.27ms |
| 최대 추정 지연 | 7964.95ms | 7204.33ms |

이 분포는 늦은 표식을 포함한 30개 전체 기준이다. summary의 `latency_matched`, `latency_timeouts`와 `request_to_decoded_pixel_upper_bound_ms`는 최초 3초 관찰 창의 결과이며, 최종 지연 수치는 `eventual_markers_received`, `board_marker_request_to_pc_decoded_ms_estimate`를 사용한다. p95는 작은 표본의 경험 분위수이며 장시간·다양한 화면의 성능 보장은 아니다.

측정 범위는 **보드의 화면 변경 요청 → 브라우저 그리기 대기 → X11 캡처 → JPEG 인코딩 → 실제 SSH 전송 → PC 디코딩·픽셀 인식**이다. 순수 네트워크 지연만의 수치가 아니다. 보드 물리 모니터의 발광 시각, 원격 브라우저의 canvas 표시·모니터 발광 시각은 측정하지 않았다. 보드 화면 변경 요청 시각은 실제 픽셀 그리기보다 앞서므로 이 구간에는 보드 렌더링 대기도 포함된다. 그 한계를 감안해도 현재 시험에서 500ms 목표를 통과했다고 볼 수 없다.

## 종료와 남은 일

두 시험 모두 namespace_exit=0, 그래픽 자식 프로세스 종료, 임시 feed 종료, VT1 복귀, framebuffer 원본과 0바이트 차이로 복원을 확인했다. 마지막 별도 조회에서도 그래픽 프로세스·private mount는 없고, 포트는 기존 SSH 22와 Manager 8081뿐이었다. VM3 domid1, VM1 domid2, VM2 domid3가 유지됐다. 비밀번호·시연 토큰은 증거 자료에 저장하지 않았다. 시험용 stage 파일은 격리 경로에 남는다.

이번 요청에서 실행 가능한 동시 인코딩·전달 지연 시험을 마쳤다. 다음 작업은 송수신 버퍼·스레드/스케줄링·PC 수신 경로를 구간별로 측정해 지연이 쌓이는 위치를 찾고, 두 인코더의 CPU를 낮춘 후 같은 조건으로 재시험하는 것이다. 진단 부하와 제품 부하도 분리해야 한다. 이 결과만으로 원인을 특정하거나 FPS·화질 목표를 임의로 낮추지 않았다.

실제 두 모니터 동시 출력·별도 화면 렌더링, 두 출력 장시간 실행, 원격 브라우저 표시까지의 지연은 모니터 두 대와 해당 수신 환경이 준비된 뒤 수행한다. **257 전체 완료로 처리하지 않았다.** 이번 턴에는 시험 도구와 검증 기록만 추가했으며 제품 코드 추가 수정·커밋·푸시는 하지 않았다.
