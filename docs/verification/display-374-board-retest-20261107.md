현재 해시가 달랐다면 덮지 않도록 적용 직전에 재검사했다.

API 재시작 직전 사용자에게 알렸고 `xenova-dom0-manager.service`만 재시작했다.
PID 1304→608116. 첫 응답은 activating 상태로 접속되지 않았지만 재시작을 반복하지 않았고,

## 실제 두 브라우저

보드의 기존 표시 서비스 자산을 PC loopback 프록시로 열었다. 토큰은 중계기 메모리에만
보관했고 브라우저에 전달하지 않았다. 현재 제품 코드는 monitor-1·monitor-2에서
`/display/combined`로 이동하므로, 두 탭 모두 팀원의 합친 차량 화면을 표시했다.
이것은 실제 두 브라우저 소비자의 수신 시험이다. 독립 HDMI 두 출력의 배치·렌더링·영상 지연
시험이나 휴대폰 시험으로 해석하지 않는다. 두 화면의 안전 정지/구동 VM 없음·값 미수신과
VM 상태 미확인 표시를 관찰했다. 주행 모드를 변경하거나 수신되지 않은 값을 만들어내지 않았다.

## 시험 후 조회

브라우저와 중계기를 종료한 뒤 수행한 별도 3회 list는 2회 성공(2.788·2.850초), 1회
TARGET_CHANGED 거부였다. 로그의 shared query 실패 종류는 InvalidState였다. 계측 당시
새 파일 교체·서비스 재시작은 하지 않았다. 이후 별도 프로세스에서 비교 함수를 감싸 항목
이름만 기록한 6회 list는 모두 성공(1.177~3.502초)했고 변경 비교 사건은 잡히지 않았다.
이 결과로 TARGET_CHANGED의 특정 원천을 확정하지 않는다. 별도 조회는 부하를 추가하므로
두 브라우저 수락 구간과 분리했다. 현재 데이터 검증을 우회하거나 오류를 성공으로 바꾸지 않았다.
