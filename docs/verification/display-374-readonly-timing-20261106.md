# 374 — 읽기 전용 지연 분리 진단

2026-11-06. 사용자의 현재 읽기 전용 진단 허용 후 수행했다. 정상 서비스 코드·설정 교체,
재시작, VM/펌웨어/CPU 변경, TTL 변경은 하지 않았다. 373 배포 해시는 종료 시에도 동일했다.
관리 API PID 139068, 표시 feed PID 598, Mosquitto PID 821은 active/running이었다.

## 공유 파일 게시

추가 API 소비자 없이 기존 공유 파일을 100ms 목표 간격으로 30초 읽었다.
파일을 open한 동일 descriptor의 fstat와 JSON을 사용했다. 첫 파일은 표본 전 생성될 수 있어
새 게시 지연 계산에서 제외했다. 새 게시 21개에서 관측 시각→파일 수정 시각은 중앙값
0.757초, 최대 1.186초, 게시 간격은 중앙값 1.384초, 최대 1.801초였다.
이 새 파일 사이에는 3초 lease가 끝난 구간이 없었다. 파일 mtime은 게시 완료 자체의
정확한 시각이 아니며, 같은 호스트 realtime/monotonic 보정으로 추정한 파일 쓰기 경계다.

## 동시 화면 API 읽기

별도 구간에서 정상 loopback presentation API를 두 소비자가 최대 각 1Hz로 65초 읽었다.
실제 브라우저·HDMI 렌더링 시험이 아니며 이전 120초 두 브라우저 수락을 대체하지 않는다.

| 항목 | 결과 |
|---|---:|
| 응답 / HTTP 200 | 128 / 128 |
| VM source stale 응답 | 53 |
| 응답 수신 후 공유 파일도 만료 | 34 |
| stale 응답이나 이후 공유 파일은 fresh | 34 |
| MQTT 연결 유지 | 128 / 128 |
| 만료 VM에 current 앱 잔류 | 0 |
| loopback 요청 시간 중앙값 / 최대 | 667.5 / 1448 ms |

공유 파일 읽기는 HTTP 응답 뒤에 수행하므로 같은 원자적 순간의 비교가 아니다.
특히 stale 응답 뒤 fresh 파일이 발견됐다는 사실만으로 feed 단독 결함을 확정하지 않는다.
응답 생성·전송 중 새 파일이 게시됐을 수도 있다. 두 stale 관련 집계는 중첩하며 합산하지 않는다.
또 순차 구간의 부하가 같지 않아 API 소비자 추가가 지연의 원인이라고 단정할 수 없다.

## 단일 조회 프로파일

별도 프로세스에서 기존 Manager list를 한 번 프로파일했다. 5개 view, 성공, 총 1.809초였다.
관측 수행 약 1.199초 중 VM별 게시 5회에 약 0.657초가 포함됐다. 각 VM의 마지막 입력 검증
5회는 약 0.374초였다. 전체 registry 읽기 2회는 약 0.242초였다. 이 값들은 호출이 중첩되므로
합산하지 않는다. 파일 fsync 자체는 총 1ms 미만으로, 이를 제거하는 것이 해법이라는 근거가 없다.
계측 오버헤드가 있으므로 이 단일 조회를 정상 서비스의 성능 합격값으로 사용하지 않는다.

별도 10초 /proc 표본에서 관리 API는 약 0.612코어, 표시 feed는 약 0.250코어,
Mosquitto는 약 0.058코어를 사용했다. 해당 PID의 utime+stime 차이이며 자식 프로세스,
다른 서비스·게스트와 전체 시스템 사용량을 포함하지 않는다. 조회되지 않은 unit의 PID 0을
서비스 정지 증거로 해석하지 않는다.

## 판정과 다음 수정 경계

**374는 계속 진행 중이다.** 정상 구간과 지연 구간이 공존하고 연속 freshness는 아직 미통과다.
지연을 숨기기 위한 TTL 연장·옛 관측 시각 갱신·신원/실행/설정 재검증 생략은 하지 않는다.
다음 로컬 작업은 관측 후 반복 검증 비용을 줄일 수 있는지 확인하되, 변경·삭제·실행 교체·
shutdown barrier가 조회 중 바뀌는 경계를 그대로 검증해야 한다. 단순 캐시 추가를 안전한
최적화로 간주하지 않는다. 후보가 검증되기 전 운영 서비스에 적용하지 않는다.

추가 수락에는 동일 버전의 실제 두 브라우저 120초 연속 수신과 정상 VM 목록 API 확인이
필요하다. 현재 진단은 그 수락이나 API 503 해소를 입증하지 않는다. SSH 진단 세션은 종료했고
추가 SSH 허용 항목이나 보드 임시 파일은 만들지 않았다. 실행 로그/비밀값은 증거에 포함하지 않았다.
수치는 [요약 JSON](display-374-readonly-timing-20261106.json), 원시 진단 자료는 PC outputs에 보관한다.

후속 [중복 경로 검사 제거 후보](display-374-record-read-cost-20261106.md)를 로컬에서 구현·검증했다.
실보드 서비스는 이 후속 후보로 바꾸지 않았다.
