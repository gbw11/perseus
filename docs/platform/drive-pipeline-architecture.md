# Xenova 자율·수동주행 파이프라인 설계 — Jetson·Raspberry Pi·ESP32

**문서 ID:** XENOVA-DRIVE-ARCH-1.0  
**버전:** 1.1 · 설계 기준본  
**작성일:** 2026-10-28  
**개정일:** 2026-10-29  
**대상:** Jetson 인지·지도·영상, Raspberry Pi/Xen/Zephyr A·B 자율·수동 앱, dom0 Gateway·복구 연계, ESP32 구동·피드백  
**목적:** 구현 담당자들이 같은 책임·데이터·실행·실패·수락 기준으로 작업할 수 있도록, 지금까지의 대화에서 채택한 방향을 하나로 고정한다.

**1.1 개정:** MANUAL의 과거 입력 복원과 현재 입력 인계를 구분하고, 모드 전환·동일 MANUAL A/B 승계의 중립·재조작 정책을 확정했다. 보존 지도 재전송과 관측 위장 재생을 구분하고 발행 빈도의 단위를 명확히 했다. 문서 revision은 MQTT wire schema 버전과 별도로 관리한다.

이 문서는 Jetson의 환경 인식부터 Raspberry Pi의 자율·수동주행 앱과 Gateway를 거쳐 ESP32의 장치 구동에 이르는 주행 파이프라인의 구성과 동작을 정의한다.

> **Jetson이 환경을 계산하고, Raspberry Pi의 앱이 주행을 결정하며, ESP32가 실제 장치를 구동한다.**  
> **지도는 정식 바이너리 전체 snapshot으로 전달한다.**  
> **자율 제어와 수동 제어는 별개의 앱으로 동작한다.**  
> **Jetson과 Pi에 MQTT broker를 하나씩 두되 bridge는 사용하지 않는다.**

영상은 HTTP GET으로 제공한다.

이 문서는 **설계의 통합본**이다. 제품 구현 완료 보고, 현시점 저장소 전체 감사, 실보드 성능 보증, 차량 안전 인증 또는 배포 승인서가 아니다. 기존 소스에서 확인한 사실과 새로운 설계 목표를 구분한다. 미확정인 상한·주기·차량 제원은 [20절](#s20)에서 공동 계약, 초기 시험·보정값, 후순위 기능으로 나누고 결정 시점과 근거를 정리했다.

### 1.3 이전 제안과 충돌할 때 적용할 정리

| 이전 대화의 제안 | 이 문서의 최종 처리 |
|---|---|
| Pi의 A/B가 각각 원 센서로 국소 지도까지 구축 | **폐기.** Jetson이 지도 작성자이고 A/B는 지도 소비자다 |
| broker 하나를 유지 | **변경.** Jetson·Pi에 하나씩 둔다. 다만 연결·처리·버퍼 분리 원칙은 그대로 유지한다 |
| 필요하면 broker bridge로 Spring에 중계 | **이번 범위에서 제외.** Spring이 필요한 broker를 직접 구독한다 |
| JSON으로 먼저 시험한 뒤 바이너리 전환 | **폐기.** 새 지도 계약부터 바이너리로 만든다 |
| WebRTC를 기본 영상 전송으로 사용 | **변경.** HTTP GET/MJPEG를 기본으로 채택한다 |
| 하나의 계산 loop에서 AUTO 다음 MANUAL을 직렬 실행 | **변경 대상.** AUTO의 계산 완료를 MANUAL이 기다리지 않는다 |
| 수동 중에도 자율 전체 계산을 무조건 계속 수행 | **변경.** 입력·상태·예산이 충족될 때 실제 준비 계산을 수행한다 |
| 두 앱이면 모든 오류에서 독립 재부팅 가능 | **변경.** 앱 재초기화로 해결할 문제는 해당 앱을 재초기화하고, VM 복구가 필요한 문제는 VM 단위로 복구한다 |

이 표는 이전 자료를 조용히 덮어쓰는 대신, 최신 결정을 적용한 지점을 드러내기 위한 것이다. 과거 보고서의 당시 구현·실패·통과 기록은 보존한다. [U]

## 2. 운용 범위·하드웨어 전제·용어

### 2.1 대상 주행 기능

목표는 **차량 형상과 운동 제약을 고려하고, Jetson이 갱신하는 국소 도로·점유 지도를 사용해 제한된 도로 환경에서 저속으로 장애물을 우회한 뒤 원래 경로로 복귀하는 주행**이다. 우회 중 VM 장애가 발생해도 준비된 다른 실행이 필요한 주행 문맥을 가지고 이어받는 것을 검증한다.

시연은 정적 장애물 중심의 제한된 도로 환경을 대상으로 한다. 현재 시야 밖의 구간도 보존 지도를 이용해 경로 계획과 주행에 활용한다. 새로 관측한 환경 변화는 지도에 반영한다.

범용 SLAM, 복잡한 교차로·갈림길, 고속 주행, 완전한 동적 객체 예측, 공도 운행의 안전 보장은 이번 설계의 확정 지원 범위가 아니다. 움직이는 물체를 관측하면 현재 경로의 사용을 제한할 수 있지만, 그 미래 궤적을 안전하게 예측한다고 주장하지 않는다.

트랙의 폭·곡률·장애물 종류·센서 가시 범위·최대 속도는 **운용 설계 범위**로 문서화해야 한다. 도로 형상 예측이나 외삽은 공간이 비어 있다는 증거가 아니다.

### 2.2 장비·소프트웨어 환경

| 장비·연결 | 구성 |
|---|---|
| Raspberry Pi 4 | Xen·Zephyr A/B·dom0 Gateway |
| Jetson Nano B01 | 센서 처리·지도·영상 |
| ESP32 | ESP32 DevKitC WROOM-32D V4 CP2102 개발보드 [CMODULE-40]. 모터·조향 제어와 로컬 차량 피드백 수집. IMU 미내장 |
| 카메라 | Luxonis OAK-D-Lite (Fixed-Focus), DepthAI 3D Camera |
| 카메라 내장 IMU | OAK-D-Lite의 BMI270 6축 IMU. 가속도 3축·각속도 3축 |
| ToF 거리 센서 | 2개 |
| 차체·구동 | 애커만 섀시·전륜 조향 서보. 구매 키트의 Double layer Chassis 구성 |
| 구동 모터 엔코더 | 키트의 듀얼 인코더 모터. 모터 회전을 수집해 차량 속도·이동거리를 계산하는 데 사용 |
| 실제 조향각 피드백 | 외부에서 실제 각도를 읽는 센서·인터페이스는 미확인. 조향 서보와 구동 모터 엔코더를 구분 |
| Pi–Jetson | Ethernet |
| Pi–ESP32 | USB 시리얼 |

차체 치수·조향 한계·엔코더 배율·제동 특성, 센서별 설치 위치·방향·품질·갱신 주기는 차량·센서 설정으로 관리한다. 차량 키트는 [듀얼 인코더 모터·전륜 서보 조향 애커만 섀시](https://ko.aliexpress.com/item/1005007778585588.html), ESP32는 [CMODULE-40 개발보드](https://www.devicemart.co.kr/goods/view?no=15313999)를 기준으로 한다.

카메라는 [Luxonis OAK-D-Lite](https://docs.luxonis.com/hardware/products/OAK-D%20Lite)의 Fixed-Focus 구성을 사용한다. 공식 사양의 BMI270 IMU는 카메라에 내장되어 있으며, 일부 초기 Kickstarter 제품에는 없다. 현재 배치에서 카메라 IMU는 Jetson을 통해 사용하므로 Jetson 없이 동작해야 하는 MANUAL·Pi 내부 차량 피드백의 필수 입력으로 삼지 않는다. IMU의 차체 운동과 구동 엔코더의 모터 회전은 실제 전륜 조향각과 구분한다. [VL53L5CX](https://www.st.com/en/imaging-and-photonics-solutions/vl53l5cx.html)는 ToF 거리 센서다.

Jetson 소프트웨어는 다음 기준을 사용해 설치 버전을 정한다.

| 항목 | 기준 |
|---|---|
| Jetson Nano용 공식 JetPack 4 계열 최종 릴리스 | 4.6.6 |
| 해당 Jetson Linux (L4T) | 32.7.6 |
| 공식 microSD 시작 이미지 | JetPack 4.6.1 / L4T 32.7.1 |
| 기반 운영체제 | Ubuntu 18.04 |
| Linux Kernel | 4.9 |
| CUDA | 10.2 |
| DepthAI | JetPack·ARM64·Python 호환 조합을 확인한 뒤 버전 고정 |
| 누적 지도 저장 | SQLite 검토안 |

[JetPack 4.6.6](https://developer.nvidia.com/jetpack-sdk-466)은 [L4T 32.7.6](https://developer.nvidia.com/embedded/linux-tegra-r3276)에 대응한다. [JetPack 4.6.1 microSD 이미지](https://developer.nvidia.com/embedded/jetpack-sdk-461)는 L4T 32.7.1을 포함하므로, 이를 기록한 직후의 설치본을 4.6.6/32.7.6으로 취급하지 않는다. 최종 설치 버전과 사용할 DepthAI 버전·호환 조합은 Jetson 설치 구성에서 고정한다.

| `ReferencePath` | 원래 도로를 추종하고 우회 후 복귀할 기준 경로. 임시 우회 경로와 다름 |
| `PlannedPath` | 현재 차량 상태에서 실행 가능한 후보를 검증·선택한 경로 |
| `ManeuverIntent` | 우회 방향·진행 단계·복귀 목표 같은 최소 주행 의도. 지도나 제어기 메모리 전체가 아님 |
| `READY` | 현재 기능을 수행·인계할 근거가 충족됐다는 보고. 구체적인 대기·활성화·실행 근거는 9.6절에서 구분하며 출력 허가나 장치 적용을 뜻하지 않음 |
| `Active / Standby` | 현재 권한을 가진 VM과 후보 VM. AUTO/MANUAL과 별개의 축 |
| 앱 재초기화 | 해당 앱의 소유 작업·상태·자원을 안전하게 정리하고 새 앱 실행으로 준비하는 지원 절차 |
| VM 복구 | Worker와 하위 Manager가 원 작업·의도·신원을 지키며 게스트 실행을 복구하는 절차 |
| 안전 정지 | 명령·권한 사용 제한과 장치의 정의된 정지 동작. 소프트웨어가 0을 보냈다는 사실만으로 물리 정지 완료를 뜻하지 않음 |

**broker J와 broker P 사이에는 bridge가 없다.** 그림의 이동량 발행은 Pi의 원천 생산자가 Jetson broker에 직접 접속하는 애플리케이션 통신이다. 다른 broker에서 임의 토픽을 받아 복제하는 범용 relay도 만들지 않는다.

### 3.2 흐름별 생산자·소비자

| ID | 자료 | 생산자 | 전달 경로 | 소비자·역할 |
|---|---|---|---|---|
| IF-01 | 바이너리 전체 국소 지도·도로 모델 | Jetson mapper | broker J | A/B AUTO의 지도 수신부 |
| IF-02 | 인지 진행·센서·Jetson 상태/오류 | Jetson 상태 생산자 | broker J | 필요한 AUTO/감시/관제. 각자 직접 구독 |
| IF-03 | 실제 이동량·공통 odom·차량 표본 | Pi의 기존 ESP32 피드백/상태 생산자 | broker J | Jetson mapper. 필요한 소비자만 직접 구독 |
| IF-04 | Pi 내부의 즉시 차량·장치 상태 | 같은 Pi 상태 생산자 | 기존 Pi 내부 경로 / broker P의 해당 계약 | Gateway·AUTO·MANUAL. broker J를 거치지 않음 |
| IF-05 | 수동 입력·입력 세션 | Spring/입력 소유자 | broker P | A/B MANUAL |
| IF-06 | control·generation·owner·모드 | Gateway | broker P | A/B 앱·관제 |
| IF-07 | 명령 후보·앱 준비·실제 진행 | 각 앱 | broker P | Gateway·필요한 Worker/관제 |
| IF-08 | VM 관리·복구·기존 Telemetry | 기존 생산자 | broker P 및 기존 관리 API | 기존 소비자 |
| IF-09 | 구동 명령·적용/센서 피드백 | Gateway ↔ ESP32 | USB 시리얼 | 각 단일 I/O 소유자 |
| IF-10 | 카메라 영상·정지 화면 | Jetson 영상 서버 | HTTP GET | 브라우저 |
| IF-11 | 인계할 최소 maneuver 문맥 | Active AUTO 제안, Gateway 권한 결합 | broker P의 별도 합의 계약 | A/B AUTO |

IF-03과 IF-04가 같은 원 표본을 사용해도 **출처·원 시각·순번을 유지**한다. 같은 생산자가 서로 다른 목적지에 자료를 제공하는 것이지, 두 broker의 전체 토픽을 동기화하는 것이 아니다. Jetson 연결 대기·재접속은 로컬 IF-04를 막지 않는다. 구체적인 신규 토픽과 이중 목적지 연결 위치는 기존 상태 생산자 소유자가 구현 전 확정한다.

### 3.3 물리 경로와 가용성의 한계

외부 Jetson broker에 직접 연결해도 Zephyr의 물리 NIC 접근은 기존 dom0 네트워크를 거친다. 두 broker는 역할·부하를 분산하지만 Pi/dom0·Xen·공유 전원·네트워크 의존성 전체를 제거하지 않는다.

Jetson과 Pi를 직결하고 Pi가 외부망 출구라면, HTTP 영상도 실제 패킷 경로에서 Pi를 거칠 수 있다. 이 문서는 스위치·추가 NIC·배선을 새로 채택하지 않는다. 현재 설치 경로에서 Jetson 주소의 도달성, 영상의 외부 경로, 공유 대역폭을 확인한다.

## 4. 책임·권한·출처·수명 경계

### 4.1 책임표

| 구성요소 | 맡을 일 | 맡기지 않을 일 |

| Spring/화면 | 현재 입력·재개 요청·상태 표시, 필요한 broker 직접 구독 | broker bridge 필수화, 표시 모드를 출력 허가로 추정 |

이 책임 분리는 기존 Worker 요청의 행동 소유권을 유지한다. [P1: W03~W04]

### 4.2 서로 대체할 수 없는 사실

```text
MQTT 연결/PUBACK ≠ 새 센서 관측 ≠ 새 계산 완료
계산 완료 ≠ 유효 결과 ≠ 기능 준비 ≠ 현재 owner ≠ 출력 허가
명령 시리얼 제출 ≠ ESP32 수락 ≠ 제어 출력 설정 ≠ 실제 차량 이동
VM 복구 COMPLETED ≠ 앱/지도/경로 준비 ≠ Standby 재합류
지도 snapshot 복원 ≠ 진행 중 maneuver 복원
같은 지도 수신 ≠ 독립적인 인지 검증
```

### 4.3 식별자의 교체 범위

| 식별자 | 수명·변경 의미 |
|---|---|
| `vm_id` | 등록 VM의 영구 UUID. A/B는 다르며 정상 VM 복구에서 유지 |
| `execution_id`, guest `boot_id` | 새 VM 실행·게스트 부팅에서 교체 |
| 앱 `app_instance_id` 또는 동등 문맥 | 해당 앱의 정당한 재초기화에서 교체. wire 표현은 기존 계약과 공동 개정 |
| v1/v2 publisher instance | 각 발행자 실행 수명. 앱 수명과 혼동하지 않음 |
| Jetson boot/mapper instance | Jetson·mapper 재시작 식별. 인증된 현재 생산자와 결합 |
| `frame_epoch` | 좌표 기준의 불연속 재설정. 순번 reset이나 rolling window 이동과 다름 |
| `map_epoch`, snapshot sequence | 지도 재구축과 동일 지도 수명 내 순번. 구체 명칭은 schema 단계에서 고정 |
| `maneuver_revision` | 우회·합류 의도 교체. 현재 권한 문맥과 결합 |
| control generation | Gateway가 발급하는 제어 문맥. map version과 별개 |
| ESP32 boot/session/counter | 시리얼 수락·재부팅·중복 방지 문맥. MQTT seq와 그대로 같지 않음 |

저장 지도를 복원해 이어서 사용하는 것과 Jetson·mapper가 새 실행으로 시작하는 것은 구분한다. 새 관측과 저장 지도의 정합은 지도·위치 대응을 판단하는 근거이며, 이전 boot/instance를 새 실행에 재사용하는 근거가 아니다.

**정상적으로 교체된 새 실행을 예전 ID와 다르다는 이유로 거절하지 않는다.** 반대로 처음 보는 ID라는 이유만으로 신뢰하지도 않는다. 현재 Manager 실행·receipt·binding·정당한 앱 교체 근거로 확인된 새 신원만 수락하고, 이전 실행의 지연 자료는 현재 준비·출력에 반영하지 않는다.

## 5. 두 MQTT broker와 연결·구독 정책

### 5.1 broker 배치

| 항목 | Jetson broker J | Pi broker P |
|---|---|---|
| 주된 자료 | 지도·인지·Jetson 상태·지도 작성용 차량 이동량 | 주행 제어·수동 입력·명령·준비·VM 관리·복구·기존 Telemetry |
| 지도 본문 | 제공 | 재발행·복제하지 않음 |
| control의 권위 원본 | 없음 | 기존 Gateway가 소유. retained는 배포 사본 |
| 외부 소비자 | 필요한 client가 직접 접속 | 기존 client가 직접 접속 |
| broker 상호 연결 | **bridge 없음** | **bridge 없음** |
| 장애 시 자동 역할 승계 | 하지 않음 | 하지 않음 |

이 선택은 broker 하나의 처리량이 부족하다고 입증했기 때문이 아니다. **Jetson 데이터의 생산·배포 책임을 Jetson에 두고, Pi의 주행 제어·관리 책임과 분리하기 위한 결정**이다.

### 5.2 client/socket·작업 분리

각 VM에는 논리적으로 다음 경로가 있다. 필요한 client 수는 서비스별 구독에 맞춰 정하며, 모든 역할에 무조건 하나씩 더 만들지는 않는다.

| 경로 | 조건 |
|---|---|
| 지도 수신 | broker J 전용 client/socket·소유 작업·전용 고정 버퍼. 큰 payload와 decode를 제어 경로에서 처리하지 않음 |
| Jetson 소형 상태 | 지도 정체와 독립적으로 읽어야 하는 소비자는 별도 client/처리 경로. 전체 지도 구독 불필요 |
| 주행 제어 | broker P의 작은 control·입력·준비·명령. 지도 lock·decode·압축 작업 없음 |
| 상세 진단 | 기존 v2 분리·제한된 수집/발행. 실패가 정상 v1의 새 필수조건이 아님 |

같은 MQTT client의 I/O·parser·latest storage는 한 소유자가 관리한다. 기존 C parser가 내부 static 상태를 갖는다면 다중 수신 스레드가 같은 parser를 동시에 호출하지 않도록 재진입성을 확보하거나 소유 경계를 유지해야 한다. 데이터 사본과 handle의 유효 수명을 명시한다. [B1]

### 5.3 전달 정책

MQTT는 binary payload를 운반할 수 있지만 QoS는 deadline·최신성·장치 적용을 보장하지 않는다. TCP는 순서 있는 바이트 스트림이므로 QoS 0에도 TCP 재전송·버퍼 대기가 남는다. [R1][R2]

| 자료 | 기본 정책 | 보존할 의미 |
|---|---|---|
| 국소 지도 전체 snapshot | QoS 0, retain false, clean session, bounded latest-only | 현재 위치와 관측에 맞는 국소 지도를 주기적으로 제공. 새 소비자는 다음 완전한 자료로 합류하고, 기존 소비자는 새 지도를 채택하기 전까지 직전 지도를 보유 |
| 새 인지·차량 주기 표본 | QoS 0, retain false, 제한된 최신값 | 원 측정 시각·원 표본 ID 유지 |
| 주기 readiness·명령 | 기존 제어 프로필의 QoS·크기·신선도 의미 보존 | 수신만으로 계산 진행을 새로 만들지 않음 |
| Jetson의 저빈도 명시적 상태 전이 | 안정된 사건 ID를 가진 제한된 사건. QoS 1 사용 여부는 상태 계약에서 확정 | ACK를 원인 해결·소비자 반영으로 해석하지 않음 |
| control·관리 요청·복구 사건 | 기존 계약 유지 | 기존 멱등성·원 ID·retained 원본 구분을 바이너리 전환과 섞지 않음 |
| 설정·보정 정보 | 버전이 있는 배포 설정. 선택적 retained 사본은 운영 계약에 따름 | 현재 준비의 증거로 사용하지 않음 |

Jetson은 누적 지도를 갱신·저장하면서 현재 차량 위치와 관측에 맞는 국소 snapshot을 계속 구성해 보낸다. 지도 내용이 같더라도 정한 주기로 완전한 snapshot을 제공하며, 재발행할 때 과거 관측 시각을 새것으로 바꾸지 않는다. 발행 주기·지도 범위·최대 크기는 함께 정한다. Pi는 수신·검증을 마친 새 지도를 채택하며, 그 전에는 직전에 채택한 지도를 유지한다.

주기 stream의 **아직 보내지 않은 후보**는 최신값으로 교체한다. 이미 TCP로 제출한 바이트는 latest slot 교체로 사라지지 않는다. 수신자는 늦은 자료를 각 자료의 계약에 따라 처리해야 한다.

부분 수신·decode 실패 시, 정한 시간·바이트 예산 안에 현재 MQTT payload를 정확하게 소비하거나 **해당 지도 연결만** 종료하고 회복한다. 메시지 중간을 다음 메시지로 해석하지 않는다. 무제한 drain·retry·대기 금지다. 지도 연결 재시작이 Pi 제어 연결을 동시에 초기화하거나 직전 채택 지도를 삭제해서는 안 된다.

### 5.4 토픽·ACL·인증

다음은 **논리 stream ID**이며 현재 배포 토픽 이름이 아니다. 실제 topic prefix·schema package·ACL은 생산자와 소비자가 공동 확정한다. 상세 Telemetry의 v2 namespace와 충돌하는 이름을 임의로 사용하지 않는다.

| 논리 stream | 발행 권한 | 구독 권한 |
|---|---|---|
| `WorldSnapshot` | 등록된 Jetson mapper | 등록 A/B AUTO, 필요 시 별도 관제용 reader |
| `PerceptionHealth` | 등록된 Jetson 상태 생산자 | 필요한 AUTO/Worker/관제 |
| `VehicleOdometry` | 등록된 Pi 원천 생산자 | Jetson mapper와 합의된 reader |
| `VehicleStateLocal` | 기존 Pi 장치 상태 생산자 | Pi의 앱·Gateway·관제 |
| `DriveCommand`·`AppReadiness` | 현재 허용된 VM/app | Gateway·합의된 감시자 |
| `ControlContext`·권한에 묶인 maneuver 문맥 | Gateway 또는 기존 단일 권한 경로 | A/B 앱·관제 |

두 broker의 계정·접속 자격·허용 topic을 각각 설치한다. 모든 소비자에게 `#` 구독을 기본 부여하지 않는다. 같은 VM의 서로 다른 socket은 서로 다른 client ID를 사용하되 VM·실행·역할과 연결한다.

인증자료는 이미지·Git·공개 로그에 넣지 않는다. 네트워크 암호화·인증서/키 공급·회전·허용 listener는 실제 위협 모델과 고정 빌드 지원에 맞춰 확정한다. username/password만으로 네트워크 도청 보호까지 생기지는 않는다. [R3]

**Spring 때문에 bridge를 추가하지 않는다.** Spring이 Jetson 상태가 필요하면 전용 client로 broker J를 구독한다. 지도 UI가 필요하다는 이유로 Worker·Gateway까지 원 지도 전체를 받게 만들지 않는다.

## 6. 정식 바이너리 데이터 계약

### 6.1 형식 결정

새 지도 계약의 기본 형식은 **Protocol Buffers**, Jetson Python과 Zephyr C가 같은 `.proto`를 사용하며 Zephyr는 **nanopb**를 사용한다. `.options`의 최대 길이·최대 개수와 고정 풀을 함께 사용한다. Nanopb의 정적 field bound와 Zephyr 빌드 연동은 공식 문서에 근거한다. [R4][R5]

전송은 **무압축 전체 snapshot 하나를 MQTT PUBLISH 하나에 담는 방식**을 기본으로 한다. TCP의 내부 분할은 애플리케이션의 지도 조각 프로토콜이 아니다. 임의 delta·지도 조각 재조립·압축·영속 replay를 처음부터 추가하지 않는다.

**바이너리를 Base64 JSON에 감싸거나 C 구조체 메모리를 그대로 전송하지 않는다.** 디버깅용 JSON 변환기는 만들 수 있지만 런타임의 병행 원본이나 기본 wire 경로로 사용하지 않는다.

기존 Pi v1 JSON·v2 Telemetry 전체를 이번 작업에서 강제로 Protobuf로 바꾸는 것은 아니다. **바이너리 전환의 확정 범위는 새 지도 계약**이다. Jetson 상태·이동량도 같은 schema 계열로 정의하는 상세안을 권하지만, 새 소형 stream의 정확한 필드·코덱은 양측 계약으로 고정한다. 기존 소비자의 호환성을 조용히 바꾸지 않는다.

### 6.2 `WorldSnapshot` 논리 필드

아래는 **필수 의미의 명세**다. 숫자 field tag·정수 폭·enum 값·단위 축약·최대 길이는 `.proto`와 함께 확정해야 한다. 현재 wire API를 그대로 복사한 표가 아니다.

| 묶음 | 필수 의미 |
|---|---|
| 계약 | schema major/minor 또는 동등 버전, 지원해야 할 의미/기능, producer의 모델/보정/생성 설정 식별 |
| 출처 | vehicle/device ID, Jetson boot, mapper instance, map epoch, snapshot sequence |
| 좌표 | frame ID·frame epoch, 지도 원점·회전 기준, 해상도·가로/세로 셀 수, cell indexing 규칙 |
| 차량 위치 기준 | 해당 snapshot의 지도 좌표계로 표현한 차량 위치·방향, 그 기준 시각과 대응 Pi 이동 표본·odom epoch. 지도 원점과 차량 위치를 구분 |
| 시간 | snapshot 기준 시각, 각 원 관측의 나이를 해석할 시계 영역, 처리 완료·발행 시각, 시계 품질/불확실성 |
| 공간 | 점유/비용 cell 배열, 관측·미관측·만료 의미, 필요한 cell/구간별 관측 나이 |
| 도로 | road/reference ID·revision, 중심선·좌우 경계의 제한된 점열, 실제 관측/보간/외삽 구분과 유효 구간 |
| 운동·형상 설정 | vehicle-model/footprint/calibration/inflation policy 식별. 이미 적용된 여유를 명시 |
| 완전성 | payload와 배열의 길이, 배열별 의미, 전체 완전 snapshot 여부, 범위 제한·잘림·원천 부족의 명시 |

`bytes` 배열을 쓰더라도 row/column 순서, byte ordering이 필요한 다바이트 cell, 비용 범위, sentinel 값, 길이 조건을 문서화한다. `width × height` 계산은 overflow를 검사한다. 예를 들어 “셀당 3바이트”는 비용·유효성·나이를 표현하는 **예산 계산 예시**이지 확정 encoding이 아니다.

시각·출처 필수값의 미제공을 0 또는 default enum으로 정상 처리하지 않는다. Protobuf decoding 성공은 의미 검증 성공이 아니다. 알려지지 않은 major·필수 기능은 거절하고, 호환 optional 확장은 정의한 정책에 따라 다룬다. field 번호 재사용·단위 변경·enum 의미 변경은 무호환 변경으로 취급한다.

### 6.3 snapshot의 불변 조건

| ID | 불변 조건 |
|---|---|
| MAP-01 | 배열·원점·해상도·도로 모델·출처는 같은 snapshot에 속한다 |
| MAP-02 | 지도 밖, unknown, invalid와 유효 기간이 정해진 관측의 expired를 임의로 통과 가능한 free로 바꾸지 않는다. 보존 지도의 재관측 부재를 자동 expired로 처리하지 않는다 |
| MAP-03 | Jetson의 재발행 시각은 과거 cell 관측 시각을 새로 만들지 않는다 |
| MAP-04 | 객체 미검출·깊이 무효·ToF out-of-range는 그 자체로 공간 전체의 free 증거가 아니다 |
| MAP-05 | 추정된 도로 중심선은 주변 장애물 부재 증거가 아니다 |
| MAP-06 | 지도에 적용한 장애물 확장과 Pi footprint 여유를 이중 적용하거나 누락하지 않는다 |
| MAP-07 | 과거 mapper/epoch/sequence의 지연 자료는 현재 지도를 rollback하지 않는다 |
| MAP-08 | 새 지도 수신·검증 중이거나 새 지도가 거절돼도 직전 채택 지도를 보유한다. 실시간 입력·관측·명령에 정해진 유효 기간은 이 보유로 연장하지 않는다 |
| MAP-09 | source·geometry·time·config 검증을 마친 전체 묶음만 atomic하게 게시한다 |
| MAP-10 | 지도 수신만으로 앱 READY·Active·AUTO 재개를 만들지 않는다 |

입력·인지 진행·지도 갱신·영구 저장·지도 전달·Pi의 지도 채택·명령의 유효성은 각자의 계약을 따른다. 보존 지도의 도로·정적 장애물 정보와 현재 센서 관측의 신선도를 구분하며, 보존 지도는 재관측하지 않았다는 이유만으로 자동 만료시키지 않는다. Pi가 직전 지도를 보유하는 목적은 새 지도를 기다리는 동안의 경로 유지와 통신 단절 시 안전 정지에 사용하는 것이다. Jetson 중단 시 남은 국소 지도로 안전 정지한 뒤 MANUAL로 전환하는 정책은 유지한다.

unknown·rolling window·footprint를 분리하는 환경 표현은 Costmap 2D를 참고한다. 구체 cell encoding과 센서의 공간 유효성은 Xenova의 별도 계약이다. [R6]

### 6.4 제한된 수신·교체 절차

```text
MQTT 길이/토픽/연결 문맥 확인
→ 고정 byte 상한 안에서 수신(원 수신 시작·완료 시각 보존)
→ 비활성 수신/디코드 영역에서 해석
→ 출처·버전·배열·좌표·시각·도로·설정 검증
→ 완전한 immutable snapshot으로 게시·새 지도 채택
→ 소비자의 사용이 끝난 이전 buffer만 회수
```

새 지도의 수신·검증이 끝날 때까지 직전 채택 snapshot을 유지한다. 새 지도 검증 실패나 통신 단절만으로 이 snapshot을 비우지 않는다. 생산 중·검증 중·소비 중인 영역을 구별한다. 실제 buffer 수는 동시 reader와 최대 체류 시간을 계산해 고정한다. **단순 double buffer라서 무조건 안전하다고 보지 않는다.** planner가 오래 참조하는 동안 새 수신이 진행돼도 사용 중인 영역을 덮지 않아야 한다.

빈 buffer가 없으면 신규 후보를 제한적으로 버리거나 이전 미게시 후보를 교체한다. 사용 중인 영역 강제 회수, planner 완료 무제한 대기, MANUAL용 메모리 빌려 쓰기는 금지한다. 계획 작업의 참조가 종료되지 않으면 수명주기 실패로 처리한다.

## 7. 좌표·시간·신선도 계약

### 7.1 좌표·단위

기준은 **앞 x, 왼쪽 y, 위 z**, 길이 m, 속도 m/s, 각도 rad다. `steer_rad`는 차량 yaw나 yaw rate가 아니라 **애커만 자전거 모델의 가상 전륜 조향각**으로 정의하는 상세안을 사용한다. 실제 서보 pulse 변환은 ESP32의 보정 프로필에 둔다. 좌표 관례는 REP-103을 참고한다. [R7]

`base_link`는 차체 고정 좌표계이며 계획/추종의 기준점은 후륜 축 중심 또는 별도 지정점으로 고정한다. `odom`은 Pi가 로컬 차량 피드백으로 유지하는 주행 중의 연속적인 이동 기준이다. `map`은 Jetson이 보존하는 지도의 좌표 기준이며, Jetson은 현재 관측·차량 이동 정보와 저장 지도의 정합으로 `map`과 `odom`의 관계를 관리한다. 장기 드리프트가 있을 수 있는 `odom`을 저장 지도의 고정 기준으로 간주하지 않는다. REP-105의 구분을 적용한다. [R8]

Jetson은 Pi에서 받은 공통 odom을 사용해 관측을 같은 좌표계에 누적한다. 개념식은 다음과 같다.

\[
p^{odom}=T^{odom}_{base}(t_{capture})\,T^{base}_{sensor}\,p^{sensor}
\]

관측 시각의 자세를 사용하며, 수신 시각의 자세로 무조건 대체하지 않는다. 카메라 optical 축과 차체 축의 변환, ToF별 위치·방향·관측 구역은 calibration에 포함한다.

위 식은 관측을 공통 이동 기준으로 옮기는 단계다. Jetson은 확인한 `map`과 `odom`의 관계를 반영하여 보존 지도를 갱신하고, Pi가 국소 snapshot과 현재 차량 상태를 같은 기준으로 해석할 수 있게 한다. 각 관계의 실제 wire 표현은 좌표 계약에서 확정한다.

Jetson은 국소 지도를 구성할 때 그 지도 좌표계에서의 차량 위치·방향과 기준 시각을 함께 제공한다. 잘라낸 영역의 원점은 차량 위치를 대신하지 않는다. 위치에 대응하는 Pi 이동 표본·odom epoch를 연결하고, Pi는 그 표본 이후의 로컬 이동분을 반영해 현재 위치에서 경로를 계획·추종한다. 지도를 받는 순간의 차량 위치가 지도 구성 당시와 같다고 가정하거나 서로 다른 장치의 단조 시각을 직접 빼서 이동분을 만들지 않는다.

**snapshot 위치에서 현재 위치로의 연결.** \(T^A_B\)는 B 좌표를 A 좌표로 옮기는 변환이다. 지도 M, Pi odom O, 차체 B에 대해 snapshot이 참조한 Pi 표본을 \(t_s\)라고 하면, 같은 odom epoch와 채택한 지도 정합 아래에서 다음처럼 현재 위치를 구한다.

\[
T^M_B(t)=T^M_B(t_s)\left(T^O_B(t_s)\right)^{-1}T^O_B(t)
\]

여기서 \(t_s\)는 서로 다른 장치의 숫자가 우연히 같은 시각이 아니라 **snapshot이 지목한 Pi 이동 표본의 기준**이다. 그 표본이나 검증 가능한 보간 구간을 찾을 수 있어야 한다. odom 이력은 예상 지도 생성·전달·검증·승계 지연과 여유를 포함한 길이로 제한해 보존한다. 기준 표본이 없거나 epoch가 다르면 최신 표본으로 몰래 대체하지 않고 새 기준 자료를 요청하며, 현재 경로의 유지·정지는 별도 유효 조건으로 판단한다.

**위치 정합 보정의 교체.** 지도 좌표계의 교체, Pi odom의 재설정, 같은 지도 안에서의 `map↔odom` 보정은 다른 사건이다. 보정을 식별할 revision 또는 동등한 불변 문맥을 지도·path·차량 표본과 연결하고, 한 번의 계산에서 서로 다른 보정의 자료를 섞지 않는다. 기존 snapshot 식별자가 변환까지 유일하게 식별한다면 별도 공개 ID를 중복 추가할 필요는 없다. 작은 보정은 경로의 현재 유효성을 재검사해 채택하고, 허용 위치·각도 오차를 넘거나 다른 대응 후보로 바뀌면 해당 경로를 보류·재구성한다. 경계값은 차량·지도 시험으로 정한다. [R8]

계획은 map 기준으로 수행하고 빠른 추종은 채택한 변환으로 odom에 옮긴 경로를 사용하는 방식을 우선 검토한다. 이 경우 변환과 경로를 함께 교체하며, 수신 callback이 사용 중인 경로 좌표를 직접 수정하지 않는다. 이는 구현 상세안이며 실제 좌표 표현은 생산자·소비자 계약으로 확정한다.

Rolling window의 원점 이동은 `frame_epoch` 변경이 아니다. odom 기준이 실제로 재설정되거나 불연속적으로 변경되면 epoch를 바꾸고 옛 지도·경로·maneuver를 재검증한다. **Jetson 재시작만으로 Pi가 소유한 odom을 임의로 초기화하지 않는다.** mapper instance·map epoch와 odom epoch는 별개로 관리한다.

### 7.2 공통 차량 이동량의 생산

ESP32의 실제 encoder/차량 피드백을 기존 Pi I/O 소유자가 수신한다. Pi의 경량 상태 생산자가 동일 차량 model과 단일 odom epoch로 처리해 Jetson과 A/B가 같은 기준을 사용하도록 한다.

Pi는 `odom`과 차체의 관계를, Jetson은 보존 지도 정합에 따른 `map`과 `odom`의 관계를 소유한다. Pi의 로컬 차량 피드백 수집은 Jetson의 지도·영상·카메라 IMU 작업을 기다리지 않는다. 영상·관성 정보를 추가로 활용하더라도 같은 좌표 관계를 서로 다른 생산자가 동시에 권위 원본으로 발행하지 않는다.

명령 속도를 실제 속도로 적분하지 않는다. encoder reset/wrap·ESP32 재시작·수집 누락·미끄럼 가능성·측정되지 않은 조향각은 해당 품질·오차로 드러낸다. 필요한 현재 자세를 얻지 못하면 자율의 지도 사용을 제한한다.

### 7.3 시각 경계

| 시각 | 의미 |
|---|---|
| 센서 측정 시각 | 카메라 노출/프레임·ToF 측정의 원 시각 또는 정의된 측정 구간 |
| 처리 완료 시각 | 해당 입력으로 관측·지도를 실제 계산한 시점 |
| 발행 제출 시각 | MQTT에 자료를 제출한 시점 |
| 수신 시작/완료 시각 | 수신 측에서 실제 bytes를 받은 로컬 단조 시각 |
| 사용 시각 | 계획·추종·Gateway·ESP32가 자료/명령을 적용 판단한 시점 |

서로 다른 장치·부팅의 monotonic 값을 그대로 빼지 않는다. UTC가 존재한다는 사실도 정확한 동기화 증거가 아니다. **시계 대응과 오차 상한을 확인하는 계약**이 필요하며, 대응을 검증하지 못한 시각을 이용해 음수 지연·가짜 신선도를 만들지 않는다. 편도 지연의 시계 오차 문제는 RFC 7679를 참고한다. [R9]

로컬 실행 deadline은 로컬 단조 시계를 사용한다. 원 관측→현재 사용의 나이는 검증된 시계 대응과 불확실성을 포함해 상한으로 다룬다. 구체 동기화 구현·갱신 주기·허용 오차는 [20절](#s20)의 출시 전 계약이다. 이를 결정하지 않은 채 수신 lease를 종단 나이 보장으로 사용하지 않는다.

시계 대응은 연결별로 확인한다.

| 연결 | 확인할 계약 |
|---|---|
| OAK↔Jetson | 원 device timestamp와 host에 대응된 timestamp를 구분. DepthAI의 `getTimestampDevice()`와 `getTimestamp()` 의미를 채택 버전에서 확인하고, 재연결·시계 대응 갱신·오차를 기록 [R28] |
| Jetson↔Pi | snapshot의 위치·관측 시각을 Pi 표본에 연결하는 방법, 대응 오차·갱신·만료. OAK↔Jetson 동기화로 대신하지 않음 |
| ESP32↔Pi | 실제 차량 표본 순번·시각과 Pi 수신 시각의 관계. 장치 재시작·누락·전달 지연을 구분 |

공식 자료의 표준편차·평균 오차를 모든 조건의 절대 오차 상한으로 사용하지 않는다. 시간 오차는 주행 오차 예산에 연결한다. 예를 들어 기준 속도 \(v_s\), 확인한 가속도 범위 \(a_{max}\), 시간 대응 오차 \(\epsilon_t\)가 있을 때 이동 오차의 검토식은 \(e_t\lesssim |v_s|\epsilon_t+\tfrac12 a_{max}\epsilon_t^2\)로 둘 수 있다. 회전 중 방향 오차와 차체 끝점의 이동도 별도로 포함한다. 이 식은 센서·미끄럼·모델 오차 전체를 보장하는 식이 아니며 실제 허용값은 위치·제동 시험과 함께 정한다.

### 7.4 지연된 정상 모양의 자료

새 MQTT seq, 최근 수신, 계속 증가하는 전송 수만으로 최신 관측이라고 인정하지 않는다. 다음은 각각 다른 진행이다.

```text
카메라 새 frame → 새 inference → 새 map update → 새 publish → 새 receive → 새 use
```

같은 장면이 실제로 다시 관측돼 같은 값을 내는 것은 정상일 수 있다. **같은 원 frame을 새 packet seq로 재생하는 것**과 구분한다. 관측이 없는 영역의 cell age는 재발행해도 증가해야 한다.

## 8. Jetson: 지도 작성과 HTTP 영상

### 8.1 인지·지도 pipeline

Jetson은 관측한 공간의 누적 지도를 유지·갱신하고 영구 저장한다. 차량 이동으로 현재 국소 지도 범위에서 벗어난 영역도 보관하여 재방문 시 활용하고, Jetson 재부팅 후에도 복원한다. Pi에 전달하는 snapshot은 이 지도와 현재 관측에서 구성한 필요한 영역의 국소 지도다.

환경 모델의 소유자는 Jetson이지만, OAK 내부에서 지원하는 처리를 Nano에서 중복 수행할 필요는 없다. 연산 배치의 우선안은 다음과 같다.

| 처리 | 우선 배치·확인할 조건 |
|---|---|
| 스테레오 깊이·지원 전처리 | OAK 내부. 해상도·FPS·깊이 설정과 다른 작업의 동시 사용 비용 확인 |
| 인지 추론 | OAK에서 지원하는 모델·연산·변환 도구가 맞으면 온디바이스 실행을 우선 비교. 부적합한 모델은 Jetson 배치를 검토 |
| MJPEG 인코딩 | OAK `VideoEncoder` 우선. 깊이·추론·인코더·USB 전송을 함께 사용한 처리량 확인 [R27] |
| 지도 누적·정합·저장·국소 영역 추출 | Jetson. OAK 출력과 ToF·Pi 차량 표본을 결합 |
| HTTP 영상 응답 | Jetson이 이미 인코딩된 JPEG를 제한된 사본/참조로 시청자에게 전달 |

JetPack·Python·DepthAI·OAK 펌웨어·모델·변환 도구를 하나의 설치 조합으로 고정한다. 참고 문서의 API 버전이 현재 Nano 설치 조합과 호환된다는 뜻은 아니며, 최신 SDK 예제를 그대로 설치 기준으로 삼지 않는다. OAK 내부 처리도 자원과 queue가 제한되므로 깊이·추론·영상의 동시 부하를 시험한다.

```text
센서 등록·보정 확인
→ 단일 수집 소유자(camera/ToF)
→ 원 표본 ID·측정 시각·유효성
→ 도로·깊이/거리·장애물 관측
→ 공통 odom의 관측 시점 자세로 변환
→ 누적 지도 갱신·변화 반영·관측 나이 관리
→ 필요한 영역의 rolling local map 구성·관측 범위 처리
→ 도로 기준 모델 유지·관측/외삽 구분
→ 완성 snapshot 검증·MQTT 발행
```

정적 장애물 중심의 시연에서는 보존 지도의 도로·장애물 정보를 시야 밖 영역의 주행 판단에도 활용한다. 현재 시야 밖이거나 재관측하지 못했다는 이유만으로 보존 지도 사용을 차단하지 않는다. 장애물의 이동·추가·제거를 새로 관측하면 지도에 반영한다. 저장·복원·재발행만으로 원 관측의 시각이나 품질을 새것으로 바꾸지 않는다. 복원한 지도를 주행에 사용하기 전에는 저장 지도의 좌표 기준과 현재 차량 위치·자세의 대응을 확인한다. 저장 범위·용량 상한·저장 시점·복원 검사와 위치 정합 방법은 세부 설계에서 정한다.

Jetson 내부에서는 보존 지도와 최근 변화 근거를 논리적으로 구분한다. 유효한 새 장애물은 통행 제약에 반영하고, 과거 장애물의 제거는 해당 공간을 실제로 관측한 free 근거로 판단한다. 단순 객체 미검출·가림·카메라 단절을 free 관측으로 바꾸지 않는다. 이 내부 구분을 위해 Pi에 모든 센서 이력을 추가 전송하지 않는다. 아직 보지 못한 새 장애물은 위치 오차 여유만으로 해결했다고 보지 않으며, 정적 장애물 중심의 시연 운용 조건으로 다룬다.

우선 지원할 지도 복원은 제자리 또는 비슷한 위치에서의 재시작이다. 재부팅 후 새로 관측해 만든 국소 지도를 저장 지도에 정합하여 기존 지도를 이어서 사용할 위치·방향을 찾는다. 약 95% 일치를 초기 판단값의 후보로 두되, 비교할 영역·관측 가능한 정보·위치와 방향의 정렬·허용 오차·점수 계산을 정의한 뒤 수치를 확정한다. 이 점수는 지도의 대응을 판단하는 값이며 VM·앱의 실행 신원을 대신하지 않는다.

복원 판정은 전체 격자의 단순 일치율 하나로 정하지 않는다. 실제 관측이 겹친 영역·특징의 정보량, 경계·도로의 위치/각도 잔차, 다른 유력 대응과의 구별, 같은 장소·근접 위치라는 사전조건, 남는 위치 불확실성을 함께 확인한다. 빈 공간이 많거나 도로 모양이 반복돼 높은 점수를 얻은 경우도 구분한다. 목표는 **허용 위치·각도 오차 안에서 근거 있는 대응을 찾는 것**이며, 95%는 이 의미가 정의된 뒤 평가할 후보값이다.

정합의 참고는 Olson의 *Real-Time Correlative Scan Matching*으로 추가한다. 제한된 평면 이동·회전 범위에서 대응을 찾고 다중 해상도로 탐색 비용을 줄이는 원리를 적용한다. 원 논문은 2D LiDAR를 대상으로 하므로 OAK depth의 평면 투영·유효 거리·높이 선택·좁은 시야의 모호성은 Jetson 연결부에서 검증한다. 이 선택이 전역 재위치 인식이나 전체 SLAM 이식을 뜻하지는 않는다. [R25]

장비를 임의의 다른 위치로 옮긴 뒤 현재 위치를 자동으로 찾는 기능과 QR 등 인쇄 표식을 이용한 위치 재인식은 후순위다. 시연에서는 사용자가 지도 저장소를 명시적으로 초기화해 새 지도를 구축하거나 비슷한 위치에서 다시 시작하는 운용을 우선한다. Jetson 누적 지도의 저장 방식은 SQLite를 검토한다. 초기화 대상은 Jetson의 지도 데이터이며, 기존 VM 신원·Authority·receipt·복구 기록은 포함하지 않는다.

지도 갱신·저장·위치 추정은 AUTO/MANUAL 모드와 별도의 작업으로 설계한다. Jetson이 정상 동작할 때 수동 이동 중에도 관측과 Pi의 차량 이동 정보를 이용해 지도를 수집·저장하고 위치를 갱신하는 편의 기능은 후순위로 둔다. MANUAL 앱은 이 지도를 구독·해석·보관하지 않는다. 같은 VM의 AUTO가 복귀 준비를 위해 지도를 수신·사용하는 것은 별도이며, 수동 지도 수집만을 위해 AUTO 전체 계획 계산을 강제하지 않는다.

라즈베리파이가 재해석해야 할 raw image나 고밀도 point cloud 대신 **경로 평가에 필요한 작은 환경 모델**을 제공한다. Jetson 내부의 모든 중간 계층을 전송하지 않는다. 차량 설정이 고정돼 있다면 거리장·기본 비용·보수적 장애물 확장도 Jetson에서 수행할 수 있으나, 선택한 실제 경로의 자세·속도·차체 충돌 검사는 Pi에 남긴다.

카메라 한 프레임과 ToF 표본을 무조건 같은 시각인 것처럼 합치지 않는다. sensor별 나이·부분 실패가 지도 어느 영역에 영향을 주는지 명시한다. ToF 2개의 관측 구역과 OAK-D-Lite의 실제 depth 유효 범위를 차량·센서 설정으로 관리한다. depth 없는 단안 관측에서 절대 거리를 증명할 근거가 부족하면 정확한 metric obstacle 형상을 만들어 넣지 않는다.

YOLO 등 모델은 의미 정보의 한 생산자일 수 있지만 특정 모델·JetPack 조합은 이 문서에서 채택 확정하지 않는다. 검출 confidence를 거리 오차·free-space 안전 확률로 직접 치환하지 않는다.

### 8.2 도로 모델과 원래 경로

Jetson은 도로 경계·중심선을 시간에 따라 유지할 수 있다. Pi가 수행하는 임시 우회로 때문에 **원래 복귀할 기준 도로**를 임시 경로로 덮어쓰지 않는다.

Reference ID와 revision을 제공하고, 가림·보간·외삽 구간과 사용 가능한 길이를 구별한다. 도로를 다시 관측했을 때 옛 경로와 대응이 불명확하면 새로운 road/frame 문맥으로 처리하거나 재정합을 요구한다. 이미 선택된 합류 목표를 좌표 숫자만 맞춰 억지로 유지하지 않는다.

### 8.3 Jetson 건강 보고

지도 갱신의 진행 상태와 보존 지도의 사용 가능 여부를 구분한다. 카메라 수집, ToF 수집, 인지 처리, 지도 갱신, 발행, 영상 인코딩도 각각 구분한다. HTTP 영상 출력이나 MQTT 송신 thread의 생존만으로 지도 갱신이 정상이라고 판단하지 않는다. 반대로 지도 갱신이 멈췄다는 사실만으로 보존 지도 전체를 사용할 수 없다고 판단하지 않는다. Jetson 중단 시에는 남은 국소 지도를 이용해 안전 정지한 뒤 MANUAL로 전환하는 정책을 따른다.

상태 생산자는 원 마지막 성공·현재 오류·지원 범위만 보고한다. 보드 전원 상실·완전 네트워크 단절은 스스로 정확한 최종 오류를 보낼 수 없으므로 수신측은 **관측 불가**를 별도로 처리한다. LWT를 쓰더라도 장치 고장 원인을 확정하는 증거로 보지 않는다.

### 8.4 HTTP GET 영상 제공

**GET 한 번의 장시간 응답으로 MJPEG 프레임을 제공**하는 것을 기본안으로 한다. 구현 후보는 FastAPI/Starlette의 `StreamingResponse`이며, `multipart/x-mixed-replace` 방식의 HTTP Motion JPEG 제공은 실제 카메라 인터페이스에도 사용된다. [R10][R11]

| 제안 endpoint | 응답·역할 |
|---|---|
| `GET /camera/stream.mjpg` | 제한된 품질·프레임률의 연속 JPEG. 접속별 bounded output |
| `GET /camera/snapshot.jpg` | 유효한 현재 프레임 1장. 오래된 프레임을 실시간처럼 반환하지 않음 |

endpoint 이름은 신규 상세안이다. 기존 Jetson 관리 REST 서버가 이미 있다고 가정하지 않는다. `requests`/`httpx`는 요청을 보내는 client이며 이 영상 GET을 제공할 server의 대체물이 아니다. 영상 제공을 위해 불필요한 범용 제어 API까지 추가하지 않는다.

영상 정책은 다음과 같다.

- 카메라를 한 번 소유하고 인지·영상 분기로 나눈다. HTTP 접속자마다 카메라·모델·MQTT publisher를 다시 초기화하지 않는다.
- OAK에서 인코딩한 JPEG를 한 번 받아 여러 시청자에게 공유하는 경로를 우선한다. 시청자마다 원 RGB를 다시 JPEG로 인코딩하지 않는다. host 인코딩이 필요하면 그 이유와 별도 CPU·queue 예산을 기록한다. [R27]
- 인지와 영상 분기에 각각 제한된 queue를 둔다. 시청자 지연·인코더 정체는 프레임 폐기/시청 연결 종료로 다루며 mapper를 기다리게 하지 않는다. GStreamer의 tee도 분기별 queue 분리를 요구한다. [R12]
- 해상도·JPEG 품질·FPS·동시 시청자·각 시청자의 최대 대기를 배포 프로필로 제한한다. CPU/대역폭이 부족하면 관제 영상부터 제한한다.
- 웹 시청자가 없어도 인지·지도는 계속 동작한다. 필요 없는 영상 인코딩은 독립적으로 줄일 수 있다.
- 촬영 시각·frame 진행·stream 상태를 UI에서 확인한다. `<img>`에 마지막 이미지가 남았다는 이유로 실시간으로 표시하지 않는다.
- 인증·도달성·HTTPS/동일 출처 또는 허용 proxy 경로를 실제 웹 배치에 맞춰 확정한다. URL에 장기 비밀을 싣지 않는다. proxy buffering·느린 연결이 지연을 키우는지 확인한다.
- MJPEG가 단순하다는 이유로 원격 운전 지연이 충분히 작다고 보장하지 않는다. 관제용 영상과 영상 의존 원격 수동운전은 별도 수락 범위다.

HTTP 영상은 Pi broker를 통과하지 않는다. 그러나 물리 외부망 경로가 Pi를 거친다면 NIC·routing 자원은 공유할 수 있다. 프로토콜 분리와 물리 장애 독립성을 혼동하지 않는다.

## 9. Zephyr A/B: 독립 실행 구조

### 9.1 두 VM의 구성

A/B는 같은 공통 firmware와 차량·schema·알고리즘 설정을 사용하되 UUID·MAC·인증·실행 신원·승인된 CPU 배치를 분리한다. **A=자율, B=수동으로 고정하지 않는다.** 두 VM 모두 AUTO/MANUAL을 수행할 수 있고 현재 모드와 Active VM 선택은 독립적이다.

AUTO↔MANUAL 모드 전환은 VM 복구·A/B 승계와 독립된 제어 기능이다. 운영자나 복구 정책은 필요할 때 이 기능에 전환을 요청하고, Gateway가 현재 문맥과 조건을 확인해 모드 전환을 수행한다. 모드는 VM 복구의 부수 효과로 바뀌지 않으며, 모드 전환 자체가 VM 재부팅·펌웨어 교체·CPU 배치 변경을 요구하지 않는다.

```text
각 Zephyr VM
 ├─ control I/O owner ── 현재 control·입력·로컬 차량 상태 snapshot
 ├─ map I/O owner ────── AUTO용 검증된 WorldSnapshot pool
 ├─ MANUAL worker ────── manual result slot
 ├─ AUTO planner ─────── immutable PlannedPath pool
 ├─ AUTO tracker ─────── auto result slot
 ├─ app supervisor ──── 각 작업의 수명·진행·기한·재초기화
 └─ diagnostic publisher ── 실제 원천의 제한된 보고
```

### 9.2 작업별 실행 계약

| 작업 | 기대 진행 | 금지되는 의존 |
|---|---|---|
| control I/O | 작은 메시지를 제한된 예산으로 수신/검증/발행. 각 result의 원 시각·문맥 보존 | 큰 지도 decode, 파일 저장, 경로 탐색, 앱 정상 상태 대신 생성 |
| map I/O/validator | 완전한 snapshot 검증·게시 또는 명시적 폐기 | 제어용 lock 장기 보유, 무제한 drain·할당 |
| MANUAL | 현재 입력에 대한 명령/중립/만료 정지 결과를 주기적으로 완료 | AUTO의 map/path/작업 종료 기다리기 |
| AUTO planner | 계획할 일이 있을 때 제한된 탐색을 완료/중단/실패로 종결 | 오래된 작업 무제한 계속, socket/Store/fsync 대기 |
| AUTO tracker | 현재 path·pose·근거리 유효성으로 명령/정지 결과 완료 | 새 plan 완성까지 blocking |
| app supervisor | 원 작업들의 실제 진행·기한·종료를 확인 | 자기 heartbeat로 하위 전부 정상 선언 |
| diagnostics | 선택된 계측·최신 평가 보고 | 필수 제어 buffer 소진, 반복 stack scan으로 제어 지연 |

**일이 없는 event-driven planner의 대기와, 주기 제어 작업의 미완료를 같은 timeout으로 감시하지 않는다.** “정지 결과 계산 완료”와 “진행할 경로 계획 성공”도 다르게 기록한다.

계산, 제어 상태전이, 오래 걸릴 수 있는 정리·I/O를 하나의 공용 실행 큐에 묶어 서로의 완료를 기다리게 하지 않는다. 각 작업은 9.4절의 수정 주체와 교환 경계를 따르며, 수신 큐를 모두 비울 때까지 처리하는 대신 건수·시간 예산 안에서 계산·감독·출력 판단으로 넘어간다. 실행 문맥을 나누는 것이 작업마다 새 thread를 하나씩 만든다는 뜻은 아니다.

Standby는 VM과 필요한 통신·감독 작업을 유지하면서 불필요한 계산 작업을 대기시킨다. 역할별 감시·동기화·승계 준비는 9.6절에서 구분한다.

### 9.3 우선순위·스케줄링

MANUAL과 활성 AUTO 추종·제어 통신은 planner·지도 후처리·상세 진단보다 필요한 실행 기회를 먼저 확보한다. 모든 compute 작업은 선점 가능한 일반 thread로 두며 긴 cooperative 실행·interrupt disable·scheduler lock을 계산 보호 수단으로 사용하지 않는다. Zephyr의 우선순위 스케줄링을 사용하되 구체 priority 숫자는 전체 I/O·진단 부하와 Xen vCPU 공급을 포함해 정한다. [R13]

낮은 우선순위의 AUTO busy loop는 선점될 수 있지만, 이것만으로 무한 CPU 소모가 허용되는 것은 아니다. supervisor가 원 deadline·반복 실패를 확인하고 지원 취소·격리로 연결한다. 커널 정체·interrupt disable·메모리 손상까지 같은 보호로 해결했다고 주장하지 않는다.

### 9.4 소유 자원 분리

AUTO 작업 영역, MANUAL 상태·출력 slot, 지도 pool, path pool, control transport, diagnostics에 각각 고정 상한과 소유자를 둔다. MANUAL 주기 경로는 동적 할당·큰 복사·disk I/O를 하지 않는다. AUTO 메모리가 고갈돼도 MANUAL 필수 자원을 침범하지 못하도록 reserve를 나눈다.

실시간 소비자는 **완성된 snapshot의 참조만 짧게 교체**한다. snapshot을 잡은 채 긴 shared mutex를 유지하지 않는다. 가변 중간 상태를 통신 callback이나 다른 앱이 직접 수정하지 않는다. stale handle·반납 중복·아직 사용 중인 buffer 회수는 오류로 처리한다.

| 대상 상태 | 수정 주체 | 짧게 보호할 변경 | 보호 구간 밖의 작업 | 포화·취소 시 처리 |
|---|---|---|---|---|
| 입력·로컬 차량 표본 | 해당 I/O 생산자 | 제한된 크기 복사 또는 완성 표본의 참조 확보·게시 | 수신·decode, 입력으로 수행하는 계산 | 최신 유효 후보를 제한해 보관. 원 시각·세션·만료를 갱신하지 않음 |
| 지도·path pool과 게시 참조 | 수신 validator·planner가 자기 후보 작성, 채택 지점이 현재 참조 변경 | buffer 예약, 참조 확보·반납, 현재 문맥 검증 후 게시 참조 교체 | 큰 배열 검증·탐색·직렬화 | 사용 중 buffer 회수·MANUAL reserve 차용 금지. 후보 폐기/거절을 기록하고 유한하게 종료 |
| 계산 작업·결과 slot | 계산 소유자가 자기 결과 작성, 앱별 감독이 사용 여부 결정 | 원 작업·수명·문맥 대조, 제한된 결과 게시·채택·철회 | 계산 callback, 메시지 직렬화·publish | 미송신 후보는 정한 최신값 정책으로 교체. 취소된 수명의 늦은 결과는 채택하지 않음 |
| 앱 lifecycle·정리 상태 | 해당 앱 감독 | 시작·취소·종료 단계와 원 요청·잔존 상태 갱신 | join·참조 회수 확인, 신뢰된 신원 승인 호출 | 수락한 요청을 최신값 교체로 버리지 않음. 잔존이면 재사용을 막고 다른 정상 앱 감시는 계속 |
| 모드·owner·전환·출력 자격 | Gateway | 현재 요청·generation·phase·허가 조건의 일관된 갱신 | 네트워크 응답·장치 ACK 대기, 외부 긴 작업 | 철회 필요 상태를 소유자가 보존. 일반 큐 포화가 철회를 유실시키지 않음 |
| 상태 사본·진단·부가 기록 | 각 생산자와 별도 소비자 | 불변 사본 참조 확보, 제한된 최근 값·처리 상태 교환 | 큰 직렬화·파일 기록·원자료 회수·느린 소비자 전달 | 부가 자료는 제한·폐기·누락 표시. 필수 요청·완료·철회를 조용히 버리지 않음 |

현재 참조를 읽는 것과 사용권을 확보하는 절차는 교체·회수와 동기화한다. 원자적 포인터 교체만으로 reader의 사용 수명이 보호된다고 보지 않는다. 계산 시작에 일관된 입력 묶음을 확보하고, 채택할 때 현재 호환성·유효성을 확인한다. revision이 갱신됐다는 이유만으로 무조건 재시작하여 정상 결과가 영원히 채택되지 않게 해서는 안 된다.

작은 공유 상태를 보호하는 동안 socket/Store 응답·장치 ACK·파일 동기화·join을 기다리지 않는다. 비대기 획득 실패를 무한 즉시 재시도로 바꾸지 않으며, 취소·출력 철회·중요 완료는 보존된 상태와 제한된 처리 예산으로 진행시킨다. 구체적인 mutex 이름·중첩 획득 순서·큐 상한은 실제 구현을 대조해 소스·모듈 설명서에 기록한다. 관리 작업의 긴 실행 소유권과의 구분은 15.4절을 따른다.

### 9.5 독립성의 보장 범위

일반 Zephyr supervisor thread는 하나의 address space에서 실행한다. thread 두 개·별도 heap만으로 memory fault가 격리되는 것은 아니다. userspace/memory domain은 실제 fixed ARM64 xenvm 지원·권한·syscall·성능 검증 뒤 채택할 수 있으며, supervisor code의 무제한 접근을 자동으로 막는다고 보지 않는다. [R14][R15]

이번 기본 목표는 **계산·대기·상태·자원 수명 결합을 줄여 지원되는 앱 오류에서 독립적으로 동작**하는 것이다. 임의의 메모리 파괴에서도 같은 VM의 MANUAL이 반드시 살아남는 보장은 별도 격리 설계 없이는 하지 않는다. 그러한 오류는 B 또는 전체 VM 복구로 대응할 수 있어야 한다.

### 9.6 실행 중인 VM에서 계산을 대기시키는 Standby

기본안은 **앱 수준 상태 동기화를 사용하는 warm standby**다. Standby의 Zephyr OS·통신·종료 처리·감독 작업은 실행하지만, planner와 비활성 주기 계산은 수행할 일이 없으면 이벤트나 대기 객체에서 잠든다. busy loop나 주기적인 가짜 계산으로 정상 상태를 증명하지 않는다. 대기는 VM 정지나 vCPU 제거를 뜻하지 않으며, 각 VM의 CPU 예약도 유지한다.

| 시점 | Standby가 할 일 | 확인하는 근거 |
|---|---|---|
| 평소 | 실행·대기 상태·오류를 가볍게 감시. 건강 증명용 경로 탐색·주행 계산 반복 없음 | 현재 실행 신원, 감독·통신 작업의 실제 진행, 예상한 대기 상태, 알려진 오류. 대기 중 계산 순번이 늘지 않는 것은 정상 |
| 새 동기화 자료 도착 | 상태 사본을 검증·적용하고 완료 여부를 확인 | 원 실행·제어 문맥, 상태 revision, 좌표·지도·설정 호환성, 마지막으로 완전히 적용한 사본 |
| 기동·재합류·승계 준비 | 필요한 초기화와 제한된 실제 실행 확인 | 모드별 필수 입력·내부 상태, 계산 결과 유효성, 자원·기한 조건. 이 단계에서도 출력 권한은 별도 |
| Active 전환 후 | 실제 주기 계산·기한·진행 검증 | 자기 실행에서 완료한 계산, 현재 입력, 명령 신선도, 주기·deadline. Standby의 대기 기준으로 감시하지 않음 |

**대기 감시·동기화 완료·계산 완료는 서로 다른 근거다.** 통신 heartbeat나 사본 적용 순번을 `loop_seq` 등 실제 계산 완료 순번으로 바꾸지 않는다. 평소의 가벼운 감시만으로 잠재된 계산 오류까지 없다고 증명할 수는 없으므로, 기동·재합류·승계 경계의 제한된 실행 확인을 둔다. 그 횟수·예산과 승계 지연은 실제 구현·측정으로 정한다.

준비·진행의 세 근거와 Gateway의 출력 허가를 다음처럼 구분한다. 이는 공통 의미를 정의한 것이며 새 wire enum 이름은 아니다.

| 근거 | 유효 조건 | 무효화·재확인 |
|---|---|---|
| 대기·동기화 자격 | 허용된 현재 실행이 정상 대기하고, 모드별 내부 상태·의존성·설정이 현재 문맥에서 유효 | 실행 교체·의존성 상실·부적합한 보정/경로·적용 실패 때 철회. 무업무 계산 순번의 정지만으로 철회하지 않음 |
| 활성화 준비 확인 | 승계 대상 실행이 새 제어 문맥을 적용하고 현재 pose·필수 입력으로 제한된 실제 계산·기한·결과를 확인 | 이전 실행·이전 전환의 확인을 재사용하지 않음. 확인 중 입력·상태·기한이 무효가 되면 출력 허가 보류 |
| 활성 실행 진행 | 선택된 실행이 자기 주기 계산·명령을 실제 완료하고 현재 입력·출력 신선도 조건을 유지 | 실제 미완료·deadline 위반·출력 경로 문제를 해당 기능 영향에 연결 |
| 출력 허가 | Gateway가 현재 실행·제어·준비·사용자 의도·출력 경로를 확인해 허가 | 앞의 근거 상실·의도 변경·출력 경로 실패에 따라 철회. 앱·Worker의 자기 승인이나 과거 허가 복원 금지 |

상태 있는 앱의 유효 내부 상태는 **현재 입력으로 지원되는 초기화·재구축을 마친 상태 또는 검증해 적용한 인계 사본**일 수 있다. 최초 기동에 인계 사본이 없다는 이유로 양쪽이 서로를 무한 대기하지 않는다. 진행 중 연속 승계에 필요한 추가 문맥은 12.3절에서 확인하며, 최초 준비 성공으로 대신하지 않는다.

대기 자격 → 활성화 준비 → 출력 허가의 선후관계는 **전환 경계의 조건**이다. 평상시 매 20ms 계산마다 감독·Gateway·송신 완료·장치 ACK의 승인 왕복을 반복하지 않는다. 현재 유효한 입력·상태·권한으로 계산하고 결과를 게시하며, 각 소유자는 근거의 만료·실패를 확인해 필요한 자격을 철회한다. 논리적 구분이 반드시 별도 메시지 네 개나 왕복 네 번을 뜻하지 않는다.

활성화 요청은 이벤트로 대상 작업을 깨우고, 완료·실패는 다음 정기 보고를 의도적으로 기다리지 않는 제한된 처리 경로로 전달한다. 시간 0을 보장한다는 뜻은 아니며, 큐 대기·전달 실패·중복 통지를 포함해 원 전환 기한 안에서 종결한다. 여기서 출력 없는 검사는 **대상 앱의 검사**를 뜻한다. 다른 정상 owner의 출력을 유지하며 준비할 수 있는지는 12.2절의 generation 계약으로 결정한다.

기존 `app.readiness`의 진행·신선도 규칙을 대기 자격에 그대로 적용하지 않는다. 대기 자격의 현재 확인과 원 사본 적용 시점, 활성 계산 완료 근거를 별도로 표현하도록 계약 프로필을 개정한다. 통신 작업자가 과거 READY의 시각·progress를 갱신해 새 계산처럼 보고해서는 안 된다. 개정된 계약을 모르는 소비자가 기존 READY 하나로 Standby 승격을 승인하는 fallback도 두지 않는다. 실제 공개 필드·전송 주기·만료는 DEC-16·DEC-19에서 기존 봉투를 재사용해 확정한다.

이 방식의 참고 사례와 적용 범위는 다음과 같다.

| 레퍼런스 | 원래 방식 | Xenova에 가져올 원리·차이 |
|---|---|---|
| Remus, NSDI 2008 [R21] | Active의 VM checkpoint를 다른 물리 host에 복제하며 백업 VM은 장애 전까지 실행하지 않음. 외부 네트워크 출력은 대응 checkpoint의 복제 확인까지 보류 | 동일 업무를 두 번 계산하지 않고 상태를 넘길 수 있다는 사례. Xenova는 VM 전체를 복제하거나 멈추지 않고 필요한 앱 상태만 동기화. 같은 RPi의 A/B는 보드·전원 장애를 분리하지 못함 |
| ZeroMQ Guide의 Clone·Binary Star [R23] | 전체 상태 snapshot으로 합류하고, 순서가 있는 갱신을 적용. snapshot 경계보다 오래된 갱신은 다시 적용하지 않음 | 재합류의 완전한 시작 사본, 상태 revision과 완료 경계, 복구한 VM의 Standby 재합류에 참고. 전송은 기존 MQTT를 사용하며 ZeroMQ·새 broker·범용 재생 큐를 도입하지 않음 |
| ClusterLabs Filesystem monitor [R22] | 기본 검사는 mount 여부를 확인하고, 별도 깊이의 검사는 장치 읽기 또는 파일 읽기·쓰기를 수행 | 가벼운 상태 감시와 실제 기능 검사를 구분하는 사례. 파일시스템 검사 자체가 주행 준비를 증명하는 것은 아니며, 앱별 실행 확인은 별도로 정의 |

Xenova의 기본안은 상태 동기화를 매 20ms 출력의 필수 응답 대기로 묶지 않는다. 따라서 Remus의 ‘이미 외부에 보인 출력에 해당하는 상태가 반드시 백업에 있다’는 보장은 가져오지 않는다. 승계에는 **마지막으로 완전히 적용했고 현재도 사용할 수 있는 상태**를 쓰며, 자료가 부족하면 12.3절의 정지 후 재개로 낮춘다. 허용할 미반영 상태 범위와 최대 승계 중단 시간은 DEC-11·DEC-19의 수락 항목이다.

## 10. 자율앱: 경량 경로 계획·추종

### 10.1 레퍼런스 적용 원칙

목적은 **국소 지도에 기반한 경량 자율주행**이다. 정해진 도로 환경에서 차량의 운동 제약을 반영해 장애물을 우회하고 원래 경로로 복귀하도록 하며, 메모리·계산량·실패 결과를 제한한다. 다음 레퍼런스는 현재 AUTO 앱의 계획·추종 상세안에 적용할 원리다. 알고리즘을 교체해도 공통 입력·제어 문맥·실제 계산 진행·준비 보고·출력·종료 계약은 유지한다. ROS/Nav2 전체를 이식하거나 해당 프로젝트의 성능 수치를 재사용하는 것은 아니다.

| 영역 | 레퍼런스 | Xenova에 적용할 원리 |
|---|---|---|
| 환경 표현 | Nav2 Costmap 2D | 주위의 제한된 격자 지도, 점유·미확인 영역 구분, 차량 footprint를 사용한 평가 [R6] |
| 계획 모델 | Pivtoraiko·Knepper·Kelly의 State Lattice, CMU-RI-TR-07-15 | 위치뿐 아니라 방향과 필요한 곡률 상태를 구분하고, 실제 차량이 수행 가능한 짧은 움직임으로 연결 [R16] |
| 계획 구현 참고 | Nav2 Smac State Lattice | 사전 계산 control set을 지도 해상도·차량 제약과 결합하고 탐색 횟수·시간을 제한 [R17] |
| 추종 | Macenski 외의 Regulated Pure Pursuit 논문·Nav2 구현 | 경로상의 전방 목표점 추종, 속도에 따른 lookahead, 곡률·장애물 근접·전방 검사에 따른 속도 제한 [R18][R19] |

정식 planner의 기본 방향은 **제한된 도로 corridor에서 운동 primitive를 연결하는 bounded lattice 계열**이다. 좌/우/중심선/정지는 행동 후보와 탐색 corridor를 정하는 데 사용한다. 단순한 3개 곡선 비교만으로 State Lattice와 같은 완전성·최적성을 주장하지 않는다.

#### 레퍼런스를 연결한 처리 흐름

```text
Jetson: 누적 지도 갱신 → 필요한 국소 지도 + 대응 차량 위치·방향 제공
Pi AUTO: 입력 검증 → 필요한 때 bounded lattice 경로 계획 → 완성된 path 게시
                                               └→ Standby에 path·상태 사본 동기화
Pi Active AUTO: 현재 path + 로컬 차량 상태 → 주기 추종·속도 제한 → 명령 후보
Gateway: 현재 실행·제어·권한 확인 → ESP32에 출력 제출
```

**환경 표현 — Costmap 2D.** Nav2의 격자·footprint·rolling window 개념을 참고하되, Pi가 센서 원문으로 지도를 다시 만드는 구조로 옮기지 않는다. Jetson이 누적 지도를 관리하고 Pi에 필요한 영역을 잘라 보낸다. Pi는 해상도·원점·차량 pose·점유 표현을 검증하고 차체가 통과할 공간을 평가한다. 현재 시야 밖의 보존 지도도 Jetson이 제공한 사용 가능한 영역으로 다룬다. 지도 저장·관측 시각과 현재 차량 상태의 신선도는 별개다. [R6]

**경로 계획 — State Lattice와 Smac.** 짧은 전진·곡선 등의 motion primitive를 차량 운동 모델로 미리 생성하고, 현재 위치·방향에서 이들을 연결해 목표 도로 구간으로 가는 경로를 찾는다. 방향만 다른 같은 위치도 다른 탐색 상태로 다루며, 곡률 연속성이 필요하면 primitive 접속 조건이나 추가 상태로 표현한다. 축간거리·조향 한계·최소 회전 반경·지도 해상도와 맞지 않는 control set은 사용하지 않는다. Ackermann 차량에 제자리 회전이나 옆걸음을 허용하지 않는다. [R16][R17]

Xenova에서는 도로 corridor·고정 node pool·확장 횟수·작업 deadline을 함께 제한한다. 무거운 계획은 새 목표·유효 경로 상실 등 필요한 사건에 반응하고, 20ms 추종 작업은 이미 완성된 경로를 사용한다. 탐색 제한에 도달하면 ‘이번 제한 안에서 찾지 못함’으로 반환한다. 경로 미발견은 앱 고장과 구분한다. 구체적인 상한·비용·결과 채택 조건은 10.4~10.6절에서 정의한다.

**경로 추종 — Regulated Pure Pursuit.** 현재 차량 좌표계로 경로를 해석하고, 진행 방향의 lookahead 목표점으로 향하는 곡률을 계산한다. 속도에 맞춰 lookahead를 제한된 범위에서 조절하며, 급한 곡선·장애물 근접·목표 지점 접근 시 속도를 낮춘다. 현재 명령으로 진행할 구간의 충돌도 제한된 계산량으로 확인한다. Ackermann에서는 곡률을 축간거리에 맞는 조향각으로 바꾸고 제자리 회전 기능을 사용하지 않는다. [R18][R19]

RPP는 경로를 따라가는 기하 제어 방법이므로, 주행 가능한 경로를 만드는 planner와 실제 제동·조향 한계를 대신하지 않는다. 원 문서의 lookahead·속도·충돌 검사 기본값을 복사하지 않고 차량 실측과 10.7절의 조건으로 정한다. Nav2 전체 실행 환경이나 원 논문의 처리율을 Zephyr에서 확보했다고 해석하지 않는다.

**계산 결과 동기화는 Xenova의 별도 설계다.** Nav2가 A/B 승계까지 제공한다는 뜻은 아니다. Active가 만든 경로와 필요한 상태를 Standby가 받아 검증하는 방식은 9.6·12.4절의 앱 수준 동기화에 연결한다. 동기화된 경로를 쓸 수 있으면 승계 때 경로 탐색을 처음부터 반복하지 않지만, 현재 pose와의 연결·충돌·제어 적용 및 자기 실행의 명령 계산은 확인한다.

**현재 연결된 계산과의 차이:** 공통 펌웨어의 [AUTO 어댑터](../../platform/apps/drive/zephyr/src/adapter.c)는 기존 `auto_step()`을 호출한다. 그 [계산 구현](../../platform/apps/autonomous/zephyr/src/autonomous.c)은 차선 편차·방향 오차로 조향하고 전방 장애물 거리로 감속·정지한다. 이 경로에 국소 지도 기반 lattice planner·RPP·위 상태 동기화가 이미 구현됐다고 보지 않는다. 이 절은 해당 앱을 확장할 설계와 출처를 정의한다.

### 10.2 자율 상태의 분리

| 내부 상태 의미 | 수행·보고 |
|---|---|
| 입력 대기 | 현재 지도·자세·설정이 없거나 무효. 입력 회복을 감시하며 가짜 계획 진행을 만들지 않음 |
| 준비/계획 | 필요한 입력으로 지도 검증·경로 생성·상태 재구성. 출력은 아직 승인되지 않음 |
| 경로 추종 | 승인된 모드/권한 문맥에서 유효 path를 사용해 명령 후보 계산 |
| 정상 정지·대기 | 장애물/경로 제약으로 정지를 선택했으나 기능 자체는 정상 |
| 기능 실패 | 계산 오류·비정상 출력·기한 위반·필수 자원 실패. 결과 제한·지원 복구 |
| 종료/재초기화 | 해당 앱 결과 사용 중지, 원 작업 취소·join·소유 자원 처리 |

위 명칭은 내부 의미 분류이며 새 공개 enum 확정이 아니다. `healthy`, `drive_capable`, `safe_hold_capable`, `readiness`, `output_permitted`를 한 bit로 합치지 않는다.

### 10.3 기준 경로·우회 의도·실행 경로

세 객체를 별도로 유지한다.

1. **ReferencePath:** 원래 도로 모델. Jetson의 road/reference revision과 대응한다.
2. **ManeuverIntent:** FOLLOW, 우회 방향, 통과·복귀 단계, 합류 목표 구간처럼 인계할 의도.
3. **PlannedPath:** 현재 pose에서 실제로 실행할 수 있도록 계산·검증한 경로.

새 snapshot이 올 때마다 reference를 임시 우회 path로 덮어쓰지 않는다. 중간에 장애물을 보지 못하게 됐다고 기존 위험 정보를 근거 없이 free로 바꾸지 않는다. 합류 목표를 변경하면 maneuver revision을 바꾸고 Standby의 옛 준비와 구별한다.

### 10.4 계획 입력과 bounded 탐색

계획 시작 시 유효한 지도·pose·reference·maneuver·vehicle config를 하나의 작업 문맥으로 고정한다. 탐색은 다음 상한을 갖는다.

| 상한 | 목적 |
|---|---|
| 공간 범위·지도 cell 수·heading/curvature 상태 수 | search 공간과 memory 상한 |
| open/closed node 수·primitive 수 | 무제한 할당 방지 |
| 최대 확장 수·한 구간의 작업량 | 실행 양의 상한·취소 확인 기회 |
| 전체 작업 deadline·결과 최대 나이 | 오래된 결과 채택 방지 |
| 경로 길이·표본 수·검사 횟수 | 추종·충돌 검사 비용 제한 |
| 시작 빈도·재계획 취소 정책 | 새 지도 폭주가 planner를 무한 재시작시키는 현상 억제 |

시간 제한만 두고 반환하지 않는 함수를 같은 thread에서 사후 검사하는 방식으로 만들지 않는다. iteration cap·bounded data structure·취소 지점을 함께 둔다.

전체 `x×y×heading×curvature` 상태를 먼저 펼치지 않고 실제 필요한 상태를 제한된 node pool에 생성하는 방식을 기본으로 한다. node 본체뿐 아니라 open queue·검색 색인·중복 queue 항목·heuristic cache·경로 복원·충돌 검사 작업 공간도 각각 상한을 둔다. 하나가 고갈돼도 다른 무제한 할당으로 우회하지 않는다. Smac의 탐색·비용·해상도 설계는 참고하되 원 구현의 자료구조 규모·성능 수치를 가져오지 않는다. [R17][R26]

계획기 시험은 확장 node 수, node별 검사 primitive 수, primitive별 차체 검사 표본 수를 함께 기록한다. 이 세 수의 곱과 취소 확인 간격을 실행 비용의 근거로 사용하고, 동일 지도·차량·설정·자원 프로필에서 처리시간·메모리 high-water·budget 종료를 비교한다.

사전 계산 primitive는 차량 제원·최소 회전 반경·필요 곡률 연속성·지도 해상도와 버전으로 결합한다. Ackermann 차량에 제자리 회전·횡방향 이동 primitive를 사용하지 않는다. 제어 집합/탐색 범위를 제한한 만큼 경로 탐색 능력에도 한계가 있음을 명시한다. [R16][R17]

곡률 상한만으로 조향 변화율이 보장되지는 않는다. \(\delta=\arctan(L\kappa)\)에서 연속적인 경로 구간의 요구 조향 속도는 다음과 같다.

\[
\dot\delta=\frac{L}{1+(L\kappa)^2}\frac{d\kappa}{ds}v
\]

접속점의 곡률 불연속은 위 미분식으로 유한한 조향 속도가 확보됐다고 처리하지 않는다. 필요한 조향/곡률 상태를 탐색 상태 또는 primitive 접속 조건에 포함하고, 실제 조향 변화율·지연에 맞는 속도 조건을 붙인다. 지도 해상도·차량 모델을 바꾸면 control set을 재생성·검증한다. 차원·primitive 수·접속 조건은 RAM과 계산 예산을 함께 보고 정한다.

도로를 국소 Frenet 표현으로 사용할 수 있으면 다음처럼 후보 corridor를 표현할 수 있다.

\[
P(s)=\gamma(s)+d(s)n(s)
\]

여기서 \(\gamma\)는 기준 중심선, \(d\)는 횡방향 변위다. 현재 위치·방향·곡률에서 이어지도록 하고, 매번 중심선의 정면 상태에서 시작하는 것으로 가정하지 않는다. 투영이 중복되거나 road model이 불연속이면 이 표현으로 억지 계획하지 않는다.

### 10.5 hard constraint와 cost를 분리

후보 경로에 대해 다음을 먼저 검사한다.

\[
F(P(\sigma))\cap O=\varnothing,
\qquad F(P(\sigma))\subseteq D_{valid}
\]

\[
|\kappa_P(\sigma)|\le\frac{\tan\delta_{max}}{L}
\]

\(F\)는 설정된 여유를 포함한 차체 형상, \(O\)는 국소 지도에서 점유로 표현된 영역, \(D_{valid}\)는 주행에 사용할 수 있는 도로·지도 영역, \(L\)은 축간거리다. \(D_{valid}\)에는 현재 센서로 관측한 영역과 정적 장애물 중심 운용에서 사용하는 보존 지도 영역을 포함한다. Jetson이 국소 snapshot에 통과 가능 영역으로 제공한 보존 지도 구간을 현재 시야 밖이거나 과거에 관측했다는 이유만으로 제외하지 않는다. Pi는 이 구간을 경로 계획·추종에 사용한다. 곡률 상한 외에 조향 변화율·가감속·현재 pose 연결 조건도 만족해야 한다.

차량 중심점만 free인지 확인하지 않는다. 회전하며 지나가는 **swept footprint**를 검사하고, 이산 표본 사이의 충돌을 놓치지 않도록 보간·검사 간격·여유를 정한다. Jetson의 inflation과 Pi의 footprint를 어떤 조합으로 쓰는지 명시한다.

통과한 후보에만 길이·도로 이탈·곡률·clearance·우회 방향 변경 비용을 적용한다. 예시적 목적함수는 다음과 같다.

\[
J=w_lL(P)+w_d\int d^2d\sigma+w_\kappa\int\kappa_P^2d\sigma
+w_cC_{clearance}+w_sC_{switch}
\]

가중치는 미확정 정책이다. 위험한 후보가 낮은 cost 때문에 선택돼서는 안 된다. 새 장애물로 기존 경로가 위험해졌으면 방향 고정 비용보다 hard constraint가 우선한다.

계획용 종합 cost와 장애물까지의 거리 근거는 분리한다. 종합 cost에는 도로 이탈·곡률·불확실성 등의 서로 다른 항이 들어갈 수 있으므로 그 값을 m 단위 거리처럼 해석하지 않는다. 근접 속도 조절에는 단위·포화 범위·좌표/기준 차체가 정의된 거리 자료를 사용하거나, 양쪽에서 의미와 설정을 고정한 inflation 모델을 사용한다. Nav2 Jazzy의 RPP `costConstraint()`는 inflation 계수·inscribed radius로 비용을 거리로 환산하므로 그 계산을 임의 cost에 그대로 적용하지 않는다. 선택한 표현과 설정은 Jetson 생산자·Pi 소비자 계약에 결합한다. [R29]

### 10.6 계획 결과의 채택

계획 중 새 지도 수신만으로 작업을 매번 취소하지 않는다. 정해진 문맥으로 bounded 계산을 끝낸 뒤 **채택 직전 현재 pose·map·maneuver·generation과 재대조**한다.

계획 기준 버전과 현재 버전이 다르더라도 좌표·형상·현재 경로 유효성을 확인하면 사용할 수 있다. 단순 버전 일치만으로 유효하다고 인정하지도 않는다. 새 장애물이 현재 경로를 막으면 새 plan 완료 전이라도 추종을 제한한다.

계획 결과는 최소한 다음을 구분한다.

| 결과 | 의미·대응 |
|---|---|
| 유효 경로 | 현재 제한 안에서 검증된 path를 게시 |
| 정상 정지 선택 | 장애물/도로 제약상 진행하지 않음. 앱 고장·VM 복구로 바꾸지 않음 |
| 제한된 탐색에서 경로 미발견 | 전체 환경에서 경로가 없다는 증명은 아님. 안전한 기존 경로 또는 정지 |
| budget/자원 소진 | 이번 작업 실패·연산 한계. 정상 plan 성공으로 표시하지 않음 |
| 입력·좌표·시각 부적합 | 자율 준비 근거 부족. 원인에 맞게 회복 대기 |
| 계산 오류·잘못된 수치 | 기능 실패. 해당 결과 무효화·감독 경로 |

경로를 찾지 못했거나 정상 정지를 선택했다는 사실만으로 앱 장애를 선언하거나 VM 복구를 요청하지 않는다. 계산의 정상 완료 여부와 차량이 이동할 수 있는 결과를 얻었는지는 별도로 판단한다.

### 10.7 경로 추종과 속도 결정

추종기는 완성된 path와 현재 실제 pose·속도로 주기 명령을 만든다. 새 계획기 완료를 기다리지 않는다. 선택한 path가 여전히 유효한 범위에서만 유지하고, 유효성 상실 시 정지/준비 철회한다.

저속 자전거 모델에서 후륜 축 기준 차량 좌표의 실제 선택 목표점을 \((x_\ell,y_\ell)\)라 하고, 목표점까지의 기하 거리를 \(d_\ell\)라 하면 기본 형태는 다음과 같다.

\[
d_\ell^2=x_\ell^2+y_\ell^2,\qquad
\kappa_{cmd}=\frac{2y_\ell}{d_\ell^2},\qquad
\delta_{cmd}=\arctan(L\kappa_{cmd})
\]

설정한 lookahead는 목표점 선택 기준이고, 경로 끝·국소 영역 경계에서 선택한 점의 실제 거리는 더 짧을 수 있다. 분모에 설정값을 무조건 넣지 않으며, 거리 0에 가까운 경우는 별도 목표 도달/정지 처리로 나눈다. 이는 적용할 기하 제어 모델의 설명이다. 실제 lookahead·조향·속도 한계는 차량 실측으로 정한다. 원 RPP 전체 구현의 기능·성능·안전 보장을 그대로 주장하지 않는다. [R18][R19][R24]

충돌 검사는 계획 path와 실제 명령을 나눈다. planner는 path의 swept footprint를 검사하고, tracker는 **조향각·변화율·속도 제한을 적용한 최종 후보**를 현재 pose·차량 상태에서 짧게 투영해 차체 통과를 검사한다. 제한 전 명령이나 path 자체가 안전하다는 사실로 대신하지 않는다. 실제 조향 피드백이 없으면 조향 추정·모델 오차를 명시하고, 측정한 것처럼 보고하지 않는다. 검사 구간·표본 수·제동 여유도 고정 예산에 포함한다.

속도는 곡률·장애물 근접·국소 지도에서 파악한 정지 공간·현재 속도·제동 성능으로 제한한다. 정지 공간은 현재 관측과 운용 조건상 사용하는 보존 지도에서 구한다. 정적 장애물과 보수적 제동 하한을 가정한 검토식은 다음과 같다.

\[
|v|\tau+\frac{v^2}{2a_{min}}+m\le d_{known}
\]

\(\tau\)는 이번 주행 판단에 쓰는 현재 차량·센서 표본의 나이와 처리·전달·구동 반응의 지연 상한, \(a_{min}\)은 확인한 최소 감속 크기, \(m\)은 위치·차체·지도 오차 여유다. 보존 지도에 기록된 정적 도로·장애물을 마지막으로 관측한 뒤 지난 시간을 \(\tau\)에 그대로 더하지 않는다. 예전에 저장한 지도이거나 해당 구간이 현재 시야 밖이라는 이유만으로 반응 지연이 계속 증가해 차량이 움직일 수 없게 만들지 않는다. 지도·위치의 오차는 \(m\) 등 해당 오차의 근거로 다룬다. 이 식만으로 실제 안전을 인증하지 않는다. 지연·제동 근거가 없으면 상한을 상상해 넣지 않고 운용 속도를 제한하거나 준비를 보류한다.

긴급 정지를 일반 가속 smoothing 때문에 늦추지 않는다. 조향을 0으로 보내는 동작이 모든 상황의 최선 정지라고 가정하지도 않는다. 정지 시 조향 유지/변경·브레이크/코스트 정책은 장치 프로필로 검증한다.

### 10.8 MANUAL 중 AUTO의 실행

아래는 AUTO 복귀·승계를 위한 준비 작업을 수행할 때의 동작이다. 평소 Standby의 건강 확인과 이 준비 작업을 구분하며, 대기 중 정상 여부를 보이기 위해 아래 계산을 무조건 계속 실행하지 않는다.

| 조건 | AUTO 동작 |
|---|---|
| Jetson 지도·현재 pose 없음/무효 | 입력 회복 감시. 옛 입력으로 정상 준비 계산을 반복하지 않음 |
| 입력 유효, path/state 준비 부족 | 정해진 예산으로 경로 재구축 |
| 입력·상태·자원·기한 조건 확보 | 출력에 적용하지 않는 실제 planner/tracker 준비 실행 |
| 제한된 준비 실행에서 계산·유효성이 확인됨 | AUTO 준비를 보고하되 MANUAL 출력은 유지 |
| 오류·정체·반복 기한 위반 | 준비 철회·지원 취소/재초기화·필요한 VM 복구 |

대기 상태 확인·동기화 완료·활성 주행 실행 확인은 구분한다. Standby를 정상으로 유지하기 위해 50Hz 주행 계산을 계속 돌릴 필요는 없지만, 동기화만 끝난 상태를 이미 활성 주행이 검증된 상태로 표현하지 않는다. 실제 AUTO 전환·승계에 필요한 현재 계산·상태·기한 조건은 해당 준비 경계에서 확인하며, 과거 READY나 heartbeat만으로 이를 대신하지 않는다. AUTO 복귀에는 기존 명시적 재개 조건도 유지한다.

<a id="s11"></a>
## 11. 수동앱: 독립된 운전자 입력 처리

### 11.1 필수 입력

MANUAL은 현재 입력 세션·control·필요한 로컬 차량/장치 상태를 사용한다. 지도 구독·해석·보관은 MANUAL 앱의 역할이 아니며, Jetson 지도·AUTO plan·Jetson broker는 MANUAL의 필수 의존성이 아니다. 같은 VM에서 AUTO용 지도 수신과 Jetson의 수동 이동 중 지도 수집이 동작해도 MANUAL은 그 자료나 처리 완료를 기다리지 않는다. 다만 Pi 로컬 차량 상태 자체가 고장 났다면 MANUAL이 무조건 계속 가능하다고 보장하지 않는다.

```text
원 입력 세션·순번·나이 검사
→ 현재 control 및 운전 허용 조건 확인
→ brake/E-stop 우선 적용
→ 키/축을 목표 속도·조향각으로 변환
→ 차량 한계·방향 전환·가감속 조건 적용
→ 실제 계산 결과와 준비 근거 생성
```

### 11.2 입력·재연결 규칙

| 조건 | 처리 |
|---|---|
| 사용자 조작 없음·정상 세션의 중립 입력 | 정상 대기·정지. 이동하지 않는다는 이유만으로 앱 장애·VM 복구를 일으키지 않음 |
| 입력 만료·세션 종료 | 지원되는 정지 요청, 준비 제한. 옛 키를 계속 유지하지 않으며, 입력 경로 문제를 앱 계산 장애와 구분 |
| `brake`/E-stop | 일반 이동·완화 규칙보다 우선 |
| 전진↔후진 | 실제 속도/정지 조건을 확인한 지원 범위에서 전환 |
| 새 입력 세션·VM/app 재시작·권한 변경 | 과거 저장·캐시한 비중립 입력을 자동 복원하지 않음 |
| 오래된 입력·현재 문맥과 맞지 않는 결과 | 현재 출력 후보로 수락하지 않음 |
| Jetson 단절·영상 종료 | 그 사실만으로 MANUAL 계산을 중단하지 않음 |

금지하는 것은 과거 입력 사본을 새 운전자 의도로 되살리는 것이다. 동일한 유효 운전자 세션에서 현재 제공되는 입력은 새 제어 문맥·운전 허용·원 입력 유효성을 확인해 새 실행에서 처리할 수 있다. A의 캐시를 B에 복사하는 것과 B가 정상 세션의 현재 입력을 받아 자기 계산을 수행하는 것은 구분한다.

| 경로 | 확정한 입력·이동 허가 정책 |
|---|---|
| 같은 MANUAL 모드의 A/B 승계 | 동일한 유효 세션의 현재 입력을 새 실행에서 처리한다. 새 제어 문맥·운전 허용·원 입력 유효성과 승계 준비를 확인하며, 승계 자체를 이유로 중립 복귀나 키를 떼었다 다시 누르는 재조작을 요구하지 않는다. A/B 양방향에 동일하게 적용 |
| AUTO→MANUAL 모드 전환 | 모드 선택과 이동 허가를 분리한다. 해당 전환 문맥에서 정상 세션의 현재 중립 입력을 확인한 뒤, 그 이후의 새 조작을 받아 이동을 허가한다. 전환 전부터 유지된 비중립 입력만으로 출발하지 않음 |

세션 종료·입력 만료·운전 허용 상실은 위 정상 입력 인계 조건에 해당하지 않는다. 세션·운전 허용의 실제 표현과 검증은 DEC-12에서 공동 확정하되, 이 두 경로의 입력 정책을 다시 미정으로 취급하지 않는다.

MANUAL로 전환한 뒤 사용자가 키나 축을 조작하지 않아 이동하지 않는 상태는 정상 대기다. 이동 입력이 발생해야 모드를 전환할 수 있다는 조건을 두지 않는다. 실제 입력 세션과 중립 상태를 확인하는 절차는 사용자에게 이동 조작을 요구하는 것과 구분한다. 사용자 조작이 없는 상태와 입력 연결이 끊긴 상태도 구분하며, 연결이 끊긴 사용자를 relay가 합성한 반복 중립으로 정상 세션처럼 유지하지 않는다.

입력 중계는 원 표본 ID·원 나이 또는 검증된 세션 유효성을 보존해야 한다. 새 MQTT seq만으로 오래된 누른 키를 새 운전자 의도로 만들지 않는다.

### 11.3 준비와 운전 허가

MANUAL 모드 선택과 실제 이동 허가는 구분한다. 중립 입력을 처리할 수 있다는 것은 MANUAL 준비 근거일 수 있지만 비중립 이동 승인은 아니다. AUTO→MANUAL 전환은 11.2절의 중립 확인·새 조작 순서를 따르고, 같은 MANUAL 모드의 A/B 승계에는 그 절차를 다시 요구하지 않는다. 어느 경우든 현재 세션·control 문맥과 운전 허용을 확인하며, 조작하지 않는 동안에는 정지를 유지한다. 운전 허용 표현과 세션 검증 방법은 [20절](#s20)에서 정하며, 미합의 필드를 기존 JSON에 임의로 추가하지 않는다.

웹 영상은 기본적으로 관제 기능이다. 영상을 보며 수동운전하는 사용을 지원하려면 영상 지연·입력 지연·가시 범위·연결 상실을 합친 별도 수락이 필요하다.

<a id="s12"></a>
## 12. 모드 전환·준비·A/B 승계

### 12.1 모드와 권한의 단일 원본

Gateway가 현재 모드·owner·generation·출력 허가와 명시적 재무장 절차를 소유한다. 앱은 제어 적용과 자기 준비를 보고할 뿐 권한을 발급하지 않는다. retained control은 내구 원본의 배포 사본이다. Gateway/host 재시작 후 과거 owner·mode 복원만으로 자동 출력하지 않는다. [P0][P1]

모드 전환 기능은 VM 복구 절차와 별도로 존재한다. 운영자 또는 복구 정책은 허용된 요청 경로로 AUTO↔MANUAL 전환을 요청하며, 실제 모드·generation·출력 허가의 변경은 Gateway가 처리한다. 복구 요청자가 `vehicle.control`을 직접 발행하거나 모드 전환 권한의 원본이 되지는 않는다. 구체적인 요청 인터페이스는 기존 제어 계약과 연결해 확정한다.

MANUAL 선택의 출처와 사유를 구분하여 현재 모드·제어 문맥과 함께 권위 원본에 보존한다.

| MANUAL 선택 | 유지·회복 동작 | AUTO 복귀 |
|---|---|---|
| 사용자가 개발·운용을 위해 직접 선택 | 사용자의 MANUAL 선택을 유지한다. AUTO가 정상·준비 완료·복구 완료가 돼도 모드를 바꾸지 않는다 | 현재 문맥의 명시적 AUTO 복귀 요청이 필요 |
| Jetson 등 AUTO 경로의 장애 대응으로 전환 | 전환 원인을 관측하고 AUTO 복귀 가능 상태를 보고한다. 원인이 회복됐다는 사실만으로 모드를 바꾸지 않는다 | 기존 준비 유지·명시적 복귀·카운트다운·제어 적용 절차를 따름 |

이미 MANUAL인 상태에서 사용자가 MANUAL 유지를 선택한 경우도 새로운 사용자 의도로 구분해 보존한다. 그보다 앞선 장애 대응이나 AUTO 복귀 요청이 뒤늦게 완료되어 이 선택을 덮어쓰지 않도록 현재 제어 문맥·원 요청 식별과 순서를 대조한다. 같은 요청의 재전달을 새 사용자 선택으로 처리하거나 generation을 반복 발급하지 않는다. 출처·사유의 실제 저장 필드와 요청 표현은 기존 Gateway 제어 계약에 연결해 확정한다.

기존 제어 적용 기한·generation·원 요청 중복 방지·실행 binding의 보호는 새 planner 때문에 완화하지 않는다. 새 상태 있는 준비 계약이 추가되더라도 오래된 소비자가 이를 조용히 무시해 승격하지 않도록 프로필을 개정한다.

### 12.2 전환의 기대 의미

| 상황 | 목표 동작 |
|---|---|
| Jetson 중단 | Pi에 남은 국소 지도를 이용해 안전 정지한 뒤 MANUAL로 전환. MANUAL·Pi 내부 차량 피드백은 Jetson 없이 동작하며, 준비·현재 입력·출력 허가는 기존 MANUAL 계약을 따름 |
| AUTO의 인지·지도 근거 상실 | AUTO 결과 제한. 같은 실행의 MANUAL이 적합하면 기존 전환 정책으로 전환, 없으면 정지 |
| MANUAL 운용 중 AUTO 경로 문제 | AUTO의 준비·복구 상태로 다룬다. 현재 MANUAL 경로에 영향이 없으면 MANUAL과 Active VM을 유지 |
| AUTO 계산만 실패 | AUTO 기능 문제의 원인과 영향을 판단하여 모드 전환·앱 재초기화·필요한 승계를 선택. 전체 VM 장애로 무조건 합치지 않음 |
| Active VM이 현재 모드의 기능을 제공하지 못함 | 해당 모드·상태를 이어받을 준비가 된 반대 VM을 검증하고 승계. 부적합하면 정지 |
| MANUAL 중 AUTO 준비 회복 | AUTO_READY가 돼도 출력은 MANUAL. 명시적 복귀·카운트다운·새 control 적용을 거침 |
| 준비가 복귀 대기 중 다시 상실 | 카운트다운/전환을 해당 계약대로 취소·종결. heartbeat로 원 기한 연장 금지 |
| 장애물을 정상적으로 보고 정지 | 유효 정지 결과와 계산 장애를 구별. 자동 VM 복구의 근거가 아님 |
| 복구된 옛 Active가 준비됨 | 현재 정상 Active의 권한을 빼앗지 않고 Standby |

전환 중 old generation 결과는 새 출력으로 수락하지 않는다. PUBACK만 확인하고 앱 적용까지 완료된 것으로 처리하지 않는다. 새 control에 필요한 적용 확인과 선택 모드의 기능 준비를 구분하고, 비선택 앱의 모든 기능 준비를 불필요하게 강제하는 새 barrier를 만들지 않는다.

전환의 다음 네 시점을 구분해 원 요청·pending/phase와 연결한다.

| 시점 | 의미·보호 조건 |
|---|---|
| 대상 선택 | 준비할 VM·앱을 고름. 선택 사실만으로 출력 자격을 주지 않음 |
| 준비 문맥 전달 | 대상이 어느 모드·상태·요청을 검사하는지 고정. 준비용 문맥과 현재 출력 문맥의 관계를 확인 |
| 기존 출력 자격 종료 | 기존 owner/generation의 출력을 더 이상 수락하지 않는 경계. 이미 근거를 잃은 출력은 대상 준비를 기다리며 연장하지 않음 |
| 새 출력 허가 | 대상의 현재 신원·제어 적용·기능 준비를 확인한 뒤 Gateway가 허가. 두 owner의 출력 자격이 겹치지 않음 |

정상 A의 출력을 유지하며 B를 준비하고 B 실패 시 A를 유지할 수 있는지는 **준비 문맥과 출력 generation의 관계**를 DEC-11·DEC-16에서 결정한다. 새 generation 발급이 즉시 A의 자격을 끝내는 계약에 이 동작이 지원된다고 덧붙이지 않는다. 기존 pending/phase의 재사용 가능성을 먼저 확인하며, 두 문맥을 구별할 수 없는 상태에서 양쪽 출력을 동시에 허용하지 않는다. 계획 인계와 이미 근거를 잃은 A의 장애 승계를 구분한다.

**Jetson 단절 중 감속·정지.** 새로운 자율 운행의 준비와 제한된 정지 수행 가능 상태는 다르다. 인지 갱신이 끊겼다는 이유로 정지에 필요한 계산·전달까지 모두 중단하지 않는다. 현재 출력 권한 아래에서 정상 AUTO 운행 결과를 제한하고 다음 경계로 종결한다.

| 근거 | 허용 동작·종결 |
|---|---|
| 현재 로컬 pose·차량 상태와 직전 경로/지도에 정지에 필요한 근거가 있음 | 새 우회·먼 목표를 만들지 않고 정의된 범위의 감속·정지 후보를 현재 실행에서 계산. 명령 신선도·Gateway·장치 검증 유지 |
| 정지 경로의 위치·경로 근거도 부적합 | 지도 기반 정지를 계속 정상으로 표시하지 않고 기존 Gateway·ESP32의 장치 정지/출력 제한 절차로 전환. 구체 동작은 장치 계약으로 확인 |
| 피드백으로 실제 정지가 확인됨 | 해당 전환의 정지 단계를 완료하고 MANUAL의 준비·입력·출력 허가 조건을 평가 |
| 정해진 기한 내 정지 확인 불가 | 정지 미확인 원인과 마지막 제출/확인 단계를 남기고 제한 상태로 종결. 모드 선택과 이동 허가를 분리해 MANUAL 이동은 허가하지 않으며 확인을 무한 대기하지 않음 |

속도 0 명령의 제출만으로 정지 완료를 만들지 않는다. 새 정지 계산의 실패를 옛 명령의 시각 갱신이나 자동 force로 우회하지 않는다. 사용할 피드백·종결 기한·장치 정지 동작은 Gateway·ESP32 담당자가 DEC-13으로 확정하고, 이 기능을 일반 VM 복구 완료와 구분한다.

### 12.3 상태 있는 승계의 두 수준

승계·Standby 재합류의 준비는 모드별로 판단한다. MANUAL에는 현재 입력·제어 문맥·필요한 로컬 차량 상태를 확인하고, 지도나 AUTO 준비를 요구하지 않는다. AUTO에는 지도·위치·경로·필요한 우회 문맥을 확인한다. MANUAL 운용 중에는 A/B의 AUTO 모두 차량 출력을 담당하지 않으며, AUTO의 준비 회복이 모드 전환을 뜻하지 않는다.

같은 MANUAL 모드의 승계에서는 11.2절에 따라 정상 세션의 현재 입력을 이어 처리하며 중립·재조작을 추가 요구하지 않는다. 이 정책만으로 연속 승계가 성립하는 것은 아니며 새 실행의 제어 적용·계산·출력 예산과 아래 조건을 함께 충족해야 한다.

| 수준 | 조건 | 미충족 시 |
|---|---|---|
| **정지 후 재개 가능** | 현재 실행·제어 문맥·선택 모드의 필수 입력·설정으로 해당 모드의 재개 준비를 확인. AUTO는 지원 초기화·재구축으로 새 경로를 구성하거나 유효 인계 상태를 검증하고, MANUAL은 현재 입력·차량 상태 확인 | 해당 모드의 준비 회복/운영자 확인 |
| **주행 중 연속 승계 가능** | 위 조건에 제어·출력 연속성까지 충족. AUTO는 현재 maneuver·합류 목표를 확인하고, MANUAL은 현재 입력 세션·원 입력 유효성을 확인 | 정지 후 해당 모드의 재개 절차로 낮춤 |

연속 승계가 프로젝트의 중요한 목표이지만, **그 조건이 없을 때도 무조건 움직이며 인계하는 것을 요구하지 않는다.** B가 살아 있거나 지도 한 장을 받은 사실만으로 연속 승계 자격이 생기지 않는다.

최초 기동은 지원 초기화·재구축으로 준비할 수 있다. 연속 승계에 필요한 사본·maneuver·출력 연속성이 부족하면 이 경로로 정지 후 재개하며, 재구축 가능하다는 사실만으로 주행 중 연속 승계를 승인하지 않는다. 각 전환은 12.2절의 네 시점과 함께 확인한다.

승계는 9.6절의 사전 대기·동기화 자격을 확인한 뒤 대상 실행을 깨우고, 새 제어 적용과 현재 계산을 확인해 출력 허가로 연결한다. 단계별 비용은 다음처럼 나누어 측정한다.

\[
T_{takeover}=T_{detect}+T_{wake}+T_{validate}+T_{compute}+T_{control\ apply}+T_{deliver}
\]

각 구간의 시작·끝과 겹치는 작업을 trace에서 정의해 중복 합산하지 않는다. 탐지 시작 전 마지막 명령이 이미 소비한 유효시간, Gateway의 출력 제한, ESP32의 실제 명령 상실 동작도 같은 시간선에 놓는다. 서로 다른 장치의 시계는 7.3절의 대응 없이는 직접 빼지 않는다. 장치 적용 확인이 없으면 `deliver`를 제출 단계와 구분하고 실제 적용까지 보장했다고 보고하지 않는다.

연속 승계 판정은 마지막 유효 명령 이후의 **남은 출력 예산** 안에서 새 실행의 유효 명령이 도달·수락되는지를 기준으로 한다. command 100ms 신선도, control 적용 1초의 실패 종결 기한, ESP32의 명령 유지/정지 조건을 동일한 예산으로 취급하지 않는다. 적용 확인을 1초 기다릴 수 있다는 사실이 과거 명령으로 1초 주행해도 된다는 뜻은 아니다.

AUTO 복귀의 명시적 요청·준비 유지·카운트다운과 이미 선택된 모드의 A/B 장애 승계는 목적을 구분해 계약을 확정한다. 같은 3초 조건을 기계적으로 재사용하거나, 승계라는 이유로 승인 없이 기존 조건을 생략하지 않는다. 사전 자격·승계 검사와 출력 예산이 연결되지 않은 상태는 연속 승계 수락으로 표시하지 않고 정지 후 재개 수준으로 기록한다. 사용자 MANUAL 선택은 어느 경로에서도 보존한다.

### 12.4 maneuver 공유와 상태 재구성

Active AUTO가 우회 방향·합류 목표를 제안한다. Gateway의 기존 권한 경계가 그 제안이 현재 owner에서 왔는지 확인해 권한에 묶인 공유 문맥으로 연결한다. Gateway가 경로를 대신 계산하거나 별도 분산 합의 시스템을 만드는 것은 아니다. 새 wire·저장·조회 범위는 관련 담당자의 공동 개정 대상이다.

B는 같은 지도일 필요보다 **같은 좌표·도로·차량 설정·현재 maneuver에 맞는 유효 상태와 실행 가능한 경로**가 필요하다. Active의 유효한 결과를 받아 검증할 수 있으며, 정상 여부를 보이려고 같은 경로를 계속 다시 탐색할 필요는 없다. 지도 전체 byte equality를 준비의 대체물로 사용하지 않는다.

동기화 자료는 필요한 앱 상태를 하나의 일관된 사본으로 구성한다. 아래는 담아야 할 의미이며 새 MQTT 필드명·토픽을 확정한 표는 아니다. wire 형식·크기·전송 주기·적용 확인은 DEC-19에서 공동 확정한다.

| 자료 | 용도·적용 확인 |
|---|---|
| 원 VM·execution·앱 instance·제어 문맥·상태 revision | 당시 허용된 출처에서 수락한 사본인지 확인. 상태 revision을 Gateway의 권한 generation 대신 사용하지 않음 |
| 지도·좌표·정합 문맥·odom epoch·도로 reference·차량/알고리즘 설정 | 다른 원점·보정·차량 모델·알고리즘 상태를 섞지 않고 현재 입력과의 호환성 확인 |
| PlannedPath revision·maneuver revision·합류 목표 | 어느 경로와 우회 의도를 함께 게시한 사본인지 고정하고 경로 교체 중 혼합 방지 |
| 기준 차량 표본·계산 완료 경계·필요한 추종 상태 | 어느 실제 계산 이후의 상태인지 식별. 앱별 필요한 상태와 재초기화 조건은 어댑터가 정의 |
| 사본 완전성·수신 실행의 적용 확인 | 어느 수신 execution/앱 instance가 어느 사본을 완전히 적용했는지 확인. 적용 실패 사본은 현재 정상 상태로 게시하지 않음 |

사본은 경로 교체·maneuver 변경 또는 정한 checkpoint 경계에서 일관된 참조/상태를 확보한다. 제어 경로의 장기 lock이나 큰 직렬화로 매 20ms 계산을 막지 않도록, 완성된 불변 사본을 제한된 작업 공간에서 직렬화한다. 전달·수신·적용 확인을 구분하며 MQTT PUBACK은 앱의 적용 확인이 아니다. 수신 VM이 재시작했으면 이전 실행의 적용 확인을 재사용하지 않는다.

수신 중인 사본과 마지막 적용 사본은 분리한다. 상태가 계속 갱신돼도 한 사본을 다른 revision의 조각과 섞지 않으며, Active가 전송 중 장애를 일으키면 마지막으로 완전히 적용한 사본부터 현재 유효성을 판단한다. 재합류는 완전한 사본으로 시작하고 그 경계보다 오래된 갱신을 거절하는 Clone 패턴을 참고한다. [R23]

상태 채택과 명령 수락의 generation 규칙은 다음과 같이 구분한다.

| 대상 | 새 owner·generation에서의 처리 |
|---|---|
| 이전 owner의 권한이 유효할 때 검증·수락한 경로/상태 사본 | 출처·사본 문맥·현재 호환성을 검증해 새 실행의 입력으로 채택 가능. 원 출처·generation을 지우지 않음 |
| 권한 종료·실행 교체 뒤 새로 도착한 옛 사본·지연 갱신 | 자동 최신화·적용하지 않음. 현재 바인딩·수락 경계와 대조하고, 검증·수락된 사본이 아니면 승계 근거로 사용하지 않음 |
| 과거 주행 명령·출력 권한·유효기간 | 승계하지 않음. 새 generation·신원·시각으로 재포장 금지 |
| 대상 실행에서 새 제어 적용 후 계산한 명령 | 현재 실행·모드·준비·입력·명령 신선도·출력 허가를 기존 Gateway 경계에서 검증 |

경로 형상·우회 방향·합류 목표·설정은 재사용할 수 있지만 차량은 과거 checkpoint 위치로 돌아가지 않는다. 현재 pose·속도·마지막 장치 적용 정보·조향 추정은 다시 확인하고, 복사된 필터·적분기·이전 명령 등은 현재 피드백과 대조해 재초기화 여부를 어댑터가 결정한다. 시리얼 제출만 확인했다면 실제 적용 상태를 알고 있는 것으로 가정하지 않는다.

사본의 최대 크기·buffer·직렬화/검증/적용 예산과 전송 경로를 따로 정한다. 큰 상태 전송이 작은 control·명령 처리를 막지 않도록 기존 I/O 소유 분리와 고정 상한을 적용한다. 내부 식별 의미가 같다면 기존 봉투·revision을 재사용하고 중복 공개 필드를 만들지 않는다.

승계 직전에는 현재 pose·속도·제어·필수 입력으로 경로 연결과 제한된 실제 계산을 확인한다. 경로가 그대로 유효하면 비싼 탐색을 반복하지 않고 추종을 시작할 수 있다. 현재 위치에서 이어갈 수 없으면 정지 후 제한된 재계획으로 낮춘다. B는 **자기 실행에서 새 명령을 계산**하며, A의 과거 명령에 새 시각·B 신원을 붙여 재생하지 않는다. UUID·boot/instance·인증정보·CPU 정책·출력 권한은 복제하지 않는다.

Active가 새 maneuver revision을 사용하면 B의 옛 revision 준비는 그 새 의도의 연속 승계 근거가 아니다. 선택 직후에도 현재 준비·generation·실행을 다시 확인한다. 양쪽 부적합이면 A/B를 반복 선택하며 세대를 폭증시키지 않는다.

현재 maneuver의 내구 보존이 필요한지, 같은 host에서의 bounded RAM 상태로 재구성할지는 구현 전 정한다. 어떤 방식을 쓰든 **지도·앱 메모리 전체 복제·매 주기 fsync**를 기본으로 넣지 않는다. 권위 문맥을 잃으면 정지 후 재확인한다.

### 12.5 메인 연속 시나리오

| 단계 | 사건 | 기대 결과 |
|---|---|---|
| 1 | 실제 설치된 A/B가 현재 입력·설정·신원으로 준비 | 출력 금지 상태에서 준비·명시적 재무장 조건 확인 |
| 2 | A AUTO 운행·도로 추종/우회 | A만 실제 출력. B는 현재 mode/maneuver의 준비 평가 |
| 3 | Jetson 중단 | A를 유지하고 남은 국소 지도로 안전 정지한 뒤 MANUAL 전환. MANUAL·Pi 내부 차량 피드백 유지 |
| 4 | A MANUAL 중 Jetson 회복 | 지도·pose·AUTO 계획/추종의 회복을 확인해 AUTO_READY 보고. A는 MANUAL 유지 |
| 5 | 현재 문맥의 명시적 AUTO 복귀 | 준비 유지·카운트다운·새 제어 적용 뒤 A AUTO. 중간 준비 상실 시 취소 |
| 6 | A VM 장애 | 현재 AUTO를 이어받을 준비가 된 B로 승계. A 복구 완료를 기다리지 않음. 조건 미충족 시 정지 |
| 7 | A의 별도 VM 복구 | 새 execution·receipt·binding·앱 instance 검증. 원 작업·기한·의도 유지 |
| 8 | A가 새 지도·maneuver로 준비 | Standby 재합류. B 권한 자동 원복 금지 |
| 9 | B VM 장애 | 그 시점에 AUTO 준비가 된 A로 재승계. 과거 READY 사용 금지 |
| 10 | B 복구 | 같은 규칙으로 Standby. 시작 owner를 반대로 한 대칭 시험도 수행 |

MANUAL 운용 중 A 장애→B MANUAL 승계와 Jetson 중단 중 MANUAL Standby 재합류는 별도 회귀 시나리오로 유지한다. 이때 지도나 AUTO 준비를 MANUAL의 선행조건으로 요구하지 않는다. 사용자 직접 MANUAL 선택 뒤 AUTO가 정상·복구되는 경우와, 장애 대응 MANUAL 중 사용자가 MANUAL 유지를 새로 선택한 경우도 확인한다. 두 경우 모두 명시적 AUTO 복귀 없이 모드가 바뀌지 않아야 한다.

VM 복구와 출력 보호·승계는 **병렬 책임**이다. 표의 나열 순서를 하나의 긴 blocking 호출로 구현하지 않는다. 기존 검토대장의 M01~M07·SC 항목은 회귀 색인으로 재사용하되 그 과거 상태표를 현재 완료 판정으로 복사하지 않는다. [P0]

<a id="s13"></a>
## 13. 앱 재초기화·VM 복구·재합류

### 13.1 앱 단위 재초기화

앱 재초기화로 해결할 수 있는 문제는 해당 앱을 재초기화하고, VM 복구가 필요한 문제는 VM 단위로 복구한다. 앱 소유 작업·자원을 정리할 수 있는 범위와 공통 runtime·kernel에 영향을 주는 범위를 구분한다.

```text
해당 앱의 명령/준비 무효화
→ 새 작업 수락 중지·진행 중 작업 취소 요청
→ 제한된 종료/join 확인
→ 해당 앱 소유 자원만 회수
→ 새 앱 instance·빈 작업 상태 생성
→ 현재 control·해당 앱에 필요한 입력·상태 재적용
→ 실제 계산·준비 확인
```

앱의 결과 slot·callback·timer·worker·path 참조가 이전 수명에 속하지 않도록 한다. 안전하게 종료되지 않은 작업의 stack·pool·handle을 새 앱에 재사용하지 않는다. Zephyr는 종료/abort된 thread의 공유 자원을 자동으로 정리하지 않는다. [R14]

**결과 사용 철회는 실제 종료를 기다리지 않고, 자원 재사용은 실제 종료·참조 회수 확인을 기다린다.** 취소 직후 늦게 완료된 결과도 이전 수명·원 작업과 대조해 게시·출력에서 제외한다. 내부 완료 플래그만으로 thread 종료를 확정하지 않으며 지원되는 join으로 확인한다. AUTO의 종료 대기를 공통 감독·제어 처리 큐에서 길게 수행해 정상 MANUAL·통신·다른 감독을 막지 않는다. 정리 기한이 지나면 잔존을 기록하고 지원 수습으로 넘긴다.

AUTO만 재초기화할 때 정상 MANUAL·공통 netfront·Store·진단 publisher를 불필요하게 함께 재시작하지 않는다. 반대로 공통 runtime 손상·memory integrity 상실·kernel fatal은 앱만 초기화해 해결됐다고 보지 않는다.

AUTO 기능과 MANUAL 기능의 문제를 분리해 판단·복구한다. Jetson 통신·인지 문제로 A/B의 AUTO 모두 준비되지 않았더라도 정상 MANUAL과의 불필요한 복구 의존을 만들지 않는다. MANUAL을 유지한 채 AUTO의 원인·진행·준비 상태를 관측하고, 필요한 AUTO 복구가 수행되더라도 그것만으로 AUTO 모드로 전환하지 않는다.

### 13.2 재초기화 허가와 신원

guest boot는 같은데 AUTO instance만 바뀌는 경우를 지원하려면 **기존 receipt/binding 모델의 개정**이 필요하다. runtime이 새 ID를 보고했다는 사실만으로 Gateway가 승인해서는 안 된다. 현재 실행에 결합된 지원 재초기화 결과와 신뢰 경로를 통해 앱 신원 교체를 확인해야 한다.

교체는 해당 앱의 신원·진행·준비만 갱신한다. 같은 저장 단위에 여러 앱을 담더라도, 현재 권위 상태·기대 이전 instance를 대조해 해당 항목을 갱신하며 오래된 전체 사본으로 다른 앱의 최신 상태를 덮어쓰지 않는다. 정상 MANUAL·guest boot·별도 Publisher 신원과 영향 없는 출력 자격은 보존한다. 검증된 새 instance는 새 진행 기준으로 수락하고 옛 instance의 늦은 결과는 거절하는 두 방향을 모두 수락한다.

게스트 slot 철회가 Gateway에 남은 옛 명령까지 제거했다는 뜻은 아니다. 해당 앱의 철회·교체를 Gateway가 확인하는 경로와, 전달 실패 시 기존 만료 보호가 출력 사용을 끝내는 시점을 함께 검증한다. 앱 재초기화는 다른 정상 앱의 상태를 일괄 초기화하는 근거가 아니다.

구체적인 앱 재시작 요청·확인 프로토콜이 확정되기 전에는 기존 신원 검사를 끄거나 원격 `restart_app` API를 임의로 추가하지 않는다. 이 연결이 출시 관문이다. 종료 안전성·신원 연결을 입증하지 못한 오류는 VM 복구 단위로 남긴다.

### 13.3 VM 복구와 원 작업 보호

Worker는 기능/시간/자원/전달의 근거와 사용자 의도·현재 실행·원 operation/attempt·기한·예산·승인을 대조해 기존 Manager 경로로 복구한다. broker·지도·입력·warm-up 부족 자체만으로 반복 restart하지 않는다. 로컬 앱 복구와 Worker가 같은 장애에 경쟁 실행하지 않도록 유예·소진·회복 근거를 연결한다. [P1: W02~W04]

S01/S02의 이력 상실 차단·같은 사건 ID·pending 보존, D02/D08의 수락/완료/미확정과 원 요청 key, D03의 원 기록·외부 효과 대조는 유지한다. Worker 복구 상태의 SQLite 채택 여부는 Jetson의 지도 저장 방식과 별도다. 새 앱 구조 때문에 원 journal 삭제·force·새 deadline을 복구 우회로로 사용하지 않는다. [P2][P3][P4]

### 13.4 새 VM의 재합류

```text
Manager가 새 실행 확인
→ 현재 실행별 credential/receipt/binding 공급·대조
→ 지원 schema·차량 설정·앱 identity 확인
→ 현재 control과 모드별 필수 입력·상태 공급
→ 해당 모드의 계산·입력·상태·시간·자원 준비
→ 해당 모드의 Standby 자격 확인
```

| 준비할 모드 | 확인할 자료 |
|---|---|
| AUTO | 국소 지도 snapshot·로컬 pose·차량 설정·기준 경로·필요한 현재 maneuver |
| MANUAL | 현재 입력 세션·control·필요한 로컬 차량/장치 상태. 지도·AUTO 준비는 요구하지 않음 |

한 모드의 준비 여부로 다른 모드의 준비를 대신하지 않는다. AUTO 준비가 아직 되지 않은 VM도 MANUAL 조건을 충족하면 MANUAL Standby로 재합류할 수 있다. 사용자가 조작하지 않는 정상 대기와 해당 모드의 기능 실패는 구분한다.

정당한 새 실행은 받아들이고 이전 실행 자료는 배제한다. 플랫폼 COMPLETED는 새 실행 관측이라는 기존 의미를 유지하며, 지도 준비·기능 회복·Standby·출력 권한과 합치지 않는다. 재부팅 후 신호 한 번으로 장애 episode·재시도 예산을 초기화하지 않는다.

<a id="s14"></a>
## 14. Gateway–ESP32 명령·피드백

### 14.1 출력 경로

A/B·AUTO/MANUAL은 각각 명령 **후보**를 생성한다. Gateway는 현재 허용된 VM/app·generation·원 계산과 입력 유효성·준비·출력 허가를 확인하고 하나만 USB 시리얼에 제출한다. 앱이 USB·모터 장치를 직접 열지 않는다.

새 데이터는 주행 결과의 의미를 바꾸지 않는다. `v_mps`는 목표 차량 속도, `steer_rad`는 명시한 전륜 조향 목표다. map/plan 전체는 ESP32로 보내지 않는다. 경로 선택·reference 복귀 판단은 Pi에 남는다.

### 14.2 ESP32의 실행 책임

ESP32는 명령 framing·길이·지원 버전·세션/epoch/counter·범위·만료를 확인하고 모터·서보를 구동한다. 원 시리얼 프레임 형식의 기존 보호를 재사용하며 새 MQTT generation/seq를 시리얼과 무조건 동일하다고 취급하지 않는다.

encoder가 실제로 사용 가능하면 로컬 속도 폐루프 제어와 피드백을 담당한다. 서보 실제 각도 센서가 없으면 target angle 또는 추정값임을 표시한다. device reset 시 출력 허가는 안전한 초기 상태에서 다시 성립해야 한다.

장치 보호는 두 가지다.

| 보호 | 의미 |
|---|---|
| 명령 상실/만료 보호 | 새로운 유효 명령이 기한 내 오지 않으면 정의된 정지 동작 |
| ESP32 실행 watchdog | device task의 실행 정체를 감지하는 별도 기능 |

하나를 구현했다고 다른 하나까지 완료했다고 하지 않는다. 마지막 명령을 무기한 유지하는 fallback은 없다. 실제 전원·배선·모터 드라이버·E-stop과 함께 정지 동작을 검증한다.

### 14.3 피드백

| 자료 | 조건 |
|---|---|
| ESP32 boot/session·표본 순번·원 시각 | 재부팅·중복·역전·표본 누락 확인 |
| encoder 누계·속도 | 실제 측정 여부, reset/wrap, 사용 구간과 오차 |
| 마지막 수락/적용 명령 참조 | UART 수신, 유효성 수락, 출력 설정 단계를 구분 |
| E-stop·watchdog·구동 fault·가능한 전압 | 실제 관측 범위만 제공. 미지원/수집 실패를 false/0으로 만들지 않음 |
| steering 상태 | 측정·추정·명령을 구별 |

**시리얼 write 성공은 장치 적용 ACK가 아니다. ACK도 실제 바퀴 이동의 증거와 다르다.** Gateway가 원 명령과 ESP32의 session/counter를 대응시켜 확인한 만큼만 표시한다. 기존에 미연결인 적용 피드백은 이 설계의 구현 대상이며 이미 완성된 것으로 쓰지 않는다. [P0][B1]

### 14.4 독립성의 한계

ToF를 모두 Jetson에 연결하면 ESP32가 Jetson과 무관하게 장애물을 인지한다고 주장할 수 없다. 별도 근거리 센서를 ESP32에 추가하는 것은 새 하드웨어 결정이며 이번 기준본에서 자동 채택하지 않는다.

Pi/dom0/Gateway가 사라지면 현재 장치 경로는 명령 상실에 따른 정지를 기대한다. 두 broker·A/B는 dom0·전원·하이퍼바이저 전체 실패에서 주행을 지속하는 보장이 아니다.

## 15. 자원·통신량·기한·저장 예산

### 15.1 수치의 상태

| 항목 | 대화/기준선에서 다룬 값 | 이 문서에서의 의미 |
|---|---|---|
| 기존 drive release | 20ms/50Hz | 기존 구현 기준. 새 planner의 처리 성능 보증이 아님 |
| 기존 command/input/readiness | command 100ms, manual input 200ms, readiness 300ms, 준비/재개 3초, control 적용 1초 | 각 시간의 원천·수신·사용 의미를 보존. 신규 지도 TTL로 그대로 복사하지 않음 |
| 이전 perception 입력 | 300ms | 새 지도/cell/pose 유효기간과 별개 |
| 기존 C client RX 기본 | 1,280바이트 | 작은 JSON 메시지 경로의 당시 설정. 지도 수신에는 별도 구현 필요 |
| 기존 Pi broker packet 상한 | 66,560바이트 | 당시 설정. 새 Jetson broker와 encoder/decoder/VM 상한을 각각 확정해야 함 |
| 기존 kernel heap | 65,536바이트 | 전체 VM RAM·자유 메모리·새 지도 예산과 다름 |
| 기존 Zephyr 자원 프로필 | 관리 소스의 1 vCPU·16MiB 프로필 | 현재 구현의 프로필값이며 이 설계의 영구 RAM 상한은 아님. 앱·통신·계획·진단을 포함한 실제 예산으로 RAM 결정 |
| 지도 예시 | 80×80, 총 3byte/cell, 10Hz | **계산 예시. 실제 해상도·영역·cell encoding·주기 확정값 아님** |

기존 수치 근거는 대화에서 확인한 `4bbdef0c…` 및 첨부 D01 보고서다. 새 구조를 그 숫자에 맞춰 시험했거나 현 보드에서 적용 중임을 주장하지 않는다. [B1][P3]

Zephyr의 RAM은 앱 설계에 맞춰 정한다. RAM을 변경할 때는 Zephyr DTS·링커 메모리 영역, 펌웨어 manifest·자원 프로필 검증, Xen guest 설정·실제 할당이 일치해야 한다. 현재 코드에 16MiB를 요구하는 검증이 있다는 사실과 앞으로도 16MiB만 사용해야 한다는 설계 조건은 구분한다. 필요한 변경은 새 프로필/번들로 검증하며 기존 불변 번들을 덮어쓰거나 `xl`의 memory 값만 바꾸지 않는다. RAM 결정으로 UUID·CPU 배치·모드 권한을 변경하지 않는다.

### 15.2 두 broker 배치에 맞춘 통신량 계산

payload 기준 broker 처리량 예산은 다음처럼 계산한다.

\[
B_{broker}\approx\sum_i f_iS_i(1+n_i)
\]

\(f_i\): 발행 빈도(Hz 또는 messages/s), \(S_i\): 메시지당 payload 크기(byte/message), \(n_i\): 실제 구독자 수다. 발행 주기 \(T_i\)(s)를 사용하면 \(f_iS_i=S_i/T_i\)다. 이 식은 CPU 사용량·tail latency·deadline 보장식이 아니다.

**예시:** 80×80×3byte = 19,200byte/snapshot, 10Hz, 지도 구독자 A/B 2개.

| 구간 | payload 예산 | 최종 두 broker 배치의 경로 |
|---|---:|---|
| Jetson mapper → broker J | 192,000 B/s = 1.536 Mbit/s | 같은 Jetson 내 전달. 보통 host 내부 경로 |
| broker J → A/B 합계 | 384,000 B/s = 3.072 Mbit/s | Jetson–Pi 외부 연결을 지도 사본 2개가 통과 |
| broker J 입출력 합계 | 576,000 B/s = 4.608 Mbit/s | broker 처리 payload 합계. 단일 물리 링크 사용량과 다름 |
| Pi broker의 해당 지도 본문 | 0 B/s | bridge·재발행이 없다는 설계 기준 |

메타데이터·도로 점열·MQTT/TCP/Ethernet·TLS·ACK·재전송·다른 stream은 제외한 값이다. Spring이 원 지도에 직접 추가 구독하면 외부 전달량도 증가한다. 불필요한 원 지도 구독을 기본값으로 두지 않는다.

네 앱이 각각 50Hz·512byte 후보를 발행하는 **별도 상한 예시**에서는 Pi broker ingress가 102,400 B/s다. 실제 송신 프로필·구독자 수를 확정하기 전 이 숫자를 제품 실측으로 표시하지 않는다.

이 계산으로 현재 broker 병목을 확정할 수 없다. protocol 수나 topic 수보다 client 처리·복사·logging·slow subscriber·공유 CPU·video 부하와 제어 지연을 함께 본다.

### 15.3 지도 packet·buffer 예산

최대 encoded snapshot은 broker packet cap에서 topic·MQTT header·필요 overhead를 뺀 값보다 작아야 한다. 메타데이터 문자열·repeated field·도로 표본을 포함한 **최대 encode 길이**를 생성 schema와 시험으로 검증한다. 단순 cell 배열 크기만 비교하지 않는다.

새 map client는 기존 JSON envelope decoder를 통과시키지 않는다. 큰 payload를 잘못 구독했을 때 끝없이 읽어 버리는 경로도 제한해야 한다. 기존 RX 설정만 올려 RX/payload/latest 여러 배열을 모두 크게 만드는 변경은 피한다. [B1]

같은 예시의 map 3개는 57,600byte다. 여기에 wire/decoder·metadata·path·search node·network buffer·stack·진단까지 더해야 한다. 64KiB heap 안에 맞는다는 의미가 아니다.

\[
M_{VM}\ge N_{map}M_{map}+M_{wire}+M_{decode}
+N_{path}M_{path}+N_{node}M_{node}+M_{index}+M_{queue}+M_{collision}
+M_{sync}+M_{odom\ history}+M_{network}+M_{stacks}+M_{runtime}+M_{reserve}
\]

검색 색인·queue·충돌 검사·상태 사본·odom 이력까지 서로 겹치지 않는 항목으로 계산한다. 컴파일된 배치·동시 참조·실제 high-water를 함께 확인한다. static buffer도 VM RAM을 사용한다. 고정 상한을 초과한 자료는 계획되지 않은 동적 할당으로 수용하지 않는다.

빌드·설치 명세에는 A/B 각각의 vCPU·승인 pCPU 배치·할당 RAM·펌웨어 메모리 영역·고정 pool·stack/heap·여유와 해당 프로필 해시를 기록한다. 실제 값이 없는 칸은 설계 미정/미측정으로 남긴다. 같은 앱을 담는 공통 번들의 자원 조건을 두 VM이 모두 충족하는지 확인하고, host 전체 RAM만으로 충분하다고 판단하지 않는다.

## 16. 장애 판정·동작·회복 대응

> **CPU·메모리·스레드 상태를 정식 건강 판정의 입력으로 사용해야 합니다. 다만 그 결과는 모두 ‘VM 재시작’으로 이어지는 것이 아니라, 경고·준비 제한·기능 축소·승계·앱 재시작·VM 복구 중 적절한 행동으로 연결돼야 합니다.** [P1][P5]

### 16.1 판정 원칙

관측 사실, 원인 추정, 영향 기능, 행동 허가를 분리한다. CPU가 높아도 실제 기능·기한이 정상일 수 있고, CPU가 낮아도 필수 작업은 멈출 수 있다. 기존 high CPU 경고를 곧바로 VM 복구 조건으로 바꾸지 않는다.

같은 경로로 오는 지도·상태·heartbeat는 독립적인 네트워크 증거 셋이 아니다. 관측 unavailable·partial·expired를 정상값·0·빈 지도·빈 VM 목록으로 바꾸지 않는다. 명시적 현재 fatal·필수 실패를 평균 정상 CPU나 heartbeat로 상쇄하지 않는다.

### 16.3 행동 주체와 실제 회복

앱 감독은 지원되는 앱 오류의 재초기화를 소유하고 Worker는 VM 복구를 소유한다. Gateway는 출력 제한·모드·승계를 소유한다. 같은 장애를 CPU·진행·heartbeat 사건 각각의 별도 복구로 증폭시키지 않는다.

회복은 새 instance·메시지 한 번이 아니라 현재 입력·자원·기능·기한의 실제 회복으로 확인한다. 재시작 직후 잠깐 정상 신호가 왔다고 장애 episode·attempt budget을 초기화하지 않는다. 로컬 복구 유예를 heartbeat마다 연장하지 않는다. [P1: W03~W04]

관측기·broker·입력만의 장애에 VM 복구로 원인이 사라진다고 가정하지 않는다. 정확한 원인이 미확정이어도 유효하지 않은 출력은 즉시 제한할 수 있다. 원인 확정을 기다리느라 이미 만료된 명령을 더 오래 쓰지 않는다.

첨부 D01 보고서는 기존 두 알고리즘을 유지하면서 건강/기한을 연결했다고 명시한다. 그 로컬/native/ARM 통과는 새 planner·binary map·독립 앱 실행의 검증이 아니다. [P3: 19~32, 64~87행]

### 17.2 공개 계약 개정 묶음

| 계약 | 함께 변경할 소비자 |
|---|---|

기존 strict enum/unknown-field 검사를 무작정 풀거나 새 field를 producer만 먼저 발행하지 않는다. 구형 `verified-drive-1`과 새 지도형 프로필의 호환/거절 경계를 명시하고, 지원하지 않는 설치본은 준비를 승인하지 않는다.

### 17.3 바꾸지 않는 관리 계약

D02/D08의 원 key·pending/unknown/completed 구분, fork와 물리 잠금의 책임, 원 실행 deadline, 사용자 stop 우선 수락, D03의 증거 기반 수습은 유지한다. 앱 설계 문서가 FastAPI·Spring 제품 코드를 대신 수정하는 승인은 아니다. [P2]

## 19. 수락 시험과 완료 기준

### 19.1 검증 단계

| 단계 | 증명할 것 | 증명하지 못하는 것 |
|---|---|---|
| 계약·host 단위 시험 | parser/계산/상태전이·bounded input·동일 C/Python 해석 | 실제 Xen scheduling·센서·장치 성능 |
| Zephyr native/제품 연결 시험 | 실제 앱/runtime·broker·소유권·fault 경계 | 물리 IRQ·NIC·SD·모터 적용 |
| 고정 ARM 빌드·부분 패키징 | 타입/빌드/링커 메모리·source→package 바이트 대응 | 실행 중 최악 지연·보드 수락 |
| 실제 Pi/Jetson 설치본 | 네트워크·전체 계산 부하·clock·제어 지연·실제 source | 아직 연결하지 않은 ESP32 물리 정지 |
| 차량 종단 | 센서→지도→판단→장치 적용·피드백, 전환·우회·재합류 | 지원하지 않은 도로·센서 배치·동적 환경 |

각 시험은 후보 commit+diff·설정·firmware/schema hash·대역 경계·원자료·기대/금지 호출을 기록한다. 실패를 고쳐 통과시켜도 수정 전 반례를 삭제하지 않는다. 플랫폼 제공부, 담당별 연동, 실제 설치본, 차량 종단의 완료 상태를 따로 기록한다.

### 19.2 필수 시험 표

아래 `ARCH-Txx`는 **이 설계서의 수락 ID**다. 기존 관리·복구 시험과 연결할 때도 원 시험 ID와 결과를 보존한다. 시험의 목적은 다음과 같이 묶는다.

각 시험은 잘못된 수락·재사용이 없다는 조건과 **정상 작업이 제한된 시간 안에 진행되는 조건**을 함께 확인한다. 계산·채택·취소·통지의 상한과 부하·입력 조건을 시험 프로필에 먼저 고정하며, 측정되지 않은 상한을 통과로 표시하지 않는다. 계속 차단한 결과만으로 정상 시작·회복까지 수락하지 않는다.

### 19.3 성능과 trace

최대 지도·A/B·제어·상세 진단·영상 부하를 함께 적용하고 단계별 지연을 나눈다.

```text
sensor capture → mapper complete → publish submit → receive complete
→ map accepted → planner result → tracker command → Gateway selection
→ serial submit → ESP32 accept/apply → actual feedback
```

전체 본문을 영구 저장하지 않는다. **실행/표본/계획/명령 ID, 원 시각과 clock 품질, 큐 깊이, 폐기 이유, byte·message 카운터, p50/p95/p99·최대 관측 지연·deadline miss**를 제한된 trace로 수집한다. Mosquitto `$SYS`는 broker 관측의 일부로 사용하되 앱 내부 지연·원 정보 나이를 대신하지 않는다. [R20]

공유 상태의 잠금은 획득 횟수뿐 아니라 **보유시간·대기시간·획득 실패·중첩 순서**를 작업별로 기록한다. 큐 대기, 계산 release 지연, 결과 게시→채택 시간을 연결해 긴 계산·I/O·정리가 다른 경로의 예산을 소비하는지 확인한다. 대상 선택·준비 문맥 전달·기존 출력 자격 종료·새 출력 허가의 네 시점과 활성화 요청→첫 유효 명령의 구간도 같은 원 요청·실행에 연결한다. 측정 구간이 겹치면 중복 합산하지 않는다.

각 장치 안의 구간은 해당 로컬 단조 시계로 측정한다. 장치 사이의 지연은 검증된 시계 대응과 오차 범위가 있을 때만 계산하고, 없으면 구간별 간격·처리시간과 원 ID 대응을 보고한다. 보존 지도의 관측 나이를 현재 명령의 처리·전달 지연으로 합산하지 않는다.

Standby 비교에서는 평소 대기 CPU·동기화 처리 비용, 준비 실행 비용, 장애 감지부터 새 명령 제출까지의 승계 중단을 나눈다. 계산을 줄인 효과와 상태 전송·확인 비용을 함께 측정하며, 정상·부분 동기화·재계획 필요 조건을 구분한다.

최대 관측값은 수학적 WCET 증명이 아니다. 단독 실행 평균뿐 아니라 전체 부하·재연결·느린 consumer·동시 오류 조건에서 판단한다. syscalls·fsync·외부 Store 작업에 대해 timeout이 실제 작업 취소까지 보장한다고 주장하지 않는다.

### 19.4 최종 완료 조건

**계약 동일성 → 고정 자원·bounded 처리 → 정상 기능 → 입력/계산/전달 실패 제한 → 지원 앱/VM 복구 → 현재 상태 재합류 → 실제 장치 적용/정지 → 같은 설치본의 회귀**까지 연결돼야 한다.

실제 센서가 아직 없으면 fixture라고 표시한다. 별도 native 시험과 별도 Manager 대역 시험을 합쳐 실제 차량의 단일 종단 통과로 보고하지 않는다. 상위 담당자 구현 대기 상태는 플랫폼 제공부 완료와 별도로 유지한다.

결정한 값은 근거·담당자·적용 프로필·관련 수락 시험과 함께 기록한다. 계약 정의, 구현, 로컬 검증, 설치본·차량 수락을 구분하고, 공동 계약에 연결되지 않은 항목을 완료로 표시하지 않는다.

실행 경계를 본문에 보완한 것은 위 결정의 wire·수치·제품 이행까지 확정했다는 뜻이 아니다. 검토 의견을 현재 제품의 잠금 결함 재현이나 성능 개선 실측으로 해석하지 않는다.

## 21. 권장 소스·배포 구성

### 21.1 소스 구성의 논리 예시

아래는 담당별 모듈 경계의 예시다. Pi 쪽은 기존 `platform/apps/drive/`, `platform/apps/common/xenova-drive-runtime/`, `platform/apps/common/xenova-mqtt-c/`와 AUTO/MANUAL 계산 코드를 우선 재사용한다. 예시의 논리 구분을 맞추기 위해 기존 코드를 일괄 이동하지 않는다. Jetson·schema·ESP32 쪽의 새 위치는 각 담당 저장소의 구조에 맞춰 정한다.

```text
contracts/drive-world/
  world_snapshot.proto / *.options
  health_vehicle.proto
  schema-version / bounded-profile / golden-vectors

jetson/
  sensors/           # 단일 소유·원 sample/clock·calibration
  perception/        # 도로·depth/ToF·장애물 근거
  mapping/           # 누적 지도·저장/복원·위치 정합·국소 snapshot
  runtime/           # 수집/처리/상태 수명·bounded queue
  transport/         # broker J publisher/subscriber
  video/             # JPEG branch·bounded viewer
  api/               # 필요한 HTTP GET stream/snapshot만
  deploy/            # broker·runtime·영상의 config/unit
  tests/

platform/apps/
  common/xenova-drive-runtime/  # 공통 제어·진행·준비·계산/통신 수명
  common/xenova-mqtt-c/         # 기존 MQTT 전송과 원 메시지 문맥
  drive/zephyr/                # 공통 펌웨어·앱 어댑터·향후 지도/계획 연결
  autonomous/                  # 기존 AUTO 계산·관련 시험
  manual/                      # 기존 MANUAL 계산·관련 시험

# 추가할 책임: 지도/path pool, planner/tracker, 앱 감독·상태 동기화
# 각각의 실제 위치는 위 기존 모듈의 소유·실행 경계를 기준으로 정한다.

esp32/
  protocol/ control/ feedback/ safety/ tests/
```

소스 디렉터리와 실행 작업은 일대일 관계가 아니다. 모듈 이름만 나누거나 thread 수만 늘리는 것으로 앱 독립성을 판단하지 않는다. 계산·대기·상태·메모리·lock·장치 소유와 실패 처리의 실제 관계를 확인한다.

### 21.2 배포물에 포함할 것

같은 릴리스에서 schema·Python/C generated code·nanopb runtime/compiler·firmware·vehicle model·primitive·calibration·broker config·ACL·runtime unit·영상 profile을 식별한다. 최신 upstream `latest`를 그대로 제품 버전으로 쓰지 않고 빌드 revision과 license를 고정한다.

공통 최종 펌웨어 번들의 해시를 A/B 설치 명세에 연결한다. 펌웨어는 같아도 각 VM의 UUID·실행별 Bootstrap·MAC·인증정보·승인 CPU 배치는 독립적으로 유지한다. 펌웨어·공용 설정과 장치별 설치 입력·비밀을 구분하고, 설치 검사에서 공통 번들 동일성과 신원 분리를 각각 확인한다.

두 broker 주소·자격·client 역할, 실제 A/B UUID, receipt/binding·권한 원본 경로, ESP32 장치 경로·serial profile을 설치 입력으로 제공한다. 비밀·운영 ID를 공개 예제값으로 배포하지 않는다. 같은 설치를 다시 실행해 UUID·Authority·기존 신뢰 정보를 멋대로 재발급하지 않는다.

서비스 시작은 local 필수 조건과 외부 연결을 구분한다. Jetson offline 때문에 Pi host admission·MANUAL·기존 관리 전체가 무한 대기해서는 안 된다. 주행 readiness는 서비스 `active`와 별도로 검사한다. Jetson은 웹 시청자 접속 전에도 지도 작성이 독립적으로 시작돼야 한다.

| 순서 | 작업 | 마감 산출물 |
|---|---|---|
| 1 | 공통 준비·건강·앱별 신원·모드/입력/상태 연결과 담당 경계, schema/clock/frame·고정 상한 확정 | DEC-10·11·16·19와 9.4절 소유표를 producer/consumer 계약·golden vectors·수락 assertion에 연결. 남은 결정의 담당·적용 시점 명시 |

| 8 | 이미지/설치·회귀·운영 문서·최종 연속 시나리오 | A/B 공통 번들과 독립 신원 확인, 같은 릴리스의 정상·실패·복구·재합류 근거 |

첫 세 묶음은 기존 계산 함수를 사용해 공통 기반부터 검증한다. 소스·설정·산출물 해시·실행한 시험·미검증 범위를 고정해 두 기준 문서의 정합성·최적화 검토에 전달한다. 담당자 요청서는 공개 계약이 확정된 뒤 실제 수정 위치·입출력·수락 조건을 기존 ID에 연결하며, 요청서 작성만으로 담당자 구현을 완료 처리하지 않는다.

이 검토 뒤 기존 관리·복구 시나리오의 플랫폼→HTTP→Spring·필요한 화면 연결을 별도 변경 묶음으로 확인한다. 원 요청·의도·기한·미확정 결과의 종단 보존부터 진행하고 18절의 소유 경계를 유지한다. Jetson·ESP32와 새 주행 상태가 필요한 사례는 위 후속 기능·장치 단계의 실제 수락과 연결하며, 대역 시험을 실제 제품 종단 수락으로 바꾸지 않는다.

단계를 나누는 것은 임시 JSON 제품을 먼저 배포한다는 뜻이 아니다. **최종 바이너리·자원·실패 계약을 처음부터 기준으로 두고 구현과 검증을 분해**하는 것이다.

### 22.3 이 기준본의 최종 해석

**현재 구조를 유지할 부분:** Pi의 Xen·netfront·dom0 네트워크·단일 Gateway·ESP32 USB 시리얼, 관리 원본과 복구 보호.  
**구현·보완할 중심:** Jetson 누적 지도 생산·영구 저장/복원·별도 broker·binary full snapshot·GET 영상, 기존 runtime을 활용한 AUTO/MANUAL의 실행·자원 경계, 지도 기반 계획·추종, 상태 동기화와 Standby·승계.  
**현재 하지 않는 것:** bridge, Pi 자체 지도 재구축, 통신 원문 전량 저장, 전면 SQLite화, UDP/UART/장치 할당 재설계, dom0 장애 후 주행 지속 보장.

> **완료 기준은 같은 설치 후보에서 입력의 의미·자원 상한·출력 권한·실제 장치 반응·실패 후 재합류를 연결해 확인하고 재현할 수 있는 것이다.**
