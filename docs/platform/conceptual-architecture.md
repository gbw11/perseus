## 0. 먼저 기억할 한 장

Xenova를 하나의 거대한 VM.status로 읽지 않는다. 다음 질문의 답을 따로 보관하는 시스템으로 읽는다.

|질문                          |그 답을 소유하는 개념            |
|----------------------------|------------------------|
|**무엇을 관리하는가?**              |영구 VM 자산                |
|**어떤 구성으로 실행할 것인가?**        |현재 구성·선택한 산출물·자원 정책     |
|**무엇을 원했는가?**               |수락된 사용자 의도              |
|**그 요구를 처리하는 일은 어디까지 왔는가?** |원 관리 작업과 journal        |
|**지금 실제로 어떤 실행이 존재하는가?**    |Xen domain과 플랫폼 실행 문맥   |
|**무엇을 근거로 그렇게 말하는가?**       |관측·표본·receipt·binding   |
|**그 실행은 필요한 일을 할 수 있는가?**   |앱의 진행·기능 준비·건강 판단       |
|**문제가 생기면 누가 무엇을 고치는가?**    |로컬 감독·복구 사건·개별 복구 시도    |
|**지금 누구의 명령을 장치에 보낼 수 있는가?**|Gateway의 제어 권위와 현재 출력 허가|

```text
호출 성공 ≠ 요청 수락 ≠ 물리 동작 완료
VM 등록 ≠ Xen 실행 ≠ OS 준비 ≠ 앱 준비
관측 성공 ≠ 대상의 모든 기능 정상
앱 READY ≠ 출력 허가 ≠ 장치 적용
복구 완료 ≠ 기능 회복 ≠ Standby 재합류 ≠ 이전 Active로 원복
실행 종료 ≠ 부분 자산 정리 ≠ 예약 반환 ≠ 원 이력 삭제
```

예를 들어 **“등록됨 / 정지 의도 수락됨 / 정지 작업 진행 중 / 도메인은 아직 존재 / 앱 현재 상태 미확인 / 차량 출력은 차단됨”**은 모순이 아니다. 서로 다른 대상의 상태를 함께 설명한 것이다. 반대로 이 중 하나만 보고 나머지를 채워 넣으면 상태 모델이 무너진다. 근거 [S01](#src01) · [S02](#src02)

## 1. 도메인 지도 — 어디에서 어떤 말이 같은 뜻을 가지는가

### 1.1 이 문서에서 사용하는 DDD 관점

경계 문맥은 같은 단어와 규칙을 공유하는 책임 범위다. 엔티티는 속성이 달라져도 신원으로 이어지는 대상이다. 값은 내용과 적용 문맥으로 의미를 갖는 설정·표본·근거다. 정책은 주어진 사실에서 허용 행동을 정한다. 과정 조정자는 여러 대상의 작업을 순서와 원 요청에 맞춰 연결한다.

이 분류는 읽기 위한 모델링이다. 모든 명사에 UUID를 만들거나, 각 문맥을 별도 프로세스로 분리하거나, 모든 전이를 MQTT 사건으로 발행하는 뜻이 아니다. 실제 원본·직렬화·잠금·저장 단위는 별도로 확인한다.

### 1.2 여덟 가지 책임 문맥

|문맥             |이 문맥이 답하는 질문                            |중심 대상                                             |넘지 않는 경계                                 |
|---------------|----------------------------------------|--------------------------------------------------|-----------------------------------------|
|**자산 관리**      |무엇을 어떤 재료·구성으로 보유하는가?                   |템플릿, VM 자산, 현재 구성, 자산 세대, 자산 작업                   |등록 완료를 실제 기동으로 선언하지 않는다                  |
|**실행 관리**      |현재 의도 아래 어떤 VM 실행을 만들거나 끝낼 수 있는가?       |사용자 의도, 원 제어 작업, host gate, 실행 문맥, CPU 정책         |앱 READY·차량 출력권을 만들지 않는다                  |

|**건강·복구 조정**   |무엇이 제한됐고, 어느 범위의 복구를 허용하는가?             |건강 판단, 복구 episode, attempt, 반복 예산, 로컬 감독 상태       |사용자 의도·Manager guard·Gateway 권한을 우회하지 않는다|

### 1.4 논리 경계와 실제 배치는 다른 그림이다

Pi의 Xen·dom0·domU 배치는 실행 환경이고, 위 표는 의미와 권한의 경계다. 하위 Manager는 Python 라이브러리·CLI 경로이며 FastAPI dom0-manager와 같은 개념이 아니다. Worker와 Gateway도 각자의 원본과 행동 책임을 갖는다.

같은 Zephyr VM 안에 AUTO·MANUAL이 함께 있어도 두 계산의 소유와 수명은 나눌 수 있다. 다만 같은 주소 공간·커널을 공유하므로 논리적 앱 분리 자체가 메모리 오염 격리를 뜻하지 않는다. A/B 이중화 역시 공통 Jetson·broker·dom0의 문제를 두 개의 독립 센서 검증으로 바꾸지 않는다. 근거 [S06](#src06) · [S10](#src10)

## 2. 플랫폼의 핵심 대상 — 무엇을 보유하고, 무엇을 실행하는가

<a id="c-template"></a>

### 2.1 템플릿과 실행 산출물

> **개념 주석** — 템플릿은 VM의 재료다. 실행 산출물은 실제로 적재할 특정 바이트다. 둘 다 현재 실행 자체는 아니다.

정체성. 템플릿은 template_id + template_version과 게시 manifest로 구별한다. 산출물은 firmware revision·manifest·artifact digest와 출처로 연결한다. 같은 템플릿에서 여러 독립 VM을 만들 수 있다.

책임과 권한. 카탈로그는 지원 자원 범위·게스트 종류·capabilities·출처를 제공한다. 준비 경로는 선택한 자료와 실제 복사 바이트를 검증한다. 실행 경로는 실행에 사용한 구성을 확인한다. 카탈로그의 지원 선언은 실제 이번 실행의 성공을 보장하지 않는다.

수명. 게시된 버전을 선택하고 검증하여 VM 자산 또는 실행에 결합한다. 새 버전을 선택해도 과거 VM의 생성 출처를 소급 변경하지 않는다. 현재 파일과 실제 적재 당시 파일의 정체성을 구별한다.

혼동하지 않을 것. initial_spec, 현재 활성 firmware, 이번 실행의 loaded_artifact는 서로 다른 사실이다. 파일이 지금 바뀌었다고 이미 실행 중인 firmware의 신원이 바뀌는 것은 아니다. [S02](#src02) · [S03](#src03)

### 2.2 VM 자산

> **개념 주석** — VM 자산은 “우리가 계속 같은 VM이라고 부르는 대상”이다. 켜져 있지 않아도 존재한다.

식별자. vm_id는 영구 UUID다. 표시 이름·내부 이름·hostname·MAC/IP·domid를 영구 신원 대신 쓰지 않는다. 표시 이름과 경로용 내부 이름도 구별한다.

책임과 원본. 자산 관리가 등록 정보·현재 구성·소유 디스크·선택한 산출물·자산 수명을 관리한다. Spring의 표시·업무 기록은 이를 참조할 수 있지만 하위 실제 자산과 실행 결과를 대신 확정하지 않는다.

수명. 신규 create는 원 작업과 private 준비를 거쳐 등록한다. 정상 start/stop/reboot와 복구는 이 UUID를 유지한다. 자산의 보관·복원·영구 제거는 별도 lifecycle로 처리한다.

```text
미등록 생성 요청 ── private 준비·게시·등록 ──▶ REGISTERED
                                              │ retire
                                              ▼
                                           RETIRED
                                              │ purge
                                              ▼
                                           PURGING ──▶ PURGED

RETIRED ── restore ──▶ REGISTERED
```

불변 조건. create의 private workspace는 아직 정상 등록 VM이 아니다. get 부재가 원 생성 요청·부분 파일의 부재를 뜻하지 않는다. PURGED 뒤에도 재사용 방지와 원 결과 조회에 필요한 tombstone·이력은 별도의 수명으로 남는다.

기억할 점. delete의 보관 의미, purge의 영구 제거, 실패한 미게시 자산의 수습은 합치지 않는다. [S01](#src01) · [S02](#src02)

### 2.3 현재 구성과 자원 정책

> **개념 주석** — 구성은 “무엇을 얼마나 줄 것인가”, 배치 정책은 “어디에서 실행하게 할 것인가”다. 실제 배치는 다시 관측한다.

값의 범위. 현재 구성에는 vCPU 수·할당 메모리·게스트 종류·활성 firmware 등의 설정이 들어간다. 최초 생성 명세는 변경 이력을 설명하는 출처다. 자원 변경 뒤 현재 구성과 최초 명세가 다른 것은 정상이다.

정책의 원본. CPU 배치는 별도 정책 revision·hash·UUID별 할당으로 관리한다. 자산 구성 해시와 CPU 정책 해시, 렌더링한 xl 설정의 해시는 각각의 대상을 가리킨다.

변경 권한. 자원·firmware·CPU 정책 변경은 해당 계약의 정지·신원·소유권·기대 revision 조건 아래 수행한다. 조회가 실제 affinity를 자동 수정하거나 정책을 새로 발급하지 않는다.

수명. 구성이 바뀌면 그 구성에 의존한 실행 허가와 준비 근거를 재검토한다. 자원/firmware 변경과 자산 lifecycle 세대 변경은 같은 사건이 아니다. CPU 전용 예약은 VM 자산을 purge했다는 이유만으로 자동 반환되는 일반 용량 예약이 아니다.

혼동하지 않을 것. CPU 배치가 정확함, CPU 사용률이 낮음, 앱 계산이 기한을 지킴은 세 가지 사실이다. [S02](#src02) · [S07](#src07)

<a id="c-host"></a>

### 2.4 Host 부팅 문맥과 실행 수락 장벽

> **개념 주석** — host 문맥은 “이번 dom0 부팅에서 유효한 세계”다. gate는 그 세계에서 새 실행을 받아도 되는지 정한다.

식별자. host_boot_id는 이번 dom0 부팅을 구별한다. 물리 보드의 영구 ID가 아니다. host 장벽의 barrier_id는 특정 수락 장벽을 가리킨다.

상태. host admission은 open / quiescing을 구별한다. VM별 boot admission은 해당 host·VM 자산 세대·의도 revision에 적용되는 허가 근거다. host가 열려 있어도 특정 VM의 복구가 허가된 것은 아니다.

수명. 부팅 문맥을 만들고 VM별 부팅 정책을 평가한다. 종료는 gate를 닫아 신규 제출을 제한한 뒤 기존 소유 작업과 자원을 확인한다. host 재시작은 옛 단조 기한·runtime binding·관측의 적용 문맥을 끝낸다.

권한 경계. 관리 API 프로세스 재시작은 host 종료가 아니다. 부팅 표시기의 complete는 그 표시 항목의 완료이며 guest OS·Agent·앱 준비를 대신 판정하지 않는다. 전원 종료 전 저장소 해제는 잔존 VM·backend·준비 자원을 확인하는 별도 책임이다. [S01](#src01) · [S02](#src02) · [S04](#src04)

<a id="c-intent"></a>

### 2.5 사용자 실행 의도

> **개념 주석** — 의도는 “이 VM을 어떤 실행 상태로 두기로 수락했는가”다. 지금 그렇게 됐다는 보고가 아니다.

원본과 식별. VM별 desired_state와 intent_revision을 내구 기록한다. 의도는 적용할 자산 lifecycle 세대와 수락한 원 작업에 연결된다.

변경. 새 사용자 제어를 수락하면 revision이 바뀐다. 이미 실행 중인 VM에 start를 수락해도 새 의도일 수 있다. 같은 key 재전달은 같은 원 의도를 확인하는 것이며 새 revision을 발급하는 이유가 아니다.

불변 조건. 수락 뒤 물리 실행에 실패했다고 의도를 과거 값으로 되돌리지 않는다. stop 뒤 새 start가 수락됐다면 늦게 도착한 과거 stop 결과가 현재 의도를 덮지 않는다.

생명주기. 수락 → 해당 세대에 적용 → 더 최신 의도로 대체되거나 세대 변경으로 부적용. 기록 보존과 현재 적용 가능성은 별개다. 오래된 복구 요청은 새 의도 아래 자기 허가를 다시 통과해야 한다. [S01](#src01) · [S02](#src02) · [S03](#src03)

<a id="c-operation"></a>

### 2.6 원 관리 작업

> **개념 주석** — 작업은 “한 번 하기로 한 일”이다. 호출자가 끊기거나 응답을 잃어도 원래 그 일을 가리킨다.

|구분            |역할                                |
|--------------|----------------------------------|
|이번 호출         |전달·대기·응답의 한 수명. `request_id`로 추적  |
|원 요청 key      |같은 의미의 요청 재전달을 찾는 기준. 대상·내용과 함께 대조|
|`operation_id`|수락·진행·결과를 추적하는 원 작업의 신원           |
|`phase`       |준비·제출·게시·제거 확인 등 실제 진행 경계         |
|원 결과          |그 작업이 무엇을 수행·확정했는지에 대한 기록         |
|현재 관측         |지금 대상이 어떤 상태인지에 대한 별도 근거          |

세 계열. 자산 operation, 사용자 control-operation, 하위 recovery-attempt는 대상·허가·진행 단계가 다르다. 서로 같은 이름의 상태를 쓰더라도 같은 enum처럼 합치지 않는다.

책임. 원 key·정확한 명세·대상·의도·기한·외부 효과·필수 결과를 연결한다. 최초 수락 이전 거절, 수락 여부 미확정, 수락 후 pending, 물리 효과 미확정, 확정 완료를 구별한다.

재전달. 같은 key와 같은 내용은 원 결과 또는 지원되는 동일 이행으로 연결한다. 같은 key에 다른 대상·내용을 붙이면 충돌이다. 조회는 원 작업을 새로 실행하거나 기한을 연장하는 행위가 아니다.

종결. 성공·실패·대체됨과 수습 필요 여부를 각각 설명한다. 원 성공 뒤 현재 조회가 실패해도 성공 이력을 실패로 덮지 않는다. 필수 완료 저장 실패는 부가 진단 저장 실패와 구별한다.

주의. 원장에 RUNNING이 남아 있음, 실행자가 현재 활동 중임, VM이 running임은 서로 다르다. 활성 실행 관측인 effective_status도 영구 상태의 대체물이 아니다. [S01](#src01) · [S02](#src02) · [S05](#src05)

<a id="c-execution"></a>

### 2.7 VM 실행과 Xen incarnation

> **개념 주석** — 실행은 “그 VM이 이번에 시작된 한 번”이다. VM UUID는 유지돼도 실행은 교체된다.

신원. 플랫폼의 execution_id와 host, 자산·의도 문맥을 실제 domid + xen_unique_id에 연결한다. domid는 재사용될 수 있으므로 단독으로 현재 실행을 승인하지 않는다.

원본의 역할. 실행 기록은 launch 준비·소유자·구성·CPU 정책·기한을 묶는다. 실제 존재와 상태는 Xen에서 확인한다. 둘이 맞을 때 managed 실행으로 읽는다. 외부 xl 실행에 임의의 managed execution을 붙이지 않는다.

```text
launch 준비: execution_id 발급·소유/구성 고정
     → 물리 제출
     → 현재 incarnation 대조·실행 결합
     → 필수 검증·원 작업 결과 확정

어느 경계든 효과를 확정하지 못하면: uncertain / 원 기록으로 재확인
실제 종료를 확인하면: stopped
```

중요한 차이. execution_id는 물리 제출 전에 생길 수 있다. observed 실행 신원도 CPU 적용 등 후속 필수 검증의 완전성과 별개일 수 있다. ID 발급, 도메인 존재, 원 start 성공, 앱 준비는 다른 완료 지점이다.

권한. 하위 실행 관리가 현재 자산·의도·host·owner·구성·CPU·기한을 guard한 뒤 Xen 조치를 제출한다. Worker는 복구를 요청하고, 앱은 기능을 보고할 뿐 이 검사를 대신하지 않는다. [S02](#src02) · [S03](#src03)

<a id="c-preparation"></a>

### 2.8 준비 workspace·예약·명시 수습

> **개념 주석** — 준비 자산은 아직 게시하지 않은 결과다. 예약은 남이 가져가면 안 되는 약정이다. 수습은 실패의 흔적을 지우는 일이 아니라 그 약정을 안전하게 끝내는 일이다.

소속. private workspace와 원 디스크·주소·용량 예약은 원 create에 결합한다. 실행 슬롯은 동시 준비량을 제한하며, 원 실행 소유권은 정확히 누가 이 작업을 수행 중인지 보호한다. 슬롯과 예약은 같은 객체가 아니다.

정상 진행. 짧은 수락 구간에서 원 작업·예약을 확정하고, 긴 복사·guest 설정은 private 공간에서 수행한다. 게시 직전 현재 source·의도·신원·gate·예약을 다시 확인해 결과를 채택한다.

실패 진행. 원 실행은 자기 자식·일시 자원의 종료를 책임진다. 남은 부분 이미지와 최초 오류는 보존한다. 명시 수습은 원 기록에 결합된 소유 자산만 정리하고, 정리 결과의 내구 확정 뒤 예약을 반환한다.

불변 조건. 실패 원인은 보존하지만 종료된 실행의 공통 잠금을 계속 보유할 이유로 쓰지 않는다. 반대로 부모 부재·슬롯 반환·기한 만료만으로 자식·열린 자산·mount/loop가 사라졌다고 보지 않는다.

종결 의미. “원 생성 실패 + 수습 완료”가 가능하다. 같은 create key는 그 결과를 가리킨다. 정상 수습 뒤 별도 신규 생성은 새 요청이며, 미수습 상태를 새 UUID로 우회하는 것과 다르다. [S01](#src01) · [S05](#src05)

## 3. 관측과 신원 공급 — 무엇을 알고 있다고 말할 수 있는가

<a id="c-observation"></a>

### 3.1 관측과 조회용 snapshot

> **개념 주석** — 관측은 특정 대상에 대해 확인한 사실이다. snapshot은 그 사실의 보관 사본이지, 대상이나 실행 허가의 원본이 아니다.

내용. 대상 VM·host·실행·자산 세대·구성·의도 문맥과 실제 Xen 상태를 결합한다. 관측한 시각과 관측 실패도 함께 해석한다.

수명. 새로 성공 관측한 근거를 게시하고, 같은 값이면 값의 revision을 유지할 수 있다. 성공 재관측은 시각을 갱신하지만 단순 재전송은 재관측이 아니다. host 변경·실행 교체·오류·만료에서는 현재값으로 사용할 수 없게 된다.

|상태를 읽는 말                        |의미                              |
|--------------------------------|--------------------------------|
|`present / absent`              |성공 관측으로 확인한 존재·부재               |
|`managed / unmanaged`           |플랫폼 실행 문맥과 실제 incarnation이 연결되는가|
|`last_success`                  |과거 성공 근거. 지금 유효하다는 뜻은 아님        |
|`last_error`                    |최근 관측 실패. 대상 사망을 뜻하지 않음         |
|`stale / unknown / current=null`|현재 판단에 사용할 수 없는 근거              |

권한. 읽는 쪽은 허용된 조회 사본을 만들 수 있지만, 읽기만으로 원 operation·의도·예약을 종결하지 않는다. 화면용 관측을 실제 stop·삭제의 최종 guard로 그대로 넘기지 않는다.

정합성. 여러 원자 파일과 Xen이 한 순간의 전역 트랜잭션을 이루는 것은 아니다. 관측 전후 문맥을 대조하고, 바뀌었다면 제한된 재확인 또는 명시 오류로 처리한다. 서로 다른 시기의 정상값을 한 현재 상태로 조립하지 않는다. [S01](#src01) · [S02](#src02)

<a id="c-measurement"></a>

### 3.2 계측 표본·capability·보고자

> **개념 주석** — capability는 측정할 수 있다는 선언, 표본은 실제로 얻은 값, 보고자는 그 값을 전달하는 실행이다.

표본의 소속. CPU·메모리·스레드·네트워크·계산 지연은 원 실행과 계측 구간에 속한다. 값뿐 아니라 단위·분모·범위·원천 오류·첫 표본·reset·잘림·만료를 함께 읽는다. 이름이 같아도 guest CPU와 Xen 실행시간, heap과 전체 할당 RAM은 같은 값이 아니다.

보고자의 수명. Agent 또는 Publisher가 새로 실행되면 그 실행 문맥을 구별한다. TCP 재연결과 Publisher 재시작, Publisher 재시작과 앱 계산 task 재초기화는 각각 다르다.

책임. Diagnostics·Agent는 실제 원천과 수집 성공을 설명한다. Publisher는 전달·폐기·ACK 등 자기 전송 상태를 설명한다. 상위 건강 판단은 이 근거를 기능·정책과 연결한다.

금지되는 확대. Agent heartbeat로 collector 전체를, v2 Publisher heartbeat로 v1 주행 계산을, 잘린 thread 목록으로 모든 스레드의 정상을 증명하지 않는다. 상세 v2 단절만으로 정상 로컬 계산과 v1 준비를 철회하지 않는다. [S07](#src07) · [S09](#src09) · [S13](#src13)

<a id="c-receipt"></a>

### 3.3 Bootstrap receipt — 실행에 신원을 공급한 기록

> **개념 주석** — receipt는 “이 실행에 이 신원·설정을 공급했고, 적용을 어디까지 확인했다”는 기록이다.

식별과 소속. receipt_id, VM·host·execution·incarnation을 결합한다. guest boot namespace, v1 앱 신원, v2 Publisher 신원을 서로 구분하되 같은 guest 실행과 연결한다.

원본과 권한. 신뢰된 dom0 provisioning 경로가 원 receipt를 만들고 XenStore에 공급한다. guest가 새로운 UUID를 주장했다는 이유만으로 현재 신원으로 승인하지 않는다. credential 원문은 필요한 private 경계에 두며 일반 상태·로그와 섞지 않는다.

진행. 공급 준비 → Store 적용 → 적용 확인. 응답 유실이나 실행 변경이면 효과가 미확정일 수 있다. 수습은 원 receipt·현재 실행·Store 값·권한·원 호출의 종료 근거를 대조한다. 재확인이 새 신원 발급이나 무조건 재주입을 뜻하지 않는다.

끝의 의미. applied는 공급 적용 확인이다. 앱의 이전 작업 종료, 새 앱의 상태 준비, 실제 계산, Gateway 출력 허가는 그 다음의 독립된 사실이다. [S08](#src08)

<a id="c-binding"></a>

### 3.4 현재 실행 binding — 보고자를 받아들일 근거

> **개념 주석** — binding은 “지금 이 VM·앱에서는 이 실행 신원만 받아들인다”는 수명 제한 사본이다.

생성. 현재 Manager 실행 관측과 적용된 Bootstrap receipt를 대조해 만든다. 보고자가 자기 payload에 적은 execution 값 하나만으로 신뢰를 얻지 않는다.

수명. host·execution·앱 instance·lease·원 관측 시각에 묶인다. 현재 근거를 다시 얻지 못하면 갱신하지 않는다. 과거 receipt가 영구 저장돼 있어도 binding의 현재성은 자동 복원되지 않는다.

소비. 수신기는 일반 seq/latest 갱신보다 먼저 현재 허용 신원을 확인한다. 그래야 옛 실행의 큰 seq가 새 실행의 중복 판정 기준을 오염시키지 않는다.

앱별 교체. 한 앱만 바뀔 때는 검증 가능한 범위에서 그 앱의 근거만 철회한다. 교체 적용이 미확정인 대상은 옛 신원과 새 신원을 모두 준비 근거로 승인하지 않는다. 영향 없는 앱의 수명을 불필요하게 초기화하지 않는다.

기억할 점. 신원 승인, 보고의 신선도, 기능 READY, 출력 권한은 네 단계다. binding은 첫 단계의 근거이며 나머지를 대신하지 않는다. [S08](#src08) · [S10](#src10)

## 4. 게스트 내부 실행 — 앱과 자원을 누가 끝까지 책임지는가

<a id="c-app"></a>

### 4.1 앱 실행

> **개념 주석** — 앱 실행은 특정 VM 실행 안에서 독립적으로 진행·준비·재초기화되는 기능의 수명이다.

정체성. AUTO와 MANUAL은 기능 이름이다. 앱 instance는 그 기능의 한 실행을 식별한다. VM A/B와 AUTO/MANUAL은 서로 다른 축이며, A를 AUTO 전용·B를 MANUAL 전용으로 추정하지 않는다.

책임. 앱 어댑터는 입력 유효성, 내부 상태 적합성, 실제 계산 완료, 출력의 유효성과 기능 준비를 판단한다. 공통 runtime은 작업 제출·취소·join·문맥·자원 수명을 지킨다. 송신자는 그 결과를 전달한다.

|축       |값 또는 근거                                                 |뜻                          |
|--------|--------------------------------------------------------|---------------------------|
|작업 단계   |`WAITING / ACTIVATING / EXECUTING / STOPPING / RESIDUAL`|일이 없는지, 계산·종료 중인지, 자원이 남았는지|
|대기·활성 준비|`QUALIFIED / READY / NOT_READY`                         |대기 조건 또는 실제 활성 계산 조건을 충족하는지|
|감독 진행   |`check_seq`                                             |실제로 입력·설정·소유 상태를 확인한 순번    |
|계산 진행   |`progress_seq`                                          |해당 앱이 실제 완료한 계산의 순번        |
|제어 적용   |`applied_generation`                                    |어느 제어 문맥을 적용했는지            |

대기. warm 대기 중에는 건강 증명만을 위한 주행 계산을 계속 만들지 않는다. 할 일이 없어 progress가 멈춘 것과 유효한 작업이 있는데 완료가 막힌 것을 구별한다. 대기 자격은 즉시 출력할 자격보다 약하다.

재초기화. 해당 앱 결과 철회 → 새 제출 차단 → 취소·종료 확인 → 소유 자원 회수 → 정당한 새 instance 적용 → 현재 입력·제어·상태로 준비. join이 실패하면 같은 stack·buffer·handle을 새 실행에 재사용하지 않는다.

권한 경계. 앱은 READY를 보고할 수 있지만 자기 자신에게 owner·출력권을 부여할 수 없다. 앱별 기능 분리가 VM 전체의 메모리 오염까지 격리하지는 않는다. [S06](#src06) · [S10](#src10)

<a id="c-job"></a>

### 4.2 계산 작업과 상태 사본

> **개념 주석** — 계산 작업은 특정 입력·제어·상태를 사용한 한 번의 실행이다. 늦게 끝난 결과는 지금 필요한 결과와 다를 수 있다.

입력 문맥. 원 입력의 수신 근거·순번, 앱 instance, 제어·연결 revision, 사용한 상태 사본, release·deadline을 보존한다. 이것을 새 송신 봉투로 포장했다고 새 계산이 되지 않는다.

소유. 계산 스레드는 실행 중인 입력 사본을 소유하고, 별도의 최신 대기 작업과 결과 칸을 둔다. AUTO의 완료를 MANUAL이 기다리지 않는다. 놓친 release를 나중에 몰아서 실행하지 않는다.

결과 채택. 실제 완료했는지뿐 아니라 현재 문맥과 호환되는지, 입력이 유효한지, 정한 기한과 결과 조건을 충족하는지 확인한다. 정상적으로 정지를 계산한 결과는 계산 실패와 다르다.

상태 사본. 상태 있는 앱의 사본은 완전하게 적용된 revision·출처·설정·좌표·maneuver 문맥에 결합한다. 최초 시작은 지원되는 현재 입력 재구축을 사용할 수 있다. 연속 승계는 별도의 인계·연속성 근거가 필요하다.

참조 수명. 작업자가 사용하는 사본은 취소 요청 직후 바로 덮거나 회수하지 않는다. 참조 종료·join 등 소유 계약의 종료가 확인돼야 재사용한다. 상태 사본은 과거 명령·출력권·만료 시간을 연장하는 도구가 아니다. [S06](#src06) · [S10](#src10) · [S12](#src12)

### 4.3 공통 runtime과 자원 소유자

> **개념 주석** — 자원을 확보한 사실, 외부에 노출했을 가능성, 사용자가 끝난 사실, 반환이 완료된 사실은 서로 다르다.

소유 단위. Store 세션, watch, netfront ring·grant·event channel, network worker, v1 client, v2 Publisher, 앱 계산 스레드는 각각 확보·사용·정리 조건을 갖는다.

정상 종료. 새 작업 수락 차단 → 실행 사용자의 정지·join → backend와 외부 참조 종료 확인 → 공유 자원 반환. 공유 Store는 모든 사용자가 끝나기 전에 개별 실패자가 닫지 않는다.

부분 초기화. 시작하지 않은 worker의 완료를 기다리지 않는다. 성공한 확보와 아직 불확실한 확보를 기록하고, 실제 보유·노출 가능한 자원만 그 규칙에 따라 정리한다.

미확정. 내부 완료 알림이 왔어도 커널의 thread 종료가 확인된 것은 아닐 수 있다. Store 응답을 잃어도 frontend가 전혀 게시되지 않았다고 단정하지 않는다. grant 회수 실패 시 해당 페이지를 새 작업에 재사용하지 않는다.

기억할 점. closed=true는 현재 자원 정리 사실이다. 최초 초기화 오류가 사라졌다는 뜻은 아니다. guest의 quiesce·협조 종료 완료도 실제 차량 정지와 같지 않다. [S11](#src11)

## 5. 건강과 복구 — 문제를 판단하는 일과 고치는 일

<a id="c-health"></a>

### 5.1 건강 판단

> **개념 주석** — 건강은 대상 전체에 붙이는 막연한 칭찬이 아니라, 특정 기능·근거·기간·정책에 대한 판단이다.

판단 입력. 실행 신원, 유효한 관측, 현재 사용자 의도, 작업 기대 여부, 실제 진행·오류·기한, 자원 범위, 전달 경로와 로컬 감독 상태를 읽는다.

별개의 축. 생존, 계산 진행, 결과 유효성, 입력 준비, 자원 여유, 전달 가능성, 관측 가능성을 구별한다. 높은 CPU가 곧 장애는 아니고, 낮은 CPU가 기능 정상의 증거도 아니다.

|확인한 사실                 |이 사실로 연결할 행동의 범위                 |
|-----------------------|---------------------------------|
|정상 고부하·기한 내 유효 완료      |정상 부하 또는 합의한 여유 조건의 경고           |
|유효 작업이 있는데 계산 정체·기한 위반 |해당 기능 준비·결과 제한                   |
|필수 계산의 실제 할당 실패        |그 기능 제한과 소유 범위의 복구 검토            |
|진단 전용 자원 실패·상세 계측 유실   |진단 제한·손실 표시. 정상 기능을 자동 실패로 바꾸지 않음|
|Agent만 손실 또는 전달 경로 미확인 |보고자·전달·OS를 구분하고 근거 범위 밖 원인 확정 보류 |
|공통 입력·broker·dom0 경로 장애|개별 VM 재부팅을 반복하는 것으로 해결하지 않음      |

권한. 앱/로컬 감독은 해당 기능의 실패와 지원 복구를 다룬다. Worker는 복구 정책을 적용하고, Manager는 실제 VM 조치 허가를 검증한다. Gateway는 출력 보호를 맡는다. 어느 하나의 health 값이 이 모든 권한을 합쳐 갖지 않는다.

회복. 새로운 유효 기능 근거와 필요한 안정 조건으로 판단한다. 정상 신호 한 번, 새 execution 한 번, old 상태의 재발행을 모두 같은 회복으로 보지 않는다. 구체적인 유예·안정 구간·반복 상한은 정책 입력이며 임의 숫자를 만들지 않는다. [S07](#src07) · [S13](#src13) · [S14](#src14)

<a id="c-recovery"></a>

### 5.2 복구 episode와 개별 attempt

> **개념 주석** — episode는 하나의 복구 문제, attempt는 그 문제를 해결하기 위해 허용한 한 번의 시도다.

식별. recovery_id는 문제를 처음 판정해 끝낼 때까지 연결한다. recovery_attempt_id는 개별 원 물리 요청에 붙는다. 같은 장애의 여러 신호는 열린 복구의 근거로 모으며 각 신호마다 재시작을 발급하지 않는다.

episode의 책임. 이유·대상·의도·시도 수·backoff·로컬 수습·최종 포기/취소·회복 판단과 pending 사건을 관리한다. 새 실행이 생겼다는 사실과 원 기능이 안정적으로 회복됐다는 사실을 분리한다.

attempt의 책임. 원 명세·host·execution·의도·deadline·force 승인을 고정하고 하위 복구를 수행·조회한다. 응답 유실로 같은 attempt를 재전달해도 시도 수와 원 기한을 새로 지급하지 않는다.

```text
episode: 판정 → 시도 진행 / 재확인 / 제한된 대기 → 완료·회복·포기·취소
                         │
                         └─ attempt: 수락 → 기존 실행 정지/부재 확인
                                        → 새 launch → 새 실행 확인 → 결과 확정
```

종결 구분. 하위 복구 완료는 새 Xen 실행과 필수 결과의 확인이다. 외부 원인으로 VM이 먼저 회복된 것, 사용자가 정지해 대상에서 제외된 것, 시도 소진으로 포기한 것은 다른 결과다. episode의 기능 회복 조건은 하위 완료에 자동 포함되지 않는다.

외부 효과 미확정. stopping/launching/uncertain을 시간만으로 지우지 않는다. 반대로 더 이상 실행 가능성이 없고 실패 종결 근거가 충분하면 지원 절차로 닫아 다음 허용 작업을 진행한다. [S02](#src02) · [S14](#src14)

<a id="c-rejoin"></a>

### 5.3 재합류 조정

> **개념 주석** — 재합류는 복구된 실행을 다시 쓸 수 있는 후보로 연결하는 일이다. 이전 권한을 돌려주는 일이 아니다.

입력. 원 복구 결과의 새 execution과 현재 Manager 관측을 대조한다. 그 실행에 맞는 Bootstrap·receipt를 확보하고 binding을 게시한다. 이어 실제 앱의 준비 근거를 확인한다.

수명. 새 실행 발견 → provisioning → binding 확인 → 앱별 준비 확인 → 적합한 Standby 후보. 실행·의도·앱 instance가 바뀌거나 근거가 만료되면 해당 단계의 근거를 철회한다.

권한. 조정자는 원 실행과 신원·준비를 연결한다. 직접 새 VM을 반복 재시작하거나 Gateway generation·출력 허가를 발급하지 않는다. 정상 Active가 있다면 복구된 이전 A가 자동으로 그 자리를 빼앗지 않는다.

중단 후. 하위 journal이나 receipt가 수습됐다는 사실을 원 ID로 다시 확인한다. 기록의 종결이 앱 READY·AUTO 복귀·재무장까지 의미하는 것은 아니다. [S08](#src08) · [S14](#src14)

### 5.4 사건과 전달 기록

> **개념 주석** — 사건은 무엇이 일어났다는 기록이다. 사건을 발행·저장·수신한 사실은 그 사건 자체와 별개다.

식별. 복구 사건은 고정 event_id와 원 recovery/attempt를 연결한다. 재전달은 같은 사건 ID를 유지한다. app progress·관측 revision·메시지 seq는 사건 ID의 대체물이 아니다.

일관성. 아직 사건 저장소에 반영하지 못한 pending 사건은 해당 상태 전이와 함께 보존한다. append·저장 응답을 잃었을 때 “아무것도 쓰이지 않았다”고 단정하지 않는다. 같은 사건을 회수·재시도하고 논리 중복을 구별한다.

보존 수명. 열린 복구, 닫힌 원 작업, 사건 로그, 진단 원자료는 보존 목적과 기간이 다르다. 사건을 정리한다고 아직 중복 방지에 필요한 원 key나 미확정 작업을 제거하지 않는다. 원 MQTT 본문 전체의 영구 저장·자동 재생과도 다르다.

부가 기록. 필수 결과가 확정된 뒤 부가 진단만 실패했다면 원 결과는 유지한다. 반대로 필수 원장 저장 실패를 “로그만 실패”로 축소하지 않는다. [S02](#src02) · [S09](#src09) · [S14](#src14) · [S16](#src16)

## 6. 주행 도메인과 출력 권한 — 계산과 허가와 적용

<a id="c-world"></a>

### 6.1 환경 모델과 차량 상태

> **개념 주석** — Jetson은 환경 모델을 만든다. Pi 앱은 그 모델로 주행을 판단한다. 명령값은 실제 차량 상태가 아니다.

환경 모델. WorldSnapshot은 출처·좌표·설정·기준 시각·완전성에 묶인 국소 지도다. Jetson은 센서 처리와 누적 지도 갱신·저장을 맡고, Pi는 필요한 국소 영역의 완전한 snapshot을 받아 검증·채택한다.

지도 수명. mapper 실행 수명, 지도 epoch, 좌표 frame epoch, snapshot 순번, 원 관측 시각은 서로 다르다. rolling window가 움직였다고 좌표 기준 전체가 재설정된 것은 아니다. 저장 지도를 새 mapper 실행에서 복원해도 이전 실행 신원을 재사용하지 않는다.

보유와 사용. 새 지도가 불완전하면 직전 채택 지도를 유지할 수 있다. 그러나 지도 보유만으로 현재 pose·입력·명령의 유효기간이 연장되지는 않는다. 보존 지도의 재관측 부재를 무조건 지도 폐기로 바꾸지도 않는다. 실제 사용 가능성은 공간·좌표·현재 상태·위험 조건과 함께 평가한다.

차량 상태. ESP32의 실제 피드백과 그로부터 계산한 이동량·odom은 출처와 기준 구간을 보존한다. 명령 속도를 실제 이동량으로, 조향 목표를 실제 조향 센서값으로 꾸미지 않는다. Jetson으로 보낼 이동량 전송이 Pi 내부의 즉시 상태 경로를 막아서는 안 된다. [S12](#src12)

<a id="c-path"></a>

### 6.2 기준 경로·계획 경로·maneuver

> **개념 주석** — 기준 경로는 돌아갈 도로, 계획 경로는 지금 따를 경로, maneuver는 우회·복귀의 이어지는 의도다.

분리 이유. 장애물을 피하는 임시 경로를 만들었다고 원 도로를 잊지 않는다. 현재 경로가 무효해져도 원래 복귀 목표와 우회 진행 단계가 같은 의미로 사라지는 것은 아니다.

책임. AUTO는 유효한 지도·차량 상태와 차량 모델을 읽어 제한된 경로 후보를 검증·선택하고 명령을 계산한다. 경로 부재나 관측 부족으로 정지를 선택하는 것은 정상 기능일 수 있다.

인계. 필요한 최소 maneuver 사본은 출처 실행·앱 instance·revision·좌표·설정·현재 제어 문맥과 결합한다. 완전한 적용과 기능적 호환성을 확인한다. 지도 복원만으로 진행 중 우회가 복원됐다고 보지 않는다.

권한 경계. AUTO의 경로·maneuver 제안은 출력 권한이 아니다. 인계 사본에 과거 명령·owner 허가·기한을 넣어 새 실행에 되살리지 않는다. 연속성을 입증하지 못한 재구축은 정지 후 재개와 구별한다. [S06](#src06) · [S12](#src12)

### 6.3 운전자 세션과 수동 입력

> **개념 주석** — 세션은 조작 주체의 연속성, sample은 실제 현재 확인, action은 실제 조작 변화다.

식별. session_id는 운전자 입력 수명이다. VM A/B 전환·앱 instance·control generation 교체만으로 세션을 새로 만들지 않는다. sample_seq와 action_seq는 각각 실제 확인과 실제 조작 변화에 속한다.

생산 책임. 입력 생산자는 인증된 현재 세션과 실제 입력·중립·단절을 전달한다. 같은 키의 정상 유지 확인은 새 sample일 수 있지만, 서버가 과거 키를 반복 발행한 것은 새 사용자 확인이 아니다.

모드별 정책. 같은 MANUAL의 A/B 승계는 유효한 현재 세션·입력을 이어받는다. AUTO→MANUAL은 이번 전환의 유효한 중립을 확인한 뒤 새 조작으로 이동을 허가한다. 새 generation 자체를 새 조작으로 세지 않는다.

출력과 분리. AUTO·Standby에서도 필요한 입력과 중립을 공급할 수 있어야 준비가 출력권에 순환 의존하지 않는다. 입력을 공급하는 것과 차를 움직이게 허가하는 것은 별개다.

시간. 원 sample의 나이와 수신 후 경과를 보존한다. 이것만으로 계측하지 않은 네트워크 전송 시간을 모두 알 수 있다고 주장하지 않는다. 세션 단절을 합성 중립의 반복으로 정상처럼 보이지 않게 한다. [S10](#src10) · [S12](#src12) · [S15](#src15)

### 6.4 Gateway 제어 권위와 현재 출력 허가

> **개념 주석** — Authority는 “어떤 모드·owner·세대를 정당하게 선택했는가”의 원본이다. 출력 허가는 그 결정과 현재 근거가 모두 맞을 때만 살아 있다.

|축                 |묻는 질문                                    |
|------------------|-----------------------------------------|
|모드                |AUTO 계산인가, MANUAL 계산인가, 복귀 대기인가, 정지 상태인가?|
|owner             |A/B 중 어떤 VM을 선택했는가?                      |
|control generation|지금 적용해야 하는 제어 문맥은 무엇인가?                  |
|적용 phase          |새 제어의 저장·전달·적용은 어디까지 확인됐는가?              |
|재무장·출력 허가         |현재 실제 명령을 보내도 되는가?                       |

원본. Gateway가 단일 제어 권위를 소유한다. MQTT retained control은 배포 사본이다. broker에 아무것도 없다는 이유로 generation을 초기화하거나, retained만으로 최신 내구 권위를 대체하지 않는다.

허가. 현재 실행 binding, 앱의 현재 문맥 적용·준비·실제 진행, 신선한 명령, 사용자 선택, 출력 경로를 함께 확인한다. 앱의 active 자기 보고나 Worker의 복구 완료는 허가의 대체물이 아니다.

수명. 권위 결정은 내구 기록으로 남는다. 현재 준비·명령·연결 근거는 만료·교체될 수 있다. Gateway 재시작에서 선택된 owner·mode를 읽더라도 실제 출력은 명시적 재무장과 현재 근거 없이 복원하지 않는다.

안전 경계. 출력 오류 시 DRIVE 사용을 먼저 철회하고 STOP을 시도한다. 그 STOP 시도도 실제 장치 적용의 증거는 아니다. 원본 손상·세대 충돌은 이전 세대로 되돌려 정상화하지 않는다. [S10](#src10) · [S17](#src17)

### 6.5 사전 준비와 권위 전환 요청

> **개념 주석** — 다음 owner를 준비시키는 일과 지금 owner의 권한을 끝내는 일은 같은 순간일 필요가 없다.

원 요청. 전환 ID·기대 owner/generation·대상 실행·앱·모드·필요 상태·고정 기한을 보존한다. 관리 VM의 start/stop operation과는 다른 요청이다.

```text
현재 owner 유지
  └─ 대상의 권한 없는 사전 준비
        → 준비 근거 확인
        → 현재 조건을 다시 확인해 권위 COMMIT
        → 이전 명령 자격 종료·새 generation
        → 대상의 새 제어 적용·실제 계산
        → 현재 출력 조건 충족 시 전달
```

원자성의 범위. 권위의 COMMITTED는 선택 변경을 확정한 것이다. 앱 적용과 최종 장치 적용까지 하나의 원자 동작으로 끝났다는 뜻은 아니다.

취소와 실패. 커밋 전에는 원 준비를 취소할 수 있다. 커밋 후 취소 요청이 과거 generation을 되살리지는 않는다. 이후의 정지·모드 변경은 그 시점의 정당한 별도 제어다. 계획 정비의 준비 실패는 정상 owner를 유지하며 정비를 보류할 수 있지만, 실제 기능 장애의 유효하지 않은 출력 유지에는 적용하지 않는다.

연속성. 준비된 후보도 실제 권한 전환 직전에 자격을 잃을 수 있다. 유효 후보와 출력 예산이 부족하면 정지 후 재개한다. 연속 운행과 단순 복구 성공을 같은 수락으로 세지 않는다. [S12](#src12) · [S17](#src17)

### 6.6 명령 후보·시리얼 제출·장치 적용

> **개념 주석** — 앱은 명령 후보를 만들고, Gateway는 허용된 후보를 제출하며, ESP32는 장치 계약으로 수락·적용한다.

명령 후보. 어느 VM·앱 instance·control generation·입력·계산에서 나온 결과인지 설명할 수 있어야 한다. 새 MQTT seq로 오래된 결과를 포장해도 새 계산은 아니다.

Gateway 제출. 선택된 owner·모드·현재 문맥·신선도·값의 범위와 차량 한계를 확인한다. 시리얼은 단일 I/O 소유자가 처리한다. 명령이 없을 때 과거 DRIVE를 무한 반복하는 것과 명시적 STOP을 보내는 것은 다르다.

장치 수락. ESP32는 자기 boot/session·epoch·counter·유효 명령·watchdog/E-stop 조건을 따른다. MQTT generation·seq가 시리얼 식별자와 자동으로 같아지는 것은 아니다.

완료 계층. 완전한 쓰기 수락 → 장치 명령 수락 → 제어 출력 설정 → 실제 속도·조향·정지 확인을 구별한다. 실제 센서가 제공하지 않은 값을 측정 사실로 만들지 않는다. 장치의 명령 상실 보호는 상위 Worker의 VM 복구 완료를 기다리지 않는다. [S12](#src12) · [S17](#src17)

## 8. 주요 파이프라인 — 각 책임이 맞물리는 순서

아래 화살표는 논리적인 확인 순서다. 모든 화살표를 하나의 긴 동기 호출이나 전역 잠금으로 구현한다는 뜻은 아니다. 특히 출력 보호와 VM 복구는 별도의 진행 책임이다.

### 8.1 VM 생성 — 자산을 만들고 등록한다

```text
[호출자] 안정된 VM UUID·생성 명세 보존
  → [Manager] 같은 원 key/결과 확인
  → [자산 준비] 저렴한 metadata·신원·주소·용량 검사
  → [준비 실행량] 필요한 슬롯 확보
  → [Manager] 현재 조건 재확인·원 operation/예약/기한 수락
  → [준비 소유자] private 검증 결합 복사·guest 설정·일시 자원 정리
  → [Manager] 현재 원장·source·예약·host gate·의도·기한 재확인
  → [자산 관리] 게시·등록·필수 결과 확정
  → [호출자] REGISTERED 자산과 원 결과 수신
```

완료 경계. 일반 create는 자산 등록의 완료다. Xen 기동과 OS·앱 준비는 다음 작업이다. 긴 준비 도중 다른 VM의 읽기·허용된 제어는 그 준비 전체를 기다릴 필요가 없다.

응답 유실. 같은 UUID·명세·원 key로 자산 operation을 확인한다. 상세 GET의 부재만으로 새 UUID를 발급하지 않는다. 부분 workspace가 남았다면 원 실패·수습 경로로 간다. [S01](#src01) · [S02](#src02) · [S05](#src05)

### 8.2 시작·재부팅 — 같은 자산의 실행을 만든다

```text
[호출자] 원 제어 key·대상·요구 제출
  → [Execution] 현재 자산·의도 수락·원 제어 journal
  → [실행 관리] 원 작업 소유·현재 정책·기한 확인
  → [Execution] 새 launch 문맥 준비
  → [최종 guard] 새 stop/host/구성/정책/신원 변경 여부 확인
  → [Xen] 물리 실행 또는 지원되는 reboot
  → [Execution] 현재 incarnation 결합·필수 검증·원 결과 저장
  → [신원 공급] guest/app/Publisher에 실행별 문맥 공급
  → [앱] 현재 입력·상태·제어로 준비
```

두 완료. 실행 관리의 완료는 앱 준비 이전에 성립할 수 있다. 앱 준비가 끝나도 차량 출력권은 Gateway에서 별도로 결정한다.

새 의도. 뒤늦은 원 실행은 최신 stop을 무시하지 않는다. 외부 효과가 이미 제출됐다면 원 journal과 실제 상태를 대조하며, 응답 timeout만으로 미실행으로 되돌리지 않는다. [S01](#src01) · [S02](#src02) · [S03](#src03) · [S08](#src08)

### 8.3 정지 — 수락과 실제 종료를 나눈다

```text
[사용자] stop 요청
  → [짧은 수락] stopped 의도·원 key/operation·revision 내구 확정
  → [응답] 실제 종료 전이면 accepted + pending
  → [원 요청의 이행 주체] 같은 요청·원 기한으로 조건부 이행
  → [실행 관리] 대상·현재 실행·의도·소유권 재검증
  → [Xen/guest] 협조형 종료와 실제 제거 확인
  → [원 작업] 완료 결과 확정
  → [화면] 원 요청 완료와 현재 VM 관측을 각각 반영
```

끝까지 남는 책임. 조회 자체가 자동 실행기는 아니다. 누가 원 pending을 이행할지 정해져 있어야 한다. 만료 뒤에도 stopped 의도는 남을 수 있지만, 과거 물리 실행 권한을 새 조회가 되살리지는 않는다.

응답 역전. 그 사이 새로운 start가 수락됐다면 옛 stop 응답은 원 작업 이력만 갱신한다. 최신 의도나 화면을 옛 완료로 덮지 않는다. [S01](#src01) · [S02](#src02) · [S15](#src15)

### 8.4 생성 실패·기한 만료 — 원 실패를 끝내고 자원을 돌려준다

```text
[준비 소유자] 오류/원 기한 만료 → 새 준비·게시 제출 중지
  → 소유 자식·일시 자원 종료 시도와 확인
  → 최초 오류·잔존 효과 보존
  → 종료 확인한 실행 핸들 반환
  → [진단] 원 operation·workspace·public 여부·사용 자원 확인
  → [명시 수습] 권한·원 대상·현재 소유권 재확인
  → 정리 계획 내구 기록
  → 자기 private 자산만 제한적으로 정리
  → 잔존·필수 저장 확인
  → 수습 결과·해당 예약 반환 확정
```

최종 결과. 원 create는 실패로 남고 수습은 완료될 수 있다. 같은 key는 이 원 결과를 재조회한다. 그 뒤 사용자가 별도 생성을 명시하면 현재 자원 검사와 새 요청으로 진행한다.

금지되는 지름길. 원장 삭제, 임의 phase 성공, 자동 force, 다른 inode·사용 중 자산 삭제, 새 UUID로 원 보호 우회. 종료·수습에 새 예산이 있어도 만료된 원 생성의 새 복사·게시·launch를 허가하지 않는다.

정체를 끝내는 기준. 종료·정리·내구 반환이 확인됐으면 다음 정상 작업이 실제로 진행돼야 한다. 안전하다는 이유로 모든 실패를 영구 차단으로만 남기지는 않는다. [S05](#src05)

### 8.5 관측→판정→복구→재합류

```text
[관측] 현재 Xen + 해당 실행의 신뢰 가능한 Agent/앱/자원 근거
  → [판정] 정상 / 입력·기능 제한 / 관측 불가 / 복구 정책 대상 구분
  → [episode] 원 문제와 열린 복구·로컬 수습·반복 예산 연결
  → [Gateway] 필요한 출력 차단·적합한 대체 실행 승계
  → [Engine] 허용된 원 attempt를 기록
  → [하위 Manager] 원 의도·신원·기한·승인 guard 후 실제 복구
  → [Engine] 원 결과 회수
  → [Coordinator] 새 실행 provisioning·receipt·binding
  → [앱/정책] 현재 기능·준비·회복 근거 확인
  → Standby 재합류
```

병렬 책임. Gateway는 Worker 완료를 기다리지 않고 출력 보호를 수행한다. 계획 정비에서는 정상 owner의 인계 가능성을 먼저 확인한다. 기능 장애 상황에 정상 owner 유지 규칙을 잘못 적용하지 않는다.

끝의 차이. 새 Xen 실행 관측, 기능 회복, episode 종결, Standby 재합류, 출력권 부여는 각각의 주체가 자기 근거로 확정한다. [S02](#src02) · [S08](#src08) · [S12](#src12) · [S14](#src14)

### 8.6 AUTO/MANUAL 전환과 같은 모드의 A/B 승계

|상황            |확인 순서                                                           |유지할 의미                                |
|--------------|----------------------------------------------------------------|--------------------------------------|
|AUTO→MANUAL   |입력/기능 문제 확인 → 출력 보호 → MANUAL 준비·현재 세션·전환 문맥 → 중립 확인 후 새 조작      |Jetson 문제를 곧바로 VM 전체 장애로 만들지 않음       |
|MANUAL→AUTO   |AUTO 준비 회복 → 현재 문맥의 명시적 복귀 요청 → 준비 유지·카운트다운 → 새 제어 적용·실제 계산 → 허가|준비 복귀만으로 자동 출발하지 않음                   |
|같은 MANUAL의 A→B|B의 현재 모드 준비·입력 세션·상태 확인 → 권위 전환 → B의 새 문맥 계산·유효 명령              |승계만을 이유로 정상 사용자의 키 재조작을 요구하지 않음       |
|같은 AUTO의 A→B  |지도·pose·maneuver/필수 상태·모드 준비·현재 실행 확인 → 조건부 권위 전환 → 새 계산·출력     |같은 지도 수신만으로 연속 승계 자격을 인정하지 않음         |
|후보 없음·양쪽 준비 불가|현재 유효 출력 제한 → 정지 유지 → 지원되는 준비·재개 절차                             |A/B 반복 선택으로 generation·복구 시도를 폭증시키지 않음|

이 표의 각 전환은 운전 모드, 실행 owner, 입력 세션, 출력 허가의 독립된 조건을 결합한다. AUTO 복귀의 준비 유지·카운트다운을 모든 A/B 승계에 기계적으로 복제하지 않는다. [S10](#src10) · [S12](#src12) · [S17](#src17)

### 8.7 앱 하나만 재초기화

```text
[신뢰된 요청] 대상 앱·현재 execution·기대 instance·원 요청 확인
  → [신원 공급] 원 receipt에 새 앱 신원 교체를 기록·Store 적용/미확정 확인
  → [guest runtime] 변경을 확인한 대상 앱의 옛 결과 철회·새 제출 차단
  → [계산 소유자] 취소에 협력하고 실제 종료
  → [runtime] join·참조 회수 확인 뒤 새 instance의 앱 활성화
  → [앱] 현재 설정·제어·입력·필요 상태로 다시 준비
  → [소비자] 현재 binding과 새 실제 준비 근거를 각각 확인
```

신원 공급의 receipt 적용과 guest의 실제 종료·재생성은 별도 확인이다. Store 미확정 또는 join 실패에서는 새 instance의 활성 준비를 승인하지 않는다. 정상 다른 앱과 공통 transport를 불필요하게 교체하지 않는다. [S06](#src06) · [S08](#src08) · [S10](#src10)

### 8.8 Host 종료·재시작

```text
[host] 신규 수락 gate 닫기
  → [관리] 기존 작업·준비 소유자 drain/미확정 확인
  → [guest] 각자의 실행·자원 협조 종료
  → [dom0] 실제 domain·backend·준비 자원 종료 확인
  → [저장소] 안전한 해제 가능 여부 확인
  → 전원/재부팅
```

```text
다음 부팅:
저장소·기존 설치 신원 확인
  → 새 host 문맥
  → 현재 정책·보존 의도의 적용성 판단
  → 허용된 VM 실행
  → 새 관측·binding·앱 준비
```

host 재시작에서 내구 이력은 남을 수 있지만 옛 host의 단조 기한·현재성·출력권은 이어 붙이지 않는다. 관리 서비스 프로세스 재시작은 이 전체 종료 파이프라인과 다르다. [S02](#src02) · [S04](#src04) · [S11](#src11)

## 9. 정합성과 진행성 — 어떤 것을 함께 지키고 무엇을 기다리지 않는가

### 9.1 일관성 묶음과 애그리거트 관점

DDD 관점에서 중요한 것은 “연관된 데이터를 전부 한 객체에 넣기”가 아니라, 어떤 결정의 불변 조건을 누가 함께 지키는가다. 아래는 기존 구조를 읽기 위한 일관성 묶음이다. 이를 새 애그리거트 클래스나 단일 DB 트랜잭션으로 구현했다고 선언하지 않는다.

|일관성 묶음           |함께 맞아야 하는 것                                 |다른 원본과의 연결                  |
|-----------------|--------------------------------------------|----------------------------|
|VM 자산            |UUID·현재 구성·소유 자산·자산 세대                      |실제 Xen 실행과 의도는 별도 문맥으로 대조   |
|원 자산 작업          |원 key/spec·대상·예약·진행·원 결과·수습 근거              |디스크 이동·삭제·DHCP 등 외부 효과를 확인  |
|사용자 의도와 제어 요청    |새 revision의 의도와 그 수락을 설명하는 원 요청             |다중 기록의 재개 가능한 수락·물리 실행 guard|
|VM 실행 문맥         |원 launch owner·host·자산/의도·구성/CPU·incarnation|실제 Xen 관측과 결합               |
|복구 episode       |원 attempt·예산·진행·결과·pending 사건               |하위 복구 결과·현재 기능 회복과 대조       |
|Bootstrap receipt|대상 실행·공급 신원·Store 효과·적용 결과                  |현재 Manager 실행과 실제 Store 재확인 |
|Gateway Authority|generation·owner·mode·pending·원 전환 결과·재무장   |앱 적용·명령·장치 적용은 별도 근거        |

로컬 파일의 원자 교체는 그 파일의 원자성이다. 여러 파일·Xen·Store·시리얼을 하나의 원자 세계로 만들지 않는다. 그래서 원 요청, 단계별 기록, 외부 효과 재관측, 재전달, 명시 수습이 남는다.

SQLite를 선택하더라도 이 권한·외부 효과 경계가 자동으로 사라지는 것은 아니다. 반대로 파일 저장이라는 이유만으로 도메인 원본이 없어도 되는 것은 아니다. 저장 방식은 의미·소유·수락 계약을 보존해야 한다. [S01](#src01) · [S05](#src05) · [S08](#src08) · [S14](#src14) · [S16](#src16) · [S17](#src17)

### 9.2 잠금·슬롯·소유·예약은 네 종류다

|개념          |지키는 것                               |반환 또는 종료 조건                |
|------------|------------------------------------|---------------------------|
|**잠금**      |현재 공유 상태를 함께 바꾸는 짧은 구간 또는 필요한 물리 직렬화|그 보호 구간이 끝남                |
|**실행량 슬롯**  |무거운 준비·관측이 한꺼번에 과도하게 실행되지 않음        |해당 실행과 소유 helper가 끝남       |
|**원 실행 소유권**|정확한 원 작업에 경쟁 실행자가 생기지 않음            |실제 소유 실행·상속 사용자의 종료 확인     |
|**논리 예약**   |미완료 작업이 약정한 디스크·주소·신원을 타 작업이 침범하지 않음|결과·수습에 따른 내구 반환 또는 정식 소유 전환|

이 네 가지의 수명은 같지 않다. 원 journal을 보존하는 것은 실행 락을 계속 잡는 것과 다르고, process가 끝났다고 예약이 자동으로 사라지지도 않는다.

진행 규칙. 긴 Linux 준비는 원 소유를 유지한 채 공통 잠금 밖에서 한다. 일반 조회는 긴 실행 전체를 기다리지 않는다. 수락·게시·현재 신원 guard 같은 필요한 경계는 짧게 보호한다. 같은 VM의 충돌은 막되 무관한 VM까지 무조건 묶지 않는다.

한계. 이 원칙이 모든 물리 변경의 완전 병렬화나 모든 스케줄에서의 무기아를 뜻하지 않는다. 실제 공통 자원·저장소 장애가 있으면 그 영향을 설명해야 한다. [S01](#src01) · [S05](#src05)

### 9.3 기다릴 수 있는 관계와 만들면 안 되는 순환

|관계                              |정당한 이유 또는 금지 이유                |
|--------------------------------|-------------------------------|
|새 앱이 옛 앱의 실제 join을 기다림          |같은 stack·상태를 안전하게 재사용하기 위해 필요  |
|저장소 unmount가 실제 VM/준비 자원 종료를 기다림|사용 중 자산 해제를 막기 위해 필요           |

|필수 완료가 부가 로그 전달을 무한 대기함         |진단 수명과 원 작업 종결을 혼합하므로 분리       |

실제 잠금 획득 순서·배치와 대기 예산은 원 구현 계약을 따른다. 이 표는 무조건 lock을 없애라는 지침이 아니라 무엇의 종료가 무엇의 선행조건인가를 설명하는 지도다. [S01](#src01) · [S06](#src06) · [S11](#src11) · [S12](#src12)

### 9.4 시간도 적용 문맥이 있는 값이다

|시간                 |제한하는 것                |제한하지 않는 것                   |
|-------------------|----------------------|----------------------------|
|이번 호출 예산           |이번 요청의 대기·조회·실행·반환    |이미 수락한 원 작업의 정체성·기한을 재발급할 권한|
|원 작업 deadline      |원 수락에 묶인 새 물리 효과 제출·이행|이미 일어난 효과를 없던 것으로 만드는 권한    |
|종료·수습 예산           |소유 자원 종료·원 효과 확인·정리   |만료된 생성·복구의 새 실행             |
|관측·binding lease   |현재 판단에 쓸 수 있는 근거의 수명  |모든 원 데이터의 종단 나이 보장          |
|계산 release·deadline|해당 작업이 결과를 제공해야 하는 구간 |다음 release로 과거 결과를 새로 만드는 권한|

|UTC 품질·불확실성        |장치 간 시각 해석의 신뢰 범위     |다른 host의 단조 시계를 직접 빼는 허가    |

host 단조 기한은 같은 host_boot_id 안에서 읽는다. guest uptime·resource clock·dom0 monotonic을 문맥 없이 서로 빼지 않는다. 수신이 신선하다는 사실은 센서 관측부터의 총 지연이 짧다는 증거와 다르다.

운영 시간값은 대상 기능·지원 환경·실측·합의 정책에 속한다. 시험 프로필의 숫자를 모든 서비스와 장치의 영구 계약으로 확대하지 않는다. [S05](#src05) · [S07](#src07) · [S09](#src09) · [S10](#src10) · [S12](#src12)

### 9.5 원본·관측 사본·기록의 저장 수명

|자료               |저장 목적                      |복원 시 주의할 점                       |
|-----------------|---------------------------|---------------------------------|
|자산·사용자 의도·원 작업   |신원·결정·중복 방지·원 결과 회수        |파일 부재/손상을 정상 최초 상태로 바꾸지 않음       |
|실행·관측·binding    |현재 host·실행의 확인 근거          |옛 현재성을 영구 저장만으로 되살리지 않음          |
|앱 상태·입력·명령 후보    |현재 작업의 제한된 기능 상태           |과거 명령·허가·lease를 복원하지 않음          |
|복구 상태·pending 사건 |같은 원 episode/attempt를 이어 확인|저장 매체·host 재시작 정책과 단조 시계 문맥 확인   |
|Gateway 권위       |단일 선택·generation·원 전환 결과   |선택 복원과 출력 재무장을 분리                |

|사건·진단 원자료        |원인 조사·이력·누락 구간 설명          |정책적 회전·중복·gap을 표시. 원 권한으로 사용하지 않음|
|누적 지도            |관측 공간의 보존·재방문              |새 mapper 실행·현재 좌표/위치와 다시 정합      |

영구 원본과 파일 경로는 같은 개념이 아니다. /srv의 원본도 필요한 내구 확인이 실패할 수 있고, /run에서 서비스 재시작을 견디는 기록도 host 재부팅 보존을 뜻하지 않는다. 상세 원자료 전체를 Worker의 작은 상태 저장소로 옮겨 영구 재생하는 구조도 아니다. [S05](#src05) · [S09](#src09) · [S12](#src12) · [S14](#src14) · [S16](#src16) · [S17](#src17)

### 9.6 검증 비용은 근거의 수명으로 설명한다

검증 하나에는 대상·목적·원천·유효 문맥·무효화 사건이 있어야 한다. 같은 단계에서 동일하게 확인한 전체 입력을 이유 없이 다시 읽지 않는다. 반면 새 실행·의도·구성·정책·host가 된 경계에서는 필요한 사실을 다시 확인한다.

예를 들어 검증 결합 복사는 실제 복사 바이트의 무결성을 한 경로에서 확인한다. 게시 전 source guard는 준비 뒤 바뀐 원본·신원·현재 허가를 확인하는 다른 경계다. 두 검사를 모두 한다고 전체 payload를 두 번 읽어야 하는 것은 아니다.

원칙은 **“검사를 줄인다”보다 “어느 근거를 언제까지 재사용할 수 있는지 설명한다”**에 가깝다. 읽기 사본을 무조건 TTL cache로 바꾸거나, 안전하다는 이유로 모든 호출에서 전체 검증을 반복하는 양쪽을 피한다. [S01](#src01) · [S02](#src02) · [S05](#src05)

### 9.7 권한도 한 종류가 아니다

|권한·소유       |확인하는 질문                           |대표 경계                                                      |
|------------|----------------------------------|-----------------------------------------------------------|
|요청 주체의 접근권한 |이 사용자가 이 VM·원 작업을 조회하거나 제어할 수 있는가?|API 인증·대상 접근 검사. key/operation ID를 아는 것만으로 허가하지 않음         |

|현재 행동의 허가   |권한 있는 요청이어도 지금 이 실행에 조치해도 되는가?    |현재 의도·신원·소유·기한·정책의 최종 guard                                |

### 한 가지 사건으로 전체를 읽는 예

VM A에서 AUTO가 기한을 넘기지만 MANUAL은 정상이라고 하자.

바뀌는 것은 우선 AUTO의 결과·준비 근거다. 이 사실 하나로 A의 자산 UUID, 사용자 running 의도, MANUAL instance, v2 Publisher, Gateway owner를 모두 초기화하지 않는다.

Gateway는 현재 모드와 입력·대체 후보에 따라 무효 출력을 차단하고 MANUAL 전환 또는 B 승계·정지를 판단한다. 앱 재초기화가 지원되는 오류라면 해당 앱의 소유 작업을 종료·정리한 뒤 정당한 새 instance를 적용한다. 공유 runtime·kernel 손상이나 정리 불능 등 VM 범위의 복구 조건이라면 Worker와 Manager의 원 attempt 절차를 사용한다.

새 실행이 돌아와도 A는 자동으로 이전 출력권을 되찾지 않는다. 신원 공급·binding·앱 준비·재합류를 거쳐 다시 후보가 된다. 각 책임은 자기 대상만 바꾸고, 다음 책임이 필요한 근거를 남긴다. [S06](#src06) · [S07](#src07) · [S08](#src08) · [S12](#src12) · [S14](#src14)

### 12.3 5번이 실제로 제공하는 계약

[정식 생성/수습 계약](cli-manager-spec.md#cmd-operation-reconcile)을 따른다. 새 Linux create는 `/etc/xenova/creation-policy.json`의 유한 정책을 요구한다. recipe는 값이 null인 예시만 `/usr/share/xenova/creation-policy.json.example`로 설치한다. 정책 부재/무효에서는 새 수락을 거절하며 운영 기본 시간값을 시험값에서 정하지 않았다. 완료 replay·원 조회·지원되는 명시 수습은 정책 부재만으로 차단하지 않는다.

새 Linux asset journal schema 1.1의 `creation.version=1`은 원 host·수락 시각·불변 실행 기한·정책을 결합한다. 원 기한은 호출 진입/대기 비용과 종료 여유를 고려해 최초 수락에서 고정하며 재전달/조회/재시작으로 늘리지 않는다. 기한 없는 legacy 미완료/다른 boot는 새 생성 기한을 발급해 재개하지 않는다. 현재 host의 명시 private 수습과 완료된 구버전 결과 replay는 별개다. 구형 writer/일부 모듈의 혼합 배포는 지원하지 않는다.

`operation-reconcile`은 읽기 진단과 명시 `discard-private` 실행을 구분한다. 원 operation 또는 key·VM·spec hash·진단 context·안정 reconciliation ID로 대상을 제한한다. 그 ID를 아는 사실이 사용자 접근/삭제 권한은 아니다. 같은 원 JSON의 `reconciliation.version=1`에 계획·진행·수습 오류·완료/반환을 보존하며 원 실패를 수습 성공으로 덮지 않는다.

실제 실행/사용 자원 종료, private 폐기, 원 기록 내구 확정, 논리 예약 반환은 각각 다른 증거를 갖는다. active/residual·관측 실패·public 충돌·원인 불명 자산 교체/부재는 차단한다. 계획 저장 실패에서는 삭제하지 않고, complete JSON이 보여도 실제 예약 소비 writer의 file/parent fsync·동일 기록 재확인이 실패하면 소비하지 않는다. xenova_creation.holds를 사용하는 생성/주소·제어·복구·자원·CPU·Zephyr guard는 같은 의미를 사용하며 CPU 정책의 전용 예약/원 UUID 이력을 일괄 해제하지 않는다.

같은 create key는 원 생성 실패+수습 결과를 회수하고 재복사하지 않는다. 내구 수습 뒤 사용자의 별도 신규 생성은 현재 자원 검사로 성공할 수 있다. source 손상/부재가 정상 게시를 막는 것과 소유 실패 사본 폐기를 막는 것은 구별한다. public에서 DHCP 적용이 이미 확인된 원 결과의 정산과, 만료 뒤 새 외부 효과/launch 제출도 구별한다. 협조 기한 검사는 syscall 강제 선점 보장이 아니다.

부분 패키지는 Python 33개+비활성 예시 1개, 설치 경로 import 11개를 확인한 범위다. BitBake/RPM/전체 이미지·실제 설치·활성 정책·보드 수락은 아니다. 이 장은 실제 삭제·서비스 변경·배포 승인이 아니다.

### 12.4 남은 정의와 후속 경계

회복 정책과 Linux 기능 모델은 원문 5장 및 [Worker](../requests/20261029-request-recovery-worker.md)·[Linux/Agent](../requests/20261029-request-linux-agent.md)의 기존 D01/D03 요청에 남는다. 원 create의 시간/수습 형식은 이제 정식 계약과 하위 로컬 결과로 확인했지만, 실제 HTTP·Spring·화면의 권한/원 key·원 기한/명시 수습·후속 이행은 [담당자 요청](../requests/20261029-request-http-spring-ui.md)에 남는다. API cgroup/backend 귀속도 별도 미완료다.

상태 있는 주행·장치, Worker host 보존 정책, 손상 Authority의 최신성 있는 복원, 기록 한도 이후 수습을 이번 문서로 결정하지 않는다. 과거 사건/원자료와 운영값·부분 포함/설치/실물 수락을 구분한다.

[기능별 기준선의 후속 표](../verification/platform-management-baseline.md#followups)는 5.5에 현재 소유 플랫폼의 반복 비용/대기 점검, 6에 실제 생산자/소비자·정책 공급 연결, 7에 동일 후보 설치/보드/제품 종단을 배정한다. 이번 1번은 그 현재 구조를 설명하고 근거를 연결한 문서 마감이며 후속을 실행하지 않았다. 0~11장의 개념을 새 Entity/서비스/DB/원장/정책 도입 계획으로 바꾸지 않았다.

### 12.5 5.5 후속의 적용 범위

현재 후속은 `9b69cdf`와 보존 작업트리의 후보 manifest를 사용한다. [후속 보고](../verification/recovery-scenario-closure-20261030.md#stage55-followup)에 원자료·단일 후보·OS별 관리 수락을 연결한다. 첫 P55가 남긴 restore 공통 대기는 대상 실행 lease와 짧은 채택/정산으로 분리했다. 검사 중 소유와 내구 수락, 활성 재전달과 종료 뒤 재개, 상속 FD와 논리 예약은 여전히 별개다.

CPU는 Debian·Ubuntu·Zephyr 모두 UUID별 정적 pinning·해제를 제공한다. 차량 A/B 전용 두 개는 초기 프리셋이며 플랫폼의 VM 개수/OS 권한 조건이 아니다. 공유 pinning과 전용 예약을 구별하고 다중 vCPU의 실제 mask를 모두 확인한다. 새 정책/journal 2.0과 구형 원본 1.0 회수는 [정식 CPU 계약](cli-manager-spec.md#cpu-contract)을 따른다. 실행 중 guest 재배치·scheduler·pool 변경은 미지원으로 유지한다.

고정 Zephyr의 기존 native kernel worker 9개 시나리오도 격리 실행했지만 실보드 주기 총비용·Xen/IRQ/SD·API backend 귀속·운영 create 정책·상위 제품 연결·장치 종단은 완료가 아니다. 0~11장의 개념 본문은 이번 구현 이력으로 바꾸지 않았다.

그 뒤의 [좁은 교차 보완](../verification/recovery-scenario-closure-20261030.md#stage55-cross-boundaries)은 firmware·자원 usage·lifecycle DHCP의 무관한 stop 대기를 분리하고, 정적 CPU 배치와 자원 수 변경·준비 오류·수습·새 host의 연쇄를 로컬 확인했다. 같은 단계의 정책/원장 재읽기는 줄였지만, 관측 후 새 journal과 효과 제출·새 실행의 검증은 유지한다. 책임/권한/식별자/수명의 개념 정의를 바꾼 작업이 아니다.

이후 [입력·진단 보완](../verification/recovery-scenario-closure-20261030.md#defaults-errors-review)은
신규 create의 선택 자원을 공통 카탈로그에서 해석하고 원 제출/확정값을 보존한다.
재전달은 현재 기본값으로 과거 결정을 바꾸지 않는다. 부가 진단의 반복 처리·출력 대기는
줄이되 오류 원인·코드·수습 구분과 필수 저장은 보존한다. 하위 CLI/Manager·Gateway의
로컬 범위이며 HTTP/Spring 연결·운영 정책·설치본/보드 수락을 완료한 것은 아니다.

그 뒤 [create 입력 호환 보완](../verification/recovery-scenario-closure-20261030.md#create-compatibility)은
같은 원 생성값의 자원 생략/명시를 양방향 동등하게 처리한다. 원장에 최초 선택을 보존하는
일과 새 표현을 같은 요청으로 인정하는 일은 별개다. 일반 호출자는 내부 저장 버전을 선택하지 않는다.
