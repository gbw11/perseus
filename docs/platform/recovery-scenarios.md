# 복구 시나리오 시기별 정리

복구 시나리오를 **언제 일어나는가** 순서로 묶은 설계서입니다. **대응은 원하는 동작**, 현재 처리는 그 동작의 구현·연결 상태입니다.

- **ID:** 통합 문서와 같습니다. A 관측, B 기능, C 메모리, D 범위, E 수명주기, F 제어 요청, G 저장, H 제어권입니다.
- **ID 접미사:** `O`가 붙은 ID(AO1, BO1 …)는 추가 옵션이고, 나머지는 필수입니다. 선택 계측을 생략할 수 있다는 뜻이지, 필수 실행·자원 조건까지 생략할 수 있다는 뜻은 아닙니다.
- **여러 시기에 나오는 시나리오:** 처음 나오는 시기에 전체를 적고, 이후에는 그 시기에 해당하는 측면만 적습니다.
- **현재 처리:** 2026-10-29, `feat/platform/health-and-recovery-contracts`의 HEAD `5ffdae662b7c1730e8a85395e69bf10b4d9433a2`와 미커밋 작업트리를 대조했습니다. 소스 확인과 설치본·실보드 수락은 구분하며, 확인하지 못한 것은 "미확인"으로 적었습니다.
- **Gateway 프로필:** 기본 `verified`와 명시적으로 선택하는 과거 `legacy` 경로를 구분합니다. 현재 처리 설명이 특정 프로필에만 해당하면 함께 적었습니다.
- **주행 설계 보완:** 아래 추가 사례는 [주행 파이프라인 설계](drive-pipeline-architecture.md)의 목표 동작입니다. 기존 ID에 연결하며, 기존 `현재 처리`가 이 목표의 구현 완료를 뜻하지는 않습니다. 사례에 적은 `ARCH-Txx`는 설계서 19절의 수락 시험 ID이고, 공개 필드·설정값의 미정 사항은 같은 설계서 20절에서 관리합니다.

<a id="1-기동"></a>
## ① 기동

> VM이 막 켜졌거나 보드가 부팅한 직후입니다. 아직 비교할 "정상 상태"가 없습니다.
>
> 원 사례의 "초기화 중 신호 중단"은 별도 항목으로 두지 않습니다. 이 시스템에서 초기화에 해당하는 경우는 모두 기존 항목으로 처리됩니다.
> - 부팅 직후 앱 초기화: E1(부팅 유예)
> - 정지 상태에서 하는 관리 작업: E2(⑧)
> - 같은 VM 안의 앱 재초기화: A4

| ID | 시나리오 | 대응 | 현재 처리 |
| --- | --- | --- | --- |
| **A1** | 처음부터 신호가 오지 않음 | 부팅 유예 동안 판정 보류 → 유예가 끝나면 시작 실패 절차 → 근거와 정책에 따른 제한된 재시도 또는 운영자. 원인(기동·provisioning·경로)을 추측해 확정하지 않음 | Worker 기본 유예는 Linux 90초·Zephyr 30초. 현재 Watcher는 대상 VM의 전달 이력이 없으면 손실 판정을 보류하며, verified 실행은 현재 실행의 첫 신호 전에도 보호함. 유예 만료만으로 첫 미수신 VM을 자동 복구하지는 않음 |
| **E1** | 기동 후 신호가 한 번도 안 옴 (A1의 처리 절차). 부팅 직후 OS·앱 준비 중인 구간 포함 | 복구 대상으로 확정되면 **최초 복구 시도 포함 총 3회**. 1회 실패 뒤 5초·2회 실패 뒤 15초 대기 → 3회 실패 뒤 추가 시도 없이 final failed. 원래 기동은 이 횟수에 포함하지 않음 | Engine 기본값은 총 3회. backoff 배열은 5·15·30초이나 총 3회 설정에서는 30초를 사용하지 않음. 같은 attempt 재전달·조회는 새 시도가 아니며 기한을 늘리지 않음. A1의 첫 미수신 판정 보류는 별도 |
| **A4** | 발행 주체가 새로 바뀜 (새 `boot_id`·instance) | 검증된 새 실행은 새 기준(seq 등)으로 다시 잡음. 이전 부팅·이전 연결의 값을 붙이지 않음 | verified는 Manager execution에 연결된 boot·v1 앱 instance를 대조하고 앱 추적·준비를 초기화. 새 ID라는 이유만으로 거절하거나 처음 본 ID라서 승인하지 않음 |

**보드 부팅 때의 autostart**
- `xenova-vms.service`가 부팅 때 한 번 VM별 `autostart` 플래그와 마지막 사용자 의도를 봅니다(CLI batch 기본 140초, unit `TimeoutStartSec=150s`).
- 정책은 `/etc/xenova/execution-policy.json`입니다.
  - `autostart_stopped: keep-stopped`: 사용자가 정지한 VM은 autostart가 켜져 있어도 켜지 않습니다.
  - `manual_running: keep-stopped`: autostart가 꺼진 VM은 사용자가 켜 두었어도 켜지 않습니다.
- 실제 등록값이 autostart=false인 VM은 `manual_running: keep-stopped` 정책에서 보드 재부팅 뒤 자동으로 켜지지 않습니다. 특정 등록 경로의 기본값을 모든 VM에 일반화하지 않습니다.

<a id="4-복구-실행-중"></a>
## ④ 복구 실행 중

> 재시작이 실제로 진행되는 동안입니다.

### 활성 VM 재시작 규칙 (결정)

> **활성(주행 중) VM은 먼저 준비된 대상에 제어권을 넘기거나 출력을 차단·정지한 뒤 복구합니다.** 예비가 없다는 이유로 고장 난 필수 기능의 출력을 유지하지 않습니다.

| 상황 | 순서 |
| --- | --- |
| 활성 VM이 이미 죽었거나 필수 기능·출력 고장 | Gateway 출력 차단 → 준비된 대상에 승계 또는 안전 정지 → 허용된 Worker 복구 |
| 필수 기능·출력이 정상인 계획 정비 | 예비 준비 확인 → 계획 인계 → 재시작 |
| 위 계획 정비에서 예비가 준비되지 않음 | 정상 활성 VM을 유지하고 정비 보류. 필수 기능 장애의 출력 유지에는 적용하지 않음 |
| 예비 VM | 출력 권한 없음·신원·의도·기한·소유권을 확인한 후 복구 |

현재 Gateway와 Worker는 별도 실행 주체입니다. 위 순서에 필요한 보호 완료 확인까지 종단 연결됐다는 뜻은 아니며, 계획 정비와 장애 출력 보호의 연결을 각각 수락해야 합니다.

주행 설계에서 출력 보호·승계와 VM 복구는 **병렬 책임**입니다. 위 순서는 출력 안전의 전제를 나타내며 하나의 긴 blocking 호출을 뜻하지 않습니다. Gateway는 Worker의 복구 완료를 기다리지 않고 출력을 보호합니다. 계획 정비의 인계 확인과 장애 직후의 출력 차단을 같은 대기 절차로 합치지 않습니다.

### 재시작 단계

```
① 요청 수락 → ② 기존 VM 종료 요청 → ③ 기존 VM 제거 확인 → ④ launch(새 도메인 생성) → ⑤ 새 실행 확인 → ⑥ 완료
```

| ID | 시나리오 | 대응 | 현재 처리 |
| --- | --- | --- | --- |
| **D2** | 보고자 고장의 승격 | 보고자 재시작 → 유예 T 안에 회복 안 되거나 N회 반복이면 VM 복구. 활성 VM은 위 규칙대로 | Telemetry 재시작 감독 로직 없음 |
| **D1** | 로컬 복구 유예 중 | 유예가 끝나거나 소진되면 VM 복구를 재평가 | — |
| **F1** | 실행은 됐는데 응답을 못 받음 | 같은 key·attempt로 원 작업 조회. 조회를 새 실행으로 바꾸지 않음. 필요한 이행도 같은 요청·원 기한으로 구분 | 하위·Engine 동일 attempt replay 제공. FastAPI는 key 있는 stop·원 key 조회 제공. Spring stop은 아직 key 없는 호출 |
| **F2** | 복구 중 사용자 stop | ⑧ 참고 | — |

| FO1 | 동시 작업 간섭 | 작업별 예산 분리, 권위 저장소·잠금·guard는 공유 | Manager.fork 구현. FastAPI key 있는 stop/조회에서 사용. fork 미지원 구형 Manager는 기존 직렬화로 복귀 |
| DO2 | 전역 복구 상한 | 전체 VM 재시작 횟수 상한 | Engine 기본 실행 worker는 하나. 전체 기간·모든 episode의 재시작 횟수 상한은 없음 |

### 주행 설계의 앱 단위 재초기화 (A4·B4·C1·C2)

지원되는 앱 재초기화는 **해당 결과·준비 무효화 → 새 작업 수락 중지 → 취소·제한된 join → 소유 자원 회수 → 검증된 새 앱 instance → 현재 제어·입력·상태 재적용 → 실제 계산·준비 확인** 순서입니다. AUTO만 재초기화한다면 정상 MANUAL과 guest boot·공통 netfront·Store·Publisher를 불필요하게 재시작하지 않습니다.

종료 미확인 작업의 stack·pool·callback·handle을 새 앱에 재사용하지 않습니다. 앱 신원 교체는 현재 Manager execution에 결합된 신뢰 경로로 확인하며, 새 instance의 자기 보고만으로 승인하지 않습니다. 이 계약·안전한 정리가 제공되지 않는 오류는 VM 복구 단위로 남깁니다. 일반 앱 재시작 기능이 이미 구현됐다는 뜻은 아닙니다. [설계 13절](drive-pipeline-architecture.md#s13), ARCH-T19·20·29로 수락합니다.

## ⑥ 제어권 전환·승계

> 주행 VM에 문제가 생겼을 때 **누가 차를 움직일지** 정하는 단계입니다. ③·④와 동시에 진행됩니다.

### AUTO가 안 될 때: 미러 승계냐 수동 전환이냐 (결정)

| 원인 | 대응 | 요구사항 |
| --- | --- | --- |
| 공통 입력 문제 (인지 장애 등) | 가능한 로컬 근거로 안전 정지 후 같은 VM 수동 전환. 입력 문제만으로 VM 재시작·A/B 반복 승계하지 않음 | S1 |
| 활성 VM만의 문제 | 예비 VM으로 미러 승계, AUTO 유지. 고장 VM 복구 | S2 |
| 예비도 같은 증상 | 수동 전환 평가 | S2 |
| 대안 없음 | 안전 정지 | S4, S7 |

수동은 사람이 조작할 준비가 돼 있어야 성립합니다.

세부 조건은 [설계 12절](drive-pipeline-architecture.md#s12)에 둡니다. 다음 연속 시나리오와 A/B를 바꾼 흐름을 확인하고, Jetson 단절 중 MANUAL 승계·재합류도 별도로 확인합니다(ARCH-T18·22·30).

```text
A Active/AUTO
→ Jetson 중단: A가 안전 정지 후 MANUAL
→ Jetson 회복·준비 유지·명시적 복귀·카운트다운·제어 적용: A Active/AUTO
→ A 장애: 준비된 B가 Active/AUTO 승계, A는 별도 복구
→ A 새 실행 검증·준비: A Standby, B Active/AUTO 유지
→ B 장애: 그 시점에 준비된 A가 Active/AUTO 승계
```

각 승계의 준비·남은 출력 예산을 충족하지 못하면 정지 후 재개로 낮춥니다. 위 흐름 자체가 항상 무정지 승계를 보장한다는 뜻은 아닙니다.

### 복구 중 정지 (정해진 방식)

**목표는 정지이며, 수락한 stopped 의도를 오래된 복구가 뒤집지 않습니다.** 미제출 create는 차단합니다. 이미 제출해 효과가 생겼을 수 있는 Xen 작업은 취소됐다고 가정하지 않고 원 실행·journal을 대조한 뒤 남은 정지를 이행합니다.

```
최초 제출 전 key 보존 → 복구 중 stop → 정지 의도 내구 저장 (accepted, pending)
  미제출 create 차단 / 이미 제출된 물리 결과는 원 작업으로 재확인
  잠금 해제 → 원 key 조회 → 원 기한 안에서 허용된 동일 stop 재전달 → 실제 정지·완료 저장
```

| 규칙 | 근거 |
| --- | --- |
| 복구는 의도가 running일 때만 가능 | 하위 Recovery.conditions와 실행 직전 guard |
| stop으로 revision이 바뀌면 기존 복구의 미제출 create 차단(`INTENT_MISMATCH`) | 하위 Recovery._once의 기존 VM 제거 후 conditions 재확인 |
| 잠금 중에는 의도만 먼저 내구 저장하고, 남은 물리 정지는 원 stop 이행으로 구분 | Manager.fork·stop admission, FastAPI request_stop |
| 이미 제출된 물리 효과는 취소됐다고 가정하지 않음 | 원 journal·실행 재확인. pending은 정지 완료가 아님 |
| 조회 예산은 원 물리 실행 기한을 연장하지 않음 | 원 operation/spec/deadline 유지. 만료 시 명시적 재확인·사용자 판단 필요 |

**현재 제공된 경로와 남은 연결**
1. **하위 수락·조회:** 원 key·operation·의도 revision을 보존합니다. 아직 제출하지 않은 새 launch는 마지막 guard로 막습니다. 이미 제출된 명령이 있으면 의도만 stopped이고 도메인은 남아 있을 수 있습니다.
2. **FastAPI:** `Idempotency-Key`가 있는 stop은 선행 get·VM mutex·공유 Manager 직렬화를 거치지 않고 요청별 Manager로 짧은 수락 경로에 진입합니다. pending은 202, 완료는 200이며 원 key 조회를 제공합니다. key 없는 기존 동기 stop은 204 계약과 기존 잠금 경로를 유지합니다.
3. **Spring·화면:** 현재 `Dom0ManagerClient.stop`은 key 없는 bodiless 호출이고 `VmService.stop`은 선행 `find`를 합니다. 따라서 위 key 있는 경로의 보호가 아직 종단 연결되지 않았습니다. pending을 실패·정지 완료로 바꾸지 않고 원 key·결과를 보존하는 연결이 남습니다.
4. **후속 이행:** Spring의 key 보존·응답 유실/재시작 후 조회·조건부 동일 요청 재전달 책임은 아직 미연결입니다. Worker가 모든 남은 stop을 자동 이행한다고 보지 않습니다. 조회는 읽기 전용이며 원 deadline을 새로 발급하거나 새 key로 우회하지 않습니다. 재부팅은 이 공백의 수습책이 아닙니다.

### 삭제(retire)

| 상황 | 현재 처리 |
| --- | --- |
| 실행 중인 VM 삭제 | 409 → Spring `INVALID_VM_STATE`. 정상 |
| retire는 성공했는데 응답 유실 → 재시도 | Spring은 성공 응답 뒤 record를 retire함. 응답 유실 뒤 실제 RETIRED 상태와 원 결과를 회수하는 종단 동작은 미확인 |
| retire key 고정(`retire-{vm_id}`) | Driver의 고정 key 확인. restore를 공개·연결할 때 새 lifecycle의 요청 구분을 별도 수락해야 함 |
