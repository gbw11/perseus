# HDMI·원격 시연 경량화 검토 — 2026-10-29

상태: 설계 제안. 아래 구조·자원 제한은 구현/측정 완료가 아니다. 현재 관측과 실험 결과를 분리한다.

## 실제 자원과 책임

8GiB Raspberry Pi 4에서 Xen이 보고한 total_memory=8052MiB, free_memory=6347MiB였다. dom0는 1024MiB, Debian은 512MiB, 두 Zephyr는 각각 16MiB였다. dom0의 낮은 메모리 여유와 디스크 대기·조회 지연이 함께 관측됐다. 키오스크를 멈춘 비교에서는 MemAvailable이 37,304KiB에서 484,892KiB로 증가했지만 플랫폼 조회 경합은 남았다. RAM 부족이 모든 지연의 유일한 원인이라고 확정하지 않는다.

사용자가 dom0 3GiB 변경을 승인했다. `/boot/boot.scr`의 한 인자만 `dom0_mem='1024M'`에서 `dom0_mem='3072M'`으로 바꾸고 U-Boot header/data CRC를 재계산·검증했다. 재부팅 후 실제 값은 별도 검증 기록으로 확인한다. 새 이미지에도 반영되도록 이 작업 브랜치의 `platform/yocto/config/local.conf.fragment`를 같은 값으로 맞췄다. 아직 공유 브랜치에 반영된 설정이 아니므로 빌드 담당의 실제 설정과 별도로 대조해야 한다.

통신·관리 서비스, HDMI 렌더러, 화면 송신기, 시험 계측기는 서로 다른 비용과 장애 경계를 갖는다. 주행 판단·failover는 화면 표시 기능이 맡지 않는다. CPU 정책의 VM1/VM2 전용 코어와 기존 통신 설정은 변경하지 않는다.

## 개선 우선순위

| 우선순위 | 제안 | 기대 효과와 보호 조건 |
|---|---|---|
| 1 | 인증된 시청자가 있을 때만 해당 출력 인코딩. 마지막 접속 종료 후 짧은 유예를 두고 종료 | 아무도 원격 화면을 보지 않을 때 encoder CPU/RAM을 사용하지 않는다. HDMI 키오스크는 계속 실행한다. 인증 실패·상태 조회만으로 encoder를 시작하지 않는다. 재접속 시 이전 프레임을 새 실시간 프레임으로 표시하지 않는다. |
| 2 | 상태 수집을 공유하고 동일 요청의 동시 실행을 합치기 | 화면·콘솔 watcher마다 전체 Xen 목록을 반복 조회하는 부하를 줄인다. 오래된 정상 상태를 재사용하거나 VM UUID·실행 세대 검증을 생략하지 않는다. 제어 요청과 표시용 스냅샷의 권위를 분리한다. |
| 3 | 진단 sampler를 제품 프로세스에서 분리하고 시험 때만 실행 | 전체 `/proc` 스캔·로그·색상 표식/CDP 주입이 평상시 비용에 섞이지 않게 한다. 순수 송신 부하와 계측 포함 부하를 모두 구분해서 기록한다. |
| 4 | 안정된 화면의 반복 CDP·XRandR 검사 비용을 계측하고 변경 시 검사와 주기 검사를 분리 | 출력 상태 heartbeat·미수신 만료는 유지한다. 느린 요청이 전체 표시 heartbeat를 막지 않게 하며, 해상도·EDID·창 영역을 확인한 상태만 실제 출력으로 인정한다. |
| 5 | 영상 최신 프레임과 버퍼 상한을 송신부터 뷰어까지 유지 | 현재 Capture는 최신 JPEG 하나만 보관하며 parser는 2MiB 제한이 있다. OS socket·HTTP·브라우저 decode 큐는 별도이므로 프로세스 메모리가 JPEG 한 장 크기로 제한된다고 해석하지 않는다. 느린 시청자에게 과거 화면을 순서대로 재생하지 않는다. |
| 6 | 브라우저 공통 프로세스 공유는 선택형 비교 후 결정 | 출력별 context·cookie·window는 분리할 수 있으나 공통 browser crash는 양쪽에 영향을 준다. 두 창/복귀 검증 실패 상태에서는 기본 동작으로 채택하지 않는다. |

단순히 실행 묶음의 파일 수를 줄이는 것은 주로 저장 공간 최적화다. 실제 RAM은 실행 중 프로세스의 사용량·공유 페이지·kernel/cache와 구분해 계측한다. RSS 합은 공유 페이지를 중복 집계할 수 있으므로 dom0 MemAvailable, OOM 기록과 함께 해석한다.

## 257에서 우선 유지할 기준

- HDMI 실제 두 출력에 계기판·인포테인먼트가 각각 보이는 상태에서 시험한다. 한 소스를 두 번 인코딩한 과거 시험과 구별한다.
- 전송 1280×720·5FPS, 두 출력 JPEG 합계 목표 8Mbps, 송신기+encoder 평균 1코어 상당, 전달 지연 p95 목표 500ms를 임의로 완화하지 않는다.
- frame 도착 간격과 화면 변화의 실제 전달 지연을 따로 측정한다. 시계차/RTT 오차와 작은 표본의 한계를 기록한다.
- MemoryHigh/CPUWeight 등 표시·영상 전용 자원 제한은 kernel/cgroup 지원과 실제 peak를 확인한 뒤 제안한다. 통신 서비스를 같은 제한 그룹에 넣거나 OOM으로 재시작시키는 구성을 적용하지 않는다.
- RAM 증설 전후를 같은 조건으로 비교한 뒤 효과가 남는 최적화를 고른다. 현재는 수치가 없는 임의의 최종 RAM 예산이나 안전 보장을 선언하지 않는다.

## 이번 실험의 범위

공유 브라우저 선택 옵션과 JPEG packet flush 보완을 작성했고 로컬 pytest 108개가 통과했다. 실제 보드 공유 브라우저 실험은 두 물리 출력의 준비 조건을 통과하지 못해 기존 방식으로 복원했다. 첫 시도에서는 daemon-reload도 시간 초과됐다. 따라서 공유 방식의 RAM 절감·영상 성능 개선을 통과로 기록하지 않는다. 실험 라이브러리는 별도 경로에 배치했고 원래 키오스크 코드와 영구 unit을 덮어쓰지 않았다.

## MR 제출 전 로컬 재검증

최신 platform `ae70805`를 작업 브랜치에 fast-forward한 뒤 표시 서비스 테스트 169개가 통과했다.
`git diff --check`와 로컬 병합 검사도 확인한다. 이번 제출에서는 보드에 접속하지 않았다.
공유 브라우저는 `--shared-browser`를 지정할 때만 사용하며 기본 실행 방식은 유지한다.
이 로컬 결과는 두 물리 출력의 장시간 안정성·RAM 절감·지연 목표 통과를 의미하지 않는다.
최종 실보드 재시험과 dom0 메모리 적용값 검증은 남아 있으며 257 완료로 처리하지 않는다.
