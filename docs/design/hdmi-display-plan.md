# DS-01·DS-02 표시 파이프라인 — 현재 설계

2026-11-02 · S15P31E110-250 · 기준 platform 24b26ff. 최초 설계 이후의 화면 변경·실보드 검증을 반영했다. 최신 결정·측정 경계는 [250 결정 기록](../contracts/display-250-decisions.md)을 따른다.

사용자의 최신 담당 범위를 기준으로 작성했다. 이전 DS-01의 ‘HDMI 직결 대체’ 문구와 기존 화면 정의서의 VM별 자동/수동 역할 구분은 이 설계에 적용하지 않는다. 기존 팀원 문서와 구현은 이번 단계에서 수정하지 않는다.

## 1. 담당 범위와 데이터 경로

```text
domU Xen PV 콘솔 ─ dom0 MO-04 ─ FastAPI ─ Spring ─ 외부 웹 터미널
domU Agent/앱 ─ MQTT 등 실제 지원 경로 ─ dom0 상태 정규화 ─ 외부 API/WS
Xen 실행 정보 ──────────────────────┘                 └ 외부 대시보드
                                      (외부 웹 페이지 라우팅은 별도 담당)

dom0 상태 정규화 ─ 표시 정책 ─ 렌더러/출력 실행기 ─ HDMI 모니터 1·2
                                   └ 동일 출력 소스 캡처 ─ 인코딩/전송 ─ 시연 PC
```

본인 담당은 데이터 수집·중계, HDMI 화면 구성과 상태별 선택/전환, HDMI 두 출력 실행, 해당 화면의 원격 전송이다. HDMI 표시 서비스는 외부 Spring/웹 접속이나 시연 네트워크가 없어도 로컬 상태로 동작해야 한다. 상태 수집이 끊기면 마지막 데이터를 정상으로 유지하지 않고 수신 지연을 표시한다.

콘솔은 텍스트 입출력이다. WebSocket은 웹 구간의 연결 방식이며 HDMI 영상이나 모든 domU→dom0 통신을 대체하지 않는다. 원격 화면은 HDMI 출력 또는 그 출력에 사용된 동일 렌더 결과를 전송한다. 수신 PC에서 텔레메트리로 다시 그린 대시보드는 원격 화면 전송의 증거로 인정하지 않는다.

## 2. VM과 화면 기본 구성

| 구성 | 실제 역할 | 화면 표시 |
| --- | --- | --- |
| Jetson | AI·인식 | 연결/인식 상태. Raspberry Pi 게스트 VM으로 표기하지 않는다 |
| VM1 / Zephyr | 주 구동, AUTO와 MANUAL 모두 가능 | UUID·주 구동 역할·현재 활성 여부·주행 모드 |
| VM2 / Zephyr | 백업·미러링, 장애 시 대체 | UUID·백업 역할·미러링/승계 상태 |
| VM3 / Debian | 인터랙션 앱 | OS 근거·앱 상태·앱 화면 또는 대체 상태 화면 |

현재 구성은 **monitor-1 = 드라이버 계기판, monitor-2 = 인포테인먼트·게스트 데이터**다. 초기 전체/상세 배치는 변경 전 이력이며 현재 UI가 아니다. monitor-1의 screen은 instrument, monitor-2는 infotainment다. view=overview|detail은 API 호환 필드로 남는다.

계기판에는 속도·배터리·확정 모드·주요 경고를 표시한다. 인포테인먼트에는 네비·음악·확정 모드·현재 실행 VM·게스트 콘텐츠·오류/작업 알림을 표시하고 별도 VM 상태 요약 패널은 두지 않는다. 속도·배터리·미디어·게스트 영상 어댑터가 연결되지 않은 값은 수신 대기로 둔다.

Pi4 시험 매핑은 monitor-1=HDMI0(USB-C 가까운 포트), monitor-2=HDMI1(먼 포트)다. 실제 connector·EDID·좌표는 설치 매핑으로 검증하며 모니터 크기·연결 순서로 추측하지 않는다. 휴대폰 자체 렌더링 모드는 별도 검토 항목이며 현재 HDMI/원격 전송 계약을 대체하지 않는다.

화면에는 VM 이름/역할, 검증된 OS 정보, Xen 상태, 앱 상태, 데이터 수신 상태를 구분해 표시한다. Zephyr 두 개를 서로 다른 OS로 꾸미지 않는다. 그래픽 앱 소스가 없는 Zephyr는 상태/콘솔 요약으로 표현하고 GUI 스트림이 있다고 가정하지 않는다. HDMI/시연 뷰어는 표시용이며 주행 입력은 별도 제어 경로를 사용한다.

## 3. 상태별 표시 결정표

위쪽 규칙을 우선 적용하되 경고 배지는 중첩 가능하다. 주행 보고의 3초 만료, 렌더러·runtime의 유효기간 등 서로 다른 신선도 기준을 하나로 합치지 않는다. 실제 구현 설정과 [데이터 계약](../contracts/display-pipeline-v1.md)을 따른다. 미연결 작업·AI·영상 소스에 관한 분기는 지원 경계이며 실제 발행 연동을 뜻하지 않는다.

| 조건 | HDMI 표시 | 선택/전환 동작 |
| --- | --- | --- |
| 출력 장치 분리 | 해당 출력 `disconnected`, 남은 출력 유지 | 재연결 시 저장된 논리 매핑과 최신 결정을 재적용 |
| 유효한 초기 상태 없음 | ‘상태 수신 대기’ | 정상/정지로 추정하지 않음 |
| 상태 수집 경로 단절 또는 유효기간 초과 | 마지막 값에 ‘지연/연결 끊김’과 수신 시각 | 정상 배지 제거, 확인되지 않은 승계 표시 금지 |
| Xen `crashed` | 장애 화면, 최근 관측 근거 | 화면만으로 재시작/주행 승계를 실행하지 않음 |
| Xen `stopped` / `stopping` / `paused` | 각각 정지/종료 중/일시 정지 | 앱 프레임은 과거 프레임으로 명시하거나 숨김 |
| 시작/복구 작업 진행 | 작업 상태 오버레이 | Xen 실행 상태와 별도 표시. `booting`을 기존 VM API enum에 추가하지 않음 |
| VM running, 앱 미준비/실패 | OS face + 앱 대기/오류 | VM 전체 장애로 단정하지 않음 |
| VM running, 앱 정상, 영상 소스 없음 | OS face + 상태/콘솔 요약 | 영상 미지원과 VM 장애 구분 |
| VM running, 앱/영상 정상 | OS face + 앱 화면 | 최신 프레임 여부 표시 |
| 권위 있는 제어 상태에서 활성 VM1→VM2 변경 확인 | 두 VM 역할/활성 배지 갱신 | ‘활성 VM 따라가기’ 설정 시에만 모니터 2를 VM2로 전환 |
| AI 장애 또는 AUTO→MANUAL 보고 | 인식 장애 및 확인된 주행 모드 각각 표시 | 활성 VM 변경으로 간주하지 않음 |
| 원격 연결/인코더 실패 | 로컬 HDMI 유지, 원격 상태만 오류 | 로컬 렌더러를 재시작하거나 출력을 중단하지 않음 |

기본 선택 방식은 `pinned`(운영자가 고른 UUID 유지)다. `follow_active`는 명시적으로 켠 경우에만 사용한다. VM1 장애만 보고 VM2가 실제 승계했다고 판단하지 않는다. 활성 VM과 주행 모드는 제어 담당의 확인된 상태가 없으면 `unknown`이다.

## 4. 렌더링·원격 전송 기술 결정

현재 확인된 보드 구성은 dom0의 전용 KMS/Xorg 세션 + Chromium 키오스크 + 로컬 표시 서비스다. 256에서 두 실제 모니터의 독립 표시와 재부팅 후 자동 시작을 확인했다. 원격 송신은 같은 X11 영역을 사용하는 MJPEG/HTTP이며 기본 FFmpeg 외에 선택형 MIT-SHM/TurboJPEG backend를 검증했다. native 배포 템플릿 추가가 상시 설치·enable을 뜻하지 않는다. Yocto 이미지 편입이나 다른 이미지 호환은 별도다.

초기 선정 순서와 후보 검토 이력:

1. 실보드의 DRM/KMS 커넥터 두 개, 사용 가능 모드, GPU 드라이버·메모리와 설치 이미지 확인.
2. 두 출력에 각각 웹 화면을 배치할 수 있는 컴포지터/키오스크 조합 확인.
3. 해당 조합에서 출력별 동일 렌더 결과 캡처 및 인코딩 시험.
4. 수신 PC에서 두 스트림을 식별·표시하고 CPU·대역폭·지연 실측 후 프로토콜 확정.

후보를 혼합 가능한 확정 구성으로 취급하지 않는다. [Weston 공식 문서](https://wayland.pages.freedesktop.org/weston/toc/running-weston.html)는 DRM 및 원격 백엔드를 설명하지만 여러 백엔드의 출력 생성이 실제 HDMI 미러링을 입증하지는 않는다. [wayvnc 공식 README](https://github.com/any1/wayvnc/blob/master/README.md)는 wlroots 기반을 요구하며 Weston을 지원하지 않는다. 따라서 Weston+wayvnc를 바로 연결하는 구성은 채택하지 않는다. X11을 선택하면 [x11vnc](https://github.com/LibVNC/x11vnc)의 실제 X 디스플레이 공유를 별도 검증할 수 있다. QEMU device-model VNC 옵션도 dom0 HDMI 화면 캡처의 증거가 아니다.

2026-10-22 사용자 확정 1차 목표는 출력별 1280×720·설정 **5 FPS**, 지연 p95 ≤500ms, JPEG 합계 ≤8Mbps, 송신기+인코더 평균 ≤1코어, 10분 이상 연속 수신이다. 최종 native 시험에서 602.55초·추가 재연결 0회, 실제 4.91~4.94 FPS, 전경 Chrome 영상 지연 p95 상한 약 456~464ms, 약 4.48Mbps·0.63코어를 관측했다. native quality85와 FFmpeg q=7은 같은 척도가 아니다. HDMI0 복귀 중 반대편 약 1.05초 draw 간격 1회는 남은 제약이다. 시계 가정·장비·LAN·동적 영상 미검증·정식 배포 경계는 [결정 기록](../contracts/display-250-decisions.md)과 [실보드 원자료](../verification/display-257-browser-acceptance-20261102.md)를 따른다. 엄격한 실측 5.000 FPS 이상이나 WAN 지연 보장을 주장하지 않는다.

## 5. 단계별 다음 작업과 완료 경계

| 순서 | 작업 | Jira |
| --- | --- | --- |
| 1 | 이 설계·표시 규칙·데이터 계약, 환경 확인과 미결정 목록 | 250 |
| 2 | domU→dom0 수집 정규화, 외부 웹 API/WS 경로 연결 | 253, 251 |
| 3 | 상태 정책 및 OS face·앱·상태 렌더러 구현 | 254, 252 |
| 4 | HDMI 2개 출력 실행, 출력별 원격 캡처·송수신 | 256, 257 |
| 5 | 장애/복구·실모니터·원격 시연 통합 시험 | 255 |

현재 250의 남은 계약 항목은 기존 Gateway 권위 상태의 표시용 전달 경로·상태 의미·발행/ACL 연결 확인이다. Gateway 원본과 담당 근거는 Git에서 확인했으며 결정 주체 자체가 없는 상황은 아니다. 253의 실제 새 펌웨어 보고, 251의 VM1·VM2 외부 콘솔, 255의 실제 제어 상태·웹/HDMI/원격 통합은 각각 후속 검증이다. 이미 수행한 보드 그래픽 가능성 확인을 미해결로 다시 세지 않는다.

초기 QEMU·가상 X11 결과는 [3단계](../verification/display-step3.md)·[4단계](../verification/display-step4.md)·[5단계](../verification/display-step5.md)의 당시 기록으로 유지한다. 이후 실제 보드 결과는 [252 상태 렌더](../verification/display-252-dual-state-20261028.md), [256 자동 시작](../verification/display-256-autostart-20261028.md), [257 실제 수신·지연·분리](../verification/display-257-browser-acceptance-20261102.md)로 구분한다. 새 문서 정리가 새로운 실보드 재시험이나 Jira 완료 변경은 아니다.

관련 문서: [데이터·전환 계약](../contracts/display-pipeline-v1.md), [환경 확인과 검증 계획](../verification/display-step1-environment.md). 기존 [화면 정의서](screen-spec.md)의 레이아웃은 참고하되 담당 경계와 VM 역할은 본 문서를 적용한다.
