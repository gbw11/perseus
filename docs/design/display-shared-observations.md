# 표시 상태 공유와 MQTT 읽기 전용 인증 (253)

현재 실보드에서는 MQTT 인증·수신 순서 수정만 활성화했다. 상태 공유는 로컬 시험은
통과했지만 실제 관측 갱신 간격이 3초를 넘어서 비활성화했다.
[2026-10-29 검증과 최종 구성](../verification/display-state-reuse-mqtt-20261029.md)을
확인한 뒤 적용한다. 아래 상태 공유 설정을 현재 보드에 바로 활성화하지 않는다.

## 목적과 실행 범위

공유 모드를 명시적으로 활성화하면 HDMI 수집기의 중복 Xen 조회를 제거한다.
설정하지 않은 기본 실행은 기존 상태 제공 경로를 유지한다.
기존 `xenova-dom0-manager` 프로세스 안에서 검증된 드라이버의 VM 목록을 한 번씩
조회하고, 기존 목록 API와 표시 수집기가 같은 결과를 재사용한다.
새 프로세스·브로커·제어 권한은 추가하지 않는다. 표시 수집기는 MQTT 상태 정리와
화면 정책을 계속 담당한다. 이 기능은 시연 후에도 필요한 화면용 런타임 기능이며
성능 측정기나 별도 진단 도구가 아니다.

```
기존 관리 서비스의 검증된 목록 조회
  └─ 같은 서비스 안의 단일 상태 제공자 (1초 간격, 동시 조회 없음)
       ├─ 기존 GET /api/v1/vms
       └─ /run/xenova/vm-observations.json → 표시 수집기 → HDMI 화면
기존 Mosquitto → observer 계정의 구독 → 표시 수집기의 앱·Agent 상태 정리
```

제어·콘솔 대상 검증의 `get_domain()`과 복구 판단 경로는 공유 캐시로 바꾸지 않는다.
기존 목록 API의 응답 스키마도 변경하지 않는다. 기본값은 비활성화이며,
관리 서비스와 표시 수집기 양쪽에 같은 `XENOVA_OBSERVATIONS_PATH`를 설정할 때만
상태 공유를 사용한다.
현재 구현은 **관리 서비스 1개 프로세스/uvicorn worker 1개**를 전제로 한다.

## 오래되거나 잘못된 상태

- 플랫폼 드라이버는 한 번의 검증된 목록에서 원래 `observed_monotonic_ms`와
  실행 식별자를 함께 전달한다. VM별 snapshot 재조회는 하지 않는다.
  파일 재독출 시각으로 관측의 나이를 바꾸지 않으며 현재 호스트와 실행 식별자를 검사한다.
- 동일 작업 잠금 안의 읽기 전용 목록에서만 lifecycle 메타데이터를 재사용한다.
  다음 목록 요청·get·제어·복구는 기존의 새 검증 경로를 유지한다.
- 별도 시각이 없는 주입 드라이버에서는 보수적으로 조회 시작 시각을 사용한다.
  조회 실패 또는 관측 나이가 3초 이상이면 `unavailable`이다. 갱신이 멈춰도 3초에 만료된다.
- 수신기는 root 소유·0600 일반 파일, 크기 제한(256KiB), 현재 호스트 boot ID,
  단조 시각, 게스트 UUID 중복과 dom0 UUID 제외를 검사한다. 링크·잘못된 자료는 거절한다.
- 게시 파일은 tmpfs에 원자적으로 교체한다. 디스크에 매초 영구 저장하지 않는다.
- 관리 서비스 재시작 또는 실행 식별자 변경 시 이전 표시 근거를 지운다.
  관리 서비스만 재시작한 경우 다음 실제 게스트 보고를 수용한다.
  실제 실행 식별자나 domid가 바뀐 경우 이전 guest boot의 보고는 다시 사용하지 않는다.
- 공유 모드를 설정한 수집기는 파일이 없거나 잘못되어도 직접 Xen을 조회하지 않는다.
- 종료 시 파일을 미확인으로 바꾸고 늦게 끝난 조회가 정상 상태를 다시 게시하지 못하게 한다.

실제 플랫폼 공유 모드는 실행 식별자를 요구한다. 주입 시험 드라이버에 식별자가
없을 때만 호스트 부팅·제공자 세대·domid까지 구별한다.
동일 domid의 관측되지 않은 실행 교체까지 증명하는 기능은 아니다.
기존 제어·복구의 실행 바인딩 검증은 별도로 유지한다.

## MQTT 인증

기존 브로커는 익명 접속을 거부한다. 표시 수집기에 계정이 없었던 것이
앞선 실보드 연결 실패의 확인된 원인이다. recovery worker의 인증 문제는 별건이다.

계정 관리 도구의 `export-account observer --format display-env`를 추가했다.
기존 observer가 `xenova/v1/#` 읽기만 허용된 경우에만 인증정보를 별도 환경 파일로
내보낸다. 계정 생성·암호 변경·ACL 수정·브로커 재시작을 하지 않는다.
비밀값은 표준 출력에 표시하지 않는다. 출력 폴더는 root 전용, 출력 파일은 0600이며
기존 파일 덮어쓰기는 거부한다. 기본 실행은 계획 확인이며 실제 작성에는 `--execute`가 필요하다.

보드 실행 진입점은 MQTT 사용자명·암호가 없으면 시작을 거부한다.
첫 VM 관측보다 inventory가 먼저 도착해 버려진 경우, 수용된 Agent heartbeat 뒤
inventory를 한 번만 재구독해 retained 자료를 다시 받는다. Agent 세대를 대조하고
retained·수신 시각을 유지한다. heartbeat 자체나 재구독을 주행 준비 근거로 사용하지 않는다.
주 구동·백업은 UUID로 구분하고 두 VM의 autonomous/manual 보고를 각각 구독한다.
`examples/dual-drive-candidate-bindings.json`은 시험 후보이며 실제 UUID나 펌웨어 적용의 증거가 아니다.

## 보드 적용은 별도 사용 시간에 수행

로컬 구현 후 사용자가 보드 사용을 다시 허용하여, 원본 코드를 보존한 `/run`의
임시 구성으로 실보드 검증을 수행한다. 시험 결과와 최종 잔여 설정은 검증 기록으로
구분한다. 아래는 정식 적용 순서이며 자동 배포 스크립트가 아니다.

1. 기존 서비스 파일·drop-in·bindings와 패키지 버전을 비밀 노출 없이 백업한다.
   기존 관리 서비스의 드라이버와 인증·MQTT·Tailscale 설정을 보존한다.
2. 대상 보드 버전과 호환되는 관리 서비스/표시 수집기 패키지를 함께 준비한다.
   팀원의 새 코드를 이전 브랜치 패키지로 덮어쓰지 않는다.
3. 기존 계정 관리 도구로 계정 상태를 검사하고 observer 설정을 새 root 전용 폴더로
   내보낸다. 예: `/etc/xenova/display-253/mqtt.env`.
   레거시 계정 상태가 새 관리 도구에서 검사되지 않으면 먼저 별도 검토한다.
   새 계정 초기화나 비밀번호 재생성으로 해결하지 않는다.
4. `manager-observations.conf.example`과 `feed-observations.conf.example`을 사용해
   양쪽 서비스 drop-in의 상태 파일 경로를 일치시킨다. 기본 unit은 자동 전환하지 않는다.
5. 관리 API와 표시 수집기만 재시작하고 파일 갱신·실제 SUBACK·각 VM의 실제 보고를
   확인한다. VM/펌웨어와 기존 브로커는 이 변경 때문에 재시작하지 않는다.
6. 같은 화면 구성에서 API 응답·조회 횟수·CPU·메모리를 이전 상태와 비교한다.
   게스트 송신이 없다면 구독 성공과 데이터 수신 성공을 구별하여 기록한다.

되돌릴 때는 두 서비스 패키지와 unit/drop-in을 함께 이전 버전으로 복원한다.
새 feed만 남겨둔 채 관리 서비스의 상태 제공 기능만 끄면 화면이 미확인이 된다.
MQTT 파일을 삭제하거나 복원해도 기존 브로커 계정과 ACL은 그대로이다.

## 검증의 한계

로컬 테스트는 상태 공유·만료·실패·재시작·종료·인증정보 전달 및 기존 API 계약을 검증한다.
보드의 실제 구독·보고 수신과 성능 개선은 이번 로컬 시험만으로 통과했다고 보지 않는다.
펌웨어 빌드·실제 VM1/VM2 보고 및 recovery worker 수정도 별도이다.
