## 1. 이슈 구조

```text
에픽 (기능 도메인)
 ├─ 스토리 (사용자 관점 요구사항, 스토리 포인트 없음)
 └─ 작업 (실제 구현 단위, [파트] 접두어 + 스토리 포인트)
```

| 유형 | 용도 | 상위 항목 | 스토리 포인트 | 담당자 |
| --- | --- | --- | --- | --- |
| 에픽 | 기능 도메인 (예: 가상 네트워크, 웹 콘솔) | 없음 | 없음 | 없음 |
| 스토리 | 사용자가 얻는 가치 단위 | 에픽 | **없음** | 없음 |
| 작업 | 1~3일 안에 끝나는 구현 단위 | 에픽 | 1~3 | 필수 |
| 버그 | 결함 | 관련 에픽 | 1~3 | 필수 |

- 작업은 스토리의 하위 작업이 아니라 **에픽 직속**으로 만듭니다.
- 작업과 스토리의 관계는 **이슈 링크 `이슈 분할`**로 연결합니다. 스토리 화면에서 "다음으로 분할: {작업 키}"로 보입니다.
- 백로그에서는 스토리 바로 아래에 그 스토리의 작업들이 오도록 순서를 맞춥니다.

## 2. 에픽

이름만 짧게 짓고, 설명에 목표·범위·관련 요구사항(명세서 Req 번호)을 적습니다.

```markdown
**목표**
dom0에 Linux Bridge와 DHCP를 구성해 VM마다 고유한 MAC/IP를 부여한다.

**범위**
- Bridge, DHCP, VM별 MAC 할당 정책, VM 간 통신 테스트

**관련 요구사항**: Req.4
```

## 3. 스토리

참고 프로젝트(S15P21E104)와 같은 User Story 형식을 씁니다. 스토리 포인트는 넣지 않습니다.

```markdown
**As a** ADMIN
**I want** 템플릿으로 VM을 생성하고 시작·정지·재부팅·삭제하고 싶다.
**So that** 콘솔에서 VM 생명주기를 직접 관리할 수 있다.

**Acceptance Criteria**

* Debian·Ubuntu·Alpine 템플릿으로 VM을 생성할 수 있다.
* 시작·정지·재부팅·삭제 후 상태가 콘솔에 반영된다.

**관련 작업**: S15P31E110-115, S15P31E110-144
```

| 역할 | 의미 |
| --- | --- |
| `ADMIN` | 관리 콘솔을 쓰는 관리자 |
| `DRIVER` | RC카 사용자·데모 관람자 |
| `SYSTEM` | 자동으로 동작하는 시스템 |
| `DEVELOPER` | 팀 개발자 (개발 환경·계약·테스트) |

## 4. 작업

### 제목

```text
[접두어] 할 일
```

```text
[PLATFORM] RPi4 U-Boot → Xen → dom0 부팅
[CTRL] Xen 드라이버 - xl 명령 래핑
[BE] VM 생명주기·인벤토리 API
[FE] VM 목록 - 배포판별 카드 및 상태 표시
```

| 접두어 | 대상 | 브랜치 part |
| --- | --- | --- |
| `[PLATFORM]` | Yocto·Xen·부트·템플릿·네트워크 | `platform` |
| `[CTRL]` | Python 제어 계층 (`services/dom0-manager`) | `ctrl` |
| `[AGENT]` | VM 에이전트 | `agent` |
| `[DISPLAY]` | dom0 표시 서비스·키오스크 | `display` |
| `[BE]` | Spring Boot 관리 서버 | `backend` |
| `[FE]` | React 관리 콘솔·OS face | `frontend` |
| `[APP]` | VM 애플리케이션 (RC카 앱) | `app` |
| `[DEPLOY]` | CI·배포·인프라 | `deploy` |
| `[COMMON]` | 계약·문서·데모 등 여러 파트에 걸친 일 | `common` |
| `[TEST]` | 테스트 (part는 대상 폴더를 따르고 type은 `test`) | 대상 폴더 |

### 설명

```markdown
## 목적
이 작업을 왜 하는지, 끝나면 무엇이 가능해지는지

## 작업 내용
- 구체적인 구현 항목

## 완료 조건
- [ ] 확인 가능한 완료 기준

## 참고
- Req 번호, 선행 작업, 멘토링 근거
```

### 필드

| 필드 | 규칙 |
| --- | --- |
| 담당자 | 반드시 한 명 |
| 스토리 포인트 | 1 = 반나절~1일, 2 = 1~2일, 3 = 2~3일. 3을 넘으면 작업을 나눕니다 |
| 우선순위 | 계약·게이트 작업은 Highest, 주요 기능은 High, 나머지는 기본값 |
| 기한 | 스프린트 안의 날짜 |
| 레이블 | 스프린트 레이블 1개 + 파트 레이블 (아래 표) |

| 레이블 | 의미 |
| --- | --- |
| `S1`~`S5` | 계획된 스프린트 (스토리는 첫 작업이 시작되는 스프린트 하나만) |
| `platform` `ctrl` `agent` `backend` `frontend` `app` `display` `infra` | 파트 |

## 6. 상태와 작업 흐름

```text
해야 할 일 → 진행 중 → 완료
```

| 시점 | 할 일 | 상태 |
| --- | --- | --- |
| 작업 시작 | Claude Code에서 `/branch {Jira키}` 실행 (또는 직접 브랜치 생성) | 진행 중 |
| 커밋 | 커밋 메시지 마지막 줄에 Jira 키 | — |
| MR 생성 | MR 설명에 `Closes {Jira키}` | — |
| develop 머지 | GitLab–Jira 연동이 자동 처리 | **완료** |

- 브랜치 이름: `{type}/{part}/{Jira키}-{설명}` (예: `feat/platform/S15P31E110-56-rpi4-xen-boot`)
- 아직 끝나지 않은 이슈는 MR에 `Closes` 없이 키만 적습니다. Jira에 MR 링크만 남습니다.
- 여러 이슈를 함께 끝낼 때는 `Closes` 줄을 이슈마다 하나씩 씁니다.
- 자동 완료는 develop(기본 브랜치)에 머지될 때만 동작합니다.

## 7. 새 이슈를 추가할 때

1. 맞는 에픽을 찾습니다. 없으면 팀장과 상의해 에픽을 만듭니다.
2. 사용자 관점 요구사항이 새로 생기면 스토리부터 만듭니다.
3. 작업을 에픽 아래에 만들고, 해당 스토리와 `이슈 분할` 링크로 연결합니다.
4. 담당자·스토리 포인트·스프린트 레이블을 채우고, 백로그에서 스토리 아래로 옮깁니다.
